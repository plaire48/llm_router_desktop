# 병렬 조사 담당 설계 (beta42 1순위, 2026-09-30)

> 아래는 최초 제안과 당시 측정 기록이다. 2026-10-01의 실제 구현 계약과 검증은 [전체 개선 기록](FULL-IMPROVEMENT-2026-10-01.md)을 따른다. 현재 입력은 2~4개 배정과 필수 start_url/constraints이며 동시 실행은 2개다. 임의 URL 열기/검색 도구와 병렬 읽기 확대는 이 제안만으로 구현된 기능이 아니다.

여러 기관이나 출처를 조사해 합치는 과제가 가장 약하다. 담당마다 자기 탭과 자기 문맥에서 읽기 전용으로 조사하고, 주관 모델은 담당이 채운 표를 합치기만 한다.

## 측정된 문제

| 과제 | 결과 | 시간이 든 곳 |
|---|---|---|
| H-04 세 기관 조사 | Sol 0/10, Luna 0/7 완료(제한 공개, 시간 초과) | 후보 58: 세 기관 열람 186초, 모은 글 분석 위임 약 95초, 답변 작성 한 번 84초(입력 29만 자), 최종 검토의 보충 요구 뒤 8분 한도 |
| H-05 접근성 비교 | 0/3 | 후보마다 공식 안내 세 가지를 확인해야 함 |
| H-03 영상과 문서 대조 | Sol 1/6, Luna 1/5 | 영상 설명과 공식 문서 왕복 |
| H-06 두 기관 재확인 | Sol 4/9(후보 58 통과) | 탭 왕복 |

지금은 한 모델이 모든 기관을 차례로 열람하고, 읽은 페이지가 모두 주관 문맥에 쌓인다. 답변 작성 호출 하나가 문맥 전체를 다시 읽는다. 브라우저 도구는 한 번에 한 작업만 돈다(`browser-agent.js`의 `active`).

## 참고한 방법론

- Anthropic 다중 에이전트 조사: 주관 에이전트가 하위 담당 3~5개를 병렬로 띄운다. 담당마다 목표, 출력 형식, 도구와 출처 기준, 범위를 구체적으로 준다(모호한 지시는 중복 조사를 낳았다). 담당은 자기 문맥에서 넓게 찾고 1~2천 토큰 요약만 돌려준다. 대상 수에 맞춘 규모 규칙(단순 사실 1개 담당, 비교 2~4개). 넓은 검색으로 시작해 좁힌다. 검색 최적화 글보다 공식 출처를 고르게 한다. 복잡한 조사 시간을 최대 90% 줄였다.
- Anthropic 문맥 설계: 하위 담당의 문맥 격리, 오래된 도구 결과 지우기, 필요할 때 읽기.
- OpenAI 에이전트 지침: 관리자 패턴(관리자가 담당을 도구로 부름). 단일 에이전트로 시작해 필요할 때만 나눈다.
- ParaGUI(2026): 계획 담당과 병렬 작업 담당. 순차 대비 성공률 12.9%p 향상, 단계 약 50% 감소, 토큰 절반 이하.

## 구조

### 주관 모델 도구 `delegate_research`

```
{tasks: [{subject: "서울도서관",
          question: "초보 방문자의 이용 자격, 자료실 운영시간, 정기 휴관일, 방문 전 절차",
          fields: ["이용 자격", "운영시간", "휴관일", "방문 전 절차"],
          start_url?: "https://lib.seoul.go.kr/", search_query?: "서울도서관 이용안내",
          source_rule?: "기관 공식 사이트만"}]}   // 1~4개
```

- 조회 과제에서만 제공한다(`lookupRun`). 변경 요청에는 주지 않는다.
- 규모 규칙: 대상(기관, 후보, 출처)이 둘 이상이면 대상마다 한 담당. 한 대상의 단순 사실은 위임하지 않는다.

### 담당 실행기 (`research-workers.js`)

- 담당마다 작업 창 안에 비활성 탭을 하나 연다. 이동은 `chrome.tabs.update`, 읽기는 `chrome.scripting.executeScript`(격리 환경)로 한다. 디버거를 쓰지 않으므로 여러 담당이 동시에 돌 수 있고, 사용자의 현재 탭과 주관 작업의 탭을 건드리지 않는다.
- 담당 도구(읽기 전용): `open_url`, `web_search`(검색 결과 페이지를 열어 결과 목록만 읽음), `find_in_page`(질문과 맞는 구간), `read_more`(다음 구간), `follow_link`(읽은 링크 번호로 GET 이동), `submit_findings`.
- 한도: 담당당 모델 호출 12회, 150초. 넘으면 그때까지 채운 항목과 못 찾은 항목을 제출한다.
- 담당 문맥은 과제 설명과 읽은 구간만 담는다. 페이지 원문은 주관 문맥에 올리지 않는다.

### 돌려주는 것

```
{subject, fields: [{name, value, source_url, quote}], sources: [{url, title}], gaps: ["방문 전 절차: 공식 안내에서 찾지 못함"]}
```

- 담당당 약 2천 토큰 이내. `quote`는 읽은 원문에서 그대로 가져온 짧은 인용이다(호스트가 원문에 있는지 확인하고, 없으면 그 값을 빼고 `gaps`로 옮긴다).
- 담당이 읽은 페이지는 조사 출처 기록(`research-source-capture.js`)에 등록한다. 최종 검토자는 주소, 제목, 인용 구간을 근거로 본다.

## 안전

- 읽기 전용 도구만 준다. 입력, 버튼 클릭, 양식 제출, 다운로드, 승인 요청이 없다. 링크는 `http(s)` GET 이동만 하고 브라우저 정책(`assertBrowserPolicy`)을 그대로 적용한다.
- 로그인 화면이나 권한 요청을 만나면 멈추고 그 사실을 `gaps`로 보고한다. 자격 증명을 다루지 않는다.
- 담당 탭은 작업이 끝나거나 취소되면 닫는다. 사용자가 작업을 멈추면 모든 담당을 멈춘다.
- 페이지 글은 자료이지 지시가 아니다. 담당 프롬프트와 주관 모델에 넘기는 결과 모두 이 규칙을 적는다.

## 측정 계획

- 기준 후보(beta41)와 나란히 Sol, Luna로 H-04, H-05, H-06, H-03, M-05를 잰다.
- 지표: 검토 통과(완료) 수, 전체 시간, 모델 호출 수(주관과 담당 구분), 최대 입력 크기, 출처 인용 확인 실패 수.
- 목표: H-04가 8분 안에 검토 통과. 단순 조회(E-02, M-04)는 위임하지 않아 시간이 늘지 않을 것.

## 다음 순서

1. 병렬 조사 담당(이 문서).
2. 필터 적용 상태 관찰: 선택된 칩, 눌린 버튼, 주소 조건을 관찰에 싣고 확인 항목으로 검사(M-01, M-02).
3. 읽기 클릭의 자가 복구와 부분 관찰의 참조 유지(Stagehand의 자가 복구 참고). 입력과 승인 대상은 지금처럼 거절.
4. 질문 전 호스트 확인: 숨은 칸, 선택하면 나타나는 칸처럼 페이지로 답할 수 있는 질문을 먼저 알려 줌(Luna M-08, H-10, E-08).
5. 한 응답의 병렬 읽기 한도(지금 2개) 확대.
