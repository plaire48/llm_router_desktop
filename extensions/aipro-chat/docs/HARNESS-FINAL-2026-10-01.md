## 이번 적용: 원문 구간 안내 (NQ-55)

일반 웹 문서의 첫 content 읽기에서 5,000자보다 긴 원문에 한해 목차를 반환한다. Markdown 구문 트리의 제목 깊이와 원래 UTF-16 위치로 시작/끝/말미 읽기 위치를 계산한다. 중첩 섹션은 겹칠 수 있으며 길이 합계를 전체 열람량으로 계산하지 않는다. 최대 32개를 반환하고 전체 개수와 생략 개수를 함께 표시한다. 후속 구간/검색 읽기에서는 목차를 반복하지 않는다.

목차의 텍스트는 페이지 자료다. 코드 블록의 가짜 제목을 구간으로 만들지 않으며, 문서가 변경되면 기존 content_hash로 이어 읽을 수 없다. 처음 반환한 본문 범위는 기존 5,000자를 유지한다. 목차에만 있는 제목을 근거 인용으로 제출해도 실제 반환 범위 검증에서 거절된다. 숨은 입력, 인증, 편집 초안은 기존 DOM 정제 밖으로 나오지 않는다.

[Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)의 필요한 정보만 찾는 방식과 [OpenAI trace grading](https://developers.openai.com/api/docs/guides/trace-grading)의 실행/결과 분리 원칙을 참고했다. 기존 [mdast-util-from-markdown](https://github.com/syntax-tree/mdast-util-from-markdown) 2.0.3 MIT 패키지의 공식 문서, 설치된 진입점/구현/라이선스를 확인해 재사용했다. 정규식으로 제목을 추정하는 방식보다 코드 블록과 setext 제목 및 원래 위치를 구분할 수 있다. 새 의존성이나 추가 모델 호출, 외부 브라우저 런타임은 없다.

## Python 활용 검토

사용자의 가능 여부 질문에 대한 설계 후보이며 이번 구현에 Python을 추가하지 않았다. [Pyodide](https://pyodide.org/en/stable/usage/wasm-constraints.html)는 별도 PC Python 설치 없이 CSV/표 계산과 통계에 사용할 수 있다. 기존 브라우저 도구가 읽은 명시적 데이터를 전달하고 결과를 기존 검증/반영 경로로 돌려주는 구조가 맞다. PC 프로세스 실행과 Windows Excel COM은 이 실행 환경의 지원 범위가 아니다.

## 핵심 회귀에서 발견한 복구 결함과 최종 수정

구간 안내 후보의 `read-loop-recovery-browser`가 실패했다. 같은 본문을 새로고침하면 실제 인용용 content_hash는 바뀌어야 하지만, 목차 내부 content_hash까지 진전 비교에 들어가 반복 읽기가 새 정보로 오인됐다. 이에 복구용 canonical 비교에서 유효한 본문 해시를 가진 page_content의 `outline`/`boundary_index`만 제외했다. 본문 해시, 실제 반환 본문/구간과 비페이지 업무 데이터는 유지하며 원래 인용용 해시나 문서 동일성 검사는 바꾸지 않는다.

같은 장문을 세 번 새로고침하는 단위 반례는 수정 전 두 번째 반복에서 1 !== 2로 실패했다. 수정 후에는 반복 복구, 실제 내용 변경, 업무 데이터 보존을 포함한 18개 관련 검사가 통과했다. 이전 핵심 검사의 실패를 그대로 보존하고, 수정한 최종 후보로 전체 검사를 처음부터 다시 실행했다. 중간 후보 검사들을 합쳐 최종 후보 전체 통과로 표시하지 않는다. 이후 최종 후보의 문맥 테스트 준비 보완과 같은 빌드 검증 연속 기록은 아래에 별도로 남긴다.

사용자 결정: 기존 30과제 평가를 유지하고, 평가 Chrome 프로필이 겹치는 이번 최종 후보 실모델 측정은 대기한다. 최종 후보 `8d4658`의 시작 시도는 `evaluation_profile_in_use`로 끝났으며 모델 호출/품질 점수로 계산하지 않는다. 중간 후보의 실측 결과를 최종 후보로 이전하지 않는다.

## 문맥 검사 준비 순서 보완

최종 8d4658 핵심 검사에서 단위 1,650개와 디자인/빌드가 통과했다. `context-browser-1`은 통과했지만 두 번째 반복에서 압축 요약 없이 첫 추론이 호출됐다. 원래 테스트는 serviceworker 이벤트 직후 대화 데이터를 storage에 쓰며, 제품의 비동기 시작 시 대화 마이그레이션 완료를 기다리지 않았다. 소스와 실패 시 입력 크기는 시작 준비 경쟁 가능성을 뒷받침한다. 실패 실행에 대화 초기값 스냅샷이 없어 이를 확정된 제품 결함이나 부하만의 문제로 단정하지 않는다.

테스트를 GET_STATE 응답으로 시작 완료 확인 → 초기 대화 주입 → 화면 재진입 → 6개 메시지 원문 일치 확인 → 압축 검사 순서로 보완했다. 요약과 중지/재개 및 실제 쓰기 횟수 검증은 유지한다. 독립 실행은 통과했다. 기존 실패 보고서는 수정하지 않고 같은 빌드의 문맥 검사 3회 및 미실행 검사를 `core-continuation/report.json`에 별도로 기록한다. 앞서 통과한 결과와 후속 결과의 출처를 연결하며 최초 일괄 검사가 무실패 통과했다고 표시하지 않는다.

`context-fixture-provenance.json`은 변경 입력이 tests뿐임과, 수정 전 테스트 파일을 대입했을 때 전체 tests 해시가 최초 보고서와 정확히 일치함을 확인한다. 제품 ZIP과 dist 해시는 그대로다.

## 최종 검증 종료 기록

`core-continuation/report.json`은 후속 57/57 통과, `buildUnchanged: true`, `inputsUnchanged: true`다. 최초 보고서의 보존된 통과 50회와 합쳐 예정된 107개 Chrome 실행 항목이 빠짐없이 확인됐다. 수정한 문맥 테스트는 3회 모두 통과했으며 최초 실패를 삭제하거나 자동 재시도로 숨기지 않았다. 테스트 수정 전후 입력 차이는 문맥 fixture 한 파일뿐이고, 제품 dist 해시는 `e33a18c7af5ad3472410860c6e455d3592133e12be1cd0b959203f3d3aee8758`로 일치한다.

최종 상태는 `passed_after_fixture_correction`이다. `result.json`에서 원래 실패 보고서, 후속 통과, 집중 9회 검사, 제품 ZIP, 실모델 대기 결정을 연결했다. 고정 후보에 대한 로컬 검증을 완료했으며, 기존 30과제 평가나 실제 계정 Chrome 프로필은 변경하지 않았다.
