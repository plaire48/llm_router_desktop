# 화면과 이미지에서 시작하는 변경 요구사항

2026-09-23. 상태: 현행 코드 확인과 공식 자료 조사, 적용 설계. 신규 이미지 검색/업로드/소스 연결 라이브러리를 설치하거나 제품 기능을 완성한 기록이 아니다.

## 권고하는 사용자 흐름

사용자가 화면에서 바꿀 부분을 선택하거나 이미지를 첨부하고 “이 검색 조건을 접을 수 있게 해 주세요”처럼 요청한다. 누비는 관련 코드와 Wiki를 찾고, 필요한 질문을 한 뒤 실행 가능한 초안을 보여준다. 사용자는 현재 화면, 변경 초안, 실제 검증 결과를 구분해서 본다.

입력은 두 가지로 나눈다. 현재 화면은 선택한 요소의 DOM, 접근성 이름, URL과 소스 위치를 함께 수집한다. 업로드한 이미지는 OCR/시각 분석으로 후보를 찾는다. 참고 디자인 이미지는 원하는 모습의 근거이며 현재 소스 위치의 증거가 아니다.

## 현재 누비에서 확인한 기반

- `packages/nubi-desktop/runtime/comparison.mjs`: Playwright로 localhost의 변경 전후 화면을 캡처하고 pixelmatch로 차이를 계산한다. 소스 지문과 텍스트 관찰을 저장하지만 실행 화면과 해당 소스 버전의 연결은 `unverified`다.
- Workbench는 비교 이미지를 나란히/겹쳐 보기로 표시한다. 이미지 첨부, 영역 선택, 이미지 기반 코드 검색은 아직 없다.
- 소스 조회, Wiki/업무 관계, 변경 계획, 현재 실행의 소스 관찰, QuestionForm, worktree와 명령 일회 승인, A2A 전달은 재사용할 수 있다.
- 제공자별 이미지 전달을 동일하게 가정할 수 없다. 현재 FabriX 어댑터는 텍스트 대화 계약을 사용한다. 모델의 이미지 지원과 요청 포맷을 먼저 검증하고, 지원하지 않는 모델에는 OCR/DOM 관찰을 전달해야 한다. 모델명만으로 이미지 이해를 지원한다고 판단하지 않는다.

## 방법론

### 1. 화면에서 실제 수정 대상을 찾는다

실행 중인 React 개발 화면은 React Grab 같은 요소 선택기를 통해 컴포넌트 스택과 파일 위치를 얻는 방식을 우선 검증한다. 일반 웹 화면은 DOM/접근성 이름, 라벨, 라우트, 테스트 ID와 실제 네트워크 요청을 근거로 기존 소스 검색을 수행한다. React 개발 메타데이터가 없는 빌드, 다른 프레임워크, iframe, Canvas는 별도 경로다.

첨부 이미지는 선택 영역의 텍스트와 시각 설명을 추출하고 소스/Wiki 후보를 검색한다. 이미지 한 장만으로 파일 경로를 확정하지 않는다. 결과에 “직접 연결”, “검색 후보”, “미확인”을 표시하고 같은 문구를 사용하는 화면이 여럿일 때 기존 객관식 HITL로 대상을 확정한다.

### 2. 프로젝트의 화면 목록을 만든다

이미지 유사도 검색은 비교할 화면/에셋 목록이 있어야 한다. 사용자가 확인한 라우트와 Storybook stories를 화면 ID, viewport, 역할/데이터 상태, 캡처 시점, 소스 버전과 함께 인덱싱한다. 무차별 링크 클릭이나 업무 제출로 화면을 수집하지 않는다.

처음에는 기존 MiniSearch의 화면 텍스트 검색과 관계 검색을 사용한다. 이미지 임베딩은 시각적으로 비슷한 화면이나 에셋을 찾는 보조 수단으로 평가한다. 비슷한 모양은 동일 기능이나 동일 소스를 뜻하지 않는다. 인증 계정의 상태와 화면 데이터는 호스트 간 자동 공유하지 않는다.

### 3. 변경 전 동작과 완료 조건을 고정한다

기존 화면의 동작, 데이터 조건, 오류/빈 상태, 키보드 조작과 반응형 조건을 기록한다. 요청한 변경과 보존할 동작을 구분하고 OpenWiki의 업무 규칙 및 DB 의미와 연결한다. 이미지에서 추론한 요구사항을 확정 요구사항으로 바꾸지 않는다. 기존 AC와 답변 이력은 같은 변경 ID에 유지한다.

### 4. 실제 컴포넌트로 변경 초안을 실행한다

기존 컴포넌트, 스타일 토큰, 누비 새 로고와 폰트를 재사용하고 별도 작업 공간에서 최소 변경을 만든다. Storybook이 있는 프로젝트는 해당 story와 상태를 재사용하고, 없으면 기존 개발 서버의 대상 라우트부터 활용한다. Storybook을 모든 프로젝트에 강제 설치하지 않는다.

디자인 방향을 비교할 때 생성한 이미지는 “시각적 예상안”으로 표시한다. 소스로 렌더링한 초안은 “실행 가능한 초안”이며, 기능 테스트를 통과해야 “검증 결과”가 된다. 시각적 유사도만으로 요구사항 완료를 선언하지 않는다. 설치/빌드/실행은 기존 준비안 승인 경계를 사용한다.

### 5. 브라우저 실행 결과를 Wiki로 연결한다

동일 viewport/데이터 조건에서 스크린샷, DOM/접근성 관찰, 실제 동작 검사를 함께 수행한다. Playwright의 trace와 assertion 결과를 연결하고 동적 값 때문에 발생한 차이와 실제 회귀를 구분한다. 마스킹 영역은 기록하며 검증해야 할 요소를 가리지 않는다.

Desktop은 소스/요구사항 근거를 A2A로 브라우저에 전달하고, 브라우저는 시나리오 초안과 관찰 결과를 돌려준다. 반환된 근거의 파일 버전과 실행 대상을 다시 확인한다. A2A 전달 완료, 캡처 성공, 테스트 통과는 별도 상태다. Wiki에는 승인한 요구사항과 변경 이유, 출처, 검증 결과를 버전으로 기록한다.

## 라이브러리 비교와 적용 판단

|---|---|---|

| [Tesseract.js](https://github.com/naptha/tesseract.js), [worker 소스](https://github.com/naptha/tesseract.js/blob/master/src/createWorker.js) | 이미지의 글자와 위치 추출 | Apache-2.0. Node/브라우저 WASM이며 Python 없이 사용 가능한 OCR 후보. 한국어 언어 데이터, 작은 글씨 정확도, worker 취소와 패키징을 평가한다. OCR만으로 아이콘의 의미나 코드 경로를 확정하지 않는다 |
| [Transformers.js](https://huggingface.co/docs/transformers.js/api/pipelines) | 프로젝트 내 화면/에셋의 이미지 특징과 유사도 검색 | 선택 도입 후보. 모델 다운로드, 메모리, 사내 PC 지연시간, 선택한 가중치 라이선스를 따로 검토한다. 처음부터 새 vector DB를 필수로 두지 않는다 |
| [Storybook](https://storybook.js.org/docs/writing-tests) | 기존 컴포넌트 상태를 재현하는 실행 초안 | 프로젝트에 있으면 재사용. 서버/데이터 의존성은 story fixture와 실제 연동을 구분한다. 공식 Visual Tests의 Chromatic 클라우드는 별도 서비스이며 로컬 오픈소스 테스트와 동일하게 표현하지 않는다 |
| [Playwright Trace Viewer](https://playwright.dev/docs/trace-viewer), [ARIA snapshot](https://playwright.dev/docs/api/class-locator#locator-aria-snapshot) | 실제 동작, DOM/접근성 상태, 캡처와 진단 | 기존 의존성을 우선 재사용. trace 보관과 조건별 assertion 연결은 추가 구현 필요 |
| [OmniParser](https://github.com/microsoft/OmniParser), [파싱 소스](https://github.com/microsoft/OmniParser/blob/master/util/utils.py) | DOM이 없는 화면의 UI 영역과 아이콘 해석 | 선택적 후속 후보. Python/모델 배포 부담이 있고 코드와 가중치의 라이선스가 다르다. 현재 README는 코드 CC-BY-4.0, 신규 detector의 MIT 기반과 이전 detector의 AGPL을 구분한다. 릴리스별 구성 확인 필요 |
| [screenshot-to-code](https://github.com/abi/screenshot-to-code) | 이미지에서 초안 생성하는 흐름 참고 | 기존 앱의 동작/상태/접근성 보존을 자동 보장하지 않으므로 생성 코드를 그대로 교체하는 기본 엔진으로 채택하지 않는다 |

## 구현 순서와 평가

1. 브라우저의 화면 요소 선택 → Desktop의 검증된 소스 후보 → 기존 요구사항 폼. 먼저 실제 React 샘플과 프레임워크 없는 HTML에서 오연결/미연결을 측정한다.
2. 이미지 첨부/영역 지정 → 로컬 OCR → 소스/Wiki 후보. 한글, 아이콘만 있는 버튼, 반복 문구와 오래된 이미지로 검색 정답률을 측정한다. 이미지 지원 모델 연결은 별도 실계정 검증이다.
3. 기존 컴포넌트 기반 작업 공간 초안 → 승인된 실행 → Playwright 기능 검사와 변경 전후 비교. 사람의 미저장 수정 보존, 실행 소스 버전, 포트와 데이터 조건을 확인한다.
4. 화면 목록이 쌓인 뒤 이미지 임베딩 검색을 추가하고 OCR/텍스트만 사용한 기준과 비교한다.

평가 지표는 관련 파일 top-k 적중률, 잘못된 소스 확정률, 필요한 질문 해결률, 기존 동작 회귀, 요구사항 충족, 소스/서버 버전 불일치 탐지, 처리 시간과 비용이다. 공개 프로젝트의 홍보 수치를 누비의 성능으로 옮기지 않는다. 이번 조사에서는 기능 또는 모델 정확도 테스트를 수행하지 않았다.
