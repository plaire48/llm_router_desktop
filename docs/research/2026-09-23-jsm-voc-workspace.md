# 사내 JSM에서 누비 VOC 워크스페이스로

상태: 타당성 검토와 구현 제안. 사용자가 확인한 환경은 사내 설치형 Jira/JSM과 회사 SSO다. 실제 JSM 주소, 설치 버전, 접근 권한, 첨부 다운로드와 저장 폴더는 아직 확인하지 않았다. 이번 검토에서 제품 코드나 의존성을 변경하지 않았으며 사내 자료를 수집하지 않았다.

## 목표와 사용자 흐름

사용자가 로그인된 JSM 탭, 수집할 범위, 저장 폴더를 선택하면 누비가 티켓 본문, 댓글, 처리 이력과 첨부 문서를 수집한다. 원본 근거와 정제 문서를 구분해 저장하고 변경된 항목만 갱신한다. 누비 Workspace는 이 자료에서 과거 처리 사례를 검색하고 현재 소스와 연결한다.

기본 화면은 `가져오기 → 정리 결과 → 이력 검색`으로 제한한다. 결과에는 신규, 갱신, 미확인을 표시한다. AI가 임의로 처리 완료를 판정하지 않는다. 반복 수집 범위와 저장 경로를 사용자가 정하면 범위 안의 읽기와 새 revision 저장은 매번 재질문하지 않는다. 수집 범위 확대, 충돌한 사용자 문서 반영, 외부 전송과 JSM 쓰기는 별도 결정이다. 일정 실행은 사용자가 정한 뒤 구성한다.

## 역할

### 사용자 요구 구체화: 누비 간 실제 작업 위임

목표는 각 누비가 A2A로 다른 누비에게 작업을 맡기고 실제 산출물을 돌려받는 것이다. JSM VOC 다운로드는 첫 활용 사례이며, 내려받은 자료는 나중에 Desktop에서 OpenWiki처럼 검색하고 소스와 연결해 재사용한다. Desktop이 항상 요청자일 필요는 없다. 브라우저에서 시작한 수집도 Desktop에 정리 작업을 요청할 수 있어야 한다.

대표 흐름은 `Desktop의 VOC 수집 요청 → Chrome의 JSM 읽기와 첨부 수집 → 원본과 수집 결과 반환 → Desktop의 지정 폴더 저장과 색인 → 저장 영수증 반환`이다. 이후 Desktop은 같은 자료로 Office에 보고서 작성을 요청하거나 Chrome에 테스트를 요청할 수 있다. 이는 목표 설계이며 현재 구현된 초안 전달 기능의 범위를 나타내지 않는다.

- 요청에는 작업 ID, 요청자와 수신자, 목적, 허용된 사이트/티켓 범위, 필요한 자료, 완료 조건을 담는다. 저장 경로는 Desktop이 소유한 폴더 권한 ID로 연결한다.
- 수신자는 자신의 기존 Pi 실행기와 도구로 처리하고 같은 작업에 진행 상태, 질문, 결과를 반환한다. 연결과 범위를 정한 뒤에는 사용자가 요청과 답변을 앱 사이에 복사하지 않도록 한다. 로그인 만료, 불명확한 범위와 실제 추가 권한이 필요한 지점만 기존 HITL로 확인한다.
- 결과는 설명 문장뿐 아니라 티켓/댓글/첨부 ID, 원문 출처, 파일 해시, 누락 항목과 실행 영수증을 포함한다. Chrome 수집 완료와 Desktop 파일 저장/색인 완료는 별도 하위 작업 결과다.
- 연결이 끊기면 같은 작업과 영수증을 조회한다. 취소는 실제 수신 실행기까지 전달하고 종료 확인 전에는 중지 완료로 표시하지 않는다. 상호 위임은 부모 작업 ID와 위임 경로로 순환을 막고, 결과를 받은 기존 작업에서 이어간다.

기존 공식 A2A SDK와 Pi 실행기를 재사용한다. [A2A 1.0의 Task, 상태, Artifact, 다회 대화 계약](https://a2a-protocol.org/v1.0.0/specification/)에 맞춰 수신 실행 연결, 구조화 결과와 파일 전달을 확장한다. 새 멀티 에이전트 프레임워크 도입은 이 경로에 필요하지 않다. 현재의 수동 요청 가져오기/답변 보내기, 초안 전용 결과, 전달 취소와 실제 실행 취소의 분리, Desktop발 요청 중심 계약은 추가 개발 대상이다.

| 구성 | 역할 | 경계 |
| --- | --- | --- |
| Chrome 누비 | 로그인된 페이지에서 관찰, 티켓 요소 추출, 허용된 다운로드 | SSO 쿠키나 인증값을 데스크톱 또는 모델로 복사하지 않는다. 실제로 접근할 수 있는 자료만 수집한다. |
| Desktop 누비 | 수집 실행 상태, 파일 수신, 검증, 지정 폴더 저장, 변환 작업 | 사용자가 지정한 폴더에만 쓴다. 브라우저가 임의의 절대 저장 경로를 요청하지 못하게 한다. |
| OpenWiki | 정제한 VOC 문서와 출처의 검색, 소스 연결 | 검색된 과거 해결책을 현재 코드의 정답이나 변경 승인으로 취급하지 않는다. |
| Office 누비 | 정제한 이력을 바탕으로 현황 문서/보고서 작성 | 기존 문서 생성과 최종 저장 HITL을 따른다. |

A2A는 작업 상태와 artifact 명세를 주고받는 데 재사용한다. 큰 첨부는 인증된 로컬 파일 전송 경로로 보내고 A2A에는 artifact ID, MIME, 크기, 해시, 수집 범위와 결과를 남기는 방식을 권장한다. A2A 자체가 파일 저장, 멱등성, 접근 권한을 보장한다고 가정하지 않는다. 파일 업로드 경로와 권한은 아직 구현되지 않았다.

## 수집 경로 결정

1. 사용자 계정으로 볼 수 있는 대표 티켓에서 제목, 상태, 댓글, 처리 이력, 첨부 목록을 먼저 확인한다.
2. 해당 회사가 허용한 인증으로 Jira/JSM 공식 API 접근이 되는지 읽기 전용으로 확인한다. 가능한 자료는 구조화된 API 응답으로 수집하고 화면과 대조한다. 설치 버전과 계정 역할에 맞는 명세를 사용한다. Cloud API와 설치형 API를 혼용하지 않는다.
3. API가 불가능한 자료는 현재 로그인된 탭의 DOM과 접근성 정보를 사용한다. 접힌 댓글, 더 보기, 페이지 구분과 가상 스크롤을 순서대로 읽고 관찰한 ID로 중복을 제거한다.
4. 이미지 전용 화면 또는 스캔 문서는 화면 캡처/OCR 후보로 분기한다. 페이지 읽기를 통과했다는 이유로 이미지와 첨부도 읽었다고 표시하지 않는다.

JSM의 티켓 본문 추출에는 전용 필드 매핑이 필요하다. 일반적인 본문 추출기는 기사 본문에 최적화되어 있어 상태, 담당자, 사이드 패널과 댓글을 생략할 수 있다. DOM 구조가 달라졌거나 수집할 항목이 누락되면 `partial`로 남긴다. 필드가 없는 경우와 현재 권한으로 읽지 못한 경우를 구분한다. 공개 답변과 내부 메모를 같은 공개 범위로 병합하지 않는다.

Chrome downloads API의 파일명은 기본 Downloads 경로에 상대적이며 임의의 절대 경로를 지정할 수 없다. 따라서 특정 workspace 경로 저장은 Desktop의 범위 제한 writer가 담당한다. 첨부 바이트를 브라우저가 읽을 수 있는 다운로드 경로인지 실환경에서 확인한다. 브라우저 다운로드 이벤트의 완료와 파일 바이트 수신/변환 완료를 구분하고, 정책상 바이트 접근이 불가능한 파일은 사용자 파일 선택 경로로 전환한다. 다운로드 성공만으로 데스크톱 저장 완료를 표시하지 않는다. [Chrome 공식 문서](https://developer.chrome.com/docs/extensions/reference/api/downloads)

## 보존과 정제

권장 구조는 원본, 구조화 데이터, AI 문서를 나누는 3단계다. 예시의 티켓 키와 파일명은 실제 자료가 아니다.

```text
사용자 지정 폴더/
  voc/<site-id>/<issue-id>/
    source/<revision>/ticket.json
    source/<revision>/comments.json
    source/<revision>/history.json
    attachments/<attachment-id>/<sha256>/<original-name>
    extracted/<attachment-id>/<sha256>.md
    generated/<revision>/summary.md
    notes.md
  openwiki/voc/<site-id>/<issue-id>/<revision>.md
  .nubi/voc/manifest.json
```

`source`는 수집한 근거이고 전체 사내 시스템의 원본 백업을 뜻하지 않는다. `notes.md`는 사용자가 작성하는 영역으로 생성기가 덮어쓰지 않는다. 소스 코드 프로젝트와 다른 폴더에 저장할 수 있어야 하므로 현재 Desktop의 Git 프로젝트 루트 제약과 별개인 수집 폴더 권한/조회 연결이 필요하다. 임의 Git 초기화나 커밋, push를 하지 않는다. Git으로 관리할 정제 문서와 접근 범위를 정한 뒤 별도 비공개 저장소 또는 기존 저장소에 연결한다. 큰 첨부와 검색 DB는 기본적으로 Git 대상에서 제외하는 방안을 검토한다.

정규화 레코드:

- 식별: 사이트, 불변 issue ID, 현재 ticket key, 원문 URL, 수집 계정의 접근 범위.
- 이력: 원문 updated 시각, 수집 시각, 상태 변경 이벤트, 댓글 ID/수정 시각/공개 범위.
- 첨부: attachment ID, 파일명, MIME, 실제 크기, 내용 해시, 변환기/버전, 누락 페이지와 실패 사유.
- VOC: 증상, 요청사항, 영향 대상, 보고된 원인, 수행한 조치, 관찰한 결과, 남은 확인 사항.
- 출처: 각 사실의 댓글 ID, 이벤트 ID 또는 첨부 페이지/구간. 명시된 사실과 모델 추론을 구분한다.

수집 시각을 사건 발생 시각으로 바꾸지 않는다. 현재 상태가 Closed라고 해서 근본 원인이 확인되거나 재발이 없다고 결론 내리지 않는다. 원인/조치/결과가 자료에 없으면 미확인으로 둔다.

## 재수집과 복구

불변 issue ID, 댓글/첨부 ID, 원문 수정 시각과 해시를 함께 사용한다. 같은 파일명이나 화면 제목만으로 중복을 판단하지 않는다. API 경로는 버전별 검색/페이지 구분에 맞춘 수정 시각 겹침 구간과 멱등 갱신을 사용한다. DOM 경로는 이전에 읽은 ID와 마지막 확인 화면을 재검증한 뒤 이어간다. 숨겨진 모든 항목을 발견했다고 추정하지 않는다.

단계는 `발견 → 내용 수집 → 파일 수신 → 해시 확인 → 변환 → 문서 저장 → 색인`으로 구분한다. 각 단계 완료 후 체크포인트를 남긴다. 부분 파일은 임시 이름으로 보존하고, 실제 해시를 확인한 뒤 확정한다. 중단 후 완료한 파일을 다시 쓰지 않는다. 권한 오류는 삭제로 해석하지 않는다. 접근 범위가 바뀐 자료는 검색 대상에서 보류하고 사용자에게 알린다. 기존 사용자 수정과 충돌하면 새 revision으로 남기고 비교한다.

## 현재 코드에서 재사용할 부분

- `extensions/aipro-chat/browser-content-dom.js`: Readability 0.6.0, Turndown 7.2.4, GFM 표 변환. 현재도 부분 수집임을 명시하며 숨긴 영역과 로드되지 않은 내용을 제외한다. 이 일반 읽기 계약은 유지하고 JSM 필드/페이지 수집기를 별도로 연결한다.
- `extensions/aipro-chat/src/document-worker.js`: PDF.js 6.3.289와 Mammoth 1.12.3으로 PDF 페이지 텍스트와 DOCX 원문 텍스트를 추출한다. 현재 PDF 150쪽/텍스트 40,000자 제한이며 OCR과 표 레이아웃 복원은 없다. 대량 수집용 스트리밍/페이지별 변환은 추가 개발이다.
- `document-tools.js`: 문서 ID, 해시, 원문 구간 기반 검색/읽기. 외부 수집 자료가 현재 대화 첨부와 다른 보존 수명을 갖도록 데이터 계약을 확장해야 한다.
- `packages/nubi-a2a`: 공식 SDK, SQLite 영수증, 수신자 격리. 현재 시나리오/문서 초안 전송만 지원하며 브라우저발 VOC 수집과 파일 업로드는 없다.
- Desktop OpenWiki: MiniSearch, RRF, Graphology와 출처 버전 확인. 외부 티켓 revision을 로컬 evidence로 연결하되 현재 읽기 전용 Claims 계약을 임의 확장하지 않는다.

| [Anthropic Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval) | 검색 단위에 티켓, 시스템, 시점 문맥을 포함 | 우선 기존 키워드/관계 검색으로 기준선을 측정. 임베딩과 reranker는 관련 사례 검색 평가에서 효과가 있을 때 추가하며 외부 성능 수치를 누비 성능으로 표현하지 않는다. |

## VOC와 소스 연결

`티켓 → 증상 → 서비스/업무 → 확인된 원인 → 조치 → 검증 결과 → 관련 커밋/파일/테스트` 관계를 저장한다. 티켓 키가 명시된 커밋, 처리 댓글의 PR 링크처럼 확인 가능한 연결부터 만든다. 텍스트가 유사하다는 이유만으로 원인이나 수정 파일을 확정하지 않는다. 추정 연결은 검토 대기 상태다.

질문 예: “이 오류는 이전에 어떻게 처리했나?”, “같은 증상의 재접수는 어떤 변경 뒤에 생겼나?”, “이번 변경의 검증에 참고할 티켓은 무엇인가?”. 답변에는 해당 revision과 원문 구간을 연결하고 과거 조치와 현재 소스의 적용 가능성을 별도로 설명한다.

## 첫 검증 범위

같은 프로젝트의 대표 티켓 10~20건을 사람이 확인한 기준 자료와 비교한다. 댓글이 많은 티켓, 재오픈, 수정된 댓글, 동명 첨부, 스캔 PDF, 한국어 표, 접근 제한, 다운로드 실패를 포함한다.

확인 항목은 발견한 티켓 대비 수집 범위, 댓글/이벤트 ID 누락, 다운로드 해시와 원문 일치, 요약의 출처 연결과 사실 오류, 질문별 관련 과거 사례 검색, 중단 후 중복 없는 재개, 사용자 문서 보존이다. 기준 표본에서 누락이 없어도 전체 JSM의 완전 수집이나 실모델 정확도를 보장하지 않는다.

구현 순서는 단일 티켓과 첨부의 실제 왕복 검증, 범위 수집/체크포인트, 증분 갱신, VOC 검색/소스 연결이다. 실제 착수에는 JSM 주소와 지정 저장 폴더가 필요하며, 회사 인증/문서 처리 정책과 대표 화면에서 읽을 수 있는 범위를 함께 확인한다.
