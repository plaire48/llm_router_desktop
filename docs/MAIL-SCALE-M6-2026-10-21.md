# M6: 합성 30만 통 기준선

상태: 생성기와 현재 저장/검색 경로의 실패 기준선 확보. 메일 규모 수용은 **미통과**. FTS5, 보관 정책, 새 파이프라인은 구현하지 않았다. §8의 18~20과 22~24에 중복된 색인 암호화/보관/tree-sitter 질문은 모두 답 대기로 취급한다.

## 결과

Mac arm64, Node 25.4.0, RAM 16GiB에서 고정 시드 21로 300,000통, 20,000스레드, 500명, 한국어/영어, 2016~2025년을 생성했다. 첨부는 메타데이터만 있다. 원문은 합성 DTO이며 실제 MIME/Office/암호화 금고 입력이 아니다. 생성 파일 SHA-256은 `2f358cbab1d9ff257bcd0aa3c0ad5b69606229342432282ef413390fc85ed1ab`.

| 측정 | 최종 원본 값 | 해석 |
|---|---:|---|
| 합성 JSONL 생성 | 3.660초 / 434,060,000바이트 | 스트리밍, 모델 호출 0 |
| 기존 Store의 메타+검색 캐시 저장 | 48.465초 / 6,192.640통/초 | DTO 적재 속도. 제품 수집 속도가 아님 |
| DB 크기 | 648,233,472바이트 | WAL checkpoint 후 |
| 전체 메타데이터 조회 | 2,797.517ms / 300,000행 | 렌더링된 첫 화면 시간이 아님 |
| 목록 API | 결과 전 힙 부족, 프로세스 12,908.567ms | RSS 표본 최대 1,718,091,776바이트 |
| 검색 API | 첫 질문 결과 전 힙 부족, 프로세스 18,172.542ms | RSS 표본 최대 1,711,816,704바이트 |
| 240개 검색 점검 | 완료 0/240 | p95/Recall은 null, 0점이나 성공으로 환산하지 않음 |

기존 `Store`와 `MailSearch`를 그대로 호출했다. 이미 준비된 version 3 검색 캐시를 사용하므로 원문 복호화나 초기 캐시 생성 비용조차 없는 조건이다. 단계별 새 프로세스, 힙 1,536MiB, 180초 상한으로 실행했다. 실패 원본에 V8 `heap out of memory`와 SIGABRT가 있다. 마지막 checkpoint의 `elapsedMs`는 종료 시간이 아니며, 실패 소요는 부모의 `processElapsedMs`를 쓴다. RSS 500MiB 조건은 초과했다.

## 결정과 남은 범위

전체 목록과 본문 사본을 매 요청에 모으는 현재 경로의 한계를 기준선으로 고정한다. 성능 한도는 바꾸지 않았다. M1 승인 전 색인 DB/암호화 경계는 변경하지 않는다. FTS p95, 실제 첫 화면, MIME/금고 수집, 밤 루틴 모델 호출/시간, 메일 중단 8종과 자연어 답변 인용 정확도는 **미측정**이다. 240개는 위치/스레드/첨부/메타/부재 검색 점검이며 의미 답변 평가를 대체하지 않는다.

처음 시도는 `ps` 표본 수집의 sandbox EPERM으로 중단됐다. 보완 뒤 run2도 같은 목록/검색 힙 부족이었으며 모두 보존했다. 초기 자료는 발신자 500명 외에 수신자 1명이 더 있어 합계 501명이라는 실패 시험을 추가하고 고쳤다. 최종 final-v2는 발신자와 수신자를 합쳐 정확히 500명이다. 이전 final도 보존했다. 최종 실행은 자료 다운로드/압축 해제 뒤 순차 실행했고 시작 loadavg 2.573/3.134/3.816였다. 단회 관측이며 안정된 처리량 추정이나 Windows 성적이 아니다.

## 검증과 인계

실패 시험을 먼저 기록한 뒤 새 단위 5개 통과. C7과 합친 새 시험 8개 233.184ms, 전체 집중 24개 720.963ms로 통과. 새 단위는 네이티브 앱 실행 없음. 별도 60통 Store/MailSearch 실행은 240/240 검색 점검과 출처 해시 확인 통과(검색 단계 901.964ms). 이를 30만 통 성적으로 확대하지 않는다.
