# 누비 브라우저 가르치기와 재사용 스크립트 설계

작성 2026-10-21, Claude. 사용자 요청 "외부 브라우저를 누비 안에서 쓰고, 화면을 보며 질문해 자동화 스크립트를 만들고, 시험해 저장하고, 워크플로우에서 쓰기".

## 0. 사용자 결정 (2026-10-21)

- 브라우저는 기존 외부 브라우저 연결 방식 그대로다. 확장으로 짝 맺은 사용자의 Chrome이나 Edge 탭을 누비가 움직이고, Electron 웹콘텐츠 뷰는 쓰지 않는다. 기본은 별도 창이다. 사용자가 브라우저 창을 누비의 브라우저 칸으로 끌어다 놓거나 붙이기 버튼을 누르면 "따라붙이기"가 켜져 창이 칸 크기에 맞춰지고 누비 창을 따라온다. 떼기 버튼으로 돌아온다(2026-10-21 사용자: "끌어다가 쓰는 건 추가하자").
- 녹화를 먼저 하고, 에이전트는 모르는 것만 묻는다. 외부 브라우저와 내부 뷰 모두 같은 녹화기를 쓴다. 사내 시스템은 외부 브라우저에서만 녹화하고 실행한다.
- 스크립트는 Workspace 안에 둔다. 공유는 나중에 연다.
- 미결: 버전 배치(§13 질문 27, 권고 1.3.1), 확장 배포 방식(§13 질문 28).

## 1. 목표와 범위

- 사용자가 한 번 보여 준 사내 웹 업무를 에이전트가 이해하고(어디를, 무엇을, 왜), 모델 없이 다시 돌 수 있는 스크립트로 만든다.
- 스크립트는 사용자가 시험하고 승인한 뒤 저장되며, 워크플로우의 한 단계와 루틴에서 호출된다.
- 화면이 바뀌어 실패하면 그 단계만 에이전트가 처리하고, 고친 내용은 초안으로 남겨 승인 뒤 반영한다.
- 범위 밖: 로그인 자동화, 자격값 저장, 쿠키 복사, 새 브라우저 엔진 반입.

## 4. 창 따라붙이기 (선택 기능, 기본은 별도 창)

- 켜는 방법은 둘이다. 브라우저 창을 누비 브라우저 칸 위로 끌어다 놓으면 누비가 창 위치로 감지해 붙이고, 브라우저 칸의 붙이기 버튼으로도 켠다. 떼기 버튼이나 창을 칸 밖으로 끌어내면 보통 창으로 돌아간다.
- 누비가 연결된 창의 네이티브 핸들을 찾는다. 확장이 보낸 창 소유 증명(window-proof)과 창 제목과 프로세스로 맞춘다.
- 누비 브라우저 칸의 화면 좌표에 맞춰 SetWindowPos로 위치와 크기를 맞추고, 누비 창의 move, resize, focus, minimize 이벤트에 따라 다시 맞춘다. 숨길 때는 창을 최소화하지 않고 화면 밖으로 두지 않으며, 누비 창 뒤로 보낸다.
- 오픈소스: node-window-manager(MIT, 창 열거와 setBounds)를 기본으로 쓰고, koffi(MIT, user32 직접 호출)는 node-window-manager가 못 하는 호출에만 쓴다. Codex의 Windows 실험(tools/browser-window-follow-spike)이 두 경로를 100회씩 재어 채택을 확정한다. 직접 구현은 하지 않는다. 새 네이티브 빌드가 필요하면 기존 Spectre와 VS 2022 절차를 따른다.
- 2단계 실험: SetParent로 누비 창의 자식으로 붙인다. DPI 변경, 팝업과 다운로드 창, 포커스와 IME가 깨지지 않을 때만 전환한다.
- macOS 개발 PC에서는 같은 모듈이 `windowEmbedded:false`로 동작하고 창은 옆에 둔다. 판정은 Windows 회사 PC다.

## 5. 녹화

- 녹화기는 페이지에 주입되는 스크립트 하나다. 캡처 대상은 click, dblclick, input과 change, select, keydown(Enter, Tab, Escape), 이동과 새 탭이다. 비밀번호 칸과 로그인 주소 페이지는 값을 기록하지 않고 "사용자가 입력함"으로만 남긴다.
- 셀렉터 후보는 Playwright 규칙을 따른다. 순서는 역할과 접근성 이름, 라벨, placeholder, 보이는 글자, data-testid, id, 짧은 CSS 경로다. 후보를 전부 저장하고 실행 때 순서대로 시도한다.
- 단계마다 실행 직전 캡처와 요소 테두리 좌표를 남긴다. 캡처는 Workspace 안에만 두고 공유 때는 선택이다.
- 외부 브라우저는 확장의 scripting으로, 내부 뷰는 `playwright-tab.cjs`의 탭 디버거로 같은 스크립트를 넣는다. 녹화 결과 형식은 동일하다.

## 6. 가르치기 흐름 (Magentic-UI 원칙)

1. 녹화가 끝나면 에이전트가 단계 목록을 읽고 "계획 초안"을 만든다. 단계마다 추측한 이유와 값의 출처 후보를 적는다. 사용자는 실행 전에 계획을 고칠 수 있다.
2. 모르는 단계만 묻는다. 질문은 세 종류다. 어디를 누르는가(번호 주석판에서 번호 고르기), 어떤 값을 어디서 가져오는가(메일 필드, 위키 문단, 실행 때 묻기, 고정값), 왜 하는가(한 줄).
3. 번호 주석판은 접근성 트리에서 누를 수 있는 요소를 뽑아 번호를 붙이고, 캡처 위에 번호를 겹친 그림과 번호별 표를 같이 보인다. 사용자는 번호와 한 줄만 적는다.
4. 답마다 근거를 붙일 수 있다. 메일 한 통, 위키 문서 한 문단, 사용자 입력 중 하나다. 근거는 참조만 저장하고 본문은 복사하지 않는다.
5. 외부에 영향이 있는 단계(제출, 저장, 삭제, 결제)는 action guard로 표시하고 실행 때 기존 승인 게이트를 지난다.
6. 사용자의 답은 기억한다. 같은 시스템의 다음 녹화에서 같은 화면이 나오면 다시 묻지 않는다. 저장 위치는 `browser-screen-knowledge.mjs`의 화면 지식이다.

## 7. 스크립트 형식과 저장

- 폴더: `browser-scripts/<이름>/script.json`, `README.md`, `captures/`, `runs/`.
- 단계 스키마는 @puppeteer/replay의 step을 바탕으로 하고 다음을 더한다.

```json
{
  "type": "click",
  "selectors": [["role=link[name='FP 산정']"], ["text=FP 산정"], ["#menu-fp"]],
  "reason": "FP 산정 메뉴로 들어간다",
  "valueSource": null,
  "guard": false,
  "assert": {"urlIncludes": "/fp/estimate", "textVisible": "산정 기준"},
  "capture": "captures/03.png"
}
```

- 입력 단계의 `valueSource`는 `{"kind":"mail","field":"subject","filter":"..."}`, `{"kind":"wiki","page":"...","section":"..."}`, `{"kind":"ask","label":"..."}`, `{"kind":"literal","value":"..."}` 중 하나다. 비밀값은 어떤 kind로도 저장하지 않는다. 비밀번호 칸은 녹화에서 제외된다.
- README는 사람이 읽는 절차서다. 목적, 선행 조건(로그인 상태, 권한), 단계 요약, 마지막 시험 결과와 날짜를 둔다.
- 공유는 나중에 연다. 열 때 README와 script.json만 올리고 captures는 선택이며, 조직 이름과 개인 식별 정보 검사는 기존 안전 회귀 묶음의 규칙을 쓴다.

## 8. 실행과 자기 치유

- 실행기는 모델 없이 Playwright로 돈다. 단계마다 셀렉터 후보를 순서대로 시도하고, assert가 맞아야 다음으로 간다. 실행마다 `runs/<시각>.json`에 단계별 결과, 쓴 셀렉터, 소요, 캡처를 남긴다.
- 모든 후보가 실패하면 그 단계만 에이전트가 맡는다. 에이전트는 현재 화면과 단계의 reason과 assert를 보고 한 번 시도한다. 성공하면 새 셀렉터와 캡처를 "초안"으로 남기고 실행은 계속한다. 실패하면 멈추고 사용자에게 번호 주석판으로 묻는다.
- 초안은 자동으로 스크립트에 들어가지 않는다. 사용자가 실행 결과 화면에서 승인하면 반영된다(Anchor 규칙).
- guard 단계는 실행 때 Desktop의 기존 승인 정책을 그대로 지난다. 자동 승인 단계는 사용자가 스크립트 단위로 정한다.

## 9. 워크플로우와 루틴 연결

- 워크플로우 단계 종류 `browser_script`를 더한다. 입력은 스크립트 이름과 `ask` 값의 바인딩이다. 출력은 영수증(실행 id, 단계 수, 캡처 경로, assert 결과)이다.
- 루틴은 기존 Task 9 규칙을 따른다. 세 번 성공 뒤 승격, 정의 해시에 script.json이 들어간다.
- 실패 영수증은 행동 필요 목록(G1)에 올라간다.

## 10. 안전

- 로그인은 사람이 한다. 로그인 주소는 녹화와 실행 모두 막는다. 자격값과 쿠키는 어떤 경로로도 다루지 않는다.
- 원격 디버깅 포트를 열지 않는다. 확장과의 통로는 기존 1회용 코드와 출처 검사다.
- 스크립트 파일에 비밀값을 넣지 않는다. 녹화기는 password 타입과 autocomplete가 cc나 otp인 칸의 값을 버린다.
- 모델에는 캡처와 접근성 트리 요약만 보내고, 가르치기의 근거(메일, 위키)는 참조만 보낸다.
- 회사 PC 선행 확인: 확장 정책(압축 해제 확장 로드 허용 여부), DeveloperToolsAvailability 정책(개발자 도구 금지면 chrome.debugger도 막힘). 둘 중 하나라도 막히면 §13 질문 28로 배포 방식을 정한다.

## 11. 측정과 수용 기준

| 지표 | 목표 | 측정 |
|---|---|---|
| 녹화 뒤 질문 수 | 10단계 스크립트에 5개 이하 | 가르치기 패널 로그 |
| 첫 실행 성공률 | 공개 웹 서식 20종에서 90% 이상 | `eval/browser-scripts/` 공개 서식 묶음 |
| 모델 호출 0인 실행 비율 | 두 번째 실행부터 80% 이상 | runs 영수증 |
| 셀렉터 자기 치유율 | 화면 변경 10종에서 70% 이상이 초안 생성 | 변형 서식으로 측정 |
| 창 붙이기 | 이동과 크기 변경 100회에서 어긋남 0 | Windows 실기기 |

공개 웹 서식과 합성 화면으로 기준선을 잡고, 회사 화면은 사용자가 Windows 실기기에서 실측한다. 회사 자료는 기준선에 쓰지 않는다.

## 12. 단계와 배치

1. 선행 확인(사용자, 회사 PC): 확장 정책과 개발자 도구 정책. Codex가 확인 절차와 결과 기록 양식을 준다.
2. 스파이크(Codex 작성, 사용자 실행): Windows 창 붙이기 스크립트. node-window-manager와 koffi 둘 다 실측하고 라이선스와 빌드 요구를 기록.
3. 녹화기와 단계 스키마와 실행기(Mac에서 개발 가능, 공개 웹 서식으로 시험).
4. 가르치기 패널과 번호 주석판(기존 UI 양식 재사용: 목록 행, 진행 행, deck-dialog, 캡처 검수).
5. 워크플로우 단계 종류와 루틴 연결.
6. 자기 치유와 초안 승인.

구현은 Codex, 설계와 검토와 측정은 Claude다. 구현 계획은 이 설계 승인 뒤 `docs/superpowers/plans/`에 쓴다.
