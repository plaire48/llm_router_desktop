# 메일과 JSM의 주기 수집 및 지식 자산화

2026-10-23 설계 초안. 사용자 지정 기준은 main `44947b56` 이후다. 이번 소스 확인은 `7dbaf0f6`에서 했다. 이번 산출물은 수집과 자산화의 범위/구현 순서이며, JSM 실계정 연결이나 신규 수집기 구현 완료를 의미하지 않는다.

## 목표와 범위

사용자가 매번 자료를 가져오거나 같은 내용을 다시 설명하지 않아도, 메일과 JSM의 변경분이 출처를 갖춘 검색 자료와 업무 지식으로 축적되게 한다.

초기 대상은 메일과 JSM이다. Knox Teams 메신저는 후속이다. 워크플로우/루틴 화면과 계획 2 UI 작업은 포함하지 않는다. `DESKTOP_FEATURES.workflows=false`를 유지하며 기존 메일과 같은 호스트 백그라운드 수집 경로를 사용한다. 기능을 켜기 위해 워크플로우나 Computer Use를 활성화하지 않는다.

사용자가 얻는 결과는 다음과 같다.

- "지난번 이 오류는 어떻게 해결했나": 현상, 원인, 조치와 적용 범위, 근거 티켓/메일을 함께 찾는다.
- "이 요구사항은 왜 바뀌었나": 요청, 결정과 변경 이력을 시점별 출처로 설명한다.
- "관련 미해결 건은 어디까지 진행됐나": 마지막 확인한 상태, 남은 요청과 관련 티켓을 표시한다.

## 전체 흐름

```text
선택한 원본과 조회 범위
  → 주기 확인
  → 새 자료/변경된 자료 식별
  → 원문 확보 및 출처/해시 검증
  → 검색 가능한 메타데이터와 버전 기록
  → 분석 대기 큐
  → 기존 선택 모델과 OpenWiki로 지식 추출
  → 근거 검증
  → 검색/질문에 제공하고 관련 자산 갱신
```

수집과 AI 분석은 별도 단계다. 모델이 연결되지 않거나 분석이 실패해도 이미 확인한 자료와 수집 영수증은 보존한다. 모델 연결이 복구되면 대기한 버전만 분석한다. 기존 자동 정리 OFF와 사용자 일시정지의 의미는 유지하고, 꺼진 수집을 숨겨서 재활성화하지 않는다.

## 주기와 수집 방식

메일 동기화 기본 주기는 사용자 결정에 따라 5분으로 반영했다(`intervalMs=300000`, 2026-10-23). JSM의 5분은 기존 초깃값 제안이다. 제목과 발신자 수집 조건은 아직 설계이며, 주기 변경만으로 필터까지 구현한 것으로 표시하지 않는다.

같은 날 사용자가 공유한 `apps.py`의 메일은 `.mysingle`을 파싱하지만, 이후 사용자는 DRM 때문에 파일 읽기를 사용할 수 없으며 공유 프로그램의 UIA 구조를 Desktop 메일에 적용하라고 재지시했다. 이에 공유 `server.py`의 창 연결/캐시 트리를 재사용한 UIA 메일 어댑터와 암호화된 관측 원문 보관을 추가했다. 현재 구현은 **열린 메일 하나**를 읽으며 전체 메일함/첨부/MIME 확보를 뜻하지 않는다. 최신 계약은 `packages/nubi-desktop/docs/KNOX-DESKTOP-UIA-MAIL-2026-10-23.md`를 따른다. 아래 파일 탐색/제목·발신자 조건/전체 동기화는 이전 설계와 후속 범위이며 현재 UIA 구현으로 완료된 것이 아니다.

| 자료 | 정기 확인 | 처음 연결할 때 | 그다음 |
| --- | --- | --- | --- |
| 메일 | 5분, 사용자 결정 | 선택한 Knox 저장소의 메타데이터를 확인하고 수집 조건에 맞는 자료부터 색인 | 저장한 조건을 적용하고 변경된 자료만 읽으며 같은 내용은 다시 분석하지 않음 |
| JSM | 5분 제안 | 선택한 프로젝트/서브시스템의 미해결 및 최근 변경 건부터 확보 | 마지막 성공 범위 이후 변경된 티켓을 페이지별 수집 |

메일의 현재 구현은 주기마다 디렉터리 트리를 다시 탐색한다. 이를 무제한 전체 탐색으로 계속 사용하지 않는다. 파일 이벤트는 변경 후보를 만드는 힌트로만 쓰고, 제한된 작업량의 디렉터리 재확인과 정기 대조로 놓친 이벤트/이동/삭제를 보완한다. 첫 대량 색인과 이후 대조는 나누어 실행하고 UI의 상태 조회가 파일 탐색을 대신 수행하지 않는다. 기존 대량 SQL 목록/커서 조회를 유지하며 새 전체 본문 영속 검색 엔진 도입과 암호화 결정은 별도로 다룬다.

JSM은 확인한 변경 시각에 겹침 구간을 두고 조회한다. 안정적인 정렬과 페이지 경계는 실제 JSM 버전/응답에서 확인한다. 같은 수정 시각의 티켓도 고유 ID로 구분하고, 모든 페이지의 수집/저장 확인 뒤에만 해당 범위의 커서를 전진시킨다. 개별 저장 영수증은 먼저 남길 수 있으므로 중간 종료 후 재조회해도 중복 분석하지 않는다. 닫힌 티켓의 재개, 댓글/설명 수정과 티켓 이동도 변경으로 다룬다. 필요한 과거 범위는 별도 이어받기로 채우며 첫 연결에서 서버 전체를 요구하지 않는다.

두 수집기는 앱이 실행되는 동안 동작한다. 앱 종료/절전 중의 수집을 약속하지 않으며, 재시작/복귀 시 마지막 성공 커서에서 누락 구간을 따라잡는다. 계정/조회 범위가 바뀌면 다른 범위의 커서를 재사용하지 않는다. 실패 시 제한된 간격 증가로 재시도하고 인증이 필요하면 로그인 대기로 전환한다.

## 메일 수집 조건 1차 범위

사용자는 제목과 보낸 사람으로 동기화할 메일을 정한다. 이는 수집 후 목록 검색 필터와 별도의 출처 설정이다. 설정은 선택한 Knox 저장소에 연결해 저장하고 5분마다 같은 규칙을 적용한다. 최초 과거 파일 수집과 이후 변경분 확인에도 동일하게 적용한다.

제목은 일반 글자 포함을 기본으로 하고, 필요한 규칙만 정규식 모드로 작성한다. 여러 제목 규칙은 OR로 묶는 안을 제안한다. 보낸 사람은 실제 From 이메일 주소로 구분하고, 화면에는 관찰한 이름과 주소를 함께 표시한다. 여러 보낸 사람도 OR다. 이름만으로 동명이인을 같은 대상으로 확정하지 않는다.

**기본 결합 제안: 항목 안에서는 OR, 제목과 보낸 사람 사이에는 AND.**

```text
(제목에 "장애" 포함 OR 제목 정규식 "^\[JSM\]" 일치)
AND
(보낸 사람 = alice@example.test OR 보낸 사람 = bob@example.test)
```

제목만 설정하면 제목 조건만, 보낸 사람만 설정하면 보낸 사람 조건만 적용한다. 양쪽 모두 입력하면 두 항목을 모두 만족해야 한다는 설명과 미리보기를 제공한다. 제목/보낸 사람 중 하나만 맞아도 모두 수집하는 전체 OR 모드는 초기 기본값에 넣지 않는다. 이 결합 방식은 다음 사용자 검토에서 확정할 제안이다.

- 메타데이터를 먼저 확인하고 조건을 판정한 뒤 일치하는 자료만 본문/첨부 분석 및 자산화 큐로 보낸다. 불일치 파일의 본문을 먼저 파싱/분석하는 구조로 구현하지 않는다. 실제 수집에 포함할 때 내용 해시를 검증한다.
- 미설정 상태와 사용자가 선택한 전체 동기화를 구분한다. 조건이 없을 때는 적용 범위를 `전체 메일`로 분명히 표시하며, 기존 조건의 입력 오류나 로드 실패가 전체 동기화로 바뀌지 않게 한다.
- 저장 전에는 실제 확인한 메타데이터에서 일치 건수와 제목/보낸 사람의 일부 예시를 보여 준다. 탐색이 끝나지 않았거나 읽지 못한 항목이 있으면 확정 전체 건수로 표시하지 않는다. 이 단계에서 본문을 모델에 전달하지 않는다.
- 정규식은 저장 전 검증한다. 잘못된 규칙은 해당 입력에서 설명하고 기존 활성 조건을 유지한다. 매칭은 UI/main 이벤트 루프와 분리하고 처리 한도를 둔다. 매칭 시간 초과를 불일치나 전체 허용으로 처리하지 않으며 해당 수집 진행과 오류를 보존한다. 사용자 패턴을 실행 스크립트로 해석하지 않는다.
- 조건 버전을 기록한다. 조건을 넓히면 과거에 제외했던 파일도 다시 평가한다. 제외 영수증을 수집/분석 완료 영수증으로 취급하지 않는다. 조건을 좁혀도 기존 원문과 이미 만든 자산을 자동 삭제하지 않는다. 자동 갱신 대상은 현재 조건으로 결정한다.
- 1차에는 제목과 보낸 사람만 제공한다. 날짜/첨부 조건, 도메인 조건과 자유로운 중첩 AND/OR 편집기는 후속으로 둔다. 기존 메일 설정을 재사용하며 새 가운데 모달이나 계획 2 UI 변경을 선행하지 않는다.

## 원문을 어디에 두는가

### 메일

- `.mysingle` 원문과 첨부는 Knox 저장소에 둔다. 전체 MIME/첨부의 누비 사본을 새로 만들지 않는다.
- 누비는 원본 참조, SHA-256, 목록 메타데이터, 수집 영수증과 분석 결과를 관리한다.
- 본문/첨부를 열거나 분석할 때 원본을 다시 검증한다. 원문이 없어지거나 바뀌면 과거 캐시를 현재 근거로 반환하지 않는다.
- 기존 사본 정리, 원본 해시가 다른 body-only 사본과 사용자 수정 자료의 보존은 현재 구현 계약을 유지한다.

### JSM

- 서버가 원문이다. 메일처럼 기존 PC 원문이 있다고 가정하지 않는다.
- 사용자에게 허용된 범위에서 실제 받은 티켓 JSON, 댓글과 이력을 버전 스냅샷으로 저장한다. 동일 내용은 다시 복사하지 않고 기존의 검증된 스냅샷이 있으면 재사용한다.
- 원문 URL, 서버/계정/조회 범위, 불변 issue ID, 당시 티켓 번호, 원격 수정 시각, 수집 시각과 내용 해시를 남긴다. 인증값과 쿠키는 원문/모델 문맥에 넣지 않는다.
- 구조화된 스냅샷에는 기존 OS 키 기반 암호화 저장 계약을 적용한다. 기존 VOC 보관 함수가 있다는 이유로 이 보호까지 구현됐다고 가정하지 않는다.
- 기본/설명, 댓글, 변경 이력, 연결, 첨부마다 실제 받은 개수와 완전성을 따로 기록한다. 목록에 보인 건수나 `expand` 응답 한 번으로 상세 전체를 확보했다고 표시하지 않는다.
- 첨부는 목록과 본문 확보를 분리한다. 필요한 첨부를 별도 큐에서 받아 해시를 확인하고 지원되는 기존 읽기 경로로 분석한다. Office/NASCA는 기존 Office 읽기 및 임시 사본 정리 계약을 유지한다. 첨부 실패 때문에 정상 본문 수집까지 되돌리지 않는다.

JSM 조회는 호스트가 제공하는 로그인된 브라우저 연결과 허용된 읽기 경로를 사용한다. 기존 Samsung Browser 로그인과 누비 브라우저 로그인이 자동 공유된다고 가정하지 않는다. 실제 세션/허용 경로를 확인한 뒤 읽기 포트를 바인딩한다. 티켓 변경, 댓글 작성, 상태 전환은 수집기에 제공하지 않는다.

| 검색 가능한 자료 | 제목, 참여자, 날짜, 프로젝트/시스템, 티켓 상태, 원문 링크와 읽은 범위 | 원문 버전 |
| 업무 이력 | 메일 회신, 요청/변경/작업/배포 티켓과 결정의 시간순 연결 | 근거가 추가/변경된 업무 |
| 재사용 지식 | 현상, 원인, 해결 절차, 적용 조건, 주의 사항과 결정 이유 | 관련 원문 버전 집합 |
| 현재 확인 상태 | 미해결 요청, 남은 작업, 마지막 확인한 담당/상태와 미확인 부분 | 마지막 성공한 조회 |

주기마다 일자별 요약 파일을 복제하는 방식을 기본으로 삼지 않는다. 원문 버전과 업무/주제 단위 자산을 유지하고 날짜는 조회 조건으로 사용한다. 메일 한 통 또는 티켓 하나의 요약도 보존하되, 관련 근거가 충분할 때 업무 이력과 해결 지식으로 합친다.

명시적인 티켓 참조, JSM 관계, 메일 회신 헤더와 문서 해시 일치를 관계 근거로 우선 사용한다. 같은 제목/날짜나 AI의 유사성 판단은 연결 후보이며 확인된 동일 업무나 인과관계가 아니다. 다른 JSM 서버의 같은 티켓 번호를 같은 건으로 합치지 않는다.

각 주장에는 `sourceId`, `revision/hash`, 원문 위치와 확인 범위를 붙인다. 원문 진술, AI 추론과 사용자 메모를 분리한다. 서로 다른 원문의 모순은 보존하고 최신 문서라는 이유만으로 다른 기록의 결정을 지우지 않는다. 변경/삭제/접근 불가가 확인되면 그 원문을 사용한 자산만 갱신 대상으로 표시한다. 실패나 접근 거부를 삭제로 처리하지 않는다.

## 상태와 복구

- 출처별 마지막 시도/성공 시각, 다음 확인 시각, 수집 커서, 누락/부분 수집, 로그인 대기와 처리 대기를 기록한다.
- 원문 저장 완료와 AI 자산화 완료를 구분한다. 큐의 한 단계 실패를 전체 성공이나 전체 유실로 바꾸지 않는다.
- 한 출처의 같은 수집 작업은 중복 실행하지 않는다. 분석은 제한된 동시성으로 실행하고 기존 호스트 모델/승인/복구 계약을 재사용한다.
- 파생 자산은 사용한 원문 버전 집합과 생성기/모델 버전에 묶는다. 성공한 분석을 매 확인 주기마다 다시 실행하지 않는다. 사용자 메모를 자동 덮어쓰지 않는다.
- 저장 커밋 뒤 영수증을 남기고 재시작 시 마지막 완료 단계부터 이어간다. 마지막 성공 시각을 현재 시각으로 꾸미지 않는다.
- 검색 결과와 답변에서 마지막 확인 시각, 읽지 못한 상세/첨부와 원문 부재를 전달한다. 오래된 JSM 스냅샷을 서버의 현재 상태로 단정하지 않는다.

## 구현 순서와 완료 판단

1. **수집 기반 고정**: 출처/조회 범위, 버전, 체크포인트와 내구 큐를 기존 저장소에 연결한다. 메일 원본 참조/중복 방지/재시작을 유지하고 주기 탐색의 작업량을 제한한다.
2. **JSM 변경분 수집**: 실제 로그인된 읽기 연결에서 범위를 확인한다. 목록부터 상세/댓글/이력 순서로 페이지 수집과 스냅샷 검증을 연결한다. 로그인 만료, 페이지 중간 실패, 동일 시각 다건과 수집 중 변경을 검증한다.
3. **공통 자산화**: 기존 OpenWiki와 선택 모델에 검증된 자료만 전달한다. 새/변경된 버전만 분석하고 메일/티켓을 업무 이력과 해결 지식으로 연결한다. 출처가 사라지거나 변경된 경우의 자산 무효화/갱신을 검증한다.
4. **실제 수집 관찰**: 실제 Windows Knox와 사내 JSM에서 변경 추가/재수정/댓글 추가, 절전/재시작, 세션 만료/복구를 확인한다. 중복 수집/분석 수, 수집 지연, 실패 후 누락, 부분 수집과 출처 연결을 기록한다.

코드/fixture 통과, 실제 Windows 파일 읽기, 실제 사내 JSM 인증/수집, 실모델 지식 품질을 각각 증명한다. 현재 연결되지 않은 JSM을 이미 주기적으로 수집한다고 보고하지 않는다. 새 화면/모달이나 워크플로우/루틴 UI는 이 단계에 추가하지 않는다.
