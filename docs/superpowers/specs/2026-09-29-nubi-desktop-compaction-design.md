# 누비 Desktop 문맥 압축 품질 설계

2026-09-29

## 1. 목적과 범위

누비 Desktop의 자동 문맥 압축이 긴 작업에서 사용자의 요청과 결정을 잃지 않게 한다. 압축 품질을 수치로 잰다.

| 포함 | 제외 |
|---|---|
| Desktop 호스트(`packages/nubi-desktop/runtime`)의 압축 연결 | 공유 압축기(`extensions/aipro-chat/context-*.js`)의 요약 안내와 요약 형식 |
| 압축 품질 평가 도구(`packages/nubi-desktop/eval/compaction.mjs`) | 브라우저 누비와 누비 Office의 압축 동작 |

공유 압축기는 2026-09-29에 브라우저 누비 세션이 수정했다. 같은 파일을 두 세션이 동시에 고치지 않는다. Desktop 쪽에서 본 공유 압축기의 문제는 6절에 남기고, 그 세션이 반영한 결과를 함께 적는다.

## 2. 현재 구현

| 단계 | 위치 | 동작 |
|---|---|---|
| 대화 이력 압축 | `compactHistory` | 실행 시작 전에 오래된 차례를 요약한다. 최근 2차례는 원문으로 둔다. 이전 사용자 요청은 입력의 8%(최대 2,048 토큰)까지 원문 발췌로 남긴다 |
| 읽기 결과 비우기 | `clearCachedToolResults` | 오래된 읽기 결과를 안내문과 근거 ID로 바꾼다. 최근 2건은 그대로 둔다. 모델 호출이 없다 |
| 중복 관찰 제거 | `clearDuplicateObservations` | 글자까지 같은 관찰은 하나만 둔다 |
| 실행 중 압축 | `createRunContext.prepare` | 요청이 입력의 75%를 넘으면 오래된 묶음을 요약한다. 최근 묶음은 입력의 20%(최대 20,000 토큰)까지 원문으로 둔다. 도구 호출과 결과는 나누지 않는다 |
| 기계 기록 | `continuityMessage` | 요약한 구간의 도구 영수증과 읽은 출처를 모델 없이 남긴다 |
| 요약 검증 | `normalizeSummary` | JSON 형식, 항목 수, 길이를 검사한다. 잘린 요약은 다시 요청한다 |

## 3. 실측에서 본 문제

측정 조건: gpt-5.6-luna, 과제 L1(문맥 한도 22,000 토큰, 4차례 대화), B2 후보.

| 관찰 | 값 | 원인 |
|---|---|---|
| 압축 뒤 현재 차례의 사용자 요청이 원문으로 남지 않음 | 4회 중 4회 | 실행 중 압축은 사용자 메시지도 요약 대상으로 본다. 원문으로 다시 넣는 것은 `goal`로 넘긴 첫 요청뿐이다 |
| 압축 뒤 요청이 더 커짐 | 4회 중 2회 (20,222자 → 25,672자, 21,884자 → 26,880자) | 요약할 구간이 3,000~5,000자인데 요약, 보호 메시지, 요구사항이 다시 들어간다 |
| 줄지 않아도 요약 호출은 실행됨 | 요약 호출 4회, 6~12초씩 | 줄었는지 검사하는 시점이 요약 호출 뒤다 |
| 첫 요청에서 바로 압축 | 1회 | 도구 정의와 시스템 안내가 입력 창의 절반을 넘는다 |
| 요약에 사실이 아닌 문장 | "현재 배송 정책 내용이 제공되지 않아 설명할 수 없다" | 요약할 내용이 없는 구간을 요약했다 |
| 토큰 추정이 실제보다 큼 | 시스템 안내 1.4배, 한국어 문장 1.7배, 코드와 JSON 1.0배 (o200k_base 기준) | 추정식이 ASCII 4자당 1토큰, 그 밖 1자당 1.5토큰이다. 실제 사용량에 의한 보정은 1배 아래로 내려가지 않는다 |
| 최근 결과 하나가 창을 채우면 실행이 멈춤 | `context_compaction_failed` | 가장 최근 묶음은 요약 대상이 아니다 |

이 모델 세션은 사용량을 돌려주지 않는다. 추정 오차는 기록된 요청을 토크나이저로 다시 세어 구했다. 사내 모델의 토크나이저로는 재지 않았다.

## 5. Desktop 변경

### 5.1 사용자 메시지 원문 보호

| 항목 | 내용 |
|---|---|
| 위치 | `runtime/agent.mjs`의 `spokenTurns` |
| 대상 | 사용자가 쓴 메시지. 작업의 첫 요청, 이후 요청, 질문에 대한 답 |
| 방법 | 실행 시작 때 대화에 남아 있는 사용자 메시지를 `protectedMessages`에 넣는다. 실행 중 압축이 그 메시지를 요약 구간에 넣으면 요약 뒤에 원문을 순서대로 다시 넣는다 |
| 한도 | 최신부터 20,000 토큰 또는 입력의 25% 중 작은 값. 지금 답하는 메시지는 한도와 무관하게 남긴다 |
| 첫 요청 | 보호 목록에 있으면 그 순서에 둔다. 이력 압축으로 목록에 없으면 기존처럼 `goal`로 넣는다 |
| 호스트 기록 등 | 사용자가 쓰지 않은 user 역할 메시지는 보호하지 않는다 |

근거는 Codex의 사용자 메시지 보존(20,000 토큰)이다.

보호 한도는 압축된 요청에 남는 자리로 정한다. `입력 한도 - 고정 부분 - 최근 구간 - 요약 출력 - 1,024`이며 최대 20,000 토큰이다. 문맥 한도 22,000 토큰에서는 고정 부분이 절반을 넘어, 붙여 넣은 회의록(2,500자)을 보호하면 실행이 `context_compaction_failed`로 멈췄다. 이 경우 회의록은 요약에 맡기고 짧은 요청만 원문으로 둔다.

### 5.2 보완 회차를 압축 전 대화에서 이어감

| 항목 | 내용 |
|---|---|
| 증상 | 압축이 일어난 실행에서 검토가 보완을 요청하면 다음 회차가 `response_invalid`로 끝났다 |
| 원인 | 보완 회차를 모델이 받은 요청(압축 후)에서 이어갔다. 실행 문맥은 압축 전 대화의 위치를 세고 있어 도구 호출과 결과의 짝이 깨졌다 |
| 수정 | `prepareContext`에 들어온 압축 전 대화를 보관하고 거기에서 이어간다 |
| 추가 | 보완 중인 답변과 최신 검토 의견을 보호 목록에 넣어, 보완 회차에서 압축이 일어나도 남게 한다 |

### 5.3 검토가 현재 차례를 알게 함

`runtime/result-review.mjs`가 질문 답변이 아닌 최신 사용자 메시지를 `currentTurn`으로 검토에 넘긴다. 이 변경은 B4에 들어 있다.

## 6. 공유 압축기에 대한 제안과 반영 결과

Desktop은 아래를 구현하지 않았다. 공유 압축기를 맡은 브라우저 세션에 실측을 전달했고, 그 세션이 2026-09-29에 일부를 반영했다.

| 제안 | 근거 | 결과 |
|---|---|---|
| 요약할 구간이 작으면 요약 호출을 건너뛴다 | 3절. OpenCode는 20,000 토큰 이상 줄 때만 비운다 | 반영됨. 요약 전에 이득을 추정한다 |
| 실제 사용량에 의한 보정을 1배 아래로도 허용한다 | 3절. 넘치면 기존 강제 압축이 받는다 | 반영됨. 0.7배까지 |
| 최근 묶음 하나가 창을 넘으면 그 결과를 비우고 근거 ID를 남긴다 | 3절 | 반영 안 함. 근거를 자르는 변경이라 보류 |
| 사용자 메시지 원문 보존 | 3절 | 공유 쪽은 그대로. 호스트가 넘기는 구조라 Desktop이 5.1로 해결 |

그 세션은 요약 형식도 바꿨다. 선택 항목 `findings`, `failed`, `current`를 추가하고 요약 안내를 인계용으로 다시 썼다.

## 7. 평가 방법

`eval/compaction.mjs`가 정해진 단계를 실제 Desktop 서비스로 재생한다. 문맥 한도를 낮춰 제품의 압축 코드가 실행되게 한다. 요약은 측정 대상 모델이 만든다. 계획과 검토는 고정 응답이다.

| 측정 | 방법 |
|---|---|
| 질문 통과 | 압축된 문맥만 주고 도구 없이 질문한다. 답에 정답 문자열이 있으면 통과 |
| 원문 유지 | 사용자 메시지가 마지막 요청에 글자 그대로 있는지 확인 |
| 요약 호출 수와 시간 | 요약 요청마다 기록 |
| 줄지 않은 압축 | 압축 뒤 토큰이 압축 전 이상인 횟수 |

질문 종류는 여섯 가지다.

| 종류 | 묻는 것 |
|---|---|
| instruction | 사용자가 정한 제약 |
| request | 지금 답해야 하는 요청 |
| decision | 사용자가 준 자료에서 정해진 값 |
| artifact | 읽은 파일 경로 |
| recall | 앞에서 읽은 사실. 사실 또는 그 사실이 있는 파일 경로를 말하면 통과 |
| continuation | 다음에 할 일 |

recall이 경로도 인정하는 이유: 오래된 읽기 결과는 비워지는 것이 설계다. 다시 찾을 수 있으면 잃은 것이 아니다.

시나리오는 두 개다.

| ID | 자료 | 문맥 한도 | 내용 |
|---|---|---:|---|
| P1-notes-across-turns | order-service(합성) | 22,000 | 4차례 대화. 2번째 차례에 회의록을 붙여 넣는다. 질문 9개 |
| P2-many-long-reads | openwiki-sds(공개) | 32,000 | 한 차례에 긴 영어 문서를 12번 읽는다. 질문 8개 |

## 8. 측정 결과

조건: gpt-5.6-luna, 시나리오 2개, 질문 17개, 구성마다 1회. 2026-09-29.

| 구성 | 질문 통과 | 사용자 메시지 원문 | 요약 호출 | 요약 시간 | 압축 횟수 |
|---|---:|---:|---:|---:|---:|
| 이전 공유 압축, Desktop B4 | 13/17 | 2/5 | 6 | 58초 | 5 |
| 이전 공유 압축, Desktop 수정 | 15/17 | 4/5 | 5 | 53초 | 2 |
| 새 공유 압축, Desktop 수정 | 16/17 | 4/5 | 2 | 39초 | 2 |

| 질문 종류 | 이전 | Desktop 수정 | 새 공유 압축 포함 |
|---|---:|---:|---:|
| instruction | 3/4 | 3/4 | 4/4 |
| request | 1/2 | 2/2 | 2/2 |
| decision | 3/3 | 3/3 | 3/3 |
| artifact | 2/2 | 2/2 | 2/2 |
| recall | 3/4 | 3/4 | 3/4 |
| continuation | 1/2 | 2/2 | 2/2 |

읽는 법:

- 이전 구성에서 모델은 "가장 최근 요청"을 첫 요청으로 답했다. 수정 뒤에는 현재 차례의 요청으로 답했다.
- 원문으로 남지 않은 1건은 붙여 넣은 회의록이다. 문맥 한도 22,000 토큰에서는 자리가 없어 요약에 맡긴다. 회의록에서 나온 결정 3건은 세 구성 모두 맞게 답했다.
- 실패로 남은 recall 1건은 모델이 위키 문서 대신 `src/status.mjs`를 다시 읽으라고 답한 경우다. 그 파일에도 답이 있다. 정답 목록에 없어 실패로 채점했다.
- 첫 측정의 request 질문은 정답 조건이 느슨해 틀린 답을 통과시켰다. 조건을 "현재 요청의 내용"과 "아직 고치지 않는다" 둘 다로 고치고 기록된 답을 다시 채점했다. 표의 이전 구성 값은 다시 채점한 값이다.
- P2는 세 구성 모두 모델 요약 없이 끝났다. 오래된 읽기 결과 비우기만으로 문맥 한도 안에 들었다.

## 9. 한계

- 시나리오가 2개, 질문이 17개다. 차이는 관찰이며 우열의 입증이 아니다.
- 문자열 채점은 다른 표현의 정답을 놓칠 수 있다. 실패한 질문은 답을 직접 읽는다.
- 재생한 단계의 assistant 메시지에는 글이 없다. 실제 실행에서는 모델이 중간 메모를 남기므로 회상 결과가 다를 수 있다.
- 사내 Qwen 3.8 27B로는 재지 않았다.
- 압축이 캐시에 주는 영향은 재지 않았다. 이 모델 세션은 캐시 토큰을 돌려주지 않는다.

## 10. 사용자 결정이 필요한 사항

| 사항 | 선택지 |
|---|---|
| 최근 도구 결과 하나가 입력 창을 채우는 경우 | 그대로 둠(현재, 실행이 멈춤), 결과를 비우고 근거 ID를 남김 |
| 보호하는 사용자 메시지의 상한 | 20,000 토큰(현재), 다른 값 |
