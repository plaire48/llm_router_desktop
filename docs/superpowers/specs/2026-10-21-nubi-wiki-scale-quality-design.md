# 위키 규모와 품질 설계: 수십만 통 메일과 큰 코드 저장소 (2026-10-21, Claude)

사용자 질문(2026-10-21): "메일은 수십만 개를 관리할 텐데 메일 위키가 감당할 수 있을까? 코드 위키는 큰 파일이나 파일 개수가 많으면 잘 만들지도 못한다. 핵심이 위키인데 어떻게 정보를 잘 만들고 오류 없이 진행하게 할까?" 이 문서는 현재 코드를 근거로 한계를 수치로 적고, 벤치마킹한 방식으로 설계와 측정 계획을 정한다. 임베딩 API와 외부 임베딩/리랭커 모델 반입 불가(사용자 제약)는 그대로다.

## 1. 지금 상태와 한계 (코드 근거)

### 메일

| 단계 | 지금 | 수십만 통에서 생기는 일 |
|---|---|---|
| 저장 | 메일 한 통이 `mail:<id>` 레코드(SQLite)와 암호화 원문 금고(`mail-raw-vault`) | 저장 자체는 견딘다 |
| 읽기 | `rows()`가 `store.list('mail:')`로 **전부 메모리에 올린다** | 30만 통이면 수백 MB, 모든 화면 갱신과 검색이 느려진다 |
| 검색 | MiniSearch **메모리 색인**(`mail-search.mjs`) | 색인 자체가 메모리를 차지하고 시작 때마다 다시 만든다 |
| 요약과 사실 | 메일마다 모델 요약, 켜져 있으면 사실 추출(`mail-facts.mjs`, 메일당 최대 96건) | 30만 통 × 모델 호출은 비용과 시간이 불가능하다 |
| 메일 위키 | OpenWiki가 암호화 세션 사본에서 전체 말뭉치로 페이지 생성(`synthesizePersonalMail`) | 전체 재생성 방식은 통수에 비례해 늘어난다 |

결론: 지금 구조는 수천 통 규모의 개인 사서함을 전제한다. 수십만 통은 **읽기, 검색, 모델 호출, 위키 생성** 네 곳 모두 바꿔야 한다.

### 코드 저장소

| 항목 | 지금 | 한계 |
|---|---|---|
| 파일 수 | 목록 상한 200,000(`wiki-source-inventory`), 넘으면 `wiki_source_limit`로 실패 | 상한 자체보다, 상한 안에서도 "어떤 파일이 중요한가"를 대표 파일 표본으로만 안다 |
| 파일 크기 | 1MiB 초과 제외(`file_too_large`), 바이너리와 인코딩 오류 제외 | 큰 소스(생성 코드, 긴 모듈)는 통째로 빠진다 |
| 계획 문맥 | 폴더 집계 200KB(W1), 생략 수 명시 | 폴더 단위 요약이라 모듈 간 의존을 모른다 |
| 생성 | 페이지 작업 큐, 동시성 1~4(W3), 내구성(W0), 커버리지 감사와 한 번 보강(W4) | 끊김은 해결했지만 "무엇을 페이지로 만들지"는 모델 판단에 기대 |
| 검색 | 전체 색인과 문맥 청크(S1), Claims 근거 | 코드 심벌 단위 근거는 없음(W7 예정) |

결론: 오류 없이 끝까지 가는 부분(W0, W4)은 됐고, 남은 것은 **무엇을 어떤 깊이로 쓸지를 결정적으로 정하는 입력**이다.

## 2. 원칙

1. **결정적인 것은 호스트가, 모델은 판단만.** 수십만 건의 저장, 색인, 묶기, 중요도 계산은 코드가 한다. 모델은 상위 K개 묶음의 요약과 질문 답변에만 쓴다.
2. **전체 재생성 금지, 증분만.** 새 메일과 바뀐 파일만 처리한다. 밤 루틴(Task 9)이 예산 안에서 돌린다.
3. **메모리 상한을 정한다.** 메일 30만 통에서 상주 메모리 500MB 이하, 코드 20만 파일에서 1GB 이하.
4. **근거 없는 문장 금지는 그대로.** Claims, 해시, 인용 검증(S1)을 모든 계층에 적용한다.
5. **측정이 먼저.** 합성 말뭉치로 규모를 재현하고 수치 기준을 세운 뒤 구현한다.

## 3. 벤치마킹

| 대상 | 가져올 것 | 버릴 것 |
|---|---|---|
| SQLite FTS5(이미 `node:sqlite`에 들어 있음, 확인함) | 수십만 문서의 BM25 검색을 디스크에서, 외부 콘텐츠 테이블로 본문 중복 저장 없음 | 없음 |
| Gmail/Outlook의 대화(스레드) 뷰 | 메일 단위가 아니라 **스레드 단위** 묶기와 최신 활동순 정렬 | 서버 측 라벨 체계 |
| Aider repo map | import 그래프에 PageRank를 돌려 중요 파일을 고르고 심벌 요약으로 문맥을 채움 | 임베딩 없음이라 그대로 맞음 |
| DeepWiki(Cognition) / Devin wiki | 저장소를 모듈 계층으로 나눠 페이지화하고 다이어그램과 소스 링크를 붙임 | 호스팅 서비스 구조 |
| Sourcegraph / Continue의 코드 색인 | 심벌 색인(정의, 참조)과 경로 기반 재색인 | 서버 색인 |
| repomix / RepoAgent | 생성 코드와 벤더 디렉터리 제외 휴리스틱, 파일 요약을 트리 상향으로 합침 | 전체 파일 덤프 |
| OpenAI, Anthropic의 긴 문맥 요약 관행 | 맵리듀스식 요약과 "요약의 요약" 계층, 인용 유지 | 한 번에 전부 넣기 |

## 4. 메일 설계 M1~M6

### M1. 저장과 색인을 디스크로

- 메일 메타데이터(id, 스레드, 보낸 이, 받는 이, 날짜, 제목, 분류, 첨부 수)는 SQLite 테이블로 두고 인덱스를 건다. `store.list('mail:')` 전체 스캔을 없애고 모든 화면은 **페이지 단위 쿼리**(날짜 범위, 스레드, 분류)로 읽는다.
- 본문 검색은 FTS5 외부 콘텐츠 테이블(`mail_fts`)로 한다. 토크나이저는 FTS5 unicode61 + 한국어 자모 분해 전처리(S2의 토크나이저와 공유).
- **암호화 경계(§8 질문 18)**: 메일 데이터는 암호화한다는 사용자 결정(2026-10-14)이 있다. FTS 색인에는 평문 토큰이 들어간다. 제안: 색인 DB를 위키 세션 사본과 같은 규칙으로 둔다. 실행 중에는 사용자 전용 디렉터리의 평문 세션 파일, 종료 때 기존 데이터 키로 파일 단위 암호화, 다음 시작 때 복호화(300MB에 수 초). 비정상 종료 뒤 남은 세션 파일은 시작 때 지우고 금고에서 다시 만든다(증분 로그로 분 단위).
- 수용 기준: 30만 통 합성 말뭉치에서 상주 메모리 500MB 이하, 목록 첫 화면 300ms 이하(기존 수락 계약), FTS 질의 p95 200ms 이하, 시작 뒤 사용 가능까지 10초 이하.

### M2. 수집 파이프라인에서 모델을 뺀다

- 기본값에서 **메일당 모델 호출 0**. 분류는 규칙(보낸 이 도메인, 제목 패턴, 수신 역할, 첨부 종류)과 기존 `mail-attention` 신호로 하고, 스레드는 `mail-thread.mjs`의 참조 헤더와 제목 정규화로 묶는다. 사람, 티켓 번호, 시스템 이름은 정규식과 용어집(S2)으로 뽑는다.
- 모델 요약은 두 경우만: 주의가 필요한 메일(기존 attention), 사용자가 연 스레드(열 때 한 번, 캐시). 사실 추출(`mailFacts`)은 기본 꺼짐을 유지하고 스레드 요약에서 파생한다.
- 수집 처리량 목표: 초당 50통 이상(파싱, 저장, 색인 포함), 중단 뒤 재개는 UIDL 영수증으로 중복 0.

### M3. 메일 위키는 스레드와 주제의 두 계층

- 1계층(결정적): **스레드 카드**. 참여자, 기간, 통 수, 첨부, 최신 상태. 모델 없이 만든다. 모든 스레드가 가진다.
- 2계층(모델, 예산 안): **주제 요약 페이지**. 최근 활동이 많은 스레드 묶음(사람별, 프로젝트별, 월별)에 대해서만 OpenWiki 페이지를 만든다. 밤 루틴이 "새 메일이 들어온 스레드"만 다시 요약한다(스레드당 갱신, 전체 재생성 없음). 예산은 설정(기본 밤당 200호출)이고 넘으면 다음 밤으로 넘긴다. 페이지의 Claims는 메일 id와 발췌에 묶인다(기존 Claims 검증).
- 메일 위키 화면은 스레드 목록(결정적)이 본문이고, 요약 페이지는 스레드 상단에 접힌 카드로 붙는다. 전체 말뭉치 생성(`synthesizePersonalMail`)은 첫 설치의 최근 90일에만 쓴다.
- 수용 기준: 30만 통에서 첫 설치 90일 요약이 1시간 안, 이후 밤 루틴이 예산 안에서 끝남, 요약 페이지의 인용 정확도 98% 이상(S1 방식).

### M4. 검색과 답변

- 질의는 FTS5 BM25 + 날짜/사람/분류 필터 + 2계층 페이지의 Claims를 합친다(S1의 RRF 재사용). 답변은 메일 id와 발췌를 인용하고, 인용 직전에 원문 해시를 다시 확인한다(S1 규칙 그대로).
- "답 없음" 정밀도를 유지한다. 검색 결과가 비면 모델에 넘기지 않는다.

### M5. 보관 정책

- 뜨거움(최근 12개월): 본문 금고 + 메타 + FTS + 스레드 카드. 따뜻함(12개월 초과): 본문 금고와 FTS는 유지, 2계층 페이지 갱신 대상에서 제외. 차가움(설정 년수 초과): 내보내기(mbox 또는 eml zip) 뒤 금고에서 제거, 메타와 스레드 카드만 유지. 기본값과 년수는 §8 질문 19로 사용자가 정한다.

### M6. 벤치마크와 수용

- 합성 말뭉치 생성기 `eval/mail-corpus/generate.mjs`: 30만 통, 스레드 2만 개, 사람 500명, 한국어/영어 혼합, 첨부 메타, 10년 분포. 회사 자료는 쓰지 않는다.
- 측정: 수집 처리량, DB 크기, 상주 메모리, FTS p95, 목록 첫 화면, 밤 루틴 소요와 호출 수, 재시작 내구성(중단 8종 재사용), 질문 200문항 Recall@5와 인용 정확도.
- 통과선: 위 M1~M4의 수치. 실패 측정은 보존하고 기준을 내려 통과시키지 않는다.

## 5. 코드 위키 설계 C1~C7

### C1. 결정적 코드 지도를 먼저 (W7 앞당김)

- 파일 목록이 아니라 **심벌 지도**를 만든다. JS/TS는 기존 TypeScript 5.9.3 파서(Q3에서 재사용 확인), Java/Python 등은 정규식 정의 추출로 시작하고 tree-sitter는 보류(네이티브 모듈 반입 조건 확인 뒤). 산출은 파일별 정의, import 그래프, 테스트 대응, 생성 코드 표식.
- import 그래프에 PageRank(Aider 방식)를 돌려 **중요도 순위**를 만든다. 계획 문맥(W1 200KB)에는 대표 파일 표본 대신 상위 중요 파일과 모듈 경계를 넣는다.
- 수용 기준: 20만 파일 저장소에서 지도 생성 2분 이하, 메모리 1GB 이하, 모델 호출 0.

### C2. 큰 파일과 생성물 정책

- 1MiB 초과 파일은 제외하지 않고 **심벌 개요 + 표본 절**(정의 목록, 상단 주석, 가장 참조 많은 함수 3개)로 넣는다. 원문 인용은 그 절 안에서만.
- 생성 코드, 벤더, 빌드 산출물(lock, dist, minified, 1줄에 2,000자 초과, `@generated` 표식)은 repomix 휴리스틱으로 자동 제외하고 커버리지 보고에 "제외 이유"로 적는다(W4 보고 확장).

### C3. 깊이는 중요도로

- 페이지 계층: 저장소 개요 → 패키지/모듈 페이지(모든 모듈) → 파일 페이지(중요도 상위만, 기본 상위 15% 또는 300개). 나머지 파일은 모듈 페이지의 표로만 다룬다. 페이지 예산을 설정으로 두고(W3 설정 모달에 "문서 깊이"), 초과분은 보강 라운드로 넘긴다.
- 수용 기준: 2만 파일 저장소에서 첫 초기화 호출 수가 파일 수에 비례하지 않고 모듈 수 + 상위 파일 수에 비례.

### C4. 증분과 변경 감지

- 이미 있는 update 모드(git diff 기준)와 Claims 해시 검증을 유지하고, C1의 지도도 증분으로 갱신한다(바뀐 파일과 그 역의존만 다시 계산). W8 drift 보고서는 "지도가 바뀌었는데 페이지가 안 바뀐 곳"을 든다.

### C5. 품질 게이트

- W6 린트(깨진 링크, 빈 절, 근거 없는 주장, 중복 페이지)를 생성 직후에 돌려 불합격 페이지는 게시하지 않고 보강 라운드로 보낸다.
- S1의 정답셋 방식을 코드에 일반화한다. 공개 OSS 저장소의 README, 테스트 이름, docstring에서 질문 200개를 자동으로 만들고(정답 span은 해당 파일 줄), Recall@5와 인용 정확도를 잰다. 회사 저장소는 쓰지 않는다.

### C6. 오류 없이 끝까지

- W0(내구성), W4(한 번 보강), 부분 게시는 그대로다. 추가로 **파일 하나의 실패가 초기화를 멈추지 않는다**: 읽기 실패, 인코딩, 파서 오류는 파일 단위로 기록하고 지나가며 보고서에 "건너뛴 파일" 목록과 이유를 둔다(지금은 일부가 `fail`로 전체를 멈춘다. 코드로 확인 뒤 목록화).
- 진행 화면에 남은 페이지 수와 예상 시간을 보인다(동시성과 평균 페이지 시간으로 계산, 추정임을 표시).

### C7. 벤치마크

- 공개 저장소 세 크기: 작음(약 2천 파일, 예: expressjs/express), 중간(약 2만, 예: nodejs/node의 lib와 test 일부), 큼(10만 이상, 예: torvalds/linux의 하위 트리 또는 chromium의 한 컴포넌트). 전부 공개 라이선스이고 회사 자료가 아니다.
- 측정: 지도 생성 시간, 초기화 시간, 호출 수, 비용 추정, 페이지 수, 커버리지 비율(W4), 린트 불합격 수, 질문 200문항 Recall@5와 인용 정확도, 실패 0, 메모리 상한.
- 비교: 같은 저장소의 DeepWiki 공개 결과(있는 경우)와 페이지 구조를 나란히 놓고 빠진 모듈과 틀린 주장 수를 센다.

## 6. 순서와 배치

| 묶음 | 과제 | 배치 |
|---|---|---|
| 메일 규모 | M6 생성기와 측정(먼저), M1 저장/색인, M2 파이프라인, M3 두 계층, M4 검색, M5 보관 | rc2 전에 M6, M1, M2. M3~M5는 후반(W2 앞) |
| 코드 품질 | C1 코드 지도(W7 앞당김), C2 큰 파일 정책, C7 벤치마크 기준선, C3 깊이, C5 린트(W6)와 정답셋, C4 증분, C6 건너뛰기 | rc2 전에 C1, C2, C7 기준선. 나머지는 후반 W6/W8과 합침 |

W7과 W6은 이 문서의 C1과 C5로 대체한다(보강 계획의 해당 절에 표시). 새 의존성은 없다. tree-sitter 네이티브 모듈은 §8 질문 20으로 반입 여부를 묻고, 그 전까지는 TypeScript 파서와 정규식으로 한다.
