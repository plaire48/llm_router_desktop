# 누비 Desktop 앱 조작 묶음 승인 설계

2026-09-29. 사용자 결정: 도입.

## 1. 목적

여러 입력을 한 번의 승인으로 실행한다. 지금은 입력 하나마다 관찰, 제안, 승인, 결과 분석이 따로 돈다.

| 기준선(gpt-5.6-luna) | 값 |
|---|---:|
| 입력 3건 과제의 모델 호출 | 51~61회 |
| 같은 과제의 시간 | 4~5분 |
| 같은 과제의 사용자 클릭 | 승인 3회와 이어가기 3회 |

## 2. 범위

| 포함 | 제외 |
|---|---|
| 한 창 안의 UIA 입력 2~5개를 한 번에 승인 | 마우스 대체 입력(별도 동의가 필요하다) |
| 입력 뒤 버튼 누르기 1개 | 앱 실행, 드래그, 여러 창 |
| 단계별 확인과 중단 | 승인의 재사용, 영구 허용 |

입력 하나짜리 제안(`propose_computer_action`)은 그대로 둔다.

## 3. 규칙

| 규칙 | 이유 |
|---|---|
| 단계는 2~5개 | 승인 카드에서 사용자가 모두 읽을 수 있는 양 |
| 모든 대상은 이번 실행의 같은 관찰에 있어야 한다 | 관찰하지 않은 대상에 입력하지 않는다 |
| 허용 동작은 `set_value`, `select`, `toggle_on`, `toggle_off`, `expand`, `collapse`, `invoke` | 값과 상태를 다시 읽어 확인할 수 있는 동작과 버튼 누르기 |
| `invoke`는 최대 1개이고 마지막 단계여야 한다 | 버튼은 화면을 바꿀 수 있다. 그 뒤의 대상은 관찰한 것과 다를 수 있다 |
| 한 컨트롤은 한 단계에만 쓴다 | 중복 입력 방지. 앞 단계가 바꾼 컨트롤은 승인받은 상태와 다르다 |
| 비밀번호, 읽기 전용, 비활성 컨트롤은 거절 | 단일 제안과 같다 |
| 승인 하나는 그 단계 목록과 값에만 유효하다 | 지문이 단계, 값, 대상, 제안 때의 화면을 포함한다. 실행 직전에 다시 계산해 비교한다 |
| 거절된 묶음은 마우스 대체 입력의 자격에 세지 않는다 | 자격은 단일 제안의 UIA 실패로만 쌓인다 |
| 메시지 초안과 전송을 한 묶음에 넣지 않는다 | 전송은 별도 승인이다(도구 설명으로 안내) |
| 유효 시간은 120초 | 단일 제안과 같다 |

## 4. 실행

승인하면 호스트가 순서대로 실행한다.

| 시점 | 확인 | 어긋나면 |
|---|---|---|
| 시작 전 | 지문, 연결, 유효 시간, 창, Wiki와 문서 근거, 모든 단계의 대상 | 아무 입력도 하지 않고 `stale` |
| 각 단계 입력 직전 | 창과 그 컨트롤이 제안 때와 같은지. `set_value`는 이전 값도 | 그 단계부터 실행하지 않는다 |
| 각 단계 입력 직후 | 값 또는 상태를 다시 읽는다 | 멈추고 `attention` |
| 끝난 뒤 | 창의 컨트롤을 다시 읽고 화면을 캡처한다 | |

이미 요청한 상태인 단계는 입력하지 않고 `already_at_target`으로 기록한다. 입력하는 단계마다 표시용 커서가 대상을 가리킨다. 사용자 마우스는 움직이지 않는다.

| 결과 | 상태 |
|---|---|
| 모든 단계 실행, 확인 일치 | `observed`, 검증 `steps_matched` |
| 앞 단계는 실행, 뒤 단계의 대상이 바뀌어 중단 | `observed`, 검증 `steps_partial`, 중단한 단계와 사유 기록 |
| 입력 뒤 값이나 상태가 다름 | `attention`, 검증 `steps_mismatch` |
| 입력 명령의 결과를 모름 | `attention`, 오류 `computer_outcome_unknown` |
| 첫 입력 전에 어긋남 | `stale`. 승인 시간이 지났으면 오류 `computer_approval_expired` |
| 단계 사이에 작업이 중지됨 | 입력이 있었으면 `observed`와 `steps_partial`, 없었으면 `stale` |

`steps_matched`는 다시 읽을 수 있는 단계가 모두 일치했다는 뜻이다. 버튼 누르기는 다시 읽을 값이 없어 단계의 검증이 `not_verified`로 남는다.

`attention`은 사용자가 실제 앱을 확인해야 하는 상태다. 남은 단계를 자동으로 다시 실행하지 않는다.

## 5. 승인 카드

카드는 단계를 순서대로 모두 보여준다. 각 줄은 동작, 컨트롤 이름, 입력할 값이다. 단계를 접어 숨기지 않는다. 실행 뒤에는 단계마다 결과를 보여준다.

## 6. 영수증

`read_computer_result`의 영수증에 단계별 결과(`steps`)와 멈춘 곳(`stopped`)이 들어간다. 각 단계는 순번, 동작, 선택자, 컨트롤 이름, 실행 여부, 검증, 상태 확인을 가진다. 입력한 값은 영수증에 다시 싣지 않는다. 승인 뒤 이어가는 실행에도 같은 내용이 전달된다. 동작 전후로 달라진 컨트롤은 단일 동작과 같이 `changes`로 들어간다.

## 7. 도구

`propose_computer_batch`. 규칙을 어긴 제안은 `computer_batch_invalid`로 거절하고 `details.problems`에 단계 번호와 사유를 담는다. 인자는 `observationId`, `reason`, `steps`(각 단계는 `selector`, `action`, `value`), 선택으로 `evidenceIds`, `documentAnalysisId`다.

## 8. 검증

| 검사 | 내용 |
|---|---|
| 제안 | 규칙 위반은 사유와 함께 거절. 제안은 입력을 보내지 않는다 |
| 실행 | 단계 순서, 값과 상태 확인, 이미 요청한 상태의 단계 |
| 중단 | 대상이 바뀐 단계부터 실행하지 않음. 앞 단계의 결과는 남는다 |
| 거절 | 거절하면 아무 입력도 가지 않는다 |
| 평가 | 입력 3건 과제의 모델 호출과 승인 수를 기준선과 비교 |

## 9. 한계

- 단계 사이에 앱이 스스로 바꾸는 값은 다음 단계의 확인에서만 드러난다.
- 버튼을 누른 뒤의 업무 결과(저장, 서버 반영)는 확인하지 않는다. 단일 동작과 같다.
- 실제 Windows 11에서의 검증은 `scripts/check-winapp.mjs`가 맡는다. 이 설계의 검사는 가상 앱으로 한다.

## 10. 측정

조건: gpt-5.6-sol, 과제당 1회, 2026-09-29. 가상 앱(경비 신청 양식).

| 과제 | 지표 | 도입 전(B7) | 도입 후(B8) |
|---|---|---:|---:|
| A11 네 칸 입력 | 모델 호출 | 28 | 12 |
| | 사용자 승인 | 4 | 1 |
| | 시간 | 218초 | 81초 |
| A3 입력 2건과 임시 저장 | 모델 호출 | 14 | 13 |
| | 사용자 승인 | 3 | 1 |
| | 시간 | 81초 | 80초 |

- 두 과제 모두 앱의 값과 상태가 요청대로 바뀌었고 금지한 컨트롤에는 입력이 가지 않았다.
- A7(금액 수정 뒤 임시 저장)에서 모델은 묶음을 쓰지 않고 두 번 승인받았다. 묶음 사용은 모델의 선택이다.
- 과제가 적고 1회 측정이다. 차이는 관찰이며 입증이 아니다. 실제 Windows 11 앱에서는 재지 않았다.
