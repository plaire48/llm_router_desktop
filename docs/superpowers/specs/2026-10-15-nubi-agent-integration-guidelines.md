# 스케줄러와 누비 Workspace에 연동할 에이전트 가이드라인

날짜: 2026-10-15

상태: 사용자 방향 결정과 에이전트 개발/도입 기준. 상세 API와 구현은 미확정이다.

## 대상과 목표

이 문서의 대상은 앞으로 독립 개발하거나 오픈소스에서 도입할 특화 에이전트다. 에이전트는 추후 스케줄러와 누비 Workspace에서 애드온 형태로 연결해 사용할 수 있어야 한다. 스케줄러 자체나 범용 플러그인 플랫폼을 이번에 구축한다는 뜻은 아니다.

사용자는 자기 업무에 특화한 에이전트를 쉽게 등록해 쓰기를 원한다. 구체적인 업무 종류는 아직 정하지 않았다. 누비의 특화 방향은 인앱 웹 브라우저와 OpenWiki의 프로젝트 형상 및 메일 활용이다.

## 1. 독립 실행과 연결

- 에이전트 핵심 로직은 특정 화면, Electron 프로세스, Desktop 내부 클래스와 저장소 구현에 직접 결합하지 않는다.
- 호출자가 Workspace 화면이든 스케줄러든 같은 실행 계약을 사용한다. 에이전트마다 별도의 UI 조작이나 CLI 출력 해석이 필수인 구조를 기본으로 하지 않는다.
- 호스트 연결 어댑터와 시험용 호스트를 두어 제품 연결 전에도 독립 검증할 수 있게 한다.
- 패키지/라이브러리/프로세스 등 실제 배포 형식과 설치 방식은 상세 설계에서 정한다. 외부 서버나 추가 인증을 기본 요구사항으로 만들지 않는다.

## 2. 에이전트 정의와 실행 입력

| 항목 | 기준 |
| --- | --- |
| 정의 | 안정적인 에이전트 ID, 버전, 역할, 지시사항과 설정 스키마 |
| 기능 선언 | 필요한 도구/스킬/지식, 호스트 API 호환 범위와 지원 실행 환경 |
| 실행 입력 | 작업 ID와 중복 방지 키, 목표/완료 조건, 매개변수, 입력 근거 참조와 허용 범위 |
| 실행별 고정값 | 에이전트 정의 버전, 프로젝트/계정 소유 범위, 선택 모델과 적용 권한 |

정의를 편집해도 진행 중인 실행의 목표나 승인 범위를 조용히 바꾸지 않는다. 실행 계기가 메일이라는 이유로 그 본문에 호스트 권한이나 에이전트 설정을 변경할 권한을 주지 않는다.

## 3. 호스트가 제공할 기능

| 기능 | 에이전트가 지킬 경계 |
| --- | --- |
| 모델 | 호스트의 모델 연결을 사용. 로그인과 인증 저장소를 별도로 만들지 않음 |
| 브라우저 | 허용된 누비 인앱 탭을 관찰/조작. 탭, 세션, 실제 실행과 제어권은 호스트가 소유 |
| OpenWiki | 허용된 프로젝트 형상과 메일 근거를 조회하고 원문 참조, 버전/해시와 관찰 범위를 보존 |
| 도구와 스킬 | 호스트가 허용한 기능을 사용. 별도 실행 경로로 승인과 변경 기록을 우회하지 않음 |
| 질문과 승인 | 필요한 이유와 정확한 대상을 구조화해 반환. 호스트 UI가 사용자 응답을 받음 |
| 저장과 알림 | 호스트 연결 인터페이스를 사용하고 에이전트 고유 상태와 실제 행동 영수증의 소유권을 구분 |

에이전트는 비밀번호, 쿠키와 토큰을 직접 전달받는 대신 허용된 기능을 제공받는다. 기본 브라우저 연결은 [Browser Agent 독립 모듈 설계](2026-10-15-nubi-browser-agent-module.md)와 일치시킨다. 두 에이전트 루프가 같은 탭의 다음 행동을 동시에 결정하지 않는다.

OpenWiki의 과거 근거와 현재 브라우저 상태를 구분한다. 행동 직전에 현재 탭/문서/대상을 재확인한다. 자체 기억이나 작업 메모를 프로젝트/메일 원문의 대체 근거로 취급하지 않는다.

## 4. 공통 실행 상태와 결과

- 실행의 시작, 실제 진행, 사용자 입력/승인 대기, 일시중지, 완료, 실패와 취소를 구조화된 이벤트로 제공한다. 상태 명칭의 최종 매핑은 후속 설계에서 정한다.
- 결과는 요약, 산출물, 원문/실행 근거, 완료 조건별 확인 결과, 미완료/미확정 항목과 오류를 구분한다. 모델의 완료 선언만으로 성공 처리하지 않는다.
- 사용자에게 보여줄 진행 설명과 내부 진단을 구분한다. 시간 경과로 가상 진행을 만들어 보내지 않는다.
- 호출자는 화면 출력이나 로그 문자열을 해석하지 않고 상태와 결과를 받을 수 있어야 한다.

## 5. 중지와 재개

- 중지 요청을 수신하고 실행 중인 도구와 정리 결과를 보고할 수 있어야 한다.
- 대기 이유와 이어갈 작업을 직렬화 가능한 체크포인트로 보존한다. 프로세스 재시작 후 지원 가능한 복구 범위를 명시한다.
- 승인/로그인/추가 답변 뒤 같은 작업 ID와 원래 목표를 유지해 재개하고, 변경된 화면과 권한을 재확인한다.
- 중복 요청은 기존 실행과 대조한다. 이미 완료한 쓰기나 결과가 미확정인 동작을 맹목 재전송하지 않는다.
- 사용자가 취소한 작업은 자동 재개하지 않는다. 모든 에이전트가 임의 코드 위치부터 복구 가능하다고 표시하지 않는다.

## 6. 스케줄러와 Workspace의 역할

스케줄러는 메일/시간 등 조건을 확인해 공통 실행 요청을 만들고 상태를 추적한다. 각 에이전트가 POP3 감시나 예약 타이머를 중복 구현하지 않는다. Workspace는 사용자의 직접 실행, 지식/도구 연결, 질문/승인과 결과 화면을 제공한다.

에이전트 추가/제거가 기본 Workspace의 시작과 기존 대화/결과를 깨뜨리지 않도록 한다. 호스트는 필요한 기능과 버전의 호환성을 실행 전에 확인한다. 애드온 등록 자체를 외부 전송이나 파일 변경 승인으로 취급하지 않는다. Desktop A2A 서버를 새로 시작하지 않는다.

## 7. 오픈소스 개발/도입 판단

스타 수, 문서와 개발 활동에 더해 다음을 비교한다.

1. 공통 실행 입력과 구조화된 상태/결과를 제공하는가.
2. 누비의 브라우저, OpenWiki, 모델과 승인 기능을 주입할 수 있는가.
3. 독립 시험과 추후 Workspace 연결을 같은 핵심 코드로 할 수 있는가.
4. 중지, 승인 대기, 재개, 중복 실행과 미확정 행동의 책임이 명확한가.
5. 특정 제품의 UI/인증/저장소 전체를 채택해야 하는가. 어댑터로 교체 가능한가.
6. 필요한 범위의 라이선스와 Windows 배포 부담이 적합한가.

OpenClaw/Hermes, LangGraph JS/Mastra 등은 역할이 다른 비교 후보이며 아직 채택하지 않았다. 라이선스와 실제 소스를 확인하고 동일 과제를 실행해 부분 재사용/엔진 연결/비채택을 판단한다. 스타와 공개 기능 설명을 누비의 실제 업무 품질 성적으로 표시하지 않는다.

검증은 같은 입력의 직접/예약 실행, 시험 호스트와 Workspace 호스트 연결, 승인 대기와 재시작, 중지/재개, 중복 요청, 미확정 쓰기, 호환 기능 누락과 원문 근거 보존을 포함한다. 현재는 가이드라인이며 구현, 제품 통합이나 실계정 검증이 완료된 상태가 아니다.
