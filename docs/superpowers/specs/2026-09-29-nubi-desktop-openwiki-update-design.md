# 누비 Desktop: OpenWiki 갱신 설계

2026-09-29. 사용자 요청: 원본이 바뀐 것을 감지하면 OpenWiki 갱신을 제안하고, 사용자가 승인하면 실행한다. OpenWiki 코드는 바꾸지 않는다.

## 1. 현재 상태

| 기능 | OpenWiki | 누비 Desktop |
|---|---|---|
| Wiki 만들기, 갱신 | `openwiki --init`, `openwiki --update`. 프로그램 진입점 `runNativeRepositoryGeneration`(`packages/openwiki/src/agent/repository-runner.ts:322`) | 실행하지 않음 |
| 바뀐 내용 감지 | 모델 호출 없이 판단하는 함수가 있음(아래 3절) | 페이지 하나씩 근거 버전을 비교해, 오래된 근거를 변경과 앱 조작에 쓰지 않음 |
| 질문 위임 | | `ask_openwiki`로 OpenWiki 에이전트에 위임. `NubiOpenWikiModel`이 Desktop의 모델 연결을 씀 |

설계 당시 Desktop에 묶인 OpenWiki(`generated/openwiki.mjs`)에는 읽기 기능만 있었다. 갱신 실행기는 없었다.

## 2. 방식 비교

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 실행기를 묶고 Desktop 모델로 실행(추천)** | `runNativeRepositoryGeneration`을 Desktop 번들에 넣고 `NubiOpenWikiModel`을 넘긴다 | 사용자가 로그인한 모델을 그대로 쓴다. 별도 자격 증명이 없다. 호출 수와 시간을 Desktop 계측에 남긴다 | 번들이 커진다. 실행기에 중지 신호가 없다(모델 호출을 끊으면 남은 페이지를 건너뛰고 끝난다) |
| B. OpenWiki CLI를 따로 실행 | `openwiki code --update --print`를 하위 프로세스로 | 번들 변경이 없다 | OpenWiki용 자격 증명과 설정(`OPENWIKI_PROVIDER`, 토큰 환경 변수)이 따로 필요하다. 사용량을 Desktop이 모른다 |

추천은 A다. 질문 위임과 같은 모델, 같은 계측, 같은 중지 경로를 쓴다.

## 3. 감지(모델 호출 없음)

프로젝트를 열 때, Wiki를 쓰는 작업을 시작할 때, 사용자가 상태를 볼 때 확인한다.

| 확인 | 방법 |
|---|---|
| 마지막 갱신 이후 바뀐 원본 | `openwiki/.last-update.json`의 `gitHead`와 현재 `HEAD`를 비교하고, 그 사이 바뀐 파일을 센다. `openwiki/`와 무시 목록(`.openwikiignore`)은 뺀다. OpenWiki의 `getUpdateNoopStatus`와 같은 기준이다. OpenWiki처럼 `AGENTS.md`의 관리 구역 변경도 원본 변경으로 센다 |
| 근거가 바뀐 페이지 | 페이지마다 Claims의 근거 버전을 현재 원본과 비교한다. `stale`(원본 바뀜), `unresolved`(원본 없음)로 나눈다. OpenWiki의 `runClaimsPreflight`와 같은 기준이며, Desktop에 이미 묶인 `ClaimsStore`와 `RepositoryEvidenceResolver`로 한다 |
| 지난 갱신의 상태 | `status`가 `interrupted`면 다시 갱신이 필요하다 |

결과:

| 상태 | 뜻 |
|---|---|
| `current` | 바뀐 원본도, 근거가 바뀐 페이지도 없다 |
| `stale` | 근거가 바뀐 페이지가 있거나 마지막 갱신 이후 원본이 바뀌었다. 페이지 목록과 바뀐 파일 수를 함께 준다 |
| `unknown` | 생성 기록이 없다(사람이 쓴 Wiki). 갱신을 제안하지 않는다 |

## 4. 제안과 승인

| 단계 | 내용 |
|---|---|
| 제안 | 상태가 `stale`이면 프로젝트 자료 패널에 "OpenWiki 갱신" 카드를 보인다. 카드가 제안이다. 에이전트는 호스트 기록(`wikiUpdate`)으로 Wiki가 원본보다 오래됐다는 것과 사용자가 자료 패널에서 갱신할 수 있다는 것을 안다. 에이전트는 갱신을 실행하거나 제안하지 못한다. 에이전트 도구 설명의 크기 한도(28,000자) 때문에 도구를 더하지 않았다 |
| 카드 내용 | 근거가 바뀐 페이지, 마지막 갱신 이후 바뀐 원본 수, 쓰는 모델, 예상 호출(계획 1회와 페이지마다 여러 회), 바뀌는 파일의 범위 |
| 1차 승인: 실행 | 사용자가 "갱신 실행"을 누르면 작업 공간의 **임시 복사본**에서 실행한다. 작업 공간은 아직 바뀌지 않는다 |
| 결과 검토 | 바뀐 페이지와 Claims를 차이로 보인다. 실행 기록(호출 수, 시간, 건너뛴 페이지)도 보인다. 반영하지 않는 파일(`AGENTS.md`의 관리 구역 등)을 근거로 인용하고 작업 공간 버전으로는 맞지 않는 근거가 있으면 그 페이지를 알린다 |
| 2차 승인: 반영 | "변경 반영"을 누르면 `openwiki/` 아래 바뀐 파일만 작업 공간에 옮긴다. 반영 직전에 작업 공간의 해당 파일이 실행 시작 때와 같은지 확인하고, 다르면 반영하지 않는다 |

임시 복사본을 쓰는 이유:

- Desktop의 다른 파일 변경과 같이, 작업 공간의 파일은 사용자가 결과를 보고 승인한 뒤에만 바뀐다.
- 실행기에 중지 신호가 없다. 중간에 멈춘 결과는 복사본과 함께 버리면 된다.
- 갱신 중에도 다른 작업은 기존 Wiki를 그대로 읽는다.

OpenWiki 갱신은 `AGENTS.md`와 `CLAUDE.md`의 관리 구역도 고친다. 반영 범위는 `openwiki/` 아래로 한정하고, 두 파일의 변경은 결과 검토에 "반영하지 않음"으로 보인다.

## 5. 실행

| 항목 | 내용 |
|---|---|
| 입력 | 복사본 경로, `mode:'update'`, 기존 Wiki의 언어, `NubiOpenWikiModel`(Desktop의 모델 연결과 중지 신호) |
| 실행기 파일 | Desktop 작업 프로세스 옆의 `openwiki-update/` 폴더. 갱신을 실행할 때만 불러온다. 시작할 때 싣는 번들(`service-entry.mjs`)에는 넣지 않는다(빌드가 검사) |
| skill | `openwiki --update`처럼 실행 전에 OpenWiki의 기본 skill을 OpenWiki 홈(`~/.openwiki/skills`, `OPENWIKI_CONFIG_DIR`을 따름)에 맞춘다. 실행기의 에이전트가 그곳에서 skill을 읽는다. 다른 skill은 그대로 둔다 |
| 복사본 | 현재 `HEAD`의 Git 작업 트리(`git worktree add --detach`). 커밋하지 않은 변경은 담지 않는다. OpenWiki가 `HEAD` 기준으로 판단하기 때문이다. 카드에 "커밋하지 않은 변경은 반영되지 않음"을 보인다 |
| 진행 표시 | 실행기의 `onEvent`로 계획, 페이지별 진행을 보인다 |
| 계측 | 모델 호출은 목적 `wiki_update`로 따로 센다 |
| 외부 전송 | 없다. OpenWiki CLI의 사용 통계(PostHog)는 번들에서 보내지 않는 모듈로 바꾼다. LangSmith 추적은 문서 조사와 같이 이 실행 범위에서 끈다 |
| 모델 연결의 제약 | Desktop의 모델 연결(ChatGPT, OpenAI 호환)은 도구 호출이 8개를 넘는 응답과, 글도 도구 호출도 없는 빈 응답을 거절한다(`response_invalid`). OpenWiki의 실행기에서 둘 다 일어났다(2026-09-29, gpt-5.6-sol). 계획 에이전트는 저장소 파일을 한꺼번에 읽으려고 8개를 넘겼고, `submit_plan`이 받아들여진 뒤에는 빈 응답으로 끝냈다. 요청마다 시스템 메시지로 호출 상한을 알린다(상한을 알린 같은 요청은 두 번 모두 8개로 나눠 성공). 거절되면 그 요청에 "도구 호출이 필요 없으면 한 문장으로 답하라"는 메시지를 붙여 두 번까지 다시 요청한다(빈 응답이던 요청이 "The repository wiki plan is complete."로 답함). 붙인 메시지는 그 요청에만 쓰고 OpenWiki의 대화에는 남지 않는다. 문서 조사(`ask_openwiki`)에서는 요청 약 1,700건 중 1건이라 바꾸지 않았다 |
| 동시 실행 | 프로젝트마다 하나 |
| 중지 | 사용자가 멈추면 모델 호출을 끊는다. 실행기는 남은 페이지를 건너뛰고 끝난다. 결과는 반영하지 않고 버린다 |
| 뒤처리 | 반영하든 버리든 복사본(작업 트리)을 지운다 |

### 5.1 번들

실행기를 그대로 묶으면 27MB가 됐고, 대부분이 Mermaid 검사용 jsdom과 mermaid였다. 둘은 OpenWiki에서 선택 설치 항목이다(`peerDependenciesMeta.optional`). 없으면 OpenWiki가 규칙으로 도표를 검사한다(`loadMermaid`가 `undefined`). jsdom은 검사 때 프로세스 전역에 `window`와 `document`를 설치해, 오래 도는 Desktop 작업 프로세스의 다른 라이브러리에 영향을 줄 수 있다.

| 항목 | 처리 |
|---|---|
| jsdom, mermaid | 넣지 않는다. 둘을 설치하지 않은 OpenWiki와 같이 동작한다 |
| CLI의 다른 모델 공급자 SDK(LangChain 공급자, Vertex용 Anthropic SDK와 Google 인증) | 쓰면 실패하는 모듈로 바꾼다. Desktop은 자기 모델을 넘기므로 호출되지 않는다 |
| OpenWiki가 자기 옆에서 읽는 파일 | 기본 skill, 로그인 화면 글꼴 CSS, 패키지 버전. 번들 옆 `openwiki/` 아래에 원래 배치대로 둔다. 새로운 파일 읽기가 생기면 빌드가 실패한다 |

결과: 실행기 파일 약 5.0MB(불러오기 약 0.15초). 시작 번들은 예전 크기(4.0MB, 6.9MB)로 돌아왔다. 새로 들어간 외부 패키지는 fast-glob 계열과 ci-info이며 `THIRD-PARTY-NOTICES.md`에 적었다.

## 6. 반영 뒤

- Desktop의 Wiki 근거 확인은 그대로 작동한다. 반영 전에 받은 근거는 페이지 해시가 달라져 오래된 근거가 되고, 다시 조회해야 한다.
- 상태 카드는 `current`로 바뀐다.

## 7. 권한과 데이터

- 새 자격 증명이 없다. 사용자가 Desktop에 로그인한 모델을 쓴다.
- 저장소 내용이 모델에 전달된다. 질문 위임과 같은 범위다. 카드에 이 점을 적는다.
- 커밋, 푸시, 브랜치 생성은 하지 않는다.

## 8. 검증

| 검사 | 내용 |
|---|---|
| 감지 | 원본을 바꾸면 `stale`과 해당 페이지가 보인다. 바꾸지 않으면 `current`. 생성 기록이 없으면 `unknown` |
| 승인 | 제안만으로는 아무것도 실행되지 않는다. 1차 승인 전에는 복사본을 만들지 않는다. 2차 승인 전에는 작업 공간이 바뀌지 않는다 |
| 반영 범위 | `openwiki/` 밖의 변경은 반영되지 않는다 |
| 경합 | 실행 중 작업 공간의 페이지가 바뀌면 반영을 거절한다 |
| 중지 | 중지하면 결과를 버리고 작업 공간은 그대로다 |
| 실행 | 시험용 모델(계획 1회, 페이지 작성)로 실행기를 끝까지 돌린다 |
| 실측 | `eval/wiki-update.mjs`. 주문 서비스 자료에서 같은 실행기와 모델로 Wiki를 만들고(준비), 원본 하나를 바꿔 커밋한 뒤 Desktop의 흐름(상태, 제안, 실행, 반영)을 sol로 잰다. 감지한 페이지, 호출 수, 시간, 바뀐 페이지를 기록한다. openwiki-sds 자료는 Claims가 자료에 없는 파일(evals, test)을 가리켜, 갱신하면 대부분의 페이지를 다시 쓰므로 쓰지 않았다 |

## 9. 범위 밖

- 새 Wiki 만들기(`--init`)는 이번 범위가 아니다. 같은 경로로 넣을 수 있다.
- 개인 모드의 외부 자료 연결(`openwiki personal`)과 파일 수집은 범위가 아니다. 코드 모드는 저장소의 파일을 스스로 읽으므로, 새 파일은 커밋하면 다음 갱신에 들어간다.
- 예약 실행(주기 갱신)은 하지 않는다. 비용이 드는 실행은 사용자가 승인한다.

## 10. 결정이 필요한 사항

| 사항 | 추천 |
|---|---|
| 실행 방식 | A. 실행기를 묶고 Desktop 모델로 실행 |
| 승인 단계 | 실행과 반영 두 번 |
| 커밋하지 않은 변경 | 반영하지 않고 카드에 알린다 |

## 11. 실측(2026-09-30)

조건: gpt-5.6-sol, 주문 서비스 자료, `eval/wiki-update.mjs`. 결과와 찾아 고친 문제는 `packages/nubi-desktop/docs/LIVE-EVAL.md`의 "OpenWiki 갱신"에 있다.

| 단계 | 모델 호출 | 시간 |
|---|---:|---:|
| 준비: Wiki 생성(페이지 11개) | 46 | 8분 |
| 갱신 실행(바뀐 원본 2개, 근거가 바뀐 페이지 5개, 결과 파일 15개) | 41 | 7분 |

- 감지, 제안, 복사본 실행, `openwiki/`만 반영하는 흐름이 실제 모델로 끝까지 동작했다. 작업 공간의 `AGENTS.md`, `CLAUDE.md`는 바뀌지 않았다.
- 모델 연결의 두 제약(도구 호출 8개, 빈 응답 거절) 때문에 첫 두 실측이 멈췄다. 5절의 대응 뒤 두 실행 모두 거절 한 번씩을 다시 요청해 넘겼다.
- 반영 뒤 한 페이지가 "원본 없음"이었다. 반영하지 않는 `AGENTS.md`의 관리 구역을 인용한 것으로 보고, 반영 전에 알리도록 했다.
