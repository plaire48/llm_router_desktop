# 누비 Workspace 하네스 1차 물결 설계 (Claude Code 벤치마크)

작성 2026-10-15. 사용자 결정: Claude Code의 하네스, 멀티 에이전트, 도구 호출 방식을 벤치마크해 누비 Workspace 에이전트의 품질을 올린다. 네 가지(과제 통과율, 속도와 토큰, 실패 복구, 작업 중 보이는 모습)를 모두 올리되, 묶음을 나눠 순서대로 간다. 이 문서는 첫 물결(묶음 1~3)의 설계다. 묶음 4~6(편집-확인 고리, 멀티 에이전트, 실패 복구)은 이 물결의 측정 결과를 본 뒤 따로 설계한다.

대상 코드: `packages/nubi-desktop/runtime`(Desktop 전용)과 `extensions/aipro-chat`(공용 런타임, 브라우저 누비도 사용).

## 0. 현황 요약 (2026-10-15 조사)

- Desktop은 `runReviewedAgent`(result-review.mjs:314)로 공용 `runAgent`(agent-runtime.js:205)를 `harness:false, stepwise:true, completeAnalysis` 옵션으로 돌린다. 공용 검토 사다리는 꺼져 있고 Desktop 검토(result-review.mjs)가 대신한다.
- 한 응답의 도구 호출은 순차 실행이며, 첫 작업 뒤 나머지는 차단된다(agent-runtime.js:893-897). 읽기 묶음 `READ_TOGETHER`(agent.mjs:131)만 예외다. 하위 분석 에이전트만 병렬 읽기(동시 2)를 쓴다.
- 첫 작업 호출 전에 계획 모델 호출이 강제된다(`work_plan_required`, agent.mjs:453; 계획 주입 agent.mjs:307-314). 계획 단계의 `completed`는 모델이 표시할 수 없고(work-plan.mjs:26) 검토만 표시한다(agent.mjs:706-712).
- 본문 루프에 최대 라운드, 시간, 토큰 예산이 없다. 끝나는 조건은 답, 대기, 취소, 정체 감지, 검토 4회뿐이다.
- 시스템 프롬프트는 13~20K자, 도구 스키마는 약 7.5K 토큰(36개). 매 요청마다 시스템 메시지 끝에 안내문이 덧붙는다(agent-runtime.js:1035-1049, recovery.mjs:20).
- 평가 틀: `eval/run.mjs`(과제 30개, dev/holdout), `eval/compare.mjs`, `eval/compare-models.mjs`. 지표는 통과, 거짓 완료, 검토 한도, 호출 수(목적별), 도구 호출, 압축, 토큰, 시간.

## 1. 묶음 1. 측정 기준선

목적: 모든 변경을 숫자로 판단한다.

절차:
1. 사용자가 회사 PC(또는 로그인 가능한 PC)에서 `node eval/model-session.mjs --provider <provider> --model gpt-5.6-sol`로 로그인한다.
2. `node eval/run.mjs --split dev --trials 1`을 sol로 한 번, luna로 한 번 돌린다. 결과 디렉터리(`output/` 아래 보고서)를 Claude에게 알려 준다. Claude는 파일만 읽는다.
3. Claude가 기준선 표를 만든다: 모델별 통과 수, 거짓 완료, 검토 한도 도달, 모델 호출 수(계획, 본문, 검토, 요약, 분석별), 도구 호출 수, 압축 횟수, 토큰(prompt, completion, cached), 시간.

판정 규칙:
- 두 모델이 모두 실패한 과제만 하네스 결함으로 본다. 한 모델만 실패하면 모델 한계로 적는다.
- 속도 비교는 호출 수로 한다(서버 속도는 같은 날에도 2배까지 달라진다). 시간은 참고만.
- 통과율은 채점기의 관찰 가능한 검사 결과만 쓴다. 검토 모델의 ready는 통과가 아니다.

목표(초안, 기준선을 본 뒤 확정): 통과 수는 유지하거나 증가, 본문+계획+검토 모델 호출 수 30% 이상 감소, 거짓 완료 증가 없음.

완료 기준: 두 모델 기준선 표가 `docs/superpowers/specs/2026-10-15-nubi-harness-baseline.md`에 적힌다.

## 2. 묶음 2. 도구 호출

### 2.1 병렬 읽기 묶음

- 공용 런타임에 옵션 `parallelReadBatches:false`(기본)를 추가한다. true이면 stepwise 모드에서도 한 응답의 호출이 전부 읽기 전용(`READ_TOOLS`에 해당, 호스트가 `isReadTool`로 판단)일 때 모두 실행한다. 실행은 동시 2개(기존 p-limit), 결과는 호출 순서대로 돌려준다.
- 한 응답에 작업(쓰기, 명령, 질문, 계획 갱신 제외) 호출이 하나라도 섞이면 지금 규칙(첫 작업만, 나머지 차단)을 유지한다.
- 결과 크기는 지금의 `readRoom`/`spent` 규칙을 그대로 쓴다. 묶음 안에서 공간이 모자라면 뒤 호출을 `deferred`로 돌려주고 다시 부르게 한다(지금 READ_TOGETHER와 같다).
- Desktop은 이 옵션을 켠다. 브라우저 누비는 기본값(false)이다.
- 시스템 안내문: "독립적인 읽기는 한 응답에 함께 불러라. 작업은 하나씩."을 추가하고, 기존 READ_TOGETHER 안내문은 이 규칙으로 대체한다.

### 2.2 도구 설명 다이어트

- 도구 설명은 한 문장의 목적과 필수 입력만 남긴다. 사용 규칙(언제 쓰고 언제 쓰지 말라)은 시스템 프롬프트의 한 절("도구 사용 규칙")로 모은다.
- 목표: 36개 도구 스키마 합계 5,000 토큰 이하(지금 약 7,500). `tests/lean-tools.test.mjs`의 예산 시험에 상한을 적는다.
- 인자 이름과 required는 바꾸지 않는다(모델이 배운 형태 유지).

### 2.3 캐시가 맞는 순서

- 시스템 메시지는 실행 시작 때 한 번 조립하고 실행 중에는 바꾸지 않는다. 매 요청 덧붙이던 stepwise 안내, 코디네이터 안내, "8회 제한" 문장을 조립 시점에 넣는다.
- 요청의 순서: 시스템 → 도구 → 대화 → 영수증(receipts) → 계획 상태. 바뀌는 것은 뒤에만 둔다.
- 측정: `createRunMetrics`에 "요청 앞부분 고정 비율(fixedShare)"과 "cached 토큰 비율(cacheShare)"이 이미 있다. 묶음 1 기준선과 비교한다.

완료 기준: 단위 시험(병렬 묶음 실행 순서, 작업 섞임 차단, deferred), 합성 모델 검사(`scripts/check-electron-agent.mjs`에 병렬 읽기 한 턴 추가), 도구 스키마 토큰 상한 시험 통과.

## 3. 묶음 3. 루프 간소화

### 3.1 모델이 직접 세우는 계획

- 첫 턴 안내: "작업을 시작하기 전에 `update_plan`으로 1~5단계 계획과 의도(intent)를 적어라." 계획 모델 호출은 모델이 계획 없이 작업 호출부터 보냈을 때만 예비로 쓴다(지금의 주입 경로 유지).
- `work_plan_required` 게이트는 유지한다. 다만 예비 계획 모델이 실패하면 지금처럼 `work_plan_invalid`로 멈추지 않고, 모델에게 "계획을 먼저 적어라"는 안내를 돌려 한 번 더 기회를 준다.
- 평가 지표에 "계획 모델 호출 수"가 따로 있으므로 효과를 바로 본다.

### 3.2 단계 완료 표시

- WORK_PLAN_SCHEMA의 status에 `completed`를 허용한다. 규칙: 지금 진행 중(`in_progress`)은 정확히 하나, `completed`는 앞선 단계에만.
- 검토가 `intent:step:i`를 supported로 확인하면 `verified:true`를 붙인다. 모델이 `completed`로 표시했는데 검토가 supported가 아니면 `in_progress`로 되돌리고 그 사실을 검토 피드백에 적는다.
- 화면(`ui/WorkspacePlan.jsx`, 공용 `TaskPlan`): 모델 표시 완료는 옅은 체크, 검토 확인 완료는 진한 체크. 공용 컴포넌트는 선택 속성으로만 바꾼다.

### 3.3 예산

- 본문 루프 상한: 모델 호출 60회, 20분. 값은 `runtime/run-budget.mjs`에 상수로 두고 평가 한도(80회, 20분)보다 작게 유지한다.
- 상한에 닿으면: 현재 라운드를 마친 뒤 도구 없이 "지금까지의 결과, 확인한 근거, 남은 일"을 답하게 하는 마무리 요청을 한 번 보낸다. 상태는 `paused`, 오류 코드 `run_budget`. 화면에 "이어서 진행" 단추(기존 `resumeAgent` 경로)를 둔다.
- 검토는 마무리 답에도 1회 돈다(근거 없는 완료 주장을 막기 위해).

### 3.4 검토 횟수

- 읽기만 한 실행(이번 실행에 제안, 명령, 컴퓨터 작업이 없음)은 검토 최대 1회. revise가 나와도 보완 루프를 돌지 않고 답에 "보완할 결과"를 접어 붙인다(오늘 넣은 접힌 검토 표시 그대로).
- 작업이 있던 실행은 지금처럼 최대 4회.

완료 기준: 단위 시험(모델 계획 우선과 예비 계획, completed 되돌리기, 예산 도달 마무리, 읽기 전용 검토 1회), 합성 모델 검사 통과, 묶음 1과 같은 절차로 sol과 luna 재측정.

## 4. 바꾸지 않는 것

- 승인 모델(제안은 사용자가 반영, 명령은 승인, 항상 허용 목록)과 근거 검증(해시, 관찰 범위, 위키 근거).
- 공용 런타임의 브라우저 기본 동작. 모든 공용 변경은 기본값이 꺼진 옵션이다.
- 평가 채점 규칙과 과제. 통과시키려고 과제나 채점을 고치지 않는다.

## 5. 위험과 대응

- 병렬 읽기로 문맥이 빨리 찬다: `readRoom`이 묶음 단위로 공간을 나누고 넘치면 deferred. 압축 횟수를 지표로 본다.
- 모델이 계획을 대충 쓴다: 계획 스키마 검증은 그대로(의도, 1~5단계). 검토가 단계와 요구를 대조한다.
- 예산 마무리가 거짓 완료를 늘린다: 마무리 답에도 검토 1회. 평가의 falseCompletion으로 감시.
- 도구 설명을 줄여 호출 품질이 떨어진다: 인자 이름과 required는 그대로, 규칙은 시스템 프롬프트로 이동. 묶음 1 수치로 되돌릴지 판단.

## 6. 검증 방법

- 단위 시험: `tests/` 아래 node:test. 공용 런타임 변경은 `extensions/aipro-chat/tests`에도 옵션 켜짐/꺼짐 양쪽 시험.
- 합성 모델 검사: 기존 QA 묶음(빌드, 디자인 규칙, 화면 검사, 단위 시험) 전체 통과.
- 실모델: 묶음 1 절차로 sol과 luna 재측정, `eval/compare.mjs`로 전후 비교.

## 7. 구현 중 바뀐 점 (2026-10-15)

- 2.2 도구 스키마 목표 5,000 → 측정값 5,800(스키마 계약은 유지)으로 예산 6,000을 시험에 고정.
- 3.3 예산 도달 뒤 상태는 `paused`가 아니라 답이 나온 `review`이며 `task.runBudget`으로 표시한다. '이어서 진행'은 일반 추가 요청 경로를 쓴다.
- 3.4 읽기 전용 실행의 검토 1회는 `service.readOnlyReviewRounds`로 바꿀 수 있다(기본 1).
