## 1. 영역 A. 작업 화면 경험

### A1. 챕터와 목차

- 도구 `mark_chapter({title, summary})`를 에이전트에 준다. 제목은 짧은 명사구(40자 이하), 요약은 한 줄. 국면이 바뀔 때만 부른다(탐색 → 구현, 수정 → 검증, 사용자가 다른 요청으로 전환). 첫 요청에는 부르지 않는다. 한 대화에 3~8개가 적정이다. 한도는 **대화 전체 20개**와 **한 실행 5개** 둘 다이며 넘으면 도구가 거부한다(`chapter_limit`). 다른 실행의 챕터는 그대로 두고 현재 실행만 더 센다.
- 저장: `task.chapters=[{id, title, summary, runId, messageIndex, at}]`. 호스트가 위치(메시지 색인)를 찍는다. 모델이 위치를 고를 수 없다.
- 화면: 해당 위치에 구분선(제목)과 오른쪽 위에 떠 있는 목차(챕터 수 2개 이상일 때만). 목차 항목을 누르면 그 구분선으로 스크롤. 챕터는 기록을 지우거나 옮기지 않는다(2026-10-14 결정: 한 번 쓴 것은 그 자리에).
- 도구 설명은 한 문장(1차 물결 규칙), 사용 규칙은 `TOOL_RULES`에 한 줄 추가.

### A2. 곁가지 작업 칩

- 도구 `spawn_task({title, tldr, prompt})`: 작업 중 발견했으나 현재 변경을 키우는 범위 밖 일(죽은 코드, 오래된 문서, 빠진 시험, 확인된 TODO)을 칩으로 제안한다. 모호한 냄새나 한 줄 수정은 거부하도록 규칙에 적는다. 한 실행에 3개까지.
- `prompt`는 자체 완결(파일 경로, 근거, 기대 결과 포함)이어야 한다. 호스트는 길이 200~4,000자를 검사한다.
- 저장: `task.sideTasks=[{id, title, tldr, prompt, runId, state:'proposed'|'started'|'dismissed'}]`.
- 화면: 그 실행의 답 아래 칩 줄. 누르면 같은 프로젝트에 새 대화를 만들어 `prompt`를 첫 요청으로 보내고 칩은 `started`. 가위표로 `dismissed`. 에이전트가 `dismiss_task(id)`로 거둘 수도 있다(같은 실행에서 고친 경우).

### A3. 산출물 카드

- 도구 `send_file({path, caption})`: 실행이 만든 결과 파일(보고서, 캡처 PNG, 생성 문서)을 대화에 카드로 붙인다. 프로젝트 안 경로나 호스트가 만든 캡처만 허용. 실행당 5개.
- 화면: 카드(아이콘, 이름, 크기, 캡션). 누르면 오른쪽 창에서 연다(이미지와 PDF는 미리보기, 텍스트는 편집기, Office는 기존 문서 읽기). 카드는 메시지 안에 남는다.
- 기존 `DocumentChips`(입력)와 `AppliedFileChanges`(변경 목록)는 그대로 둔다.

### A4. 사이드바

- 읽지 않음: 사용자가 보고 있지 않은 대화에서 답이 끝나거나 질문이 생기면 점을 표시한다. 대화를 열면 지운다. 저장 `task.unread`.
- 보관: 대화 `…` 팝오버에 보관(복구는 "보관함" 필터에서). 설정에 자동 보관 일수(기본 30일, 0은 끔). 보관된 대화는 검색에 포함되고 기본 목록에서 빠진다. 삭제와 다르게 데이터는 그대로다.
- 묶음: 이번 물결에서는 하지 않는다(프로젝트가 이미 묶음 역할).
- **재확인**: 고정은 Codex가 끝냈다(고정 그룹, `sessionSidebarGroups`). 읽지 않음과 보관은 그 함수에 필터로 붙이고 고정 동작을 바꾸지 않는다.

### A5. 자동 모드 안전 규칙

- `approval-policy.mjs`에 "되돌리기 어려운 작업" 목록을 둔다: 파일 삭제가 포함된 제안(기존 파일 제거), `git push --force`, `git reset --hard`, `rm -rf`와 Windows 동의어(`Remove-Item -Recurse -Force`, `rd /s`), 외부 발송(메일 보내기, JSM/Confluence 쓰기, 공개 게시). "파일과 명령 자동" 모드에서도 이 목록은 승인을 기다린다. "항상 허용"으로 지정한 정확한 명령만 예외.
- 규칙 판정은 호스트가 한다(모델 설명 아님). 명령은 토큰 단위로 검사하고 매칭 근거를 승인 카드에 표시한다.
- MCP 도구: `destructiveHint`, `openWorldHint`(읽기 전용 아님), 또는 이름(send, publish, post, submit, deliver, notify, mail, delete, remove, purge, drop, destroy, truncate, reset)으로 외부 반영이나 삭제로 분류된 도구는 모든 모드에서 매번 확인하고 항상 허용을 받지 않는다(§8 답 7).
- **재확인**: 모드 전환 안내 모달(`AUTO-APPROVAL-WARNING`)은 유지하고, 그 안내문에 "되돌리기 어려운 명령은 자동 모드에서도 확인" 한 줄을 더한다. 작업 단위 판정은 이 항목이 새로 만든다.

### A6. 진행 상태 한 줄 (보류)

- **재확인**: 모델의 진행 서술(`progressNarration`)이 도구 호출 전에 한 문장을 말하고 기록에 시각 순으로 보인다. 같은 자리를 두 번 채우지 않도록 이번 물결에서는 하지 않는다. 서술이 비는 실행이 실측에서 자주 보이면 호스트 trace로 채우는 안을 다시 꺼낸다.

### A7. 미결: 명령 기록 기본 접힘

- 1.2.8에서 사용자 결정(2026-10-14: "실행 결과 보기" 없이 제자리에 열어 둠)대로 열었으나 1.2.9 Codex가 기본 접힘으로 되돌렸다. 어느 쪽이 현재 결정인지 §8에서 확인한다. 확인 전까지 코드를 바꾸지 않는다.

## 2. 영역 B. 하네스 2차 (묶음 4~6)

### B1. 기준선 실측 (사용자 실행)

- 1차 물결 설계 §1 절차 그대로: `node eval/model-session.mjs` 로그인 뒤 `node eval/run.mjs --split dev --trials 1`을 sol과 luna로 한 번씩. Claude는 `output/` 결과 파일만 읽어 `docs/superpowers/specs/2026-10-16-nubi-harness-baseline.md`에 표를 만든다(통과, 거짓 완료, 검토 한도, 목적별 호출 수, 도구 호출, 압축, 토큰, 시간).
- 판정 규칙은 1차와 같다: 두 모델 모두 실패한 과제만 하네스 결함. 통과율은 채점기 결과만.
- B2~B4 구현 뒤 같은 절차로 재측정한다.

### B2. 편집-검증 고리 (Codex 계획과 나눠 맡음)

- **재확인**: 관련 테스트 발견, 최신 소스 버전에 묶인 검사, TypeScript 프로젝트 검사, 개발 과제 12+12와 문맥 정책 비교는 사용자가 승인한 개발 사이클 계획(§9 2~5단계, §8)이 맡는다. 이 설계는 그 계획에 없는 두 가지만 한다.
- 편집 뒤 자동 검사(Claude Code의 hook 자리): 프로젝트 설정 `afterEditCheck`(셸 프로필과 명령 1개, 예: `npm test -- --changed`). 제안 묶음이 반영되면 호스트가 이 명령을 기존 명령 승인 흐름으로 올린다(자동 모드면 실행, 아니면 승인 카드). 영수증은 `developmentChecks`의 test 증거로 묶인다. 관련 테스트 자동 발견이 들어오면 이 설정은 "항상 함께 실행하는 명령"으로 남는다.
- 완료 게이트의 호스트 판정: `developmentChecks`가 있는 실행에서 검증 명령 종료 코드 0이나 브라우저 읽기 영수증이 반영 이후 시각에 없으면 검토 모델 답과 무관하게 `revise`. 개발 사이클 계획 2단계가 같은 판정을 넣으면 그것을 쓰고 이 항목은 확인만 한다.
- 평가 과제는 추가하지 않는다. 효과는 개발 사이클 계획의 과제군(버그 수정, 기능 개발, 검증과 전달)으로 본다.

### B3. 조사 하위 에이전트 일반화

- 도구 `delegate_research({goal, scope:{paths[], wiki:boolean, mail:boolean}, budget:{calls≤20, chars≤24000}})`: 하위 에이전트가 자체 문맥에서 읽기 도구(`READ_TOOLS`)만 써서 조사하고 `{summary, findings:[{claim, source:{path|wikiPage|mailId, range}}], unresolved[]}`를 돌려준다. 쓰기, 명령, 질문, 승인은 없다.
- 실행: 동시 2, 실행당 6(문서 분석 작업자와 같은 한도, 같은 큐). 하위의 호출은 실행 예산(60회)에 합산하지 않고 하위 예산으로만 센다. 결과 크기는 `readRoom` 규칙.
- 이어서 묻기: `continue_research({id, question})`로 같은 하위 문맥에 한 번 더 묻는다(최대 2회).
- 화면: 기존 하위 작업자 표시(`AnalysisHistory`)에 같은 형식으로 보인다. 하위의 완료 선언은 증거가 아니고, 메인이 출처를 다시 읽어야 근거가 된다(Codex 판단 유지).
- 평가 지표에 "하위 호출 수"를 따로 둔다.

### B4. 실패 복구 보강 (남은 두 가지)

- **재확인**: 도구 실패 복구(교정 피드백, 같은 실패 3회 금지, 정체 탈출 한도)와 명령 실패 뒤 자동 검토는 끝났다. 압축의 다음 범위와 지표는 `CONTEXT-COMPACTION-BENCHMARK`와 개발 사이클 계획 4단계가 맡는다. 이 설계는 둘을 다시 하지 않는다.
