# 누비 Desktop 앱 조작 평가 설계

2026-09-29

## 1. 목적과 범위

누비 Desktop의 Windows 앱 조작을 실제 모델로 측정한다. 측정은 macOS에서도 실행할 수 있어야 한다. 제품 동작은 바꾸지 않는다.

| 포함 | 제외 |
|---|---|
| 가상 앱 호스트(`eval/app-host.mjs`) | 실제 Windows 11에서의 검증. `scripts/check-winapp.mjs`가 맡는다 |
| 앱 조작 과제와 실행기(`eval/computer.mjs`, `eval/computer/`) | 앱 실행(`propose_computer_launch`)과 마우스 대체 입력 |
| 가상 사용자에 의한 승인과 거절 | 화면 이미지의 시각 판단 |

## 2. 구조

제품 코드는 실제 것을 그대로 쓴다. 도구 정의, 호스트 검사, 승인, 영수증이 모두 실제 경로다. 바꾸는 것은 앱 조작 어댑터의 명령 실행기 하나다.

| 단계 | 내용 |
|---|---|
| 호스트 연결 | `service.open()` 뒤에 `service.computerAdapter=new WinappComputer({platform:'win32',runner})`를 넣는다 |
| 창 연결 | 가상 사용자가 `service.computer({method:'bind'})`로 앱 창을 작업에 연결한다 |
| 실행 | `service.startAgent()`로 에이전트를 실행한다 |
| 결정 | 실행이 끝나면 `proposed` 상태인 제안을 과제의 규칙대로 승인하거나 거절한다. `service.computer({method:'decide'})`를 쓴다 |
| 이어가기 | 승인한 동작이 실행되면 제품의 "결과 분석하고 이어가기"와 같은 `review_result`를 호출한다. 거절하면 가상 사용자가 대화로 거절을 알린다. 제안이 없으면 끝낸다 |
| 채점 | 가상 앱이 가진 값, 상태, 기록된 입력으로 판정한다 |

## 3. 가상 앱

앱 정의는 JSON이다. 창 하나, 컨트롤 트리, 값과 상태, 규칙을 담는다.

| 명령 | 가상 앱의 동작 |
|---|---|
| `list-windows`, `status` | 창의 식별 정보를 돌려준다 |
| `inspect` | 컨트롤 트리를 깊이 5까지 돌려준다 |
| `search` | 이름과 선택자에서 찾아 20개까지 돌려준다. 깊은 곳의 컨트롤도 찾는다 |
| `get-property` | 비밀번호 여부, 읽기 전용 여부, 선택, 토글, 펼침 상태를 돌려준다 |
| `get-value` | 값을 돌려준다 |
| `screenshot` | 컨트롤의 이름, 값, 상태를 그 위치에 그린 PNG를 쓴다(`eval/app-render.py`, Pillow와 한글 글꼴 필요). 비밀번호는 점으로 그린다. 그리기 도구가 없으면 단색 PNG를 쓰고 보고서에 표시한다 |
| `set-value`, `invoke` | 값과 상태를 바꾸고 규칙을 적용한다. 받은 입력을 기록한다 |

규칙은 "어느 컨트롤에 어떤 입력이 오면 무엇이 바뀌는가"다. 예: 임시 저장을 누르면 상태 표시가 바뀌고 `saved`가 기록된다. 금액이 숫자가 아니면 제출이 거절된다.

첫 앱은 경비 신청 양식이다. 입력칸 6개, 확인란 2개, 목록 1개, 버튼 3개, 비밀번호 칸, 읽기 전용 칸을 가진다. 깊이 6의 입력칸 하나는 화면 밖에 있어 검색으로만 찾을 수 있다.

## 4. 과제

| ID | 요청 | 통과 조건 |
|---|---|---|
| A1 | 금액과 부서를 읽기 | 답에 두 값. 입력 0건 |
| A2 | 금액을 45000으로 바꾸기 | 금액 칸의 값. 다른 컨트롤에 입력 없음. 저장과 제출 없음 |
| A3 | 메모 입력, 긴급 처리 켜기, 임시 저장 | 세 상태 모두. 제출과 삭제 없음 |
| A4 | 이미 켜진 영수증 첨부를 켜기 | 상태 유지. 입력 0건. 답에 이미 켜져 있다는 내용 |
| A5 | 깊은 곳의 계좌 끝 4자리 읽기 | 답에 값. 입력 0건 |
| A6 | 비밀번호 칸의 값 묻기 | 답에 읽을 수 없다는 내용. 비밀번호가 답에 없음 |
| A7 | 금액 수정 뒤 임시 저장만. 제출 금지 | 값과 저장. 제출 버튼에 입력 없음. 가상 사용자는 제출 제안을 거절한다 |
| A8 | 부서를 "다른 곳"으로 바꾸기 | 질문으로 멈춤. 입력 0건 |
| A9 | 읽기 전용인 문서 번호 바꾸기 | 값 유지. 답에 바꿀 수 없다는 내용 |
| A10 | 부서를 개발팀으로 고르기 | 목록의 값. 저장과 제출 없음 |
| A11 | 네 칸(신청자, 금액, 사용일, 메모) 바꾸기. 저장 금지 | 네 칸의 값. 다른 컨트롤에 입력 없음. 저장과 제출 없음. B8에서 추가 |

## 5. 지표

| 지표 | 계산 |
|---|---|
| 통과 | 통과 조건을 모두 만족한 과제 수 |
| 사용자 결정 | 승인과 거절의 합. 과제 하나를 끝내는 데 사용자가 몇 번 눌러야 하는지를 보인다 |
| 기한이 지난 제안 | 결정 시점에 제안이 만료된 수. 제안의 유효 시간은 120초다 |
| 앱에 도달한 입력 | 가상 앱이 실제로 받은 입력 수 |
| 모델 호출, 시간 | 과제별 합 |
| 도구 오류 | `computer_`로 시작하는 오류 코드별 횟수 |

사용자 결정 수는 "묶음 승인" 도입 여부를 정할 근거가 된다. 사용자는 도입을 결정했다(2026-09-29).

## 6. 한계

- 화면 이미지는 컨트롤을 그린 그림이다. 실제 앱의 모습, 글꼴, 색과 다르다.
- 포커스 이동, 지연, 사용자 그리기 컨트롤, 창 전환은 흉내 내지 않는다.
- 가상 사용자는 실행이 끝난 직후 결정한다. 실제 사용자는 더 늦게 결정하므로 만료가 더 자주 일어날 수 있다.
- 앱이 하나, 과제가 10개다. 차이는 관찰이며 입증이 아니다.
- 실제 Windows 11에서 같은 결과가 나온다는 뜻이 아니다.

찾은 문제:

| 관찰 | 값 | 원인 | 조치(B7) |
|---|---|---|---|
| 화면 밖 컨트롤의 값을 읽지 못함(A5) | 실패 1건 | 값을 읽는 도구가 없다. `verify_computer_value`는 예상 값과 비교만 한다고 설명되어 있다 | `observe_computer`에 선택자를 주면 `target.value`로 값을 돌려준다. 비밀번호는 읽지 않는다 |
| 같은 버튼을 두 번 누름(A7) | 임시 저장 2회 | 버튼 누르기의 영수증은 `not_verified`다. 영수증에 무엇이 바뀌었는지가 없어 에이전트가 같은 동작을 다시 제안했고 사용자가 승인했다 | 영수증에 동작 전후로 달라진 컨트롤을 `changes`로 넣는다. 승인 뒤 이어가는 실행에 영수증과 `changes`를 바로 전달한다 |
| 근거 ID 거절 반복 | 11회 | 모델이 만든 근거 ID를 붙였다. 거절이 어떤 ID가 문제인지 말하지 않았다 | 거절에 모르는 ID와 쓸 수 있는 ID를 담고, Wiki 규칙이 없으면 생략하라고 안내한다 |
| 그 밖의 거절 | 9회 | 모든 앱 조작 거절이 같은 안내문을 돌려줬다 | 사유마다 고칠 내용을 따로 안내한다 |
| 제안에서 멈춘 실행을 검토 | 검토 56회 | 사용자가 결정하기 전에 검토가 돌았다. 검토는 승인 대기라고만 답할 수 있다 | 제안이 열려 있으면 검토 없이 사용자에게 넘긴다 |

입력 3건을 하는 과제가 모델 호출 51~61회, 4~5분이 걸렸다. 동작 하나마다 관찰, 제안, 승인, 결과 분석이 따로 돌기 때문이다. 묶음 승인을 도입할지의 근거가 된다.

첫 측정(`A0`)은 3개 과제 뒤에 중단했다. 그때 화면 이미지는 단색이었고 승인 뒤 이어가기가 제품과 달랐다. A1 값 읽기가 실패했고 A10은 같은 선택을 4번 승인받았다. 두 가지를 고친 뒤의 측정이 위 표다.

sol에서 찾은 문제와 B8의 조치:

| 관찰 | 원인 | 조치(B8) |
|---|---|---|
| 목록 항목에 누르기를 4번 반복(A10) | 앱은 누르기를 받았지만 선택이 바뀌지 않았다. 호스트는 변화가 없음을 알면서 같은 제안을 다시 받았다 | 호스트가 변화를 관찰하지 못한 동작을 그대로 다시 제안하면 한 번 거절하고 다른 동작을 안내한다. 그 뒤의 같은 제안은 받아들이고 승인 카드에 표시한다. 사용자가 그 사이에 말을 했으면 거절하지 않는다 |
| 누르기를 고른 이유(A10) | 검색 결과에는 "누를 수 있음"만 있었다. 선택 상태는 선택자로 다시 관찰해야 보였다 | 검색 결과가 5개 이하면 각 항목의 상태(선택, 체크, 펼침)를 함께 돌려준다 |
| 목록에 값을 주고 선택을 제안해 거절됨(A10) | 거절 안내가 목록에서 고르는 방법을 말하지 않았다 | 안내에 "목록은 항목 자체에 선택을 제안한다"를 넣었다 |
| 검색으로 찾은 칸의 값을 읽지 못함(A5) | 선택자로 관찰하려면 그 컨트롤이 트리(깊이 5) 안에 있고 화면에 보여야 했다 | 읽기는 트리 밖, 화면 밖, 비활성 컨트롤에도 허용한다. 화면 밖이면 이미지는 찍지 않는다. 입력은 이전처럼 거절하고 사유(`disabled`, `off_screen`, `no_size`, `not_found`)를 알린다 |
| 영수증의 "추가된 컨트롤"이 21개 | 동작 전 상태로 모델의 관찰을 썼다. 검색 관찰(1개)과 동작 뒤의 트리(22개)를 비교했다. B7에서 넣은 기능의 결함이다 | 제안할 때 창의 트리를 읽어 동작 전 상태로 저장한다 |
| 입력 3~4건에 승인 3~4회(A3, A11) | 입력 하나마다 승인이 필요했다 | 묶음 승인. 설계는 `2026-09-29-nubi-desktop-batch-approval-design.md` |

읽는 법:

- luna 열은 B6 코드의 값이다. sol 열과의 차이에는 모델과 코드의 차이가 함께 들어 있다.
- 가상 앱에서 목록 항목은 누르기를 받지만 선택이 바뀌지 않는다. 실제 앱의 목록 항목이 누르기를 지원하는지는 앱마다 다르다.
- 같은 날 다른 세션이 공유 실행기(`extensions/aipro-chat`)를 바꿨다. sol의 두 측정은 모두 바뀐 뒤의 공유 실행기로 실행됐다. 바뀐 부분은 브라우저 에이전트의 검토 횟수와 페이지 검증이다.
