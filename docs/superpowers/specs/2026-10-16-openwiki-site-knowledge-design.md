# OpenWiki 사이트와 화면 지식 설계안

후속 구현: 화면 안내 저장/현재 구조 재확인/다음 Pi 요청 재사용과 선택 Stagehand 연결의 첫 범위는 [구현과 실측](../../research/2026-10-16-browser-screen-knowledge-implementation.md)에 있다. 아래의 전체 사이트 지도/업무 관계/검토 UI 설계가 모두 구현됐다는 뜻은 아니다.

2026-10-16. 상태: 사용자 논의를 구체화한 제안. 제품 기능 구현/통합 완료나 신규 오픈소스 적용 결과가 아니다. 근거 검토는 [BP와 벤치마킹](../../research/2026-10-16-openwiki-system-screen-knowledge-benchmark.md), 실제 공개 사이트 성적은 [네이버 개발 실측](../../research/2026-10-16-browser-agent-naver-public.md)을 따른다.

## 1. 분류: 시스템별 보관과 업무별 연결

사이트는 수집 출처, 시스템은 업무 기능의 묶음, 화면은 관찰 단위, 업무 절차는 재사용 단위다. 하나의 도메인이 여러 시스템을 호스팅하거나 하나의 시스템이 여러 origin을 사용할 수 있으므로 URL을 시스템 ID로 쓰지 않는다. 시스템과 사이트 연결은 호스트 등록 정보나 확인한 근거를 사용한다.

사용자에게는 같은 지식을 다음 세 가지 관점으로 보여준다.

- 시스템별: 그룹웨어, 변경 관리, 업무 포털 등. 각 시스템에서 화면과 사용 방법을 찾는다.
- 업무별: 변경 검토, 자료 조회, 요청 작성 등. 관련 시스템과 코드/문서/메일을 함께 찾는다.
- 자료별: 코드/형상, 문서, 메일, 브라우저 수집 자료. 각 원본의 출처와 확인 범위를 본다.

이는 같은 내용을 세 번 복사하는 폴더 구조가 아니라, 동일한 지식과 원본 참조를 관계에 따라 보여주는 탐색 방식이다. 프로젝트/공유 범위와 접근 권한은 호스트가 관리한다. 공유 시스템의 설명과 개인 계정에서 관찰한 업무 자료는 자동으로 합쳐 공개하지 않는다.

운영/검증 환경, 접근 역할에 따른 화면 변형을 구분한다. 사용자별 실제 인증 정보는 지식에 넣지 않는다. 동일한 기능의 목록/상세/작성 화면, 같은 URL에서 바뀌는 검색 전/후 상태와 팝업/프레임도 구분한다.

## 2. 저장 단위

| 단위 | 저장할 내용 |
| --- | --- |
| 시스템 | 목적, 확인한 사이트/환경, 주요 기능과 연결 자료 |
| 화면 템플릿 | 목적, 영역, 필드와 표의 의미, 진입 방법, 관련 화면 |
| 화면 변형 | 상태, 역할, 프레임/팝업 문맥과 차이 |
| 업무 절차 | 목표, 입력 슬롯, 적용 조건, 하위 단계, 확인/복구 방법 |
| 업무 자료 | 개별 이슈/메일/문서/코드의 원본 참조와 허용된 내용 |
| 관계와 근거 | 두 지식의 연결 이유, 원본 식별자, 확인 시각/범위/버전 |

화면 설명에 특정 고객/이슈/검색어를 굳혀 넣지 않는다. 개별 데이터와 현재 요청값은 템플릿에서 분리한다. 임시 DOM ref/실행 targetId, 세션 URL과 인증값을 재사용 지식으로 저장하지 않는다.

관계는 `시스템에 속함`, `이 화면으로 이동`, `업무에서 사용`, `원본을 설명`, `근거로 확인`처럼 의미를 명시한다. 코드/메일/이슈 사이 연결은 확인 가능한 링크나 식별자를 우선하고 모델의 유사성 제안은 후보로 남긴다.

예상 구조 필드는 system/site/environment/screen 식별자, 화면 변형, 접근 범위, 관찰 시각, 원본/위키 버전, 근거 참조와 읽은 범위다. 실제 계약과 버전은 별도로 정의한다. 현재 knowledge-map schema 1에 새 종류를 억지로 넣지 않고 호환성을 유지하는 스키마 확장/마이그레이션이 필요하다.

사람이 읽는 Markdown과 에이전트가 읽는 구조 데이터는 동일한 원본/버전에서 생성한다. 위키와 JSON을 각각 독립적으로 고쳐 내용이 어긋나게 하지 않는다. 원본 관리와 동시 변경은 기존 호스트 저장/검토 계약을 재사용한다.

## 3. 분석과 위키 생성 방법

1. 범위 설정: 사용자가 연 화면 또는 허용한 업무 범위를 선택한다. 현재 작업에 필요한 화면부터 시작하고 사이트 전체를 먼저 크롤링하는 것을 선행 조건으로 두지 않는다.
2. 수집: 기존 호스트 Page/탭을 통해 접근 상태를 확인하고 DOM, 접근성, 프레임과 보이는 표/폼/링크를 읽는다. source 시각, 문서/관찰 ID와 읽기 범위를 보존한다.
3. 영역 분해: 메뉴, 검색, 결과, 상세, 입력/편집, 첨부 등 의미 영역으로 나눈다. label이 없으면 주변 표 제목/행/필드 문맥을 확인하고 필요한 부분만 시각 판독한다. 이미지 판독 추정과 DOM에서 확인한 사실을 구분한다.
4. 템플릿화: 검색어/레코드 값/날짜를 화면 구조에서 분리한다. 같은 화면의 반복 레코드는 템플릿을 재사용하고 구조가 다른 경우 변형 후보를 만든다.
5. 지식 추출: 화면 목적, 필요한 정보 위치, 필드 의미, 입력 제약과 다음 화면을 근거와 함께 초안으로 만든다. 관찰만으로 버튼의 실제 동작/저장 결과나 업무 정책을 확정하지 않는다.
6. 관계 연결: 등록된 시스템/서비스와 기존 코드/문서/메일 지식을 찾아 근거가 있는 관계를 연결한다. 원본 접근 범위를 보존하고 잘린 내용이나 접근 불가를 표시한다.
7. 검토와 기록: 기존 OpenWiki 정책으로 초안을 저장/검토한다. 성공한 작업에서 확인한 절차는 독립 결과 검증 후 후보로 기록한다. 절차 자동 선택은 기존 reviewed/revalidated 계약을 따른다.
8. 다음 업무에서 활용: 목표 + 현재 시스템/환경/화면으로 지식을 찾고 필요한 영역과 짧은 안내만 Pi에 제공한다. 실제 대상은 현재 관찰에 다시 바인딩한다.
9. 갱신: 구조 변화가 발견되면 관련 부분을 재관찰하고 위키 변경 후보를 제안한다. 과거 근거를 덮어 지우거나 확정 쓰기를 다시 실행하지 않는다.

위키 설명의 품질은 `직접 관찰`, `모델 해석/후보`, `실제 결과 검증`을 구분해 관리한다. 최신 hash가 맞는다고 해석이 옳다는 뜻은 아니다. 또한 Ajv로 스키마가 맞아도 사실의 정확성/관찰의 완전성까지 통과한 것은 아니다.

## 4. 오픈소스 선택안

| 구성 | 제안 결정 | 목적과 조건 |
| --- | --- | --- |
| 기존 Playwright MCP와 선택 Playwright 어댑터 | 유지/재사용 | 호스트가 가진 화면의 실제 관찰/고정 동작. 추가 브라우저나 인증 저장소를 만들지 않음 |
| [Stagehand](https://docs.stagehand.dev/v3/basics/extract) | 신규 비교 실험 1순위 | schema 기반 의미 추출, 부분 영역 추출을 기존 관찰과 비교. 첫 적용은 읽기 전용 후보 생성. 실제 Page/모델 연결과 선택 릴리스의 계약을 확인한 후 사용 |
| [Mozilla Readability](https://github.com/mozilla/readability) | 기존 구현 재사용 | 도움말/공지/문서형 페이지의 본문 추출. 업무 폼/표/버튼 구조는 이 경로로 축약하지 않음 |
| [Ajv](https://github.com/ajv-validator/ajv) | 기존 구현 재사용 | 생성된 화면/관계 지식의 구조, 필수 메타데이터와 버전 검사 |
| [Graphology](https://github.com/graphology/graphology) | 기존 구현 재사용 | 시스템/화면/절차/자료 관계의 저장 표현과 탐색. 의미가 맞는 관계인지 별도 근거 검증 |
| [browser-use](https://docs.browser-use.com/open-source/browser-use-cli) | 선택적 비교 어댑터 | 상태 추출/요소 인식이 현재 관찰에서 부족한 경우 같은 과제로 비교. 직접 제어 표면과 자체 Agent 실행기를 구분하고 기존 Pi/승인 우회 금지 |
| [Crawl4AI](https://docs.crawl4ai.com/core/page-interaction/) | 공개 문서의 다중 페이지 수집이 필요할 때 별도 평가 | 기본 인앱 업무 브라우저 경로에는 넣지 않음. 허용된 수집 범위/원본 증거 계약 안의 import 어댑터 후보 |
| [Graphiti](https://github.com/getzep/graphiti) | 초기 도입 보류 | 시간에 따른 관계 변경과 출처 관리가 유용하나 추가 그래프 백엔드/운영 의존성이 생김. 우선 기존 지식 그래프에서 필요를 검증 |

현재 소스 확인: `extensions/aipro-chat/package.json`의 `@mozilla/readability` 0.6.0과 `browser-content-dom.js`의 실제 사용, Desktop의 Ajv 8.20.0/Graphology 0.26.0 및 knowledge-map 사용을 확인했다. 신규 후보를 설치했다는 뜻은 아니다.

Stagehand 공식 문서는 구조화 추출과 부분 영역 지정, 사용자 지정 모델 client를 제공한다. 현재 로컬 Claude Code complete 계약이 그대로 호환된다고 확인한 것은 아니다. 선택 릴리스를 고정하고 기존 호스트 모델/관찰 ID/접근 범위를 유지하는 어댑터 검증이 먼저다. `extract` 출력은 출처 대조 전 사실로 승격하지 않는다. [추출](https://docs.stagehand.dev/v3/basics/extract), [모델 설정](https://docs.stagehand.dev/v3/configuration/models)

라이선스 검토 범위: upstream 표기로 Stagehand/Ajv/Graphology는 MIT, Readability/Graphiti는 Apache-2.0이다. 실제 도입에서는 고정 릴리스와 전이 의존성/NOTICE를 확인하고 유지한다. 이번 변경은 설계 문서이며 신규 라이브러리/코드 복사를 포함하지 않는다.

## 5. 방법론의 적용 위치

- WebChallenger: 페이지의 의미 영역과 사이트 지도. 무차별 클릭 탐색을 실서비스에 복사하지 않는다.
- PlugMem: 원시 로그 대신 사실/절차/경험을 구분하고 관련 지식만 검색하는 방식. 기존 OpenWiki를 다른 기억 저장소로 대체하지 않는다.
- AWM: 입력값을 분리한 공통 하위 절차와 다른 요청에서의 재사용. 실제 관찰/승인/검증은 유지한다.
- Glean: 시스템별 원본과 권한을 유지하면서 업무 관계로 연결한다.
- Scribe/UiPath: 처리한 업무에서 초안을 만들고 여러 실행의 공통점과 변형을 축적한다.

각 방법론의 공식 근거는 앞선 BP 문서에 있다. 논문/제품 소개의 성적을 누비의 성적으로 이전하지 않는다.

## 6. 속도와 품질 검증

비교군은 지식 없음, 본문 저장만 있음, 화면/관계 지식 있음, 지식과 검증 절차 있음이다. 수집한 위키/안내를 고정하고 같은 모델/시작 상태/권한/화면 범위로 비교한다. 온라인 누적 학습 평가는 별도로 기록한다.

필수 사례는 같은 업무의 새 값, 같은 화면의 다른 요청, 다른 화면으로의 이동, UI 변경, 역할/환경 차이, 오래되거나 관련 없는 위키다. 구형 fixture의 이름 없는 요소, 중첩 프레임, 팝업, 커스텀 편집기와 지연 렌더도 유지한다. 공개 사이트와 fixture, 사내/Windows 결과는 분리한다.

| 품질 항목 | 확인할 내용 |
| --- | --- |
| 분류 | 올바른 시스템/환경/화면 선택, 중복/잘못된 병합 |
| 근거 | 중요한 설명과 관계의 원본 대조, 미관찰 범위 유지 |
| 검색 | 현재 요청에 필요한 화면/절차가 검색되는지 |
| 업무 결과 | 독립 정답/readback으로 정확한 완료 확인 |
| 복구 | 오래된 지식을 감지하고 확정한 작업을 반복하지 않는지 |
| 속도 | 최초 유효 결과, 전체 시간, 모델/도구 호출, 새 탐색 횟수 |
| 총비용 | 최초 분석 + 반복 실행 + 갱신/검토 비용 |

자동 실행 대상 지식에 근거 없는 핵심 주장이나 잘못된 연결이 있으면 수정한다. 승인/접근 범위를 넘는 실행과 확정 쓰기 중복은 허용하지 않는다. 최초 분석 시간과 반복 사용 시간을 분리하고, 기존 개발 과제의 새 입력 3회 모두 25초 목표는 해당 고정 과제의 재사용 측정에서 유지한다. 실패/시간 초과도 분모에 남긴다. 이 기준을 실제 사내 품질 보장으로 표시하지 않는다.

속도 개선은 구조 메타데이터의 저비용 추출 → 필요한 영역만 모델 분석 → 동일 템플릿 재사용 → 변경 부분만 갱신 순서로 시도한다. 원시 DOM과 전체 위키를 매 호출에 전달하지 않는다. 읽기 사실을 정리하는 일은 호스트가 허용한 자료와 기존 작업 방식으로 지연 처리할 수 있으나 새 자동화/스케줄러를 생성하는 제안은 아니다.

## 7. 개발 순서와 경계

1. 시스템/화면/절차/근거 스키마와 기존 위키/지식 지도 호환 연결을 정의한다.
2. 독립 모듈에서 호스트가 준 관찰을 위키 초안 후보로 반환하고 기존 OpenWiki 저장 포트로 연결한다.
3. 하나의 화면을 추가한 뒤 다른 요청에서 관련 지식을 꺼내 쓰고 새 화면과 대조하는 흐름을 확인한다.
4. 같은 과제에서 Stagehand 읽기 전용 추출과 기존 경로를 비교한다. 사실 누락/허위 관계/시간을 함께 측정해 적용 범위를 결정한다.
5. 시스템 간 자료 연결과 화면 변경 후 부분 갱신으로 넓힌다.

모듈의 입력/결과/중지/재개와 호스트 주입 계약을 유지한다. Workspace가 탭/모델/위키/접근/승인을 소유하며 core는 Desktop 내부 구현을 직접 참조하지 않는다. 현재 작성한 것은 위 설계와 선정안이며 실제 OpenWiki 저장, 신규 SDK와 Workspace UI 연결은 후속 구현이다.
