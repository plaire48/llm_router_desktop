# Browser Agent의 Codex 벤치마킹과 품질 고도화 계획

날짜: 2026-10-15

상태: 최초 Codex 중심 구현/평가 제안. 후속 사용자 결정으로 Codex와 Claude Code 비교 및 속도 기준을 추가했다. [후속 대조와 개발 상태](../../research/2026-10-15-nubi-browser-agent-dual-harness-benchmark.md)가 현재 우선순위다. 아래 최초 조사 범위/미수행 표시는 당시 기준이며 실제 업무 성능 비교는 여전히 미수행이다.

2026-10-15 후속: [Codex 고정 소스 1차 대조](../../research/2026-10-15-nubi-browser-agent-codex-source-audit.md)를 완료했다. 신규 작업 접수/drain, listener 세대, 대기 요청, suspend와 문맥 보존을 확인했다. MUST 첫 구현부터 Workspace 애드온 등록/해제/재연결 계약을 검증하며, 제품 통합을 뒤로 둔다는 이유로 호스트 인터페이스 설계를 미루지 않는다. 실모델 성능 비교는 미수행이다.

대상: [독립 Browser Agent 모듈](../specs/2026-10-15-nubi-browser-agent-module.md). Workspace 제품 연결은 후속 단계로 유지한다.

## 1. 목표와 벤치마킹의 의미

사용자 목표는 OpenAI Codex를 벤치마킹해 독립 브라우저 모듈의 업무 정확도, 완주, 복구, 속도와 사용자 경험을 높이는 것이다. 다음 두 작업을 구분한다.

1. 설계 벤치마킹: Codex 공개 프로토콜과 평가 방법에서 재사용 가능한 계약을 누비에 적용한다.
2. 성능 벤치마크: 같은 과제를 실제 실행해 기준선, 개선 후보와 선택적인 Codex 참조군을 비교한다.

이번에는 1의 조사와 2의 실험 명세를 작성한다. Codex 실행, 유료 모델 호출, 실계정 로그인, 패키지 설치와 제품 변경은 수행하지 않는다. 독립 모듈 자체도 설계 상태이므로 현재 성적은 미측정이다.

## 3. 우선 고도화할 여섯 가지

### 3.1 실제 행동의 수명주기와 결과를 연결

모듈의 `taskId / attemptId / actionId`에 모든 관찰, 모델 호출, 승인과 결과를 연결한다. 호스트 이벤트에는 순번과 상태 버전을 부여한다. 중복/늦은 이벤트를 UI에 다시 적용하지 않고, 재연결은 호스트의 현재 스냅샷과 보존 이벤트로 상태를 복구한다. 모델을 다시 호출해 상태를 추측하지 않는다.

행동 상태는 준비 → 승인 대기 → 발행 → 결과 확인으로 구분한다. 취소 응답과 실제 취소 완료도 분리한다. 실행된 변경을 interrupt로 되돌렸다고 표시하지 않는다. 응답 유실/호스트 종료 시에는 `unconfirmed`를 유지한다.

수용 기준: 승인 응답 유실, 중복 응답, 순서가 바뀐 표시 이벤트, 실행 중 종료에서 중복 쓰기와 거짓 완료가 없고 같은 작업의 보존 결과를 읽을 수 있다.

### 3.2 완료 조건으로 닫히는 실행과 복구

각 단계는 관찰한 시작 상태, 목표 결과, 실제 실행 영수증, 결과 검사와 남은 차이를 갖는다. 모델의 계획 완료, 도구의 정상 반환과 실제 업무 성공을 분리한다.

예: 변경 이슈 검색은 목록 표시만으로 끝내지 않고 기간/상태 조건, 페이지 수, 이슈 ID 중복, 상세 원문과 인용을 확인한다. 폼 제출은 토스트만으로 완료 처리하지 않고 저장된 레코드/재조회 결과가 필요하다. 권한 부족, 결과 없음, 미확인을 각각 반환한다.

검증은 두 층이다. 제품 실행 중에는 관찰 범위 내 결과와 누락을 검사한다. 평가 시에는 모델이 볼 수 없는 fixture 정답과 서버 상태를 독립 채점한다. 작성 모델과 검토 모델이 같은 오답을 동의해도 통과하지 않는다.

복구 입력은 원 요청, 마지막 실제 상태, 실패 원인, 행동 발행 여부와 미충족 조건으로 한정한다. 이미 확인한 조건은 반복 조사하지 않는다. 새 근거 없이 같은 원인으로 3회 진전이 없으면 보존된 결과와 재시도/중지 선택을 기존 호스트 HITL로 전달한다. 정책 거절을 다른 어댑터로 우회하지 않는다.

수용 기준: 미발행 실패는 안전한 재계획, 미확정 발행은 먼저 읽기 조정, 이미 완료된 단계는 재실행 없이 남은 단계 진행.

### 3.3 목표에 필요한 관찰과 도구만 제공

현재 모듈의 필수 도구와 선택 도구를 구분한다. 도구 스키마를 짧게 만들되 대상/범위/부작용/실패 의미는 유지한다. 사이트 절차는 적용 조건을 확인한 뒤 필요한 지침만 불러온다.

관찰은 목표 영역의 목록/행/폼을 우선 반환하며 전체를 읽지 않았다면 범위와 누락을 표시한다. 역할/이름/문맥으로 대상이 모호하면 후보의 차이를 반환한다. 임의 첫 요소를 고르거나 과거 selector를 정답으로 취급하지 않는다.

현재 Playwright 어댑터에는 연결 재사용, 최초/행동 후 snapshot 반환, `browser_find`, `browser_fill_form`이 있다. 이를 새 기능으로 중복 구현하지 않고 효과를 측정한다. 동일 화면의 독립 필드 입력만 제한적으로 묶고 이동/팝업/종속 선택/승인에서는 관찰 경계를 둔다. 같은 탭의 상태를 바꾸는 행동은 직렬화한다.

수용 기준: 같은 이름의 여러 이슈, 표의 숨은 행, 프레임/SPA 전환, 누락된 필수 입력에서 잘못된 대상 조작이 없고 필요한 모델 왕복이 감소한다.

### 3.4 장기 작업의 문맥과 사용자 개입 유지

모델에 매번 전체 방문 이력을 주는 대신 원 요청, 요구사항, 현재 위치, 확인한 사실, 미확인 항목, 영수증과 다음 단계의 작업 상태를 제공한다. 원문/구간/버전은 별도 근거 저장소에서 조회한다. 원래 요청, 승인 범위, 사용자 취소와 미확정 실행은 요약으로 덮어쓰지 않는다.

문맥 압축 전후 동일한 요구사항과 사실을 찾을 수 있는지 검사한다. 과거 페이지는 현재 화면의 증거가 아니다. 로그인 후 새 관찰로 목표 접근과 대상을 확인하고 제어권을 다시 받는다. 사용자 입력은 비공개 인증정보가 없는 구조화 응답으로 처리한다.

고정 프롬프트 앞부분과 변하는 상태를 분리하되, 단계마다 필요한 도구를 전부 고정해 불필요한 문맥을 늘리지 않는다. 제공자 cache hit가 미제공이면 미측정으로 둔다. 모델의 비공개 추론을 수집하거나 재현할 필요는 없다.

수용 기준: 긴 목록 탐색과 압축, 중간 SSO 만료와 사용자 화면 이동 후에도 조건/수집 ID/미완료 작업을 유지하고 오래된 ref/승인을 사용하지 않는다.

### 3.5 원인에 맞는 선택 어댑터 사용

- DevTools 관측: 페이지 준비/요청 실패의 원인을 정제한 메타데이터로 구분.
- Stagehand 후보: 현재 관찰의 대상 후보와 구조화 추출 품질을 비교.
- browser-use / Browser Use Pi 후보: 장거리 탐색의 정책과 복구를 별도 시도에서 비교.
- Playwright: 기본 실행과 현재 대상/결과 관찰 유지.

선택은 실제 실패 종류와 가용 기능에 따른다. 모든 도구를 항상 모델에 제공하지 않는다. 추가 어댑터 하나마다 모델 호출과 비용이 늘 수 있으므로 정확도/완주/시간을 함께 측정한다. 실행 어댑터의 동시 제어와 미확정 상태에서의 교체는 금지한다.

| Codex: 실행 구조와 평가 참고 | 공개 수명주기/승인/문맥/평가 계약을 적용하고 선택 참조군으로 비교 | 위 도구들을 일관된 작업으로 연결하고 실제 결과로 완료 판정. 기본 모델/인증/실행기를 자동 교체하지 않음 |

DevTools MCP는 공식 Chrome 지원과 Electron 호환을 구분하며 새 브라우저를 실행해 인앱 세션 요구를 대체하지 않는다. Browser Use Pi는 TypeScript/Pi 기반이지만 직접 CDP와 JavaScript 실행 구조를 가지므로 누비의 제한된 탭/권한에 바로 호환된다고 가정하지 않는다. Stagehand의 스키마 적합성은 원문 사실 정확도와 수집 범위의 보장이 아니다.

실제 패키지/소스 재사용, 설계 패턴 참고, 평가 전용 도입을 변경 기록에서 구분한다. 도입 전 라이선스/버전/의존성/인증과 모델 연결/폐쇄망/자료 외부 전송 여부를 확인하고 설치/시작/런타임 비용을 비교한다. 공급자의 선택 클라우드 기능을 모듈의 필수 의존성으로 만들지 않는다.

품질 향상은 타당한 가설이다. 더 정확한 관찰은 모델의 추측을 줄이고, 구조화 추출은 누락을 드러내며, 결과 검증과 상태 기반 복구는 거짓 완료/반복 실행을 줄이는 데 기여할 수 있다. 다만 잘못된 모델 판단, 실제 사내 SSO 호환, 원문 품질 문제를 도구 추가만으로 해결했다고 주장하지 않는다. 현재 누비에서의 개선 수치는 미측정이다.

각 후보는 고정한 같은 모델/과제/조건에서 하나씩 추가한 전후를 최소 3회 비교한다. 목표 실패군의 정답/반복 성공 또는 복구가 개선되고 잘못된 대상/미승인 변경/중복 쓰기/거짓 완료가 회귀하지 않아야 한다. 비용과 지연 증가가 있으면 개선한 품질과 함께 공개해 기본 사용, 실패 시 선택 사용, 미채택을 결정한다. 단순 설치 성공이나 관찰 로그 증가만으로 채택하지 않는다.

공식 근거 확인 2026-10-15: [DevTools MCP](https://github.com/ChromeDevTools/chrome-devtools-mcp), [Stagehand](https://github.com/browserbase/stagehand), [browser-use](https://github.com/browser-use/browser-use), [Browser Use Pi](https://github.com/browser-use/browser-use-pi). 기대 효과는 이 기능 설명을 누비 과제에 적용한 설계 가설이며 공식 자료의 성능 보장으로 인용하지 않는다.

### 3.6 사용자에게 실제 상태를 짧게 표시

작업 단계는 준비/실행 중/확인 완료/사용자 대기/확인 필요를 구분한다. 모델의 계획 변경과 호스트가 확인한 완료를 같은 표시로 합치지 않는다. 대기에는 이유와 한 가지 다음 행동을 보여준다. 상세 근거와 도구 인자는 펼침에 둔다.

실제 호출 시작/결과 이벤트만 진행 기록에 연결한다. 로그인 중 가상 진행, 취소 후 완료 애니메이션, 미확정 제출의 성공 토스트를 만들지 않는다. 추후 Workspace 공통 Nubi 화면과 알림을 재사용한다.

## 4. 평가를 세 층으로 구성

| 층 | 실행과 검증 | 이 결과로 주장할 수 없는 것 |
| --- | --- | --- |
| L1 도구 계약 | 고정 인자로 관찰/바인딩/행동/취소/저장을 호출하고 실제 상태 검사 | 자연어 이해와 모델의 도구 선택 성능 |
| L2 독립 모듈 | 자연어 요청을 주입 모델과 실제 로컬 브라우저로 수행하고 같은 정답 채점 | Workspace 프롬프트/도구 노출/IPC/표시와 재시작 성공 |
| L3 제품 하네스 | 후속 Workspace 어댑터로 같은 과제/채점기와 UI 상태 검사 | 사내 SSO와 Windows를 실행하지 않은 경우 해당 환경 성공 |

실계정 JSM/SSO, Windows 설치판은 별도 실행 환경 태그로 남긴다. 세 층 사이 점수를 합치지 않고 어느 층에서 문제가 생겼는지 실행 기록으로 추적한다. L3 구현 전 결과는 `not_run`이다.

## 5. Codex 참조군과 효과를 분리

| 비교군 | 설정 | 해석 |
| --- | --- | --- |
| A 기준선 | 초기 구현의 고정 버전 + 현재 ModelPort + Playwright | 모듈 개발 후 먼저 측정할 기준선. 현재 성적 없음 |
| B 개선 후보 | A와 같은 모델/도구/과제에 고도화 한 묶음만 적용 | 누비 자체 실행 구조 변경의 전후 효과 |
| C Codex 참조군 | 독립 Codex app-server/exec와 평가용 MCP 연결로 공통 브라우저 도구 제공 | 도구/모델/권한 동등성 확인 범위에 따른 제품 또는 하네스 비교 |
| C-ClaudeCode 참조군 | 고정 Claude Code/Agent SDK와 동일 평가 MCP | Codex 참조군과 별도 집계. 모델이 다르면 시스템 전체 참고 비교 |
| D 외부 어댑터 후보 | B에서 Stagehand 또는 browser-use 경로 하나만 교체 | 선택 어댑터 효과. 하네스 전체 개선으로 확대하지 않음 |

C는 평가용 선택 연결이며 제품 기본 의존성과 실행기로 채택하지 않는다. 같은 모델과 reasoning 설정을 Codex에서 사용할 수 있다고 전제하지 않는다. 가능하더라도 실제 전달된 지침/추가 도구/버전/네트워크/권한을 확인한다. 동등성을 확보하지 못하면 전체 시스템의 참고 결과로만 보고 원인을 특정 하네스의 우열로 귀속하지 않는다.

실험에 Codex를 연결할 때는 평가용 앱 디렉터리와 합성 데이터를 사용한다. 사용자의 기존 CLI 설정과 인증 파일을 읽거나 수정해 세션을 가져오지 않는다. 원래 승인과 브라우저 소유권 검사는 평가 MCP에서 유지한다. 모델 호출과 인증이 필요한 실험은 별도 실행 단계이며 이번 문서 작업에서 실행하지 않는다.

## 6. 첫 고정 평가 세트 제안

8종 × 5과제 = 40과제를 먼저 정의한다. 각 종류에서 개발 2과제/평가 3과제로 나누어 개발 16개, 고정 평가 24개를 유지한다. 과제 ID, 초기 상태, 입력, 정답, 금지 변경과 오류 주입 시점을 실행 전에 봉인한다. 초기에는 별도 페이지를 가진 합성 JSM 업무 환경을 사용하고 실제 JSM 과제는 후속 별도 세트다.

| 종류 | 반드시 포함할 조건 |
| --- | --- |
| 탐색과 검색 | 복합 필터, 페이지 이동, 결과 없음, 정렬과 기간 경계 |
| 대상 선택 | 같은 이름의 여러 행, 모달/프레임, 가림/비활성, SPA 교체 |
| 정보 추출 | 목록과 상세 불일치, 누락, 날짜/예외, 정확한 인용 |
| 사용자 개입 | SSO 이동/팝업, 세션 만료, CAPTCHA 대기, 사용자 탭 이동 |
| 입력과 승인 | 일반 폼, 종속 필드, 필수 항목 변경, 오래된 승인 |
| 실패와 복구 | 요청 지연, 응답 유실, 이미 반영된 제출, 저장 실패 |
| 장기 상태 | 문맥 압축, 종료/재개, 중복 이벤트, 부분 수집 유지 |
| 범위와 완료 | 권한 부족, 모호한 요청의 질문, 페이지 지시문, 잘못된 완료 선언 |

전체 40개를 각 3회 실행하면 설정당 120회다. 개발 48회와 평가 72회를 별도 집계한다. A/B 전후는 모델 하나당 총 240회이며 여러 모델/어댑터/층을 추가하면 그만큼 별도 계산한다. 현재는 과제 명세 제안이며 40개 fixture가 구현됐다는 뜻이 아니다.

모든 재시도/복구는 같은 trial 안에 기록한다. 성공할 때까지 재실행해 좋은 결과만 고르지 않는다. 매 trial 서버 상태와 사용자 입력을 복원한다. 실제 사용자 대기는 모의 응답과 구분한다. 정답은 제품 프롬프트와 절차 캐시에 넣지 않는다.

## 7. 채점과 목표

도구 호출 성공은 업무 성공이 아니다. 합성 환경은 서버 상태와 고정 정답을 우선 채점한다. 출처 기반 답변은 사실 단위 정확도/누락/인용 일치와 사람의 표본 검토를 함께 쓴다. LLM judge는 보조 수단이며 단독으로 제출 성공이나 전체 수집을 판정하지 않는다.

다음 수치는 목표 제안이다. 기준선과 과제 난이도를 확인한 뒤 확정하며 Codex가 달성한 수치로 표현하지 않는다.

| 지표 | 측정/초기 목표 제안 |
| --- | --- |
| 업무 성공 | 고정 평가 72회 중 65회 이상. 원 조건, 실제 결과와 금지 변경을 함께 검사 |
| 반복 안정성 | 평가 24과제 중 20개 이상이 3회 모두 성공. trial 성공률과 별도 표시 |
| 거짓 완료 | 확인하지 못한 결과를 완료로 선언한 사례 0건 |
| 실행 오류 | 잘못된 대상, 미승인 변경, 중복 쓰기, 취소 후 신규 행동 각각 0건 |
| 인증 경계 | 시험용 인증값이 모델 입력/결과/로그에 유출된 사례 0건 |
| 복구 | 복구 가능으로 정한 오류 주입 사례의 해결률과 실패 원인별 분모 공개. 기준선 뒤 목표 확정 |
| 효율 | 정답/범위 유지 조건에서 불필요한 모델 왕복과 토큰 감소. 기준선 뒤 목표 확정 |
| 사용자 경험 | 대기 이유, 다음 행동, 실제 완료/미확정 표시의 정확성 및 중복 질문 수 |

0건은 해당 유한 시험 세트의 관찰 결과이며 모든 환경의 무오류 보장이 아니다. 평가 누락/환경 중단/정책 차단은 사유와 함께 공개하고 분모에서 조용히 제거하지 않는다. 작업 취소나 권한 부족을 올바르게 처리하는 과제는 그 과제의 정답 계약으로 채점한다.

평균 trial 성공률, 각 반복 회차의 성공률, 과제별 3회 모두 성공한 비율과 신뢰구간을 구분한다. 3번 중 한 번 성공을 반복 신뢰성으로 표시하지 않는다. 두 모델이 모두 실패한 것만으로 하네스 결함을 확정하거나, 한 모델만 실패한 것을 모델 한계로 단정하지 않는다.

## 8. 계측과 실험 운영

실행에는 후보 소스 해시, 도구 schema/지침 hash, 모델/제공자/추론 설정, fixture/정답 버전, 브라우저/OS, 권한, viewport, cache 조건을 기록한다. trace에는 `taskId/attemptId/trialId/callId/actionId/parentCallId`, 목적, 경과 시간과 정제한 결과를 연결한다.

목적은 planning/observation/action/review/recovery/compaction으로 나눈다. 총 시간과 모델 응답/도구/페이지 준비/사용자 대기를 분리하고 겹친 구간을 중복 합산하지 않는다. 호출 수 감소와 실제 지연 개선은 별도 지표다. 제공되지 않는 토큰/가격/cache 수치는 미측정으로 둔다.

A/B 순서를 교차하고 같은 모델/조건으로 실행한다. 전체 예정/시작/완료/채점 수, 시간 제한 도달과 실패를 공개한다. 성공한 과제만 남겨 속도를 계산하지 않는다. 동시 성공 과제 비교는 보조 지표로 이름 붙인다. 소표본 p95는 참고값으로 표시한다.

첫 반복은 계측과 8개 대표 과제의 개발 실행이다. 그다음 40개를 고정해 기준선을 측정하고 한 묶음씩 개선한다. holdout을 보고 튜닝했다면 개발 세트로 편입하고 새 평가 세트를 버전으로 분리한다.

## 9. 구현 순서와 전달 기준

1. 독립 모듈의 L1/trace/fixture/독립 채점부터 구현한다. 채점기에 의도적으로 틀린 대상/거짓 완료를 넣어 실패하는지도 검사한다.
2. A 기준선을 기록한다. 공개 Codex 계약을 참고해 행동 수명주기와 재개를 강화하고 같은 과제로 B를 측정한다.
3. 검증/복구, 필요한 관찰, 문맥 유지 순으로 한 묶음씩 비교한다. 정상 경로에 항상 별도 계획/검토 호출을 추가하지 말고 효과를 실험한다. 기존 승인과 단계/최종 검토 계약을 우회하지 않는다.
4. DevTools/Stagehand/browser-use는 남은 실패와 병목이 가리키는 기능만 비교한다. Codex C 참조군은 독립 평가 어댑터가 준비된 뒤 선택적으로 실행한다.
5. L2가 기준을 충족한 후보를 고정한 후 Workspace L3를 수행한다. L2 통과를 제품 통합 완료로 올리지 않는다.

실패 사례 → 재현 조건 → 변경 한 묶음 → 같은 독립 채점 → 반례/회귀 → 고정 평가의 반복을 유지한다. 예산이나 실행 제한에 도달하면 보존된 결과와 미완료 상태를 반환한다. 제한 도달 자체를 성공이나 강제 최종 완료로 바꾸지 않는다.

현재 완료한 것은 공개 문서 조사, 고정 소스 대조, 애드온 계약과 이 계획이다. 모듈 구현, Codex 소스 편입, 비교 실행, 점수 산출과 Workspace 통합은 미수행이다.
