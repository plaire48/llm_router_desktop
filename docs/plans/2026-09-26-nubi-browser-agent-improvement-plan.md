# 누비 브라우저 에이전트 개선 및 벤치마킹 계획

작성일: 2026-09-26. 상태: 제안 및 구현 명세. 구현/평가 실행 전.

## 목표와 진행 순서

사용자가 요청한 업무를 정확히 마치는 비율을 높이고, 같은 작업에 필요한 불필요한 탐색과 모델 호출을 줄인다. 기준 모델은 `QWEN3.8-27B-FP8-256K`이며 사용자가 저장한 모델 선택은 유지한다.

**계측 및 기준선 → 의미 기반 대상 검색 → 기존 짧은 스크립트 활용 → 검토 중복 최적화 → 복구/사이트 지식 검증** 순으로 진행한다. 한 번에 한 요인만 바꾸고 효과가 확인된 변경만 다음 기준선에 포함한다.

근거는 [Claude 배포 코드와 누비 비교 분석](../research/2026-09-26-claude-browser-nubi-agent-analysis.md), [분석 파일 해시](../research/2026-09-26-claude-browser-nubi-evidence.json), 현재 `extensions/aipro-chat`의 소스다. Claude 코드의 존재는 실제 성능 우위의 증거가 아니다. 아래 통과 기준은 누비의 제안 기준이며 공식 인증 기준이 아니다.

## 2. 작업 A — 계측과 평가 기준선

**목적:** 모델이 느린지, 대상을 못 찾는지, 검토를 반복하는지 분리한다. 계측 자체의 오류를 모델 성능으로 계산하지 않는다.

관련 파일: `src/api.js`, `completion-reader.js`, `agent-runtime.js`, `agent-trace.js`, `scripts/evaluation-model-evidence.mjs`, `scripts/live-evaluation-score.mjs`, `scripts/evaluate-agent.mjs`.

방법:

1. `run_id / task_id / trial_id / call_id / parent_call_id`로 주 실행, 검색 보조, 검토, 복구 호출을 연결한다. `purpose`는 planning, action_decision, target_search, plan_step_review, checkpoint_review, final_review, recovery로 분리한다.
2. 요청 시작, HTTP 헤더, 첫 유효 모델 이벤트, 첫 사용자 표시 텍스트, 최종 유효 응답, 실패/취소를 별도 기록한다. 헤더 수신을 모델 응답 완료로 계산하지 않는다.
3. 도구에는 시작/종료, 오류 코드, 실행 여부, 결과 확인 여부, 관찰 버전과 영수증 ID를 기록한다. 원문 입력값, 인증값, 전체 모델 응답은 일반 계측에 저장하지 않는다.
4. 총 소요 시간, 사용자 대기 시간, 사용자 대기를 제외한 시간, 병렬 하위 호출의 누적 시간을 분리한다. 병렬 시간 합계를 전체 wall-clock 시간으로 표시하지 않는다.
5. 현재 `trackModelEvidence`는 `response.body()` 검증에 5초 제한을 둔다. 이를 실제 긴 스트림으로 먼저 재현한다. 제품의 정상 응답 종료와 평가 수신 기록을 연결하고, 평가 시간 종료 시 미확인/중단을 남긴다. 기한만 늘려 성공으로 처리하지 않는다.
6. 기존 `liveEvaluationScore`의 실제 응답/중복/누락 검사는 유지한다. 잘못된 계획, 중복 trial, 미수집 결과는 종합 점수를 내지 않는다. API 오류나 에이전트 실패는 정상적으로 시작한 시험의 실패로 보존한다.
7. baseline manifest에 소스/번들/프롬프트/모델/설정/브라우저/과제/채점기 버전과 해시를 고정한다. 변경 전후 결과에 동일한 계측을 사용한다.

완료 조건:

- 5초보다 긴 정상 스트림, 끊긴 스트림, 취소, HTTP 200 형식 오류를 구분한다.
- 모델 호출을 실제 단계별로 합산할 수 있고 누락 호출을 감지한다.
- 새 계측이 동작 순서, 도구 입력, 승인 또는 모델 선택을 변경하지 않는다.
- 현재 계획 형식 복구를 실제 Qwen으로 재시험한다. 이미 있는 오류 피드백/구조화 응답 경로를 재구현하지 않는다.

## 3. 작업 B — 의미 기반 대상 검색

**가설:** 한국어 요청과 화면 문구가 다르거나 여러 행에 같은 버튼이 있을 때, 관찰 범위를 제한한 보조 추론이 잘못된 대상 선택과 반복 탐색을 줄인다.

관련 파일: `browser-dom.js`, `browser-information.js`, `evidence-search.js`, `browser-agent.js`, `analysis-agents.js`, `agent-harness.js`, `agent-runtime.js`.

방법:

1. 기존 정확한 역할/이름 검색과 MiniSearch를 첫 경로로 유지한다.
2. 검색 실패 또는 후보 의미가 모호할 때만 전용 읽기 전용 helper를 호출한다. 초기에는 모델이 명시적으로 선택하도록 하고, 자동 발동은 별도 실험으로 분리한다.
3. 후보를 어휘 검색 결과만으로 제한하지 않는다. 동의어 불일치에서는 원하는 대상이 어휘 후보에 없을 수 있으므로, 현재 관찰한 관련 영역/역할의 요소도 제한된 예산 안에서 포함한다. 빠진 범위와 후보 수를 명시한다.
4. 입력은 사용자 의도, 관찰 ID, tab/document/frame 식별자, 역할/이름/주변 행 정보다. 출력은 기존 ref, 근거, 모호함, 읽지 못한 범위다. 모델이 만든 selector, JS, 승인 또는 클릭 명령은 허용하지 않는다.
5. ref 집합과 관찰 버전을 호스트가 검증한다. 후보 근거가 부족하면 재관찰 또는 사용자 질문으로 반환한다. 존재하지 않는 항목을 찾아냈다고 응답하지 않는다.
6. 검색 결과는 부모 실행기에 제안만 한다. 실제 클릭/입력은 최신 대상 확인, Playwright actionability, 기존 HITL을 다시 통과한다.
7. 현재 선택 모델과 기존 읽기 전용 하위 호출 제한을 사용한다. 동일 관찰/질문의 중복 호출을 억제하며 사용자 정정/취소 후 늦은 결과를 적용하지 않는다.

비교군: B0 기존 검색, B1 같은 실행기에 의미 검색만 추가. 계획/프롬프트/검토 정책을 동시에 바꾸지 않는다.

완료 조건: 대상 선택 정확도와 업무 완주를 별도로 측정하고, 잘못된 ref/오래된 문서 채택이 재현 시험에서 0건이어야 한다. 의미 불일치 과제에서 효과가 없거나 비용만 늘면 자동 활성화하지 않는다.

## 4. 작업 C — 짧은 스크립트의 효율 개선

**가설:** 이미 관찰한 한 양식의 독립 필드들은 기존 `run_playwright`로 함께 입력하면 정확도를 유지하면서 모델 왕복을 줄일 수 있다.

관련 파일: `browser-script-api.js`, `browser-agent.js`, `script-preflight.js`, `script-feedback.js`, `agent-runtime.js`.

방법:

- 모델 지침과 예제에 관찰된 필드 2~3개의 초안 입력을 한 스크립트로 작성하는 패턴을 명확히 한다. 새 호출 규약보다 현재 지원 계약을 우선한다.
- 클릭/이동/팝업/새 문서/승인이 필요한 지점에서는 기존 checkpoint를 유지한다. 앞선 동작의 결과가 필요한 다음 동작을 미리 추측해 실행하지 않는다.
- 각 명령의 started/returned/failed, actionIssued와 최종 readback을 유지한다. 재렌더링이나 오류가 생기면 완료한 명령과 미실행 명령을 분리한다.
- 입력값 간 자동 계산이나 dependent select가 있으면 독립 필드로 묶지 않는다. 최종 제출은 별도 승인과 한 번의 실행을 유지한다.

비교군: C0 기존 사용 패턴, C1 짧은 스크립트 활용 지침만 보완. 실패/전환 경계를 완화하는 실험은 포함하지 않는다.

완료 조건: 최종 필드 값/서식/범위 정확도와 승인 위반/중복 쓰기 결과를 먼저 확인한다. 두 구성 모두 성공한 같은 과제 쌍에서 모델 호출 수와 시간을 비교한다. 실패가 빨리 끝난 것을 성능 개선으로 계산하지 않는다.

## 5. 작업 D — 검토 중복 비용 최적화

**가설:** 동일한 근거로 같은 단계 조건을 반복 확인하는 일부 호출을 줄일 수 있다. 현재 지연의 원인이라고 확정하지 않았으므로 계측 결과가 먼저다.

관련 파일: `agent-runtime.js`, `goal-review.js`, `review-recovery.js`, `context-evidence.js`, `task-plan.js`.

방법:

1. checkpoint, plan_step, final의 호출 횟수/시간과 입력 근거 변화를 비교한다.
2. 반복 검토가 실제로 발견된 경우에만 실행 내 검토 결과 재사용을 실험한다. key에는 원래 요청과 수정 이력, 검토 phase, 완료 조건, 모델/검토 규약 버전, 근거 ID/hash/범위, 관련 영수증/상태를 포함한다.
3. 같은 요구사항 문자열만으로 재사용하지 않는다. 새 관찰, 사용자 정정, 입력/탭/문서 변화, 새 오류, 미확정 영수증이 생기면 무효화한다.
4. `plan_step` 결과를 `final` 검토로 대체하지 않는다. 최종 검토는 전체 원래 요청과 남은 불확실성을 현재 근거로 다시 확인한다.
5. 형식 오류나 partial/blocked 결과를 성공 캐시로 만들지 않는다. 독립 검토가 거절한 행동을 캐시 경로로 승인하지 않는다.

완료 조건: 변경된 증거를 과거 판정으로 덮는 회귀가 0건이고, 완주/오답 완료 지표를 악화시키지 않으면서 실제 중복 검토 호출을 줄여야 한다. 중복이 드물면 이 작업은 도입하지 않는다.

## 6. 작업 E — 복구와 계획의 실제 효과 검증

누비의 자동 recovery, 계획 형식 복구와 질문 대기는 이미 구현된 기능이다. 새 워커 수를 늘리는 대신 다음 실패 분류별로 검증한다.

| 실패 종류 | 방법 | 성공 결과 |
| --- | --- | --- |
| 계획 JSON/도구 형식 오류 | 현재 오류 코드와 수정 피드백, 유효 계획/질문만 허용 | 첫 관찰까지 도달. 최종 완주와 별도 기록 |
| 존재하지 않거나 가려진 대상 | 새 관찰 → 기존 recovery의 고정 근거 분석 → 다른 접근 | 실제 맞는 대상에 한 번 실행 후 검증 |
| 느린 모델/일시 통신 오류 | 실제 모델 활동과 전송 오류별 복구 | 도구 작업을 재전송하지 않고 추론만 이어감 |
| 성공한 쓰기의 응답 유실 | 같은 문서/대상/영수증 확인 | 이미 실행된 쓰기 재전송 0회 |
| 반복 검토 거절 | 누락 요구/근거를 좁혀 다음 조회 제안 | 같은 검토만 반복하지 않고 필요한 근거 추가 또는 구체 질문 |
| 사용자 정정/취소 | 미실행 제안과 하위 분석을 중단하고 원 요청/답변 보존 | 오래된 지시 실행 0회, 취소 자동 재개 0회 |

## 7. 작업 F — 사이트 Wiki와 스킬 선택

Claude domain skill 갱신 패턴은 기존 누비 site Wiki/OpenWiki 기능의 검증에 활용한다.

방법: 사이트/provider별 출처를 유지하고, 작업 의도에 맞는 Wiki를 조회한 뒤 필요한 원문만 실행 문맥에 연결한다. 사용자가 편집한 문서, 갱신된 화면과 충돌하면 현재 관찰을 우선하고 불일치를 표시한다. 문서가 제시한 과거 selector나 승인 문구를 현재 실행 권한으로 취급하지 않는다.

비교군: F0 Wiki 없이 현재 관찰만 사용, F1 검증된 업무 지침을 연결. 과제별 필요한 문서와 혼동 문서를 함께 둔다. 관련 문서 선택률, 구버전 배제, 첫 유효 행동까지의 호출 수를 평가한다.

OpenWiki는 자료/근거 조회에 재사용한다. 실시간 브라우저 조작을 별도 Wiki 에이전트에 맡기거나 새 로컬 서버 설치를 요구하지 않는다.

## 8. 내부 벤치마크 설계

초기 정식 비교는 **6종 × 4과제 = 24과제**, 구성별 과제당 3회다. 기준선과 변경 후보를 합하면 **144회**다. 이는 계획 수량이며 실행 결과가 아니다. 유료/실모델 전체 평가 실행과 예산은 후속 실행 단계에서 확정한다.

각 종류의 1~2는 개발용, 3~4는 고정 평가용으로 분리한다. 같은 구조를 쓰더라도 평가용 페이지의 문구/행 순서/값/정답은 개발 fixture와 다르게 유지한다. 고정 평가 실패로 튜닝하면 해당 세트를 개발용으로 전환하고 다음 비교에는 새 평가 세트를 고정한다.

| 종류 | 1. 개발 | 2. 개발 | 3. 고정 평가 | 4. 고정 평가 |
| --- | --- | --- | --- | --- |
| 대상 선택 | 요청과 버튼 문구의 동의어 | 접근성 이름 있는 아이콘 | 같은 이름 버튼의 다른 행 | 실제 없는 대상과 유사 후보 |
| 양식 | 독립 필드 3개 초안 | select와 체크박스 상태 | 입력 후 다른 필드 재렌더링 | 자동 계산/dependent select |
| 이동과 관찰 | 지연 SPA와 로딩 상태 | 새 탭/팝업 목적지 | iframe 안의 같은 이름 대상 | 같은 URL 재로드 후 stale ref |
| 조사와 문맥 | 두 출처 수치 비교 | 긴 문서의 지정 구간 | A→B 이동 뒤 A 인용 보존 | 조사 중 원문 변경과 부분 열람 |
| 실패 복구 | 일시 추론 오류 | 가려진 대상/요소 교체 | 쓰기 성공 후 응답 유실 | 계획/검토 형식 오류와 복구 |
| 사람/지식 경계 | 필요한 값만 질문 | 관련 사이트 Wiki 선택 | 구버전/다른 사이트 지침 | 진행 중 정정/취소/최종 승인 |

평가 과제는 요청과 정답으로 정의한다. 특정 도구 호출 순서를 정답으로 강제하지 않는다. 정답이 없는 과제는 지정된 조사 범위를 실제로 확인하고 없음을 보고하는 것이 성공 조건이다. 확인 가능한 정보를 사용자에게 되묻고 끝낸 것은 완주로 계산하지 않는다.

평가 절차:

1. 개발 과제 중 종류별 1개로 구성별 1회 smoke를 실행한다. 12회는 연결/계측 점검이며 성능 결론에 쓰지 않는다.
2. 과제/채점기/프롬프트/설정과 환경 초기값을 고정한다. 모델에 정답 fixture, 평가 전용 DOM 표식이나 정답을 주입하지 않는다.
3. 기준선과 후보를 같은 초기 상태에서 실행하고 순서를 교차/무작위화해 시간대 영향을 줄인다. 브라우저 설정, 권한, viewport, 언어와 모델 옵션은 동일하게 둔다.
4. 매 회 사이트 상태와 대화를 초기화한다. 실패 회차를 지우고 성공할 때까지 바꾸어 실행하지 않는다. 누락/환경 장애/모델 실패/제품 실패를 원래 계획에 남긴다.
5. 양식은 실제 DOM 및 테스트 서버 상태, 조사는 원문 hash/범위/정답 항목으로 독립 채점한다. 에이전트가 완료라고 말한 것만으로 통과시키지 않는다.
6. 시간/호출 예산은 양 구성에 동일하게 사전 고정한다. 평가 중단 한도를 제품의 자동 취소 정책으로 이식하지 않는다. 한도 도달은 budget_exhausted로 기록한다.
7. 개발/고정 평가 결과를 분리한다. 3회 반복은 초기 안정성 점검이며 작은 차이의 통계적 우월성 증명이 아니다. 확대 시험의 수량/조건은 결과를 보기 전에 별도 계획으로 고정한다.

## 9. 보고 지표와 채택 판단

| 지표 | 정의 |
| --- | --- |
| 요청 완주율 | 독립 채점에서 모든 필수 요구를 충족한 시행 / 계획된 유효 시행 |
| 대상 선택 정확도 | 실제 선택 대상이 과제의 정답 집합에 속하는 비율. 미선택/모호함을 별도 표시 |
| 잘못된 완료 | 독립 채점은 실패인데 사용자에게 완료로 보고한 시행 수/분모 |
| 첫 행동 도달 | 계획 후 의미 있는 관찰/행동에 도달했는지. 최종 완주와 구분 |
| 복구율 | 주입한 실패 종류별로 원래 목표를 완료한 비율 |
| 반복 안정성 | 3회 중 성공 수와 3/3 성공한 과제 수. 한 번이라도 성공한 비율과 분리 |
| 효율 | 모델 호출/목적별 토큰, p50/p95 시간, 도구 시간, 사용자 대기 |
| 사용자 개입 | 예정된 최종 승인, 필수 모호함 질문, 불필요한 도움 요청을 분리 |
| 경계 위반 | 승인 전 쓰기, 중복 쓰기, 소유권 밖 동작, 취소 후 행동, 오래된 근거 채택 건수 |

환경 장애로 비교가 불가능하거나 실제 모델 응답/정답 기록이 부족하면 전체 결과를 미완료로 둔다. 별도 유효 시행 비율을 보여주되 실패나 누락을 숨겨 분모를 줄이지 않는다. 기존 점수 함수의 지표 정의를 바꿀 경우 보고서 스키마 버전도 올린다.

채택 판단:

- 경계 위반 또는 잘못된 대상에 대한 중대한 쓰기가 발생하면 해당 후보의 자동 채택을 중단하고 원인을 해결한다. 시험에서 0건이어도 일반적인 안전성이 증명된 것으로 표현하지 않는다.
- 의미 검색은 고정 평가의 대상 선택/요청 완주 개선과 추가 시간/호출 비용을 함께 보고 채택한다. 효과가 불명확하면 제한된 실험 상태로 유지한다.
- 스크립트/검토 최적화는 정확도와 오류 지표를 먼저 비교한다. 같은 성공 과제에서 효율이 개선돼야 하며 실패를 줄인 구성의 더 긴 완료 시간을 단순 열등으로 판단하지 않는다.
- 가중 합산 종합 점수나 임의의 “Claude 대비 동등성 %”는 만들지 않는다.

## 10. 실제 사이트, 공식 벤치마크, Claude 비교

세 가지 시험은 서로 대체하지 않는다.

| 시험 | 방법 | 주장할 수 있는 범위 |
| --- | --- | --- |
| 실제 공개 사이트 | 기존 `public-sites-50.mjs` / `naver-50-v2.mjs`의 사전 지정 일부부터 읽기 전용 실행 | 선택한 사이트/시점/계정/모델에서의 실측 |
| 공식 벤치마크 | 고정 upstream 환경/과제/평가기로 실제 누비 실행을 채점 | 정확히 실행한 benchmark subset 결과 |
| Claude 비교 | 동일 초기 페이지와 요청, 같은 승인 정책으로 공식 확장을 직접 실행 | 제품 구성 전체의 차이. Qwen 하네스만의 인과효과는 아님 |

현재 `evaluate-naver-sso.mjs`는 ChatGPT SSO와 GPT-5.6 Luna에 고정돼 있다. 이를 Qwen 시험으로 부르지 않는다. Qwen용 실행 경로를 기존 AI Pro 제공자와 실제 인증 흐름에 연결하고 응답 수신 근거를 확보해야 한다. 공개 사이트의 게시일/검색 결과는 변하므로 날짜와 실제 열람 근거를 남긴다.

기존 `evaluate-webarena.mjs`는 `webarena-verified` 1.2.3 및 평가기/데이터 checksum을 고정한 **산출물 채점 어댑터**다. 그 결과만으로 누비 실행을 증명하지 않는다. `run-webarena.mjs`와 실제 실행 trace/네트워크 산출물/빌드 해시를 연결한 뒤 사용한다. 현재 고정 도구의 출처/라이선스/설치 환경을 실행 준비 단계에서 재확인하고 다른 WebArena 계열 점수와 혼합하지 않는다.

[WebArena 원본](https://github.com/web-arena-x/webarena)은 자체 호스팅 환경과 독립 평가의 참고 기준이다. [BrowserGym](https://github.com/ServiceNow/BrowserGym)은 다중 벤치마크 실험 환경의 후보로 검토했다. 기존 어댑터가 있으므로 지금 새 평가 프레임워크를 도입하지 않는다. 공식 과제 일부만 실행하거나 HITL을 추가했다면 그 차이를 명시하고 전체 leaderboard 점수로 표시하지 않는다.

Claude 비교에서는 확장 버전, 활성 UI 경로, 선택 모델/모드, 사이트 권한, 계정 한도, 개입과 실행 시각을 기록한다. 동일 Qwen으로 Claude를 실행할 수 없으므로 “Claude의 이 하네스 패턴 때문에 더 좋다”는 인과 결론은 누비 B0/B1 시험에서만 검토한다. 실계정/허용 환경이 없으면 Claude 비교는 미실행으로 남긴다.

## 11. 변경 관리와 산출물

| 단계 | 산출물 | 다음 단계 조건 |
| --- | --- | --- |
| A | 계측 규약, 고정 과제/정답, 기준선 manifest/report | 모델/도구/검토 시간과 실제 응답 증거 확보 |
| B | 의미 검색 명세와 선택적 실험, 변경 전후 결과 | ref/문서 경계 회귀와 효과 검토 |
| C | 현재 스크립트 사용 개선, 부분 실행 회귀, 비교 보고서 | 입력 정확도/승인/중복 쓰기 조건 충족 |
| D | 검토 중복 조사와 필요 시 실행 내 재사용 | 최종 검토 유지 및 증거 변경 무효화 확인 |
| E/F | 실패 종류별 복구 결과, Wiki 선택/신선도 결과 | 원래 요청/답변/출처와 실행 권한 보존 |
| 통합 | 채택한 변경만 합친 후보의 고정 평가와 회귀 | 현재 소스 해시와 일치하는 검증 근거 |

기존 `quality-work.json`의 구현/검증 상태는 이번 계획 작성으로 변경하지 않는다. 구현을 시작할 때 기존 항목과 중복을 확인하고 각 실험의 상태를 proposed → implemented → local_verified → real_model_measured → adopted/deferred로 구분한다. 항목별 증거 없이 완료로 옮기지 않는다.

가벼운 변경 검증 후 실제 영향에 맞는 기존 단위/Chrome 검사를 실행한다. 통합 후보는 `npm run verify:quality`와 `npm run quality:status`로 동일 소스 근거를 확인하며, UI를 바꾸면 기존 `verify:identity`, 배포 준비는 기존 `verify:browser` 조건을 따른다. 같은 검사를 반복 합산하지 않는다.

실행 환경/모델 연결이 없으면 소스와 fixture 검증까지만 완료로 표시한다. 그 상태에서 정확도나 실제 업무 완주를 추정하지 않는다. 이 계획 작성은 실모델 대규모 실행, 최종 배포 또는 사용자 계정의 업무 제출을 수행한 것이 아니다.

## 12. 구현 인계 지시

첫 구현 작업은 A만 진행한다. 관련 AGENTS와 현재 소스를 다시 확인하고, 5초 응답 검증 제한의 실제 영향을 긴 스트림 fixture로 재현한다. 기존 평가기와 제품 응답 파서를 재사용해 호출 목적/응답 종료/도구 영수증을 연결한다. 모델 입력과 실행 정책을 바꾸지 않은 상태로 개발 과제 smoke를 확인하고, 실제 Qwen 기준선의 준비 상태와 미확인 조건을 보고한다. B~F를 한 변경에 묶지 않는다.

후속 구현은 이 문서의 입력/출력 계약, 비교군, 독립 채점과 채택 조건을 작업 단위로 사용한다. Claude 배포 코드/프롬프트/자산을 복사하지 않고 기존 Pi, MiniSearch, Playwright, OpenWiki를 재사용한다. 새 의존성이 꼭 필요한 경우에만 라이선스, 브라우저 번들 크기, 유지보수와 호출 비용을 다시 비교한다.
