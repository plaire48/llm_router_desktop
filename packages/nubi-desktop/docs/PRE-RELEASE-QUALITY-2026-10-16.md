# 배포 전 기능 검증과 하네스 보완

대상은 2026-10-16 현재 1.2.8 소스다. Mac의 단위 검사, 임시 프로젝트와 로컬 모델 fixture를 사용하는 Electron 흐름을 확인한다. Windows 설치판, 사내 SSO/메일/결재 실서비스, 실제 모델의 정답률을 대신 증명하지 않는다. 이번 작업에서 버전 변경, 업로드, 설치 파일 생성과 배포는 하지 않는다. 사용자가 취소한 메일 HTTPS/파생 기록 암호화 작업도 제외했다.

## 벤치마킹한 방법과 반영

- [OpenAI: Unrolling the Codex agent loop](https://openai.com/index/unrolling-the-codex-agent-loop/): 도구의 실제 결과를 다음 판단에 넣고 목표가 충족될 때까지 이어가는 구조를 참고했다.
- [OpenAI: Iterative repair loops](https://developers.openai.com/cookbook/examples/codex/build_iterative_repair_loops_with_codex): 실행, 검증, 수정의 연결과 확인 가능한 실행 기록을 참고했다.
- [Anthropic: Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents): 코드 작성 선언과 실제 기능 검증을 구분하고, 진행 기록과 검증 결과를 다음 작업에 연결하는 원칙을 참고했다.

누비에 이미 있는 Pi 실행, 계획, 승인, 복구, 인앱 확인 경로를 유지했다. 새 SDK, 외부 서비스와 인증 경로는 도입하지 않았다. 공개 방법론을 적용한 것이며 Codex/Claude의 비공개 구현을 복제했다는 의미가 아니다. 실행 권한이나 재시도 횟수를 늘리지 않았다.

## 발견한 문제와 수정

### 오래된 성공이 최근 실패를 덮는 문제

개발 결과 검토에서 `verify` 실행 중 성공한 것이 하나라도 있으면 근거 후보가 됐다. 같은 명령의 나중 실행이 실패하거나 아직 진행 중이어도 이전 성공이 남았다.

`development-workflow.mjs`에서 작업 경로, 셸, 정확한 명령별 최근 실행을 우선한다. 최근 실패/진행/취소는 이전 성공을 대체한다. 시간 정보가 없거나 같은 시각의 결과가 충돌하면 성공으로 채택하지 않는다. 별개의 명령이나 다른 경로/셸의 실행은 서로 대체하지 않는다.

### 승인한 수정 명령의 검증 근거 누락

`applyCommandRepair`는 실제 프로세스에 `repairOf`를 남겼지만, 에이전트/검토 입력으로 전달하는 실행 기록에는 이 연결이 없었다. 수정 명령은 원래 `verify` action과 직접 연결되지 않아 성공한 테스트도 검증 근거로 인정되지 않았다.

`agent.mjs`가 호스트의 원래 프로세스 ID와 작업 경로를 전달한다. 검토는 호스트가 생성한 수정 관계를 따라 원래 검증을 확인한다. 수정된 실행은 이전 실행을 대체한다. 원래 검증 기록을 찾지 못하거나 단순 환경 조회를 고친 경우에는 테스트 성공으로 승격하지 않는다.

검토 입력에는 허용된 프로세스 ID도 포함한다. 이는 출처 후보일 뿐 테스트 의미나 최종 성공 판정이 아니다. 종료 코드 0, 버전 조회, 빌드, 페이지 열기만으로 기능 성공을 선언하지 않는 기존 계약은 유지한다. 불완전/잘린 실행 로그도 계속 제외한다.

### 시작할 때 프로젝트 복원 충돌

실제 Electron 호스트와 보조 웹 화면을 같이 시작하는 검사에서 파일 버튼이 비활성으로 남았다. RPC 진단으로 `openCurrent → project_busy`를 재현했다. 두 화면이 동시에 같은 프로젝트를 열면서 두 번째 복원이 거절된 경우다.

`project-restore.cjs`의 진행 중 복원 공유 함수를 `main.cjs`의 시작 복원 경로에 적용했다. 같은 복원은 한 번만 실행하고 호출자들이 그 결과를 받는다. 완료 후에는 결과를 캐시하지 않아 현재 프로젝트를 다시 읽으며, 실패도 그대로 전달한다. 다른 프로젝트로 이동하는 잠금과 기존 제한된 Git 타임아웃 복구는 바꾸지 않았다.

단위 검사 13건과 같은 실제 Electron/보조 웹 시나리오의 9단계를 최신 실행 번들로 두 번 통과했다. 처음 수정 직후 실행은 main 번들 재빌드가 빠졌으므로 수정 증거에서 제외했다. 재빌드 후 두 번의 재검사와 Electron 수명주기 검사를 통과했다. 검사에는 RPC 메서드와 안전한 오류 코드만 남겨 다음 실패 지점을 찾을 수 있게 했다. 본문, 인증값, 요청 인자는 진단에 남기지 않는다.

### 기존 누비 모달 토큰과 검사 정렬

위키 갱신의 ‘중단 이유’ 아이콘이 고정 14px여서 글자를 확대하면 상대적으로 작아졌다. 기존 모달처럼 `--nubi-icon-small`, `--nubi-work-control-gap`, `--nubi-weight-label`을 사용했다. 폰트와 색상, 레이아웃, 승인 동작은 유지했다. 1280px와 440px 창(루트 글자 20px)에서 아이콘 크기와 수직 정렬, 버튼 잘림, 이어서 갱신/충돌/중지/버리기를 확인했다.

기존 위키 이어쓰기 UI 검사는 모든 버튼을 한 줄로 기대해 나중에 추가된 ‘위키 다시 만들기’의 독립 행을 실패로 보고했다. 실제 화면을 확인한 뒤 복구 버튼 3개는 한 줄, 전체 초기화는 아래 별도 행으로 검사 기준을 수정했다. 제품 레이아웃을 옛 검사에 맞춰 바꾸지 않았다.

## 검증 기록

- 변경 전 전체 단위 검사: 1,556건 중 1,360 통과, 실패 0, 건너뜀 196. 실행 시간 약 358초. 건너뜀은 활성 기능 검증 성공으로 세지 않는다.
- 새 회귀 검사 첫 실행: 7건 중 6건 실패로 재현. 구현 후 7건 통과. 이후 작업 경로/셸 격리, 같은 시각의 충돌과 조회 명령 구분을 추가했다.
- 최종 개발 검증, 명령 복구, 결과 검토, 검토 복구 검사: 62건 통과. 실제 임시 Bash 프로세스가 포함되며 모델 응답은 fixture다.
- 하네스 수정 후 전체 단위 검사: 1,565건 중 1,369 통과, 실패 0, 건너뜀 196. 약 357초. 이후 추가한 복원 변경은 별도 13건으로 확인했으며 전체 1,567건을 다시 실행했다고 표시하지 않는다.
- 승인된 수정 명령의 실 프로세스 검사: 한 번만 실행되고, 후속 에이전트 입력에 원래 프로세스와 경로가 전달됨을 확인했다.
- Electron 빌드, TDZ 408개 파일, 아이콘 70개, 디자인 토큰 검사 통과.

UI/브라우저 검사는 병렬로 실행하지 않았다. 위 표의 모델, 메일과 계정 데이터는 로컬 fixture이며 실제 사내 서비스가 아니다. 최신 UI 토큰 수정 후 전체 화면 검사 결과도 최종 산출물에 보관한다.

## 남은 실제 환경 검증

1. Windows 11 새 설치/동일 버전 재설치/업데이트, 컷신, 기본 터미널, Office 2016/NASCA 첨부 읽기.
2. 사내망의 실제 GHES, SAML 새 탭 POST, 메일 로그인과 세션 만료 확인 팝업, 결재 목록/본문.
3. 실제 연결 모델로 동일 과제 정답률/근거 정확도/속도 비교. 이번 회귀 검사 통과를 실모델 품질 상승 점수로 환산하지 않는다.

검증 파일은 `verification/pre-release-2026-10-16/`에 보관한다. 로컬 통과만으로 위 세 경계를 통과 처리하지 않는다.
