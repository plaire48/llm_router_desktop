# Office 첨부 읽기 시간 초과 보완

사용자 보고 문구는 `document_office_timeout`이다. 이전 호스트는 Office 실행, 파일 열기, 본문 읽기, 닫기와 정리를 합쳐 60초가 지나면 PowerShell을 중지했다. 중간 단계는 프로세스 종료 응답에만 있어 시간 초과 시 어디까지 읽었는지 알 수 없었다. Excel은 UsedRange 전체에서 셀마다 COM Text를 읽고 내부 반복 조건에서도 COM Count를 다시 조회했으며 합계 20,000셀을 넘으면 읽기를 거절했다.

이 사실은 현재 소스에서 확인했다. 사용자가 실패한 실제 파일의 Office/NASCA 실행 단계나 보안 안내 창은 관찰하지 못했으므로 특정 파일의 원인을 확정하지 않는다.

## 구현

- STA PowerShell의 stderr로 허용된 단계와 실제 수량만 알린다. 파일명, 경로, 셀 내용이나 예외 본문은 이 채널에 넣지 않는다. stdout의 최종 JSON 계약은 유지한다. 호스트는 잘린 프레임을 합치고 프레임 크기를 제한하며 잘못된 형식과 다른 앱의 신호를 버린다.
- 일괄 60초 제한을 제거한다. 마지막으로 진행을 확인한 뒤 120초가 지나면 보류하고 전체 실행은 15분으로 제한한다. 동일한 수량 반복이나 일반 stderr 출력은 제한 시간을 연장하지 않는다. 시간 초과에는 마지막 단계, 앱, Office 버전, 시트 순번, 실제 읽은 수량과 경과 시간, 진행 미확인/전체 시간 한도 구분을 남긴다. 자동 메일 첨부 읽기는 기존 백그라운드 큐를 사용한다.
- Excel은 행/열 개수를 한 번 읽고 최대 2,048셀 블록의 Value2를 빈 셀 확인에만 사용한다. 실제 값이 있거나 병합 여부가 확실하지 않은 셀은 기존 Text로 읽는다. 날짜, 금액, 앞자리 0, 빈 문자열을 돌려주는 수식의 표시와 병합 셀을 원시 값으로 바꾸지 않는다. 입력/시트/본문 예산 안의 큰 시트를 끝까지 읽으며 20,000셀 일괄 거절을 제거했다.
- 메모리/출력 경계는 유지한다. 입력 128MiB, 본문 8,000,000자와 전체 응답 48MiB, 200개 시트/1,000개 슬라이드를 넘으면 전체 읽기 완료로 기록하지 않는다. Excel의 탭과 줄바꿈도 본문 예산에 먼저 포함해 거대한 빈 UsedRange의 출력 생성을 제한한다. 전체 파일을 모델의 한 요청에 넣는 변경은 아니다.
- 자동 읽기의 현재 파일/시트/실제 수량/시간을 기존 메일 상태창에 표시한다. 비율은 현재 시트 또는 슬라이드의 실제 분모가 있을 때만 표시하며 첨부 전부의 완료율로 부르지 않는다. 시트가 바뀌면 시간 추정의 식별자도 바뀐다. 검증과 닫기 단계에서는 비율을 만들지 않는다.

원본과 사본 SHA-256, 사용자 ACL, ReadOnly와 실제 FullName 대조, 매크로/이벤트/링크 갱신 차단과 원래 설정 복구를 유지한다. COM 실패를 외부 파서 성공으로 바꾸지 않고 다른 사용자 Office 문서를 닫거나 Office 프로세스를 강제 종료하지 않는다. 실패한 첨부의 재시도는 기존 명시적 다시 읽기 동작을 사용하며 완료한 다른 첨부나 사용자 위키를 재발행하지 않는다.

범위와 셀이 같은 RCW를 공유할 수 있어 획득한 참조별로 `ReleaseComObject`를 한 번 호출한다. 블록 안의 `FinalReleaseComObject`로 살아 있는 다른 범위까지 무효화하지 않는다. Microsoft의 [FinalReleaseComObject 계약](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.marshal.finalreleasecomobject?view=net-10.0)을 따른다. Windows 파서 게이트에는 같은 생산 해제 함수를 사용하는 Scripting.Dictionary 참조 공유 검사를 추가했으며 이번 macOS 실행에서는 이 Windows COM 검사를 실행하지 않았다.

## 근거와 검증 경계

Microsoft의 [Excel 성능 안내](https://learn.microsoft.com/en-us/office/vba/excel/concepts/excel-performance/excel-tips-for-optimizing-performance-obstructions)는 큰 범위의 묶음 읽기를 권장한다. [Range.Text](https://learn.microsoft.com/en-us/office/vba/api/excel.range.text)는 표시 문자열이며 여러 셀의 내용을 한 번에 얻는 기능이 아니다. [Value2](https://learn.microsoft.com/en-us/office/vba/api/excel.range.value2)는 날짜/통화의 자료형을 그대로 유지하지 않으므로 표시 본문을 통째로 대체하지 않았다.

관련 39개 로컬 검사에서 진행이 있는 긴 읽기, 파일 열기 무응답, 반복 신호, 절대 한도, 프레임 분할/크기 제한, 취소, 저장한 진단의 재열기와 실패한 첨부만 다시 읽기, 시트별 수량과 검증 단계 구분을 확인했다. 실제 자식 Node 프로세스의 pipe로 호스트 감시기를 검사했으며 Office COM 실행은 아니다.

공식 GitHub 릴리스와 SHA-256을 확인한 임시 PowerShell 7.6.8에서 실제 PS1을 파싱하고 격리된 생산 읽기 함수를 실행했다. 관리형 가상 Range의 30,000셀에서 네 개의 실제 표시값을 읽고 빈 셀에는 개별 Text 호출을 하지 않으며 각 블록은 2,048셀 이하였다. 날짜/금액/앞자리 0/빈 수식 표시, 1셀/세로/가로 범위, 병합 셀과 이름/본문이 없는 진행 신호를 확인했다. 이 실행은 Windows PowerShell 5.1이나 Office COM의 성능 측정이 아니다. 검증용 PowerShell은 앱에 추가하거나 시스템 기본으로 설치하지 않았다.

Chrome과 빌드한 실제 Electron에서 기존 하단 상태창을 여는 흐름을 각각 8항목 확인했다. 1,000/360px에서 현재 시트 2/3, 1,200/2,400셀, 50%와 해당 읽기의 경과 시간을 확인했고 검증 단계에서 임의 %와 다른 정리 작업의 시간을 섞지 않았다. 별도로 실행한 `check-mail-background-ui.mjs`는 메일 설정의 `포털 로그인` 버튼을 찾지 못해 중단됐다. 이 별도 설정/연결 흐름을 통과로 표시하지 않으며 이번 첨부 처리 화면 8항목의 근거와 구분한다.

화면/전체 회귀/빌드/소스 입력/안전 검사 결과는 `verification/office-read-progress-2026-10-24/`에 보존한다. 실제 Windows Office 2016, 회사 NASCA, 보안 안내 창, 설치판과 보고된 첨부의 읽기는 별도 확인이 필요하다. 일반 첨부 선택 요청의 장시간 UI 대기와 이 자동 메일 큐의 처리 시간도 같은 측정으로 표시하지 않는다.
