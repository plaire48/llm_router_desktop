# 메일 본문 이미지와 위키 생성

사용자는 본문이 이미지인 메일도 첨부파일처럼 읽어 위키를 만들고, AI Pro에서 GLM을 사용하면 이미지는 Qwen으로 판독하도록 요청했다.

## 원인과 반영

본문 이미지는 `inlineImages`로 분리돼 질문 시 판독에는 연결돼 있었지만, 자동 위키의 생성 입력과 대화별 위키의 첨부 순회에서는 빠졌다. 폴더 가져오기도 이미지뿐인 메일을 빈 본문으로 거절했다.

- 기존 `prepareMailWikiAttachments`를 자동/대화별 위키에서 함께 사용한다. 일반 첨부와 원문에서 검증한 CID/data 이미지를 순서대로 읽고 기존 캐시를 재사용한다. 이미지 판독기를 새로 만들거나 OCR 라이브러리/별도 계정을 추가하지 않는다.
- 이미지 판독은 기존 `readImageAttachment`/`modelTransport`와 인증 카탈로그를 사용한다. AI Pro GLM에서는 카탈로그의 Qwen만 선택하며 명시한 이미지 미지원과 모델 부재를 유지한다. 이미지 이외의 생성/검토 호출과 저장한 선택 모델은 GLM으로 유지한다.
- 생성과 독립 검토에 전달할 때만 이미지의 추출 텍스트를 첨부 근거에 합친다. 일반 첨부 개수와 메일 표시를 바꾸지 않고, 원본 이미지/base64를 GLM의 텍스트 입력이나 위키에 복사하지 않는다.
- 원문/이미지 해시 검증, 판독 뒤 재읽기, 취소와 캐시 바인딩을 유지한다. 저장한 위키는 기존 파일 해시/readback과 암호화 계약으로 확인하며 본문 이미지 해시와 판독 범위를 함께 기록한다.
- 가져오기는 텍스트가 없어도 원문에 본문 이미지가 있으면 허용한다. 이미지도 없는 빈 메일은 기존처럼 거절한다.
- 바이트가 없는 외부 URL 이미지, 누락된 CID 원본, 지원하지 않는 data 이미지와 판독 실패는 부분 범위로 남긴다. 자동 위키의 확인 영역과 대화 위키의 coverage에 미확인을 표시한다. 외부 URL을 임의로 내려받거나 회사 세션을 복사하지 않는다.

기존 생성 완료/사용자 편집 페이지를 일괄 덮어쓰지 않는다. 새 생성과 명시한 대화 위키 생성부터 반영하며, 미확정 저장의 기존 prepared 영수증을 버리고 재실행하지 않는다. Windows Office 첨부의 기존 COM 경계도 유지한다.

## 검증 경계

원래 CID/data와 자동/대화별 생성, 이미지 부재 범위의 6개 회귀가 실패한 것을 확인한 뒤 수정했다. 새 통합 검사는 실제 MIME 파싱, 암호화 원문 저장, 이미지 판독 호출 라우팅, 위키 생성/독립 검토 입력, 파일 저장/readback, 추출 캐시, 원문 변경과 취소를 실행한다. 모델 응답과 인증 저장소는 합성 대체물이다. Qwen의 실제 이미지 인식 정확도, 실제 AI Pro 계정/사내 외부 이미지 접근, Windows 설치판/Office/NASCA는 이 검사로 통과시키지 않는다.

| 검사 | 결과 |
| --- | --- |
| 본문 이미지 위키/판독/기존 질문 경로와 모델 라우팅 | 33/33. CID/data의 자동/대화별 생성, 검토 유무, 캐시와 실제 저장, 이미지뿐인 폴더 가져오기, GLM의 잘못된 이미지 지원 플래그, Qwen 부재/명시한 이미지 미지원, 원문 변경/취소, 외부 URL/누락 CID의 부분 범위 |
| 기존 메일/대화 위키/가져오기/재개/저장/Office 첨부/지식/암호화 | 115/115 |
| `check-mail-body-images.mjs` | CID/HTTP 표시, 실행 콘텐츠 격리, 파일 URL 차단, 좁은 화면의 기존 5개 검사 통과 |

새 라이브러리 도입 대신 기존 모델 라우팅과 이미지 판독기를 연결했다. 원본과 별도 캐시/합성용 텍스트 투영을 유지해 기존 메일/보안/COM 계약을 보존했다.

`npm run build:electron`도 통과했다. macOS 빌드에서 PowerShell native 파서 검사는 환경 부재로 건너뛴 것이며 Windows 검증 성공이 아니다.
