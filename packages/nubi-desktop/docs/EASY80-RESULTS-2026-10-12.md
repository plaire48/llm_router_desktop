# 쉬운 과제 80개 평가 결과

2026-10-12, Claude Opus 5.5(`claude-opus-5-5`)에 추론 강도 medium을 요청해 각 영역 20개를 실제 누비 Agent로 한 번씩 실행했다. 자동 기준은 **76/80 통과**다. 이 수치는 제품 전체 정확도나 반복 성공률이 아니다.

## 최초 기준선

| 영역 | 자동 기준 통과 | 시간 중앙값 | 시간 95백분위 | 답변 글자 수 중앙값 |
|---|---:|---:|---:|---:|
| Bash 연속 실행 | 20/20 | 149초 | 186초 | 646 |
| 여러 메일 종합 | 19/20 | 74초 | 128초 | 945 |
| 적절한 스킬 활용 | 18/20 | 37초 | 95초 | 410 |
| OpenWiki 조회 | 19/20 | 82초 | 95초 | 878 |

80개 모두 실행했고 중도 오류, 사람 확인 대기, 미실행은 없다. 모든 작업의 원본 파일 보존 검사가 통과했다. 4개 작업을 동시에 실행했으므로 시간에는 제공자 병렬 부하가 포함된다. 중앙값은 가운데 두 값의 평균, 95백분위는 nearest-rank로 계산했다. 원본 보고서의 중앙값 계산과 작은 차이가 있다.

31분 10초 동안 제품 입력 파일 469개의 해시가 바뀌지 않았다. 기준선 후보는 `07e59d41e4b26a453e28fb748ebc85a1dd9d8385e521f8a60d1c49b3a1ea5fe8`, 평가 명세 해시는 `7736ebe2f3152fc70f08bc356f0e89c18e85b82253c6d4a7ed00c000c4b679a4`다.

## 실패와 평가 한계

- **mail-16: 실제 정보 누락.** 담당자와 인계 문서를 함께 물었는데 담당자만 답했다. 검색어의 모든 단어가 한 메일에 있어야 하는 조건 때문에 문서 목록 메일을 놓쳤다. 검토 모델은 넓게 재검색하라고 했지만 원래 요청을 supported, 문서 항목만 intent unknown으로 표시했다. 호스트가 이를 모델이 추가한 요구로 간주해 재검색을 생략했다.
- **skill-06: 기대 형식과 다른 스킬.** 배포 안내 대신 인수인계 형식으로 바뀌었다. 질문에 배포 안내라는 목적이 명시되지 않아 두 선택이 모두 가능하다. 검토가 계획의 스킬 이름을 고집한 문제도 있다. 원래 자동 실패를 유지하고 문항의 모호함을 함께 표시했다.
- **skill-10: 스킬 선택과 출력 구성.** 고객 확인 답변에 기대한 support-reply 대신 bug-report를 썼다. 고객에게 보낼 초안은 포함했으나 불필요한 오류 보고가 앞섰다. 질문의 산출물 표현이 모호한 점과 스킬 검색/선택의 일관성을 함께 개선해야 한다.
- **wiki-09: 조회 경로 차이.** 위키 파일 두 개를 직접 읽고 정확히 인용했다. ask_openwiki/wiki_query 호출을 요구하는 자동 기준만 실패했다. 정답은 맞지만 위임 조회 경로는 이 사례에서 검증되지 않았다.
- **bash-09: 자동 통과 문항의 단위 모호함.** 입력 수치의 초/분 단위가 없고 도구가 합계를 60으로 나눴다. 숫자 10은 맞지만 답변은 단위를 다르게 해석했다. 숫자 일치만으로 의미까지 맞다고 처리하지 않았다. 다음 평가판에서 입력 단위를 먼저 명시해야 한다.

모든 최종 답변을 고정 입력과 직접 대조했다. 핵심 사실은 78개에서 확인했고, 1개는 정보 누락, 1개는 입력 단위가 모호해 확정하지 않았다. 이 수동 검토는 같은 담당 Agent의 점검이며 별도 인간 평가자나 독립 모델 평가가 아니다. 정답 사실이 맞는 것과 스킬 선택, 문장 품질, 요청한 도구 경로 준수는 구분한다. 원본 `falseCompletion` 값 4는 검사 실패 상태로 전달됐다는 기계 표시로, 허위 사실 4건을 의미하지 않는다.

## 반영한 개선

1. 개인 메일 도구에 검색어의 AND 조건을 명시하고, 요청 일부가 검색되지 않으면 같은 필터 안에서 주제어로 넓혀 다시 찾도록 했다.
2. 검토 지침은 원래 요청의 모든 항목이 답변됐을 때만 request를 supported로 판단한다. 모델의 계획과 다른 적절한 스킬/방법을 선택했다는 이유만으로 답변을 다시 쓰게 하지 않는다.
3. 검토가 재작업을 요청했지만 intent 항목만 미확인인 경우, 종료 전에 원래 요청의 누락인지 한 번 더 확인한다. 모델이 추가한 요구만 남은 경우의 답변 전달은 유지한다. 형식 복구는 기존 한 번만 허용한다.
4. 간단한 답변은 핵심 결과, 직접 출처, 결론에 영향을 주는 불확실성만 남긴다. 없는 첨부, 무관한 문서, 묻지 않은 정보와 반복된 도구 설명을 생략한다. 제공한 오류 문구를 정리하는 일을 원인 분석 요청으로 확대하지 않는다.

## 검증 범위

실제 모델, Pi, ProjectService, Bash 프로세스, Personal Wiki 검색/원문 읽기, 프로젝트 스킬과 OpenWiki 위임을 사용했다. 메일 서버 전송부는 고정 합성 입력이며 실제 회사 POP3 수신을 검증한 것은 아니다. 위키 생성/갱신, Windows PowerShell, 대규모 검색과 반복 일관성도 이번 80개 성적에 포함하지 않는다. Bash는 기존 보고서 CLI를 두 번 실행하고 출력을 확인하는 과제이며 자유로운 셸 코딩이나 장애 복구 평가가 아니다.

실제 CLI 카탈로그의 문맥 한도 1,000,000을 유지했다. medium은 요청값이며 CLI가 실제 적용 강도를 별도로 확인하지는 않았다. 질문과 정답은 실행 전에 고정했고 정답 파일은 모델 작업 폴더에 넣지 않았다. 사용자 개인 메일과 인증은 복사하지 않았다.

## 수정 후 검증

최종 후보 `34876a13feca34daec27e8d6a580b883b2aad4b1c0315f116f38e70af1bad319`에서 동일한 고정 명세로 대표 8개를 재실행해 **8/8 통과**했다. Bash 2개, 메일 2개, 스킬 2개, Wiki 2개이며 기존 실패 mail-16을 포함했다. 변경된 후보의 전체 80개 성적으로 확대하지 않는다.

- mail-16은 최종 대표 실행과 추가 2회에서 **3/3 통과**했다. 매번 이하린, 운영매뉴얼, 점검표를 원문과 함께 답했다. 같은 후보/입력/모델이며 추가 단독 실행의 시간은 4개 동시 평가 시간과 직접 비교하지 않는다.
- 실패 당시의 첫 검토 결과를 그대로 주고 실제 Claude에게 원래 요청의 충족 여부를 다시 검토시켰다. 실제 추가 호출 한 번에서 request를 unknown으로 바로잡고 인계 메일 재검색을 요청했다. 이 재현은 기록 재생 + 실제 검토 1회이며 새 전체 Agent 과제로 세지 않는다.
- 대표 8개 답변의 총 글자 수는 6,107에서 4,368로 약 **28% 감소**했다. 핵심 사실과 실제 출처/실행 검사를 함께 확인했다. 모든 답변이 짧아진 것은 아니며 전화번호 가림 문항은 오히려 늘었다.
- 같은 8개의 작업 시간 합계는 808초에서 619초로 줄었다. 한 번씩의 관측이고 제공자 부하가 달라 보장된 속도 개선률로 표시하지 않는다. 주 모델 호출 합계는 65회에서 57회로 줄었다.
- 오류 제보 정리(skill-15)는 원래 8회 호출에서 5회로 줄었으며, 요청하지 않은 코드 원인 조사는 하지 않았다. 날짜 종합(mail-01)은 13회에서 6회로 줄었다.
- 새 종료 조건 회귀 3개 중 수정 전 2개 실패를 재현했다. 수정 후 관련 55개가 통과했다. 전체 검사에서 작은 문맥용 도구 설명 길이 초과를 발견해 설명을 압축했으며, 검사 한도는 완화하지 않았다.
- **최종 전체 단위 검사: 977개 중 779개 통과, 실패 0, 건너뜀 198개.** 건너뜀은 기존 비활성 Computer Use/A2A, Beta 첨부와 환경별 검사이며 통과로 세지 않는다.

최종 대표 결과는 `verification/eval-live/easy80-final-focus-20261012/`에 있다. `comparison.json`은 이전/이후 같은 문항의 수치, `semantic-review.json`은 원문 대조, `review-replay.json`은 종료 조건의 실제 모델 재검토다. 반복 결과는 `easy80-mail16-final-repeat2-20261012/`, `easy80-mail16-final-repeat3-20261012/`다. 중간 후보 8/8 결과와 시작 실패(소켓 연결 전, 모델 과제 미실행)는 별도 폴더에 보존했고 최종 성적에 합산하지 않았다.

## 남은 품질 과제

핵심 정보 누락은 해당 회귀에서 고쳤지만 **단순 조회의 속도와 답변 가독성은 아직 개선 여지가 크다**. 최종 답변에도 없는 첨부나 무관한 문서에 대한 설명이 남는다. Bash 두 번 실행에 2분 이상 걸리는 사례도 있다. 승인과 결과 검증을 없애지 않으면서 중복 모델 검토/문맥 전달 비용을 줄이는 별도 실험이 필요하다.

다음 평가판에서는 단위와 원하는 산출물을 명확히 하고, 위키 직접 읽기와 OpenWiki 위임을 서로 다른 경로 기준으로 기록해야 한다. 더 큰 메일함/위키, 검색 누락 복구, 실패 명령 수정, 길어진 대화 및 Windows 실제 입력은 별도 중간 난도 평가가 필요하다. 이번 쉬운 과제 성적을 제품 전체 '상' 또는 95점으로 바꾸지 않는다.

최종 로컬 Electron 빌드도 통과했다. 이 변경은 소스와 로컬 빌드에 반영됐으며 Windows 설치판 재빌드/게시를 완료했다는 뜻은 아니다. 기존 Claude 세션의 OpenWiki 보존 대상 10개 파일 해시는 모두 동일하다. `runtime/agent.mjs`는 메일 검색 설명과 응답 문구 지침 외에는 기준선과 바이트 단위로 동일해 조사 예산 및 연결 3곳을 유지했다.
