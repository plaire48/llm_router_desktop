# Codex 공개 방법론과 누비 하네스 비교

누비의 Pi 실행기를 유지하면서 불필요한 준비 호출을 줄이고, 독립 조사만 나누며, 실제 결과로 완료를 판단한다. Codex의 비공개 내부 구현을 복제했다는 의미가 아니다.

## 공개 근거와 적용 판단

2026-10-15 확인한 공식 문서:

- [Codex prompting guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide): 단순 요청에 불필요한 계획을 만들지 않으며 실행과 검증까지 이어간다. 독립 조회는 묶되 의존 작업의 순서를 지킨다. 모델별 가이드이므로 다른 제공자에 동일한 성능을 보장하지 않는다.
- [OpenAI multi-agent guide](https://developers.openai.com/api/docs/guides/agents-api/multi-agent): 명확한 질문과 산출물로 독립 조사를 분담한다. 짧거나 순서가 중요한 작업은 메인이 처리하며 공유 파일 쓰기는 조정한다. 호스팅 API의 기능을 로컬 Codex의 구현과 동일시하지 않는다.
- [Codex CLI와 Agents SDK 워크플로](https://developers.openai.com/cookbook/examples/codex/codex_mcp_agents_sdk/building_consistent_workflows_codex_cli_agents_sdk): 역할별 제한된 문맥, 산출물과 검증을 통한 인계를 참고한다.

설계 원칙만 적용한다. 새 SDK나 서비스를 도입하지 않으므로 의존성, 인증 경로, 라이선스 구성과 실행 비용 체계는 바뀌지 않는다.

| 비교 항목 | 현재 누비 | 이번 판단 |
| --- | --- | --- |
| 의도와 완료 조건 | 원래 사용자 요청, 제약, 예상 결과와 수정 가능한 계획을 분리 보존 | 유지. 모델의 계획이 사용자 지시를 대체하지 않는다 |
| 계획 시점 | 도구 목록 조회에도 별도 planner 호출 필요 | 수정. 메타데이터 조회 뒤 실제 프로젝트 작업 전에 계획 |
| 도구 노출 | 작은 문맥에서는 핵심 도구와 선택한 작업 도구만 제공 | 유지. 모든 모델에 일괄 적용하기 전 품질 비교 필요 |
| 작업 분담 | 읽기 전용 조사, 동시 2개, 최대 6개 대기/진행 기록 | 유지. 개수 확대보다 독립성과 조사 범위가 중요 |
| 하위 문맥 | 배정된 근거와 조회 범위만 전달 | 유지. 쓰기 권한과 사용자 승인은 메인에 남긴다 |
| 결과 합치기 | 출처, 불확실성, 부분 결과와 실패 기록 보존 | 유지. 하위의 완료 선언을 최종 검증으로 취급하지 않는다 |
| 명령 실행 이후 | 실제 출력과 실행 기록으로 같은 요청을 계속 처리 | 유지. 종료 코드만으로 사용자 요구 충족을 선언하지 않는다 |
| 사용자 표시 | 실제 진행 발화와 도구 기록, 승인 폼, 결과 | 유지. 내부 진단이나 비공개 추론을 진행 설명으로 꾸미지 않는다 |

## 이번 수정

`runtime/agent.mjs`의 두 경계에서 `discover_capabilities`와 `select_tools`만 계획 이전에 허용한다. 이 도구들은 카탈로그 메타데이터를 조회하거나 모델에 제공할 도구를 선택한다. 스킬 본문 읽기, 파일 조회, 메일 검색, 명령 제안과 실행까지 허용한 것이 아니다.

- 이 두 도구만 요청한 회차는 자동 계획 호출을 하지 않는다.
- 다음 회차가 프로젝트 작업이면 기존 계획 검증을 수행한다.
- 조회와 프로젝트 작업을 같은 응답에 넣어도 작업 전에 계획을 검증한다.
- 계획 작성이 실패하면 조회 결과는 남고 프로젝트 작업은 실행하지 않는다.
- `/mail`, `/code`, 검토 복구, 사용자 질문 대기와 하위 권한 제한은 계속 적용한다.

순수 도구 조회 fixture에서 planner 호출은 1회에서 0회로 줄었다. 조회 후 실제 파일을 읽는 경우에는 1회를 유지하며 호출 시점만 늦췄다. 전체 과제의 모델 비용이나 지연 감소율로 확대 해석하지 않는다.

## 확인한 결과

수정 전 새 회귀 검사 2건이 실패하는 것을 재현했다. 하나는 조회 전 불필요한 계획 호출, 다른 하나는 실제 작업이 결정되기 전에 계획을 만드는 문제다.

- Desktop 도구 선택, 명령 후속 처리, 검색 범위, 메일/Wiki 근거, 하위 분석 기록 검사: 37건 통과.
- 초기 계획, 잘못된 계획, 계획 중 취소, 질문 후 재계획 검사: 7건 통과.
- 공유 하위 분석 조정기 검사: 20건 통과. 실제 비동기 겹침, 2개 슬롯과 6개 작업 처리, 실패 격리, 취소, 미수집 결과 보존, 오래된 근거와 부분 결과를 확인했다.

## 후속 품질 비교 기준

기존 고난도 40문항을 Bash, 메일, 스킬, Wiki 각 10문항으로 유지한다. 동일 모델 ID, effort, 입력 문맥, 도구/권한, 원본 데이터와 깨끗한 작업 사본을 고정한다. 변경 전후를 각각 3회 실행하고 개별 실행 성공과 과제별 3회 모두 성공을 별도로 집계한다. 이번에는 이 실모델 재평가를 실행하지 않았다.

1. 정답과 근거 정확도: 독립 정답 및 원문과 비교한다. 답변 형식과 누락도 채점한다.
2. 완료의 정직성: 근거 없는 완료, 미실행을 성공으로 표시한 수, 중복 쓰기는 각각 집계한다. 승인 우회나 중복 쓰기가 있으면 채택하지 않는다.
3. 효율: planner/actor/child/reviewer 호출 수, 토큰, p50/p95 시간, 중복 조회와 사용자 개입을 구분한다. 호출 수 감소를 속도 향상으로 대신 표시하지 않는다.
4. 분담 효과: 독립 조사 사례에서 메인 단독과 읽기 전용 분담을 비교한다. 한 하위 실패, 출처 충돌, 취소 사례도 분모에 유지한다.
5. 채택 조건: 정답/출처 품질을 떨어뜨리지 않고 비용 또는 지연이 개선된 설정만 기본값으로 승격한다. 좁은 과제의 성공을 제품 전체 점수로 표시하지 않는다.

다음 우선순위는 도구 노출 축소의 제공자별 효과, 여러 자료의 충돌을 명시적으로 다루는 결과 통합, 문맥 압축 뒤 미완료 도구 결과 보존 순서다. 기존 구현이 있는 항목은 실패를 재현한 뒤 변경하며 프레임워크 교체나 외부 A2A 확대는 하지 않는다.
