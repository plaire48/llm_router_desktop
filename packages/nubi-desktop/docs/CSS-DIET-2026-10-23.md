# CSS 다이어트 기준선과 결과 (계획 2a, 2026-10-23)

설계 §6, 계획 `docs/superpowers/plans/2026-10-23-nubi-desktop-light-flow-2a-css-diet.md`. 기준 커밋 main `44947b56`.

## 재는 방법

- 크기: `node scripts/css-report.mjs --out <json>`. 실제 설치판과 같은 렌더러 빌드(`rendererBundleOptions`, minify)의 첫 화면 CSS(`renderer.css`)와 지연 묶음 CSS를 잰다.
- 버킷: 맨 끝 복합 선택자에 클래스, 태그, id가 없으면 universal(모든 요소가 검사하는 규칙)이다.
- 화면: `node scripts/compare-captures.mjs <전> <후>`. `check-all-surfaces` 캡처 115장은 기본 잡음 기준(장당 20픽셀, 움직이는 4장은 따로)이다. `check-shared-ui` 상태 캡처 50장은 두 번 실행으로 잰 장별 잡음의 두 배를 허용한다(scratchpad의 보정 파일). 실행마다 24만 픽셀이 다른 `ui-conversation-history.png`는 판정에 쓰지 않는다.
- 시간: `npm run test:light-flow`(조건 A, 세 번 실행 중앙값, 빠진 장면은 실패).

## 결정: 바꾸는 꼴 (작업 1)

`node scripts/measure-selector-cost.mjs`(Chrome headless, CPU 4배 느림, 요소 3,000개, 규칙 1,000개, 문서 전체 다시 계산, 20번 중앙값), 두 번 실행:

| 맨 끝 꼴 | 중앙값 |
|---|---|
| `:is(.k1,.k2)` | 19.4, 18.8ms |
| 펼친 `.k1`, `.k2` | 19.4, 18.8ms |
| `[data-k]` | 18.7, 17.2ms |
| `span` | 18.9, 17.0ms |
| `*` | 47.1, 46.1ms |

`REWRITE_FORM=C`. `:is()`, 속성만, 태그 끝은 지금 Chrome에서 비용 차이가 없어 그대로 둔다. 비싼 것은 맨 끝 `*`뿐이다(약 2.5배). 작업 2는 맨 끝 `*` 선택자만 다룬다. universal 150 이하 목표는 쓰지 않는다(효과 없는 일).

## 작업 2: 맨 끝 `*` 선택자 (측정 뒤 하지 않음)

실제 앱 CSS에서 맨 끝이 `*`인 규칙 35개를 CSSOM으로 모두 지우고 조건 A wiki 1280 장면을 두 번씩 쟀다.

| | 스타일 계산 최대 | 합계 |
|---|---|---|
| 그대로 | 34.1, 34.5ms | 125.5, 109.8ms |
| `*` 규칙 35개 지움 | 36.7, 38.6ms | 114.6, 142.6ms |

차이가 잡음 안이다. 대부분 줄인 움직임 미디어 안에 있어 평소에는 쓰이지 않는다. 좁히는 작업은 효과가 없어 하지 않는다. 첫 열림 비용은 규칙의 양(CX, 덮어쓰기 층)에서 온다고 보고 작업 3~5로 간다.

## 규칙 양의 효과 (작업 3~5 근거)

화면을 연 뒤 body를 숨겼다 보여 스타일을 전부 다시 만드는 시간(레이아웃 포함, CPU 4배 느림, 15번 중앙값). 같은 세션에서 화면의 어떤 요소에도 맞지 않는 규칙을 모두 지운 뒤 다시 쟀다(가지치기의 상한).

| 화면 | 모든 규칙 | 맞는 규칙만 | 지운 규칙 |
|---|---|---|---|
| wiki | 24.5ms | 13.1ms | 10,271 |
| chat | 18.5ms | 10.9ms | 9,747 |
| mail | 18.5ms | 9.9ms | 10,159 |

규칙 양이 비용의 40~47%다. CSS 변수는 상위에 1,229개 선언(이름 1,110개)이지만 별도 실험에서 다시 계산 한 번에 약 2.5ms(1,200개 요소, CPU 4배)만 더해 부차적이다.

## 결과

### 작업 3: CX에서 Desktop이 쓰지 않는 규칙 빼기

| 항목 | 전 | 후 |
|---|---|---|
| 첫 화면 CSS | 1,524,280 | 1,308,294바이트(-14%) |
| CX `styles.css` 몫 | 469,738 | 253,752바이트 |
| 선택자 | 12,983 | 10,652 |
| 뺀 CX 규칙 | | 2,157(남은 것 1,733) |

- 클래스가 소스 어디에도 없고 이어 붙이는 접두사(`is-`, `message-` 등)로도 시작하지 않을 때만 뺀다. `:is()`/`:where()` 안은 하나만 쓰여도 남기고, `:not()` 안의 클래스는 따지지 않는다(처음 구현에서 `:is(.app-shell,.cx-detail-panel)`를 잘못 뺀 것을 시험으로 잡아 고침).
- 시험 화면 빌드(`check-all-surfaces`, `check-shared-ui`)가 CX 스타일시트를 직접 불러 플러그인을 거치지 않았다. 설치판과 같은 CSS를 보도록 두 빌드에 플러그인을 넣었다.
- 확인: 상태 캡처(헤드리스) 차이는 무작위 인사말과 움직임 위상뿐이다. 같은 순간의 계산된 스타일을 플러그인 켬과 끔으로 떠서 비교해도 움직임 위상(transform, opacity)과 인사말 폭만 다르다. Electron 화면 캡처는 실제 마우스 위치에 따라 실행마다 다른 장이 바뀌고(두 번 실행에서 겹치지 않음), 플러그인을 끈 빌드도 같은 장들이 기준과 달랐다. 그래서 잡음으로 본다.

작업마다 채운다.

### 작업 4: 같은 선택자에서 덮여 죽은 선언 지우기

- `node scripts/css-dead-declarations.mjs --fix`: 첫 화면 CSS 순서(esbuild metafile)에서 같은 조건, 똑같은 선택자의 뒤 규칙이 같은 속성을 다시 정하면 앞 선언을 지운다. 한 규칙 안의 선언(대체값), 축약과 개별 속성, 앞쪽 `!important`, 벤더 접두 값은 건드리지 않는다. CX 파일은 고치지 않는다.
- 지운 선언 184개(18파일). 대부분 `electron-app/ios-tokens.css`(62), `design/workspace-density.css`(32), `design/workspace-identity.css`(21).
- 첫 화면 CSS 1,308,294 → 1,302,044바이트. 덮어쓰기 층 대부분은 선택자가 달라(예: `:root:root .x`와 `.x`) 이 규칙으로는 안전하게 지울 수 없다.
- 확인: `check-shared-ui`가 캡처마다 모든 요소의 계산된 스타일을 저장한다(`NUBI_STYLE_SNAPSHOT_DIR`, 무작위는 고정 시드). 같은 코드 두 번 실행에서 흔들리는 캡처 2장(`ui-connected-fixture`, `mail-filters-no-scroll-440`)을 빼고 41장에서 바꾸기 전과 후의 차이 0.

### 작업 5: 화면 전용 CSS를 지연 묶음으로 (측정 후 옮기지 않음)

- esbuild 0.25는 `import()`로만 닿는 CSS도 첫 묶음 `renderer.css`에 넣는다. 지연 묶음의 CSS 파일(`chunks/*.css`)은 만들어지지만 아무도 불러오지 않는다. 그래서 import 줄을 옮겨도 첫 묶음은 그대로다.
- 시작 때 쓰지 않는 CSS는 93파일, 332,444바이트(첫 묶음의 25%, 규칙 8,065개 중 1,569개)다. Monaco 편집기 CSS 약 11만 바이트, AI Workspace 묶음, 위키, 메일 화면 CSS다.
- 두 가지 옮기는 방법을 시험했다.
  - 화면 시트를 뒤에 붙이면 같은 우선순위의 규칙끼리 순서가 바뀐다. `workspace-identity.css`, `workspace-density.css` 같은 덮어쓰기 층이 순서로 이기도록 만들어져 있어서, 정적 분석으로 안전을 증명할 수 없다(후보 겹침 6만 건 이상).
  - 첫 묶음의 원래 자리에 규칙을 끼워 넣으면 순서는 그대로다. 하지만 Chrome이 큰 시트 전체의 규칙 색인을 다시 만든다. 276규칙을 넣는 데 CPU 4배 느림에서 약 60ms가 걸렸다(별도 시트를 붙이면 약 7ms). 메일과 위키는 버튼에 마우스를 올릴 때 미리 불러오므로, 이 비용이 마우스를 올릴 때 생긴다.
- 효과 측정(`node scripts/measure-lazy-css-cost.mjs`): 프리징 장면 픽스처를 지연 CSS가 있을 때와 비웠을 때로 각각 빌드했다. 장면을 열고 CPU 4배 느림에서 전체 스타일 재계산 9회의 중앙값을 3회 반복했다.

| 장면 | 지연 CSS 있음 | 비움 | 비고 |
|---|---|---|---|
| 대화 | 20.0ms (20.1, 20.0, 20.0) | 20.5ms (21.4, 20.0, 20.5) | 차이 없음(잡음 안) |
| 위키 | 19.1ms | 17.1ms | 비운 쪽은 위키 자신의 CSS도 없어 실제보다 유리 |
| 메일 | 17.1ms | 15.8ms | 위와 같음 |

- 결론: 대화 화면처럼 그 CSS가 실제로 빠질 화면에서 이득이 없다. Chrome은 규칙을 맨 오른쪽 클래스로 색인하므로, 화면에 없는 클래스의 규칙은 재계산 비용이 거의 없다. 그래서 옮기지 않는다. 위키 첫 열림 39ms와 탐색 37ms는 규칙 양이 아니라 처음 그리는 요소 수와 JS 쪽 비용으로 보고, 계획 2b에서 다룬다.
