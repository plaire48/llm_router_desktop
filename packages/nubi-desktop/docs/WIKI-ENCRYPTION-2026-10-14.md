# 위키·메일 저장 파일 보호 (검토, 2026-10-14)

사용자 질문: 위키가 저장하는 파일이 보안 우려를 산다. 누비 Workspace만 열 수 있게 암호화할 수 없나.

## 지금 상태

| 자료 | 위치 | 보호 |
| --- | --- | --- |
| 프로젝트 위키 | 프로젝트 폴더 안 `openwiki/`(Markdown) | 없음. 소스와 같이 Git에 올라갈 수 있다(공유 규칙은 `WIKI-SHARING-2026-10-12.md`) |
| 개인 메일 원본, 메일 위키, 첨부 읽기 결과 | 앱 데이터 `workspace/` 아래 | Windows에서 사용자 전용 ACL(`protectMailDirectory`, `privateDir`). 같은 계정의 다른 프로그램은 읽을 수 있다 |
| 계정 연결 정보(토큰 등) | 앱 데이터 | Electron `safeStorage`(Windows DPAPI)로 암호화(`connection-vault.cjs`) |

OpenWiki 코어는 디스크의 Markdown을 읽는다(코어 수정 금지, 2026-09-29). 그래서 "파일을 암호화해 두고 누비만 연다"는 **저장 시 암호화 + 사용 중 복호화 사본**으로 구현해야 한다.

## 할 수 있는 것

| 단계 | 조치 | 막는 것 | 못 막는 것 | 작업 |
| --- | --- | --- | --- | --- |
| 1 | **Windows EFS**로 앱 데이터 폴더 암호화(`cipher /e /s:`, 설치 뒤 한 번) | 다른 계정, 디스크 분리, 관리자의 파일 열람(키 없이) | 같은 계정으로 실행되는 다른 프로그램 | 코드 변경 없음. 설치 안내 또는 첫 실행 때 실행(Windows Pro/Enterprise 필요) |
| 2 | **앱 암호화 저장**: 메일 원본, 메일 위키, 첨부 결과, 사실 기록을 DPAPI(`safeStorage`)로 암호화해 `.enc`로 저장. 실행 중에는 사용자 전용 ACL의 세션 폴더에 복호화 사본을 두고 OpenWiki가 그것을 읽게 하며, 종료·잠금 때 지운다 | 파일을 복사해 가져가도 다른 PC·다른 계정에서는 못 연다 | 같은 계정에서 실행 중인 악성 프로그램(세션 사본과 DPAPI 모두 접근 가능) | 실행기 4일, 복구(비정상 종료 뒤 사본 정리) 1일, 검사 2일 |
| 3 | **서버 키**: 사내 SSO 로그인 때 서버가 내려 주는 키로 2의 데이터 키를 감싼다. 키는 메모리에만 | 로그아웃·퇴사·PC 분실 뒤에는 같은 계정이라도 못 연다. "누비만 연다"에 가장 가깝다 | 서버가 필요하고, 오프라인에서는 못 연다 | 서버 API 설계 후 3일 |
| 4 | 사용자 암호(비밀번호) 기반 암호화 | 키 관리 부담, 암호 분실 = 데이터 손실 | | **권하지 않음** |

프로젝트 위키는 소스와 같은 폴더에 있어 Git으로 공유되는 자료다. 암호화하면 공유와 검색이 깨지므로, 대신 **"위키를 Git에 올리지 않기" 스위치(`.gitignore`에 `openwiki/`)**와 민감 프로젝트 표시를 둔다. 암호화 대상은 개인 메일과 앱 데이터다.

## 추천

1차(이번 달): 1을 설치 안내에 넣고, 2를 메일 원본·메일 위키·첨부 결과에 적용한다. 설정의 메일 항목에 자물쇠 아이콘으로 "암호화 저장 켜짐"을 보이고, 끄면 평문으로 되돌리는 동작은 두지 않는다(한 방향).
2차: 사내 서버가 있으면 3으로 올린다.

정직하게 말하면 "누비만 열 수 있음"은 3이 있어야 성립한다. 1과 2만으로는 "같은 PC 같은 계정의 다른 프로그램"은 막지 못하고, 그것은 OS가 제공하는 경계라서 어떤 앱도 혼자서는 넘지 못한다.

## 결정 필요

- 2를 진행할지(복호화 사본 방식, 메일 위키부터).
- 사내 서버 키(3)를 둘 수 있는지.
- 프로젝트 위키를 Git에 올리지 않는 기본값으로 바꿀지.

## 결정 (2026-10-14): 메일만, 2단계 진행

사용자 결정: 메일 자료만 암호화해 관리한다. 프로젝트 위키와 다른 자료는 손대지 않는다. 메일 위키부터 시작한다.

### 설계

- **키**: 실행기가 `connectionVault`(main의 `safeStorage`, Windows DPAPI)에서 `mail-wiki-key`(32바이트)를 읽고, 없으면 만들어 저장한다. 키는 실행기 메모리에만 있다. `safeStorage`를 못 쓰는 PC에서는 암호화를 켜지 못하고 상태에 `unavailable`로 보인다(평문 유지, 한 방향 원칙상 이미 암호화된 페이지는 열 수 없으므로 키 없는 PC에서는 "잠김"으로 표시).
- **저장 형식**: `<wiki>/<이름>.md.enc` = `NWK1` + IV 12바이트 + 태그 16바이트 + AES-256-GCM 암호문. 평문 `.md`는 저장 폴더에 남기지 않는다(기존 평문은 첫 실행 때 암호화하고 지운다).
- **세션 사본**: 실행기가 시작할 때 `<mail>/session-wiki/`를 비우고 다시 만들어(사용자 전용 ACL) `.enc`를 복호화해 둔다. `PersonalMail.wikiRoot`는 이 세션 폴더를 가리키므로 OpenWiki, 위키 화면(`wiki-library`), 검색은 지금과 같은 경로로 읽는다. 저장 레코드의 `row.path`는 파일 이름으로 세션 폴더 아래에서 다시 푼다.
- **쓰기**: 실행기가 페이지를 쓰면 세션 사본과 `.enc`를 함께 쓴다. 위키 화면에서 사용자가 고친 페이지(main의 `wiki-library`가 세션 폴더에 직접 씀)는 실행기가 세션 폴더를 감시(`fs.watch` + 30초 보정)해 다시 암호화한다. 메일 범위의 편집 전 사본(`wiki-revisions`)은 만들지 않는다(평문 유출 경로).
- **정리**: `dispose`(앱 종료, 실행기 재시작)와 다음 시작 때 세션 폴더를 지운다. 비정상 종료로 남은 사본은 다음 시작 때 지워진다.
- **상태와 화면**: `mail.status().encryption = {state:'on'|'unavailable'}`. 메일 설정 '사내 포털 연결됨' 머리글 옆 자물쇠 아이콘(툴팁: "메일 위키 암호화 저장 켜짐" 또는 "이 PC에서는 암호화 저장을 사용할 수 없어요").
- **다음 단계(메일 범위 안)**: 메일 원본(`raw/`)과 첨부 읽기 결과·검색 색인(SQLite)도 같은 키로. 원본은 읽을 때만 복호화하면 되므로 세션 사본이 필요 없다.
