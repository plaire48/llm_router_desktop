# 모션 아틀라스 반영과 끊김 조사

2026-10-23. 첨부한 두 `motion_interaction_atlas.html`과 현재 Desktop 소스를 비교했다. 파일을 실제 Chrome에서 열어 예제를 조작하고 현재 Electron 화면과 대조했다. 첫 파일은 18개, 두 번째는 동일한 18개와 장식용 3D 예제 3개다.

이번 변경은 버튼의 방향성 눌림, 기준점에서 열리는 메뉴, WebGL이 없어도 이어지는 선택 모션을 보완한다. 끊김을 일으킬 수 있는 상태 비교의 불필요한 객체 작성과 유리 렌즈 밖의 굴절 계산도 줄였다. 사용자 Windows의 GPU/드라이버에서 직접 재현한 결과나 Windows 설치판 배포 결과는 아니다.

## 예제와 실제 적용 범위

| 6. 크로스페이드 | 기존 View Transition과 모달 교체를 유지한다. |

| 9. 캡슐 확장 | 기존 유리 선택의 이동 방향 늘어남과 눌림을 재사용한다. 새 독립 캡슐 위젯을 추가하지 않는다. |
| 10. 순차 등장 | 기존 제한된 목록 진입과 공통 stagger 토큰을 유지한다. 승인 폼이나 작업 결과를 순서 효과 때문에 늦게 표시하지 않는다. |
| 11. 고무줄 스크롤 | 기존 native 스크롤을 유지한다. Windows 휠/키보드 스크롤을 별도 물리 엔진으로 가로채지 않는다. |
| 12. 스와이프 동작 | 새 삭제/보관 제스처는 추가하지 않는다. 기존 명시적 작업과 승인을 유지한다. |
| 13. 독 확대 | 읽는 동안 메뉴 전체가 커지거나 다른 항목을 밀어내는 효과는 추가하지 않는다. 기존 선택 렌즈의 작은 hover 반응을 유지한다. |
| 14. 스퀴시 눌림 | **보완:** 기존 균일한 `.98` 축소 대신 공통 X `1.025`/Y `.95` 토큰으로 누르고 spring으로 복귀한다. |
| 15. 슬라이딩 선택 | **보완:** WebGL 부재/손실에도 동일한 spring과 방향성 늘어남을 CSS 선택 배경으로 이어간다. |
| 16. 기준점 메뉴 | **추가:** 실제 버튼 위치를 원점으로 공통 280ms/spring 진입을 적용한다. 자연 크기로 배치해 입장 중 축소된 경계 때문에 메뉴 위치가 틀어지지 않게 한다. |
| 17. 액체 유리 반응 | **최적화:** 기존 shader/색/이동을 유지하고 렌즈 주변만 굴절 계산한다. 정지/비활성 때 루프를 멈추고 180k backing pixel 한도를 유지한다. |
| 18. 시차와 깊이 | 기존 절제된 배경과 레이어를 유지한다. 본문/입력 글자를 포인터에 따라 이동시키지 않는다. |
| 19~21. 3D 형태 변환, soft body, metaball | 예제를 확인했으나 업무 화면에 새 WebGL/SVG 필터/상시 렌더 루프를 추가하지 않는다. 모찌 같은 선택 늘어남은 기존 spring에서 처리한다. |

파란색, 글꼴, 모달 간격, 접근성 이름과 초점은 기존 공통 디자인을 사용한다. 메뉴 이동량 4px와 시작 배율 .96도 중앙 모션 토큰이다. 모션 감소 설정에서는 버튼/선택의 탄성을 제거하고 메뉴는 공통 120ms 불투명도 전환만 적용한다. 강제 색상/투명도 감소 설정은 기존 native 선택 표시를 유지한다.

## 재현한 CPU 부담

상태 스냅샷은 약 1초마다 들어온다. 기존 `mergeSnapshot.js`는 값이 같아 최종적으로 이전 참조를 반환하는 메시지와 출처 객체도 먼저 만들고 속성을 다시 작성했다. 현재 UI 스레드의 이 작업은 다른 애니메이션 프레임을 지연시킬 수 있다.

50개 작업과 각 200개 메시지, 출처/검토 메타데이터를 포함한 26,516,601바이트 합성 자료를 동일하게 사용했다. Chrome CPU 4배 지연에서 각 조건 5회 비교했다. 사용자 실대화의 크기나 Windows 실행 시간을 측정한 것은 아니다.

| 조건 | 변경 전 중앙값 | 변경 후 중앙값 | 바뀌지 않은 중첩 객체의 속성 작성 |
| --- | ---: | ---: | ---: |
| 기본 Metal GPU | 52.3ms | 20.7ms | 120,200회 → 0회 |
| 강제 SwiftShader | 50.3ms | 21.5ms | 120,200회 → 0회 |

첫 실제 차이가 발견될 때만 객체/배열을 만들도록 바꿨다. 그대로인 메시지/출처의 참조, 바뀌기 전 배열 prefix, sparse 배열의 길이/빈 슬롯, `__proto__`라는 own key를 유지한다. 대화 삭제, 내역 축약, 폴링 지연이나 승인 생략으로 얻은 수치가 아니다. 스냅샷 직렬화/전송 및 여전히 필요한 전체 비교 비용까지 없앤 것은 아니다. 공용 모션 검사와 별도로 이 병목을 측정했다.

## 유리 렌즈의 불필요한 GPU 계산

기존 renderer는 작은 렌즈도 전체 rail/tab canvas에 fragment shader를 실행했다. 이전 그림은 전체 clear로 지우고 실제 렌즈의 경계에 12px 여유를 더한 scissor 안에서만 shader를 실행한다. 빈/유효하지 않은/화면 밖의 렌즈는 clear 후 그리지 않는다.

통제한 240×100 캔버스에서 shader 대상은 24,000에서 7,936픽셀로 줄었다. 같은 입력의 변경 전/후 픽셀을 합성 비교했을 때 Metal과 SwiftShader 모두 최대 채널 차이 0이었다. 이 장면의 이동 프레임 P95는 전/후 모두 약 16.7ms였다. 따라서 계산량 감소와 동일한 출력은 확인했지만, 이 장면에서 FPS가 개선됐거나 사용자 Windows가 software GPU였다고 주장하지 않는다.

WebGL이 없거나 context를 잃었을 때는 선택 배경이 즉시 점프하던 기존 경로 대신 같은 spring을 CSS 배경으로 그린다. 매 상태 변경마다 context 생성을 반복하지 않는다. 복구되면 WebGL을 다시 만들고 현재 선택으로 이어간다. 기존 RAF 주사율 적분, 정지 시 종료, 비활성 창/모달 뒤 일시 정지와 글자 비확대 계약은 유지한다.

## 검증 근거

- 관련 단위 검사 36개 통과. 참조 공유, 변경 순서, prototype 키와 sparse 배열 회귀를 추가했다.
- 통제된 아틀라스 검사 12/12 통과. 기본 GPU/강제 SwiftShader, CPU 4배 지연, DPR 1.5, WebGL 부재와 모션 감소를 구분했다. 변경 전 실패 10개와 통과 2개도 `before/result.json`에 남겼다.
- 공통 모션 품질 검사 145/145 통과, 미판정 0. 기존 시간/동시 상호작용 수 제한을 완화하지 않았다. 눌림 기대값만 실제 공통 X/Y 토큰으로 바꿨다.
- 모달 열기/크기 변경/닫기, 사이드바 드래그와 View Transition을 CPU 4배 지연에서 변경 전/후 각각 3회 검사했다. 변경 후 프레임 P95 약 16.8ms, 최대 약 33.4ms이며 50ms 이상 long task, 남은 모달 레이어와 입력 잠금이 없었다. 변경 전에도 이 모달 장면은 통과했다.
- 실제 빌드 Electron에서 모션을 명시적으로 켜고 임시 로컬 프로젝트의 메뉴/탭/설정/재진입/넓은 창/좁은 창을 확인해 17/17 통과했다. 프로젝트 메뉴의 기준점/화면 경계/키보드 초점 복귀를 확인했고, 이동 구간에서 관찰한 18프레임 중 17회 선택 위치가 전진했다. WebGL context 손실 뒤 CSS 선택과 복구도 확인했다. 화면은 실제 제품이며 별도의 optical probe만 합성 줄무늬 fixture다.
- 전체 `npm test`: 2,667개 중 2,466개 통과, 실패 0, 생략 201개. 관련 36개 검사와 중복되는 항목이 있으므로 별도 성적을 더한 총 통과 수로 표시하지 않는다.
- `npm run build:electron`과 `npm run design:check` 통과. 기존 `windows-bash-process.mjs`의 CJS/import.meta 빌드 경고는 이번 모션 변경으로 해결했다고 표시하지 않는다.

실제 모션을 켜자 기존 UI 검사에서 두 오류가 드러났다. 첫 시도는 입장 중인 모달의 변환된 close 버튼 크기를 정적인 정사각형으로 비교했다. 두 번째는 기존 좁은 하단 시트의 `28px 28px 0px 0px`를 일반 모달의 `28px`로 비교했다. 입장 애니메이션 완료 후 치수를 재고 기존 시트 조건일 때만 정확한 시트 반경을 검사하도록 정정했다. 두 실패 로그와 후속 결과를 보존했다. 제품 반경/모션 시간이나 성능 한도를 바꾸어 통과시키지 않았다.

`verify:identity` 첫 실행도 현재 제품에서 제거된 “저장된 메일 연결” 버튼을 찾다 실패했다. 검사를 현재의 `Knox Desktop`, `POP3`, `포털 (외부 브라우저)` 세 선택지의 정확한 값/이름 확인으로 고쳤다. 시각 검사에서 실제 연결을 시도하지 않는다. 초기 로그와 정정 후 실행 로그를 각각 보존한다.

**전체 디자인 게이트는 미통과다.** 정정 후 `test:ui`의 실제 Electron 24개 확인과 `test:skills-ui`는 통과했지만 `test:shared-ui`에서 공통 반투명 그라데이션 아래 글자 5개가 `contrast_unmeasured`로 남았다. 이는 낮은 대비가 입증됐다는 결과도, 대비 통과 결과도 아니다. 이 검사기는 해당 알파 그라데이션을 지원하지 않는다. 예외를 추가하거나 흰 배경이라고 가정해서 통과시키지 않았다. 이후 `test:forms-ui`, `test:mail-ui`, `test:modals-ui`도 순차적으로 실행했으며 각 오래된 fixture 번들의 SVG 로더 누락으로 실행이 중단됐다. 현재 제품의 `hourglass.svg`를 불러오지 못한 검사 설정 오류로 기록하고 해당 UI 과제 전체를 통과로 표시하지 않는다. 이번 수정 범위의 실제 모달/메뉴/모션 검증과 이 전체 게이트의 실패를 구분한다. 최종 원장과 `remaining-identity.json`에 남겼다.

## Windows에서 남은 확인

관찰된 소스의 불필요한 CPU/GPU 작업은 수정했다. Windows에서 사용자가 느낀 끊김이 이 원인만으로 발생했는지, 그 PC의 GPU 가속/드라이버/배율/실제 데이터가 어떤 상태인지는 이 macOS 측정으로 확정할 수 없다. 이번 로컬 Electron의 GPU compositing/WebGL은 enabled였다. 모든 애니메이션이나 하드웨어 가속을 끄는 설정은 추가하지 않았다.

로컬 소스 수정과 Electron 빌드는 이미 설치된 Windows 앱에 자동 반영됐다는 증거가 아니다. 이번 작업은 Windows 설치 파일 제작/설치/업데이트/재실행을 검증하지 않는다. 같은 버전 문자열만으로 설치된 바이트가 같다고 판단하지 않는다. 해당 기기의 실제 빌드와 GPU 상태, 문제 장면의 frame/long task를 확인해야 Windows 체감 해결을 확정할 수 있다.

공식 참고: [web.dev animation performance](https://web.dev/articles/animations-and-performance), [animation rendering guide](https://web.dev/articles/animations-guide), [Electron app GPU status API](https://www.electronjs.org/docs/latest/api/app), [GPUFeatureStatus](https://www.electronjs.org/docs/latest/api/structures/gpu-feature-status/). 레이아웃/페인트를 반복하는 예제 효과를 그대로 붙이지 않고 기존 transform/opacity 및 제한된 렌즈 경로로 적용하는 판단에 사용했다.
