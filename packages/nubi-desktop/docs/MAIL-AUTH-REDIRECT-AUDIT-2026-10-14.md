# 메일 인증과 리다이렉트 구조 점검

> 아래는 수정 전 점검 기록이다. 후속 사용자 결정에 따라 포털 홈 로그인만으로 자동 연결하도록 수정했다. 최종 구조와 검증은 [세션 수정 보고서](MAIL-AUTH-SESSION-FIX-2026-10-14.md)를 따른다. 별도 메일 이동 동작은 최종 구현에서 제외했다.

2026-10-14. 현재 1.2.5 소스와 직전 기능 점검 수정본을 대상으로 한다. 이번 작업은 구조 검토와 재현이며 제품 인증 코드는 변경하지 않았다. 실제 사내 인증 URL, 쿠키, 토큰, 폼 값과 페이지 본문은 수집하지 않았다.

## 결론

동일한 Electron 세션에서 브라우저 SSO를 진행하고 실제 메일 API로 인증을 확인하는 기본 구조는 적절하다. 하지만 로그인 중간 화면을 완료로 추정해 이동시키는 보정과 고정 origin 검사가 인증 전환을 방해할 수 있다. 현재 구현을 다단계 사내 SSO에 대해 검증 완료로 볼 수 없다.

## 실제 구현

1. `mail-portal-contract.cjs`의 기본 진입 주소는 `http://samsung.net/`, 메일 주소는 `http://kor3.samsung.net`이다. 환경변수로 각각 변경할 수 있다. 옛 문서의 HTTPS 직행 설명은 현재 기본값과 다르다.
2. BrowserHost의 인앱 탭에서 로그인한다. 본창, 소유 팝업, 숨은 메일 조회 창은 `persist:nubi-company`를 사용한다. GHES의 회사 로그인 창도 이 partition을 사용하지만, 같은 세션이라는 사실만으로 각 서비스의 인증이 완료되는 것은 아니다.
3. 팝업은 Electron `createWindow`에 WebContents를 반환한다. URL만 가져와 GET으로 다시 여는 방식이 아니므로 기본 POST/opener 흐름을 유지한다.
4. 메일 origin의 페이지에서 고정된 사용자/메일함 API를 POST로 조회한다. `credentials:same-origin`으로 브라우저 세션이 적용되며 쿠키를 추출해서 API 토큰으로 바꾸지 않는다. API fetch에는 `redirect:error`가 적용된다. 로그인 페이지의 브라우저 리다이렉트 허용과 API 리다이렉트 거절은 서로 다른 동작이다.
5. 사용자 정보와 메일함을 얻고 숨은 조회 창에서도 메일함을 확인해야 `portalConnect` 후 연결 완료가 된다. 폴링 간격은 요청 종료 후 2초, 로그인 대기는 5분, 각 API 요청 제한은 30초다.

## 확인한 결함과 위험

### P1: 중간 페이지를 완료로 추정해 강제 이동

`mail-portal.cjs:83`의 `advanceLoginTab`은 회사 도메인의 페이지에 비밀번호/OTP 입력칸이 없고 URL에 몇 가지 로그인 단어가 없으면 메일 origin으로 `loadURL`을 호출한다. `/bridge`처럼 인증 내용을 자동 제출하거나 리다이렉트를 기다리는 화면도 이 조건에 해당한다.

재현에서 중간 페이지가 메일로 이동됐다. 또한 로딩 중인 SSO 자식 창을 후보 목록에서 제외한 뒤 부모 창을 이동시켰다. 현재 인증 중인 팝업을 기다리는 계약이 없다. 이 동작이 사내 404의 원인이라고 확정할 수는 없지만 다단계 흐름을 끊을 수 있는 앱 측 동작은 확인됐다.

### P1: HTTPS 전환을 로그인 실패로 취급할 수 있음

`mail-portal.cjs:32`, `:57`, `:70` 및 `mail-portal-contract.cjs:17`은 origin을 문자열로 일치시킨다. 기본값 HTTP에서 같은 호스트 HTTPS로 전환해도 숨은 창은 이동을 차단하고, 화면에 정상 열린 HTTPS 메일 페이지도 읽기 대상으로 인정하지 않는다. 단순히 화면 리다이렉트만 허용해도 해결되지 않으며 조회 스크립트의 origin도 일치해야 한다.

모의 이벤트로 HTTP→HTTPS 차단을 재현했다. 실제 회사 서버가 해당 전환을 하는지는 사내 환경에서 확인해야 한다. HTTPS 기본값 변경이나 임의 호스트 허용은 이번 점검에서 하지 않았다.

### P2: 인증 전에 숨은 창이 메일 접속을 시작

`read`의 fallback은 `readBackground`를 호출하고 인증 중에도 메일 origin을 로드한다. 재현에서 SSO 팝업이 로딩 중일 때 숨은 창의 메일 로드가 발생했다. origin 밖 이동은 차단되지만 서버 요청 자체는 발생한다. 로그인 복귀 정보를 서버 세션에 기록하는 SSO라면 두 흐름이 경쟁할 가능성이 있다. 경쟁으로 서버 상태가 손상되는지는 미검증이다.

이는 같은 파일의 ‘인증 성공 이후 배경 문서 시작’ 주석보다 넓게 실행된다. 6초 제한은 해당 시도를 제한할 뿐 완료 확인을 대신하지 않는다.

## 실제 실행한 검사

- [다중 리다이렉트 재현 코드](../verification/mail-auth-structure-2026-10-14/multi-redirect.mjs): 격리된 Electron에서 302 진입 전환, 팝업 POST, 307/308 POST 유지, 303 GET 복귀, opener 복귀, 메일 API 검증과 소유 탭 정리 통과. [결과](../verification/mail-auth-structure-2026-10-14/multi-redirect.log)
- [구조 재현 코드](../verification/mail-auth-structure-2026-10-14/structural-repro.mjs): 실제 MailPortal 메서드에 합성 WebContents를 연결해 중간 페이지 강제 이동, 팝업 로딩 중 부모 이동, 인증 전 배경 로드, HTTPS upgrade 차단을 확인했다. [결과](../verification/mail-auth-structure-2026-10-14/structural-repro.json)
- 성공 모의 서버의 인증 여부는 합성 상태다. 실제 쿠키 정책, 사내 SSO, Windows 11 설치판 성공을 입증하지 않는다.
- 직전 전체 단위 검사 통과는 이 중간 전환 문제의 부재를 입증하지 않는다. 이번에는 제품 코드를 변경하지 않았으므로 전체 검사와 설치 빌드를 반복하지 않았다.

## 수정 설계

1. 로그인 준비, 사용자 인증 중, 메일 세션 확인, 연결 완료를 명시적인 상태로 나눈다. 비밀번호 필드 부재를 인증 완료 근거로 사용하지 않는다.
2. 로그인 중인 본창/팝업/자동 POST가 소유한 흐름을 기다린다. 중간 페이지를 강제로 navigate하지 않는다. 실제 메일 페이지 도착 또는 확인 가능한 포털 로그인 완료 신호 이후에 메일 세션 확인을 시작한다. 회사 홈의 실제 완료 신호는 사내 환경에서 확인해야 한다. 신호가 없으면 추측 이동 대신 사용자가 완료 후 메일로 이동하는 명시적 동작을 제공한다.
3. 인증 전 숨은 창의 반복 메일 진입을 중지한다. 앱 시작 시 저장된 세션 복원과 사용자가 시작한 로그인 흐름이 겹치지 않도록 직렬화한다.
4. 허용된 메일 호스트의 HTTP→HTTPS upgrade를 처리하고 확인된 최종 origin을 API 검사에 같이 적용한다. HTTPS→HTTP downgrade나 임의 호스트로 조회 대상을 확대하지 않는다. 공개 TLS 검증 해제는 필요하지 않다.
5. 실환경 진단에는 경과 시간, 고정 단계, 본창/팝업, 리다이렉트 횟수, HTTP 상태/고정 오류만 남긴다. 원문 URL/쿼리/hash, 쿠키/헤더, POST body와 페이지 본문은 기록하지 않는다. 이 진단은 아직 제품에 추가하지 않았다.

## 공식 계약 대조

- [Electron WebContents](https://www.electronjs.org/docs/latest/api/web-contents): `createWindow`와 탐색/리다이렉트 이벤트. 현재 팝업 방식은 이 기본 계약과 일치하며, 취소 이벤트는 후속 탐색을 막는다.
- [Electron Session](https://www.electronjs.org/docs/latest/api/session): 동일한 `persist:` partition은 앱 내부 페이지가 지속 세션을 공유한다. 외부 Chrome/Edge/삼성 브라우저 로그인 저장소 공유를 뜻하지 않는다.

공식 브라우저/세션 경로를 유지하는 것이 적합하며 쿠키 복사, POST 재생성, 인증 우회 라이브러리는 필요하지 않다.
