# Common mail intake settings

The first intake from POP3, the portal, Knox Desktop or an exported-mail folder asks which mail to collect and where to store it. The shared dialog is also available from mail settings before or after connecting. It contains a date range, included mailboxes, optional sender/domain and subject conditions, exclusions, original-file retention, and separate original/Wiki folder choices. The chosen configuration persists; background checks do not repeatedly prompt. Cancelling the dialog or the native folder picker does not confirm it or start the pending intake action.

Every adapter applies the same validated collection policy before storing a message or queuing Wiki work. Exclusions take priority. Sender matching uses actual parsed addresses and exact domains, not partial domain-name matches. Multiple choices within a field use OR; different fields use AND. A date restriction excludes missing dates instead of inventing them. POP3 can authenticate without retrieving message bodies while the first configuration is pending. Portal collection and UIA snapshots also wait for configuration. UIA still covers only the open message and available metadata, not a complete mailbox, original MIME or unread attachments. POP3 can require reading a message to evaluate its collection conditions; excluding a message means it is not retained or sent for Wiki generation, not a promise of server-side filtering.

Excluded UIDs are separate policy-bound records, not successful download or processing receipts. The current policy suppresses repeat downloads; changing it makes excluded messages eligible for review again. File imports show an exclusion count separately from additions, duplicates and errors and do not create a successful file receipt for an excluded source. Existing messages, Wiki pages and user labels are retained when the rules change.

With original retention off, MIME is reconstructed as a derived body copy even when there are no attachments. The encrypted body copy is stored as `body.eml.enc`, with the original hash retained as provenance. Original MIME and ordinary attachment payloads are not stored. The encrypted manifest preserves body and extracted attachment evidence; inline body images remain readable for rendering and Wiki vision. Source readback, search signatures, body-data image reads and export use the corresponding source payload. The reader labels/downloads the result as a body copy, never an original. Existing source records are not rewritten. Knox Desktop's UIA body record remains an observation, never an original EML.

Raw storage uses the existing verified migration. Wiki selection moves the encrypted at-rest page store while keeping the decrypted working-session path stable, preserving source receipts, open pages and user edits. Files are copied and hash-checked before the stored pointer changes; source directories, symlinks, nested roots, a non-empty destination and changed files are rejected. The temporary Wiki session cannot contain the original store. Cleanup follows pointer commit; failures preserve data. The two location moves are individually committed, so an already-completed raw move can remain if the subsequent Wiki move fails. The intake policy is confirmed only after requested setup succeeds. Active ingestion or Wiki writes prevent a competing location change. Folder choices remain drafts until Save.

Settings saving uses the existing background task flow and actual migration quantities. A manually opened settings panel closes after a successful save and can be opened again from its toolbar entry. Failed saves retain the draft. The normal pending connection/import action continues only after confirmation. The source retains the previous storage component for compatibility; current Workbench and mail settings use `MailIntakeSetup`.

Verification evidence is under ignored `verification/mail-intake/` and `verification/desktop-mail-uia-2026-10-23/`. Pure policy and local adapter/storage tests cover first-run gates, exclusions, policy changes, encrypted body copies, CID/data images, search/readback, import counts, Wiki migration, failure preservation and reopen. Production-component browser checks cover four entry methods, cancellation, failed-save drafts and continuation, along with the previous Desktop window-selection and storage flows. Native Electron validation uses an isolated storage root and `OPENWIKI_CONFIG_DIR`, actual configuration/storage/migration, parser/folder intake and app restart; only native folder choices are injected. The initial native attempt mixed a temporary connection vault with the default Wiki location and was correctly blocked by the missing-key guard; subsequent validation isolates both locations. Early native assertions also treated an asynchronous status predicate as completion and were replaced by explicit condition polling. These local checks do not establish connected company POP3/SSO, physical Windows UIA/Office/NASCA, installer delivery or real-model quality.

Final local results: all 352 mail tests passed with no skips, the browser gate passed 10 scenes, the built macOS Electron check passed four scenarios, and the Electron build and design identity check passed. The newly added CID/data-image fixture initially used invalid image bytes; it was replaced with the existing valid one-pixel PNG fixture. The native check also caught the need to close the hidden parent settings panel after a successful manual save so its toolbar entry can open it again.
