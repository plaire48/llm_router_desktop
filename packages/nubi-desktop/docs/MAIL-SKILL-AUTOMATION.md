# 메일 자동화와 스킬 실행 준비

2026-10-01 사용자 방향을 반영한 구현 설계. 현재 구현과 후속 실행기를 구분한다.

## 사용자 흐름

1. 사내 메일을 연결한다. `개인 Wiki 자동 정리`를 ON/OFF한다. OFF여도 메일과 첨부 원본은 수집하며 모델로 보내지 않는다. 자동 수집 자체는 연결 관리에서 멈춘다.
2. ZIP 또는 폴더로 스킬을 등록한다. 후속 채팅/드롭 입력도 같은 등록기에 연결한다. 사용자 요청 “이 ZIP을 스킬로 등록해 줘”와 실제 첨부 식별자를 사용한다. 모델이 임의 경로나 다운로드 주소를 만들어 등록하지 않는다.
3. “변경 요청 메일이 오면 변경 검토 스킬을 실행해 줘”라고 요청한다. 누비는 조건, 대상 Workspace, 선택 스킬과 버전, 사용할 모델, 실행/승인 범위를 한 카드에 보여준다. 등록과 자동화 활성화는 다른 상태다.
4. 새 메일 이벤트가 조건과 맞으면 작업을 만든다. 스킬 시작 준비를 거친 뒤 기존 Pi 하네스에서 진행한다. 설치/명령/반영 승인과 결과 검증은 기존 호스트 계약을 유지한다.

현재 채팅/드롭 등록과 자동화 카드, 메일의 스킬 자동 실행은 후속 범위다. ON/OFF 및 기존 ZIP/폴더 등록을 이 기능들의 완료로 표시하지 않는다.

## 공식 방법론과 실제 선택

- [OpenAI Skills](https://learn.chatgpt.com/docs/build-skills): SKILL.md와 scripts/references/assets, description 기반 암시적 선택과 사용자 명시적 선택, 필요한 내용만 읽는 progressive disclosure를 적용한다. 공식 앱 자체의 등록 UI나 Codex 런타임을 누비에 포함하는 기능은 아니다.
- [Anthropic Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills): 지침/리소스/코드의 전체 패키지, 필요 시 코드 실행, 대표 과제부터 평가하고 개선하는 방식을 적용한다.
- [Agent Skills 규격](https://agentskills.io/specification): compatibility는 환경 요구사항 설명이며 scripts는 의존성을 명시하거나 독립 실행 가능해야 한다. 필수 공통 설치 manifest나 자동 설치 명령은 정의하지 않는다. 외부 스킬에 누비 전용 manifest를 강제하지 않는다.
- [Anthropic Effective Agents](https://www.anthropic.com/engineering/building-effective-agents): 이벤트 전달/중복 방지/환경 준비는 코드로 제어하고, 메일 의미 분류와 업무 수행은 모델과 도구 결과에 연결한다. 이미 검증한 Pi 실행기와 SQLite/프로세스 기록을 재사용한다.
- 기존 yauzl/YAML/MiniSearch 등록/선택과 호스트 실행 준비를 재사용한다. 새 에이전트 프레임워크나 원격 스킬 서버를 추가하지 않는다. skills-ref는 형식 검증의 참고 후보이며 실행 환경 준비를 제공하지 않으므로 런타임 의존성으로 도입하지 않는다. 공식 구현을 그대로 복제한다고 표현하지 않는다.

## 스킬은 폴더 전체

SKILL.md, 실행 스크립트, 참조 문서, 이미지/템플릿/바이너리와 package.json/lockfile/requirements 등 추가 파일을 함께 보관한다. 구조와 바이트를 유지하고 상대 경로는 스킬 루트를 기준으로 해석한다. 등록 시 전체 파일 해시를 확인하고 변경된 동일 이름은 덮어쓰지 않는다. 현재 등록기의 경로/링크/크기/항목 수 제한은 유지한다.

이름과 설명만 먼저 발견하고 활성화하면 지침, 실행 시 필요한 스크립트와 자료만 읽는다. 모든 바이너리 자료를 텍스트 프롬프트에 넣지 않는다. 스킬 본문, 스크립트, 데이터 의존성의 버전이 서로 다른 채로 실행하지 않는다.

## 시작할 때 환경 준비

공통 시작 단계는 `선택 → 필요한 파일 읽기 → 환경 검사 → 준비/승인 → 실제 설치 확인 → 실행/승인 → 결과 검사`다. 현재 실행기는 compatibility를 활성화 응답에 보존하고 이 단계로 연결하도록 안내한다. 전용 prepare_skill과 환경 캐시는 후속 구현이다.

- compatibility, SKILL.md의 실행/설치 지침, README와 실제 manifest/lockfile을 근거로 계획한다. setup.ps1/setup.sh라는 이름이 있다는 이유만으로 실행하지 않으며 모델이 누락한 의존성을 설치 완료로 추정하지 않는다.
- Windows에서는 `.ps1`을 PowerShell 프로필로 실행한다. 현재 호스트의 Windows PowerShell 5.1과 PowerShell 7을 구분한다. `.sh`는 설치된 Bash 프로필을 검사한다. Bash를 찾지 못하면 준비 상태로 남기고 설치 제안을 만들며 스크립트를 자동 변환하거나 WSL로 우회하지 않는다.
- Python/Node 프로그램은 필요한 버전과 라이브러리를 확인한다. 다른 호스트의 번들 런타임이 있다고 Workspace에도 있다고 추정하지 않는다. 새 전용 실행기는 누비가 제공하는 검증된 런타임을 우선 사용하고 스킬 의존성을 스킬별 환경에 둔다.
- 환경 캐시 키는 전체 스킬 패키지/설치 입력 해시, OS/아키텍처, 실제 런타임 버전이다. 캐시 영수증만 믿지 않고 사용 직전 런타임과 의존성을 재검사한다. 맞는 환경은 재사용하고 변경 시 새 환경을 준비한다. 등록 원본 폴더와 사용자의 전역 Python/Node 환경을 설치 대상으로 사용하지 않는다.
- 공통 상태는 `등록됨`, `준비 필요`, `설치 승인 대기`, `준비됨`, `실행 중`, `결과 확인 필요`, `완료`다. 설치 종료 코드 0을 업무 완료로 표시하지 않는다. 사용자가 취소한 설치/실행은 자동 재개하지 않는다.
- 정확한 설치 명령, 셸, 작업 폴더, 다운로드/설치 후크/변경 범위와 확인 방법을 기존 propose_setup_action 승인 카드에 연결한다. 현재 승인은 한 명령이며 한번 준비 승인이 향후 모든 스크립트/전역 설치 승인이 되지 않는다. 환경 재사용은 승인 확대와 별개다.
- 진행 상태/영수증/실제 출력은 SQLite 프로세스 하네스에 기록한다. 설치나 쓰기 결과가 미확정이면 실제 환경과 기록을 대조하며 같은 명령을 맹목 재전송하지 않는다. 실패는 원인을 모델에 반환하고 수정 명령을 기존 승인으로 연결한다.

## 채팅 등록과 드래그 앤 드롭

입력 경로는 달라도 한 등록 서비스를 사용한다. 호스트가 선택 파일/첨부의 실제 소유권과 Workspace를 고정한 attachmentId를 발급하고, 등록 요청은 그 식별자만 받는다. 브라우저 드롭의 File.path를 추정하지 않는다. bounded bytes와 상대 경로를 전달하고 호스트는 기존 ZIP/폴더 검증을 그대로 적용한다. 미지원 폴더 드롭은 실제 폴더 선택기로 이어간다.

채팅으로 새 스킬을 만들어 달라는 요청은 필요한 입력/출력, 언제 쓸지, 준비/실행 절차를 기존 질문 폼으로 확인하고 패키지 초안을 만든다. 자연어만 받은 상황을 이미 등록된 파일로 표시하지 않는다. 기존 동일 이름의 충돌은 보존하고 구체적인 교체안을 별도로 검토한다. 메일 첨부가 스킬 형태라는 이유만으로 등록/활성화하지 않는다.

## 메일 이벤트와 실행 연결

자동화는 지속적인 새 메일 수집과 별도 설정이다. 원본 수집 완료 `mail.ingested`와 개인 Wiki 저장 완료 `wiki.saved` 중 조건에 맞는 이벤트를 명시적으로 선택한다. 기본은 원본 수집 완료다. Wiki OFF가 메일 업무까지 묵시적으로 끄지 않는다. Wiki 갱신을 요구한 자동화는 저장 성공 이벤트만 받는다.

규칙은 대상 Workspace, 조건, 선택 스킬 경로/패키지 해시, 이벤트 종류, 모델 목적지, 활성 여부와 버전을 보존한다. 개인 메일을 어느 프로젝트에 쓸지 자동 추정하지 않는다. 모델 의미 분류는 현재 조건과 소스 ID에 대한 run/hold/unrelated를 구조화하고 호스트가 검증한다. 스킬 description의 일반 자동 선택과 사용자가 등록한 메일 조건은 구분한다.

`eventId + ruleVersion + sourceHash + skillPackageHash`로 작업 생성/재수신을 중복 방지한다. 대기/실행/질문/승인/중단/미확정과 실제 결과 영수증을 기록하며 Wiki 재정리로 같은 스킬을 반복 실행하지 않는다. 스킬이 바뀌면 기존 규칙을 다시 검토한다. 호스트 실행 중이면 큐에서 기다리며 기존 Workspace 동시 실행 제한을 우회하지 않는다.

원래 사용자 규칙이 업무 지시이며, 메일과 첨부는 출처를 가진 입력 자료다. 이메일 안의 명령, 과거 승인과 allowed-tools를 설치/쓰기/발송 승인으로 사용하지 않는다. 추론 목적지가 바뀌면 현재 개인 메일 연결처럼 다시 확인한다. 단순 작업 종료나 모델의 완료 선언이 실제 파일/업무 성공이 아니다. A2A 첨부 협업은 사용자 추가 요청으로 MAIL-DOCUMENT-COLLABORATION.md의 필수 구현 범위에 포함했다. 현재 비활성 경로와 실제 구현 완료를 구분한다. SMTP 발송은 별도 범위다.

## 단계별 완료 기준

1. 개인 Wiki ON/OFF: OFF 중 원본 수집과 모델 미호출, 앱/화면 재진입 설정 보존, ON 시 대기열 처리와 중복 방지. 현재 구현됨.
2. 스킬 시작 준비: 전체 파일 등록/활성화와 compatibility 전달은 구현됨. 기존 환경 조회/실행 제안은 재사용 가능. 전용 환경 생성/캐시/재검사와 Bash/PowerShell 실제 호스트 검증은 후속 범위.
3. 채팅/드롭: 기존 등록기 연결, 실제 바이트 저장/readback, 화면 재진입, 충돌/취소/응답 유실을 검증한다.
4. 메일 트리거: 조건 일치/불일치/보류, Wiki OFF, 스킬/모델 변경, 중복 수신, 설치 필요, 승인 거절/취소, 호스트 재시작/미확정 실행과 사용자 편집을 검증한다.
5. 대표 스킬 과제로 실모델 선택/준비/실행/결과 품질을 따로 평가한다. 합성 이벤트/모델과 Chrome 검사를 사내 서버/Windows/Bash/PowerShell 실서비스 성공으로 표시하지 않는다.
