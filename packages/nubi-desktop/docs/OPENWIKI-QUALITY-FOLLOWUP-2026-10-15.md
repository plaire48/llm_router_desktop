# OpenWiki 후속 개선과 재평가

## 변경 범위

생성 문서의 과장, 과거 메일을 현재 상태로 읽는 문제, 반복 설명과 조회 지연을 대상으로 수정했다. 원문, 평가 문제와 정답, 승인 계약은 바꾸지 않았다. 기존 사용자 편집과 다른 세션의 변경도 유지했다.

- Code 문서 작성 시 구현의 실제 조건과 예외를 확인한다. 몇 개의 테스트, 정수 입력 검사, 일반적인 상태 이름만 보고 모든 입력에서 안전하다고 쓰지 않도록 했다. 읽은 테스트와 실행한 테스트, 실제 검증과 권장 사항도 구분한다.
- Personal 문서 작성 시 원문의 시점, 효력 발생일과 수집일을 구분한다. 과거의 대기 상태를 오늘의 대기로 옮겨 적지 않고, 상충하는 결정과 정정 근거를 보존한다.
- 답변과 최종 검토에 같은 시점 구분을 적용한다. 상태를 말하는 첫 문장에 근거 범위를 밝힌다. 정보 부재를 사실 부재로 바꾸거나 필요조건을 충분조건으로 바꾸는 것도 검토한다.
- 명시적인 `/code`, `/mail` 조회는 짧은 전용 지침을 사용한다. 불필요한 편집·화면 조작 안내를 제거하고, 알려진 독립 자료는 함께 읽는다. 간단한 사실 조회는 먼저 검색하고, 해결되지 않는 종합 질문에서 OpenWiki에 위임한다.
- 조회 답변은 결론, 결정적인 조건과 출처를 우선한다. 같은 사실을 인용문과 목록으로 반복하거나 Wiki 노트 상태를 덧붙이지 않도록 했다. 상세 요구사항, 중요한 불확실성과 출처는 남긴다. 화면에서 답변을 잘라 버리는 방식은 사용하지 않았다.

## 검증 방법

동일한 40문항(Code 20, Personal 20), 원문과 채점기를 유지한다. Claude Code의 Claude Opus 5.5, medium으로 실제 Desktop 계획·검색·읽기·검토 경로를 실행한다. 회사 자료 대신 기존 합성 자료를 쓴다.

최종 재평가는 문항별 1회다. 이전 기준선의 첫 번째 실행과 짝지어 비교하며, 과거 3회 반복 성적 전체와 혼합하지 않는다. 자동 키워드·출처 검사와 사람이 읽은 의미 검토를 분리한다. 생성 품질은 같은 11개 소스의 폴더 위키를 다시 생성하고 직접 대조한다.

제공자에 두 답변 평가와 문서 생성이 함께 요청된다. 관측된 지연 변화는 비교 자료이며, 모든 부하에서 같은 비율로 빨라진다는 보장은 아니다. 원시 기록은 `verification/openwiki-quality-followup-2026-10-15/`에 보관한다. `pilot-*`와 `final-a/b`는 이전 후보의 진단 기록이며 최종 40문항 결과에 합산하지 않는다.

## 관련 자동 검사

런타임·메일·위키·검토·Claude 회귀 검사 177개, OpenWiki 생성/메일 요약 검사 8개가 통과했다. 런타임 빌드도 통과했다. 이 검사는 실모델 답변의 의미 정확도나 Windows 설치판 성공을 대신하지 않는다.

## 최종 측정

Claude Opus 5.5 medium으로 같은 40문항을 각각 1회 완료했다. 비교 대상도 이전 첫 번째 실행 40건으로 고정했다. 표시 문자 수는 출처 링크의 긴 내부 주소를 제외하고 링크 이름을 남긴 값이다.

| 지표 | 이전 | 개선 후 |
| --- | ---: | ---: |
| 답변 전달 | 40/40 | 40/40 |
| 결정적 원문 출처 포함 | 40/40 | 40/40 |
| 평균 표시 문자 수 | 487자 | 195자 |
| 응답 시간 중앙값 | 42.3초 | 32.9초 |
| 응답 시간 95백분위 | 57.4초 | 47.0초 |
| 평균 모델 호출 | 5.03회 | 4.17회 |
| 자동 키워드 포함 검사 | 38/40 | 36/40 |

답변은 평균 60% 짧아졌고 중앙값은 관측상 22% 감소했다. 원본 변경이나 실행 행동은 40건 모두 없었다. 자동 검사는 악화됐으므로 그대로 남겼다. 실패 4건은 `code-05`의 “자동으로 넘어가지 않습니다”, `code-14`의 “판단할 수 없습니다”, `personal-09`의 “오전 1:00”, `personal-12`의 상충 설명이 채점기의 특정 표현과 일치하지 않은 경우다. 정답/키워드를 바꾸거나 수동 판단을 자동 통과로 덮어쓰지 않았다.

구현 담당자가 원문과 답변을 모두 읽은 의미 검토에서는 39건의 핵심 결론이 근거와 맞았다. `personal-12`는 상충과 권한 미확인을 보존했으나, 의미가 명시되지 않은 본문 시각을 “결정 시각”으로 해석해 제한 판정을 남겼다. 이는 독립 블라인드 평가나 일반 정확도 97.5%를 뜻하지 않는다. 일부 답변은 3문장을 넘거나 불필요한 구현 미확인 설명을 덧붙였다. `personal-20`은 담당자 미확인 결론보다 메일 메타정보가 먼저 나왔다. 간결성과 두괄식이 모든 답변에서 완벽해졌다고 평가하지 않는다.

## 같은 폴더의 위키 재생성

원본 11개 파일과 corpus hash를 유지했다. 생성 결과는 12페이지에서 14페이지로, 주장 기록은 75개로 생성됐다. 생성 원문을 사람이 수정하지 않았다.

- 할인 계산 문서가 이제 안전 정수 범위를 검사하지 않고 큰 중간 연산에서 반올림될 수 있음을 명시한다. 같은 반례를 실행해 실제 결과 8376695306908210과 정확한 정수 계산 8376695306908200의 차이를 재확인했다.
- 상태 전이 문서가 이제 `toString` 같은 상속 속성에서 `TypeError`가 발생함을 명시한다. 같은 호출을 실행해 확인했다.
- 따라서 앞서 발견한 두 과장 표현은 개선됐다. 모든 생성 주장 75개를 완전 검증했다는 뜻은 아니다.
- 생성 시간은 611.2초에서 721.9초로 늘었다. 호출도 38회에서 46회로 늘었다. 페이지 수와 동시 부하가 달라 원인별 기여는 확정하지 않았다. 조회 응답 속도와 달리 생성 속도는 개선되지 않았다.
- quickstart의 Mermaid가 텍스트 코드 블록으로 내려가는 표시 문제가 남았다. 생성 자료를 손으로 고쳐 성공 처리하지 않았다.

근거: `generation-folder/report.json`, `generation-folder/content-audit.json`, `generation-folder/corpus/`.

## 추가로 발견한 Personal 요약 문제

같은 Personal 02/03/12의 원문을 사용한 별도 요약 검사에서, 원문에 없는 확인 작업과 위키 파일 정리 작업을 생성하고 설명되지 않은 날짜를 결정 시각으로 해석하는 문제가 나왔다. 이 검사는 40문항의 검색/답변 검사와 별개다.

원인은 개별 메일의 불변 요약에도 여러 자료를 종합해 canonical 파일을 관리하는 전체 지침이 들어가 있었던 것이다. 공유 근거 규칙을 분리하고 개별 요약에서는 명시된 요청만 actionItems에 남기도록 했다. 조건부 승인 기록을 배포 행동으로 바꾸지 않고, 빈 목록을 허용하며, 현재 상태가 미확인이라는 사실을 승인되지 않았다는 뜻으로 바꾸지 않도록 보완했다. 첫 요약부터 근거 시점과 불확실성을 보존하도록 했다. 전체 canonical 위키의 기존 파일 관리 기능은 유지한다.

40문항과 Code 재생성은 후보 `113b5cdd643994b8fa6cae4314a428b7637111ebc39653e9188d015929220416`에서 수행했다. 이후 변경은 Personal 생성 지침과 그 검사에 한정된다. 최종 후보와 별도 요약 재검사는 `personal-synthesis.json`에 기록하며, 마지막 변경이 포함된 상태에서 40문항 전체를 다시 수행했다고 표시하지 않는다.

최종 Personal 후보는 `6bead3db7ead209a428638c4c07620d52771ebed9c8cebfb0983af6530a4386c`다. 같은 세 요약 입력을 2회씩 실행했다. 6건 모두 첫 요약에서 원문 시점과 최종 결정 미확인을 보존했고, 원문에 없는 후속 작업은 생성하지 않았다. 조건부 승인에는 actionItems가 비었고, 지급 승인 요청에는 그 요청만 남았다. 다만 상충 사례의 한 사실 항목은 여전히 “아직 해소되지 않았다”의 범위를 명시하지 않아 제한 판정이다. 첫 요약의 개선을 전체 사실 목록의 완전한 정확성으로 확대하지 않는다. 관련 OpenWiki 검사 9개와 런타임 빌드가 통과했다. 원시 결과와 수동 판정은 `personal-synthesis.json`, `personal-synthesis-review.json`에 보관했다.

## 검증 범위와 남은 일

실제 Claude Code와 Desktop 하네스를 사용했지만 자료는 합성 자료다. 회사 메일, Windows 설치판, 다른 모델과 반복 안정성 전체를 검증하지 않았다. 조회 답변 품질은 좋아졌지만 상충 시각 해석과 불필요한 문장의 잔여 사례, 생성 속도와 Mermaid 표시 문제는 후속 대상으로 남는다. 배포나 Windows 설치 파일 생성은 이번 작업에서 수행하지 않았다.

## 버전별 컷신 확인

현재 `ui/CinematicIntro.jsx`는 `nubi-opening-scene-v1`에 본 버전을 기록한다. 실제 패키지 버전이 달라진 뒤 첫 실행에서 전체 컷신을 재생하고, 같은 버전의 다음 실행은 로고와 진행 표시만 보여준다. 같은 버전 재설치에서 사용자 데이터가 유지되면 전체 컷신을 반복하지 않는다. 클릭/키 입력으로 건너뛸 수 있으며 시스템 모션 감소 설정에서는 생략한다. 현재 소스 확인이며, 배포된 Windows 설치판에 반영됐는지는 별도 검증하지 않았다.
