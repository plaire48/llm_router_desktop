# AI Workspace와 메일 기능 점검

2026-10-14. 최신 Claude 수정본을 기준으로 점검하고 재현된 연결 문제를 수정했다. 사내 실서비스 성공이나 Windows 11 설치판 검증으로 표시하지 않는다.

## 기준과 결론

- 기준: 1.2.5, `5810c1c11ae326a936c962b666831c06d398b7d8`, Windows 빌드 `38560111691`.
- GitHub의 가장 최근 빌드는 초안이다. 먼저 공개된 같은 번호 설치판을 기준으로 삼지 않았다.
- 최신 커밋과 최종 번들 입력을 Git blob 해시로 대조했다. 기존 입력 679개가 동일하며 아래 수정 파일 7개와 새 중계 모듈 2개만 달라졌다. Claude의 다른 변경은 유지했다.
- 로그인 취소, 오래된 요청의 결과 처리, 빈 성공 응답, 파일 앱 진입과 전송 크기에 실제 결함이 있었다. 이번 소스에서 수정했고 재현 검사와 화면 검사를 추가했다.
- **로컬 기능 회귀 통과와 사내 실계정 검증은 별개다.** 실제 mySingle 404의 원인이 해결됐다고 단정하거나 배포 승인으로 표시하지 않는다. 이번 작업에서는 Windows 릴리즈를 만들거나 게시하지 않았다.

## 재현과 수정

| 문제 | 재현 결과 | 수정 |
|---|---|---|
| 메일 로그인 탭을 닫으면 다시 연결 불가 | `mail_cancelled` 후 `connecting:true`, 다음 시도 `mail_busy` | 탭 닫기를 실제 취소로 연결하고 연결 중 상태를 해제. 이전 시도의 뒤늦은 종료가 새 로그인 탭을 닫지 않도록 세대를 검사 |
| 예전 메일 연결이 새 연결을 훼손 | 예전 목록 요청의 인증 오류가 새 연결에도 disconnect 호출. 늦은 폴더 목록도 새 상태를 덮음 | 폴더/본문 수집/결재의 비동기 경계에서 연결 세대 검사. 오래된 실패는 새 상태나 worker를 변경하지 않음 |
| Talk 좋아요 취소/댓글 삭제의 성공이 오류로 표시 | `204` 응답을 `new Response(Uint8Array(0))`로 재구성하면 예외 | 본문 없는 204/205/304는 null body. 실제 Talk 클라이언트의 좋아요 취소와 readback 검사 추가 |
| AI Workspace 로그아웃 뒤 이전 응답 도착 | 중계가 계정 변경을 검사하지 않고 오래된 응답을 반환 | 같은 계정 세대에서만 요청/헤더/본문 결과를 반환. 로그아웃의 AbortController 연결. 기존 2분 자격 확인 캐시 유지 |
| 파일 앱을 누르면 열리지 않음 | 설치판의 `app://...#workspace/site=...`는 웹 URL 열기에서 거절. 별도 경로에도 `#workspace#workspace/site=...` 중복 | 내장 앱 목록을 native `openWorkspaceApp`으로 연결. 기존 hash를 정확히 교체. 실패 안내와 재시도 유지 |
| GitHub 요청의 redirect 계약 불일치 | 클라이언트는 `redirect:error`를 요청하지만 호스트는 follow로 변경 | 클라이언트의 error/manual 계약 유지 |
| 50MB 이하 파일 앱도 저장 실패 | 원본 19MiB → 요청 26,564,062 bytes. 이전 24MiB 제한에 걸려 `ghes_body_limit`, 네트워크 호출 전 실패 | 파일 앱의 중첩 Base64 표현을 반영한 96MiB 한도를 Git blob/사이트 문서 경로에 한정. 일반 API의 기존 제한 유지. localhost 페이지 중계도 동일 기준 적용 |
| 숫자 ID로 사용자 조회 불가 | 포팅된 관리자 클라이언트의 `/api/v3/user/<id>`가 중계 허용 경로에서 누락 | 해당 고정 사용자 조회 경로 허용. 다른 저장소/호스트 거절 유지 |
| 포털 로그인 검사가 이전 구조를 검사 | 예전 메일 전용 세션과 실제 회사 주소를 가정 | 현재 company 세션과 설정 가능한 진입 URL로 모의 검사 갱신. 모든 테스트 주소는 example.invalid, POST/opener와 소유 탭 정리 확인 |

큰 파일 지원은 원본 50MiB와 2,000개 경로의 중첩 인코딩 상한 계산, 19MiB 업로드 요청 및 24MiB 초과 응답의 localhost 중계로 확인했다. 실제 50MiB 파일을 사내 GitHub에 업로드한 결과나 회사 PC의 메모리/지연 측정은 아니다. 무제한 전송이나 TLS 검증 해제는 적용하지 않았다.

## 검사 결과

최종 수치는 [results.json](../verification/workspace-mail-audit-2026-10-14/results.json)과 같은 폴더의 원본 로그를 참조한다.

- 전체 단위 검사: 총 1,238개 중 1,042 통과, 실패 0, 건너뜀 196. 건너뛴 검사는 통과 수에 포함하지 않았다.
- 최종 Electron 로컬 빌드와 디자인 identity 검사 통과. Windows 설치 파일 빌드는 수행하지 않았다.

- 최초 관련 검사: 159 통과, 실패 0. 이 검사만으로 위의 새 결함이 없다고 판정하지 않았다.
- 수정한 실패 경로와 실제 앱 클라이언트, 큰 파일 중계를 묶은 회귀: 28 통과, 실패 0.
- 현재 내장 Workspace UI: 1100px/440px에서 앱 목록/열기/등록/오류/재로그인, Talk 목록/작성기 통과. pageerror 없음.
- 메일 설정 UI 9개 확인 통과, 위키 저장소 UI 13개 확인 통과, 실제 Electron 스킬 흐름 11개 확인 통과, 메일 통합 흐름 9개 확인 통과.
- 기존의 테스트 호출 실수/fixture 구성 오류는 로그에서 식별한 뒤 해당 fixture만 바로잡았다. 제품 실패를 assertion 제거로 통과시키지 않았다.

## 추가 인증 구조 점검

후속 다단계 SSO 점검에서 중간 페이지 강제 이동, 인증 전 배경 진입과 HTTP→HTTPS 차단을 재현했다. 정상 경로 회귀 통과만으로 해당 흐름을 정상으로 보지 않는다. [인증 구조 보고서](MAIL-AUTH-REDIRECT-AUDIT-2026-10-14.md)는 수정 전 재현이다. 이후 포털 홈 자동 연결과 세션 조회로 보완했으며, 최종 변경과 검증 범위는 [세션 수정 보고서](MAIL-AUTH-SESSION-FIX-2026-10-14.md)를 따른다.

## 남은 실제 환경 확인

1. 회사 Windows 11에서 mySingle 로그인 → 받은/보낸/임시/스팸함 → 본문/결재 → 종료/재실행. 이번 변경이 사용자가 겪은 Whitelabel 404의 원인 자체를 해결했다는 증거는 아직 없다.
2. GHES 실계정으로 스킬/위키/앱 목록과 등록 권한, Talk 읽기/쓰기, 사진. 앱 파일 열기는 ai_workspace 저장소에 배포된 웹 UI를 이용하므로 해당 배포와 권한도 확인해야 한다.
3. 큰 HTML 앱의 회사 PC 처리 시간/메모리와 실제 업로드/재열기. 제한 일치와 모의 전송 성공을 사용자 PC 성능으로 확대하지 않는다.
4. Windows 설치판 반영은 별도 빌드가 필요하다. 같은 1.2.5 수정판끼리 자동 업데이트가 안 되는 기존 감사 Q02도 배포 전에 증가한 버전으로 해결해야 한다.

## 방법 선택

기존 소스의 불변 Git revision/readback, 세대별 요청 무효화, bounded response, 원문 해시 검사와 Playwright 실제 조작을 재사용했다. 새 인증/평가 프레임워크를 추가하지 않았다. 브라우저 쿠키나 인증값을 추출하지 않고 실제 사내 글을 시험 게시하지 않았다. 화면만 보고 성공이라 하지 않고 버튼→요청→저장 결과/원문과 재진입을 연결해 확인했다.
