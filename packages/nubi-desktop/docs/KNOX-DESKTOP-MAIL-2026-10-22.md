# Knox Desktop 저장 메일 수집

2026-10-22. 사용자 요청에 따라 메일 기본 연결을 Knox Desktop Message의 로컬 저장 파일 읽기로 전환했다. 제공된 Python의 저장소 탐색 방식을 참고하고, 구현은 기존 Node/Electron 수집기와 MIME 파서에 연결했다. Python, 8770 서버, MCP 토큰이나 새 의존성은 필요하지 않다.

## 사용 흐름

1. 기존 메일 설정에서 `저장된 메일 연결`을 누른다.
2. Windows의 `C:\mySingle\DesktopMessage\DesktopMessageEnv.xml`에서 저장 위치를 읽는다. 설정 파일이 없거나 저장 위치가 비어 있을 때만 `C:\mySingle`을 탐색한다. 잘못된 XML이나 상대 경로는 다른 위치로 우회하지 않고 오류를 표시한다.
3. 각 저장 위치의 하위 폴더 중 `UserSavedBoxInfo.xml`이 있는 실제 사용자 폴더를 찾는다. 저장소가 하나면 연결하고, 여러 개면 사람이 정확한 저장소를 고른다. 경로나 계정을 임의로 추정하지 않는다.
4. `.mysingle` 파일만 가져온다. `INDEX`와 링크 폴더는 제외한다. 일반 파일 가져오기는 기존 EML, MHTML, MHT, MYSINGLE 지원을 유지한다.
5. 자동 정리가 켜져 있으면 약 1분 간격으로 변경분을 확인한다. `새 파일 확인`은 명시적 수동 확인이다. 자동 정리 OFF와 수집 일시정지는 백그라운드 확인을 멈춘다.

저장소 탐색은 15초로 제한한다. 취소는 진행 중인 탐색 결과를 기다리지 않고 연결 요청을 종료하며, 늦은 결과를 반영하지 않는다.

이 방식의 범위는 Desktop Message가 이미 PC에 내려받은 사본이다. 서버 전체 메일함, 최신 수신 상태나 서버에서만 보이는 메일을 확인한 것으로 표시하지 않는다. 비 Windows 환경에서는 자동 탐색의 제한을 설명하고 기존 폴더 선택을 제공한다.

포털은 접힌 `다른 연결 방법`에서 직접 선택할 때만 사용한다. 기본 화면 조회가 포털 세션을 복원하거나 로그인 창을 만들지 않는다. 과거 포털 만료 오류가 정상적인 로컬 연결 상태를 덮지 않도록 분리했다.

## 저장과 복구

- 기존 `scanMailFolder`, `readMailImportFile`, `PersonalMail.startFolderImport`를 재사용한다. 원본은 읽기 전용으로 열고 파일 상태를 전후 대조한다. 원본 파일이나 읽음 표시를 쓰는 경로를 추가하지 않았다.
- 파일 경로별 기존 SQLite 영수증에 크기, 수정/변경 시각과 파일 식별을 기록한다. 완료한 동일 파일은 수집 확인 중 MIME 본문을 다시 읽지 않는다. 실제 열람과 분석에서는 매번 원본 해시를 검증한다.
- **최신 사용자 결정: Knox의 `.mysingle`을 유일한 원문으로 참조한다.** 새 Desktop 수집은 `message.eml`, 본문 manifest와 첨부 `.bin`을 만들지 않는다. SQLite에 선택한 저장소 루트, 상대 경로, 분류와 원문 SHA-256 및 메타데이터 목록만 기록한다. 원문 참조와 큐 기록이 완료된 뒤 영수증을 남긴다. 본문/HTML과 첨부 bytes를 이 기록에 넣지 않는다. 위키와 분석 결과는 기존 별도 저장 계약을 유지하며 SQLite 메타데이터까지 암호화했다고 표시하지 않는다.
- 본문, HTML 표시, AI 근거, 원문/첨부 다운로드는 모두 동일한 참조에서 원본을 읽고 해시를 확인한다. 경로 이탈, 링크 교체와 읽는 중 파일 교체를 거절한다. 본문 검색의 메모리 캐시도 원본 재검증을 통과해야 재사용한다. 원본이 없으면 `mail_source_missing`, 권한이 없으면 `mail_source_unavailable`, bytes가 바뀌면 `mail_source_changed`로 실패한다. 저장 사본이나 오래된 분석을 현재 원문 대신 반환하지 않는다.
- 파일 내용이 바뀌면 새 해시 버전을 색인한다. 이전 메타데이터와 분석 이력은 보존하지만 바뀐 원본을 이전 버전의 출처로 열지 않는다. 같은 분류 안에서 같은 내용이 새 경로로 재발견되면 기존 ID의 참조 경로를 갱신한다. Knox 파일을 지우거나 누비 데이터를 초기화해도 Knox 원본에 쓰기/삭제를 하지 않는다.
- 기존 누비 사본은 **원본 및 저장 사본의 해시 검증에 모두 성공한 경우에만** 같은 ID/원문 해시를 유지한 참조로 전환한다. SQLite의 참조 커밋 뒤 검증한 누비 `message.eml`, 첨부 `.bin`과 manifest만 제거한다. 중간 종료 시 정리 영수증으로 다음 확인에서 이어 정리한다. 원본이 없어졌거나 변했거나, 사본이 손상됐거나, 과거 첨부 제외로 만든 body-only 사본처럼 해시가 다르면 지우거나 출처 해시를 다시 쓰지 않는다. 사용자 위키와 태그/고정은 보존한다.
- 중지하면 완료 파일의 영수증을 보존하고 자동 수집 일시정지도 저장한다. `이어 가져오기`로 명시적으로 재개한다. 늦게 끝난 저장소 탐색은 취소된 연결을 다시 활성화할 수 없다.
- 저장 공간, 쓰기 권한 또는 암호화 오류는 자동 확인을 일시정지한다. 복구 후 사용자가 이어 가져온다. 일시적인 원본 위치 접근 오류와 일부 파일 오류는 긴 간격으로 재확인한다.
- 선택한 저장소가 사라지거나 바뀌어도 다른 계정을 자동 선택하지 않는다. 연결 해제와 앱 종료 시 수집을 중단한다.
- 누비 데이터 위치가 Knox 원본 위치와 겹치지 않도록 연결과 저장 위치 변경을 검사한다. Knox 연결에는 원문 저장 위치 변경이나 첨부 복사 옵션을 표시하지 않는다. 포털/POP3와 명시적인 일반 파일 가져오기는 기존 암호화 사본과 보관 옵션을 유지한다. Office 첨부 읽기의 임시 읽기 사본/정리 계약도 유지한다.
- `AUTO_*` 폴더의 기존 수신, 발신과 결재 분류를 유지한다. `ML_T_QUEUE`는 대기함, `ML_T_TRASH`는 휴지통으로 표시하고 새 Desktop 수집에서는 AI 자동 정리 큐에 넣지 않는다. 폴더명을 실제 결재 실행 상태나 승인 권한으로 승격하지 않는다.
- 결재 화면은 로컬 모드에서 색인한 결재 원문을 보여 준다. 로컬 모드에서 포털 결재 API를 암묵적으로 호출하지 않는다.

## 변경 경계

- `runtime/mail-desktop-source.mjs`: 저장소 탐색과 계정 선택, 확인 주기와 중지/재개.
- `runtime/mail-desktop-reference.mjs`: 호스트가 만든 원본 참조 검증과 읽기, 폴더 분류 메타데이터. 참조 경로를 렌더러 입력으로 받는 API는 추가하지 않는다.
- `runtime/mail.mjs`, `mail-file-import.mjs`, `mail-file-kinds.mjs`, `mail-reset.mjs`: 기존 수집, 영수증, 수집 상태와 초기화 연결.
- `electron-app/mail-source-status.cjs`, `main.cjs`: 기본 로컬 상태와 포털의 명시적 선택 분리. 렌더러는 탐색한 profile ID만 선택할 수 있고 임의 원본 경로를 전달하지 않는다.
- `ui/KnoxDesktopMail.jsx`, `MailLibrary.jsx`, `MailHistory.jsx`, `ApprovalHistory.jsx`: 기존 메일 설정과 원문 화면에 연결.
- 기존 SQLite 메타데이터 목록과 검색, 지연 원문 읽기를 재사용한다. 새 대규모 전체 본문 검색 엔진을 추가한 변경은 아니다.
- 계획 1의 Claude 담당 파일은 수정하지 않았다. 새 CSS와 새 가운데 모달도 만들지 않았다. 기존 메일 설정의 본문과 공통 컴포넌트를 재사용했다.
- `scripts/check-electron-shell.mjs`의 메일 설정 진입 검사는 실제 새 접근성 이름과 기본 연결 버튼에 맞췄다. 검사 흐름과 한도는 제거하지 않았다.
- 새 화면 검사는 기존 `scripts/check-mail-ui.mjs` 마지막에 연결했다. 기존 게이트 명령을 없애거나 바꾸지 않고 브라우저를 순서대로 실행한다.

## 최초 연결 구현 검증

- 원본 참조 변경 전 소스의 `mail-desktop-source`, `mail`, `mail-portal`, `mail-file-import`, `mail-import-resume`, `mail-storage-policy`, `mail-reset` 79개 검사 통과. 로그: `verification/desktop-mail-2026-10-22/unit.log`. 아래 최초 기록은 최신 원본 참조의 검증으로 소급하지 않는다.
- 새 저장소 검사 11개는 XML과 UTF-16, 링크 제외, 여러 저장소 선택, 변경분과 원본 보존, 재시작, 취소 후 늦은 응답, OFF와 일시정지, 저장 위치 분리, 공간 부족 후 명시적 재개, 탐색 시간 초과 후 재연결을 확인한다.
- `scripts/check-desktop-mail-ui.mjs`: 기존 설정 화면에서 1280px와 440px, 저장소 하나/여러 개의 4개 흐름 통과. 실제 Chrome과 합성 호스트 응답이다.
- 기존 `scripts/check-mail-ui.mjs`: 포털 대체 연결, POP3 대체 연결, 중지와 재개, 저장과 초기화 등 13개 흐름 통과. 실제 Chrome과 합성 응답이며 회사 접속 결과가 아니다.
- Electron 빌드와 최종 runtime/renderer 번들 생성 통과. 기존 Windows Bash의 `import.meta` CJS 경고가 남아 있다. Mac에서 PowerShell이 없어 Office Windows 파서 검사는 제외됐다.
- `scripts/check-electron-desktop-mail.mjs`: 실제 Mac Electron의 4개 검사 통과. 기본 상태에서 포털 창이 없고, 합성 MYSINGLE의 암호화 수집, 검색, 원문 읽기와 native 저장, 목록 갱신 뒤 원문 선택과 설정 재진입을 확인했다. 700px 재진입 화면도 확인했다. 기록은 `verification/desktop-mail-2026-10-22/native/result.json`이며 임시 프로젝트와 합성 메일만 사용했다.

초기 검사 오류도 구분한다. 새 UI 검사기의 CSS alias 누락을 고쳤다. 제한된 실행 환경에서는 localhost 서버 생성이 `EPERM`으로 막혀 기존 메일 검사 13개가 실행 전 실패했으며, localhost가 허용된 환경에서 같은 검사를 통과했다. 초기 Electron 검사기는 갱신된 목록을 반영하는 버튼의 접근성 이름과 표시 시점을 잘못 처리해 원문 선택까지 진행하지 못했다. `메일 목록 업데이트`라는 실제 이름과 명시적 갱신 대기를 사용하고, 설정 재진입은 메일 이력 안의 버튼으로 한정했다. 검사 한도나 제품 필터를 바꾸지 않았다.

## 원본 참조 전환 최종 검증

- 같은 7개 메일 검사 파일의 최종 **88/88 통과**. Desktop 검사 20개와 기존 메일 회귀 68개다. 로그는 `verification/desktop-mail-2026-10-22/reference-unit.log`에 보관했다.
- 새 참조 검사는 저장소에 본문/첨부 사본이 생기지 않는 것, HTML/본문/인라인 이미지/첨부 다운로드와 원본 bytes 일치, 삭제/변경 뒤 검색 캐시와 근거/위키 읽기 거절, 같은 내용 이동 후 동일 ID 유지, 경로 이탈과 링크 교체 거절을 확인했다. 기존 사본의 해시 검증 후 제거, 첨부 사본 제거, 손상 사본 보존, 정리 중단 후 재시작, body-only 사본의 출처 해시 보존, SQLite 공간 부족 후 명시적 재개도 확인했다.
- Electron 빌드 통과 후 최종 runtime과 renderer 번들을 다시 생성했다. 기존 `windows-bash-process.mjs`의 CJS `import.meta` 경고는 남아 있다. Mac의 PowerShell/Office 실행은 검증하지 않았다.
- 기존 Chrome 메일 설정 흐름 13개를 유지했다. 최신 Desktop 화면 4개 흐름(1280px/440px, 저장소 하나/여러 개)이 통과했다. 원본 참조 안내와 복사 설정 숨김을 확인했다. 실제 Chrome과 합성 호스트 응답이며 Windows 연결 검증은 아니다.
- 실제 Mac Electron 앱 **5개 검사 통과**. 기존 일반 파일 가져오기의 암호화 보관 호환을 확인한 뒤, 임시 시험 DB에 참조 레코드만 주입하고 누비 사본을 제거했다. 실제 번들/IPC에서 원문/HTML 표시와 native 다운로드가 원본과 같고, 원본 삭제 시 `mail_source_missing`으로 실패했다. 읽기 화면과 700px 설정 재진입도 확인했다. `verification/desktop-mail-2026-10-22/native-reference/result.json`에 기록했다. 이 DB 주입은 시험 전용이며 제품에 임의 경로 입력 API를 추가하지 않았다. Windows 탐색과 전환 절차 자체는 Node 파일 fixture로만 확인했다.

전환 후 검사기에서 두 오류를 고쳤다. 연결 전에 연결 후 수집 범위 문구를 기다리던 UI 검사를 연결 완료 뒤로 옮겼고, 다운로드 검사는 호스트가 거절하는 일반 `mail/download` 호출 대신 실제 native 저장 경로인 `downloadMail`을 사용했다. 제품의 IPC 허용 범위를 넓히지 않았다.

실제 Windows Knox 저장소, 회사 계정과 보관 메일, Office 2016/NASCA, 설치판 업데이트와 실모델 지식 품질은 이번 Mac 검증으로 통과시키지 않는다. 원격 업로드나 릴리스는 하지 않았다.
