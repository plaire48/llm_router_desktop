# 위키와 메일 지식화 우선순위

사용자의 2026-10-22 지시에 따라 1.3.0의 우선순위를 위키 작성과 메일 지식 자산화의 완성도로 둔다. 사용자가 가장 불편했던 부분은 모은 자료가 쓸 만한 위키 지식으로 정리되지 않는 점이다. 다음 기준으로 실제 사용 흐름을 다듬는다.

1. **보존**: 수집한 원문과 첨부, 사용자가 보충한 지식을 저장하고 재실행 후 다시 읽을 수 있어야 한다. 중단과 재연결에서 누락하거나 중복 수집하지 않는다.
2. **작성 품질**: 원문의 중요한 요구, 결정, 조건과 변경 이력을 정확히 담는다. 확인하지 않은 내용을 사실로 작성하지 않고 원문 출처와 누락 범위를 유지한다.
3. **검색과 재사용**: 질문에 필요한 원문과 위키를 찾고 서로 연결한다. 검색하지 못한 본문과 첨부를 확인했다고 표시하지 않는다.
4. **갱신과 복구**: 바뀐 원문을 반영하되 사람이 수정한 내용을 보존한다. 완료한 단계를 반복하지 않고 실패 위치에서 이어간다.
5. **실제 사용성**: 많은 메일과 문서에서도 목록, 검색, 작성 상태와 실패 이유를 쉽게 확인할 수 있어야 한다. 화면을 닫았다가 다시 열어도 진행과 선택 상태가 맞아야 한다.

## 첫 수정: 종료 직전 편집 유실

`MailWikiVault.dispose()`가 `disposed=true`로 전환한 뒤 `syncAll()`을 호출했다. 이 함수는 종료 상태에서 곧바로 반환하므로 마지막 편집을 암호화 저장소에 반영하지 않고 세션 사본을 삭제했다. 기존 내용을 저장한 다음 세션 파일을 수정하고 즉시 종료와 재열기를 수행하면 수정 전 내용으로 돌아가는 결함을 재현했다.

종료 시 새 감시는 멈추되 마지막 동기화는 실행하도록 수정했다. 진행 중인 동기화와 마지막 저장을 기다린 뒤 세션 사본을 제거하며, 중복 종료는 같은 작업을 기다린다. `MailWikiVault` 재열기와 실제 `PersonalMail`의 수집, 위키 생성, 사용자 편집, 종료, 재열기에서 최신 편집과 메일 원문 보존을 검사한다.

관련 검사: `tests/mail-wiki-vault.test.mjs`, `tests/mail-wiki-encryption.test.mjs`, `tests/mail-knowledge.test.mjs`, `tests/mail-reset.test.mjs`, `tests/wiki-lifecycle.test.mjs`.

이 검사는 로컬 파일과 합성 호스트의 보존 및 복구 근거다. 실제 회사 메일과 모델의 내용 품질, 강제 종료와 정전, Windows 설치판 검증으로 확대하지 않는다. 위 다섯 기준 전체가 완벽해졌다는 의미도 아니다.

## 핵심 품질 공백: 자료 요약과 주제 지식의 연결

현재 Desktop 메일 작성 경로는 `synthesizePersonalMail()`로 메일 한 통의 요약, 사실과 후속 요청을 받고 메일별 불변 Markdown을 저장한다. `mailFrontMatter()`가 쓰는 태그는 기본 `mail`과 문서 구분이며 업무 주제 정보는 연결하지 않는다. 관계 지도는 회신 관계와 기존 메타데이터에서 묶음을 투영하지만 여러 자료를 누적한 주제 문서를 실제로 작성하거나 갱신하는 단계가 아니다.

OpenWiki personal 작성 지침에는 이미 주제 통합, 출처별 근거 보존, 결정과 후속 조치, 충돌하는 주장과 변경 이력의 정리 원칙이 있다. Desktop의 단일 메일 요약 함수는 이 작성 경로와 다르다. 프롬프트 문구나 종류 이름만 바꾸어 주제별 지식화가 구현됐다고 표시하지 않는다.

최우선 개선 결과는 여러 메일과 자료를 바탕으로 같은 주제의 한 문서에서 현재 확인된 상태, 중요한 결정과 조건, 담당자와 명시된 기한, 변경 이력과 출처, 아직 모르는 내용을 읽는 것이다. 새 자료는 영향을 받는 문서를 갱신하고 예전 결정을 현재 사실로 섞지 않아야 한다. 원문 단위 페이지와 주제별 지식 문서는 역할을 유지하며 사람이 보충한 내용도 보존해야 한다. 이 주제별 누적 작성 경로는 이번 삭제 및 보존 수정에서 구현하거나 실모델 검증한 것으로 표시하지 않는다.
