# 실측 평가와 계측

누비 workspace의 품질과 비용을 실제 모델로 측정하는 틀이다. 설계는 `docs/superpowers/specs/2026-09-29-nubi-desktop-live-eval-design.md`, 실행 방법은 [eval/README.md](../eval/README.md)를 따른다.

## 구성

| 부분 | 위치 | 제품 포함 |
|---|---|---|
| 계측 | `runtime/run-metrics.mjs`, `runtime/recovery.mjs`, `runtime/agent.mjs` | 예 |
| 평가 실행기 | `eval/` | 아니오 |
| 과제와 정답 | `eval/cases/` | 아니오 |
| 고정 자료 | `eval/corpus/` | 아니오 |

## 계측이 남기는 것

기존 SQLite `events` 표에 세 종류를 남긴다.

| 종류 | 내용 |
|---|---|
| `metric_model` | 호출 목적, 시도 번호, 요청 크기, 추정 토큰, 실제 사용량, 지연, 종료 사유, 호출한 도구 이름 |
| `metric_tool` | 도구 이름, 주 실행기와 하위 분석의 구분, 지연, 결과 크기, 이미지 수, 오류 코드 |
| `metric_compaction` | 압축 원인, 전후 추정 토큰 |

대화 본문, 도구 인자, 도구 결과 내용은 저장하지 않는다. 오류는 정해진 형식의 코드만 남긴다. 30일이 지난 계측은 다음 실행을 시작할 때 지운다. 기록에 실패해도 실행은 계속한다.

호출 목적은 `actor, planner, reviewer, summary, analysis, document`다. 호출 지점이 직접 표시한다.

## 지표

| 지표 | 계산 |
|---|---|
| 독립 통과 | 결과가 `passed`인 과제 수 |
| 답변 전달 | 작업이 `review`에 도달하고 답변이 있는 과제 수 |
| 잘못된 완료 | 작업이 `review`이고 검토가 `ready`인데 채점이 실패한 과제 수 |
| 불필요한 질문 | 질문하지 않아야 하는 과제에서 질문한 수 |
| 필요한 질문 누락 | 질문해야 하는 과제에서 질문하지 않은 수 |
| 고정 비용 비중 | 시스템 안내와 도구 정의의 글자 수를 전체 요청 글자 수로 나눈 값 |
| 캐시 비율 | 캐시 토큰을 입력 토큰으로 나눈 값 |
| 추정 오차 | 실제 입력 토큰을 추정 토큰으로 나눈 값. 사용량을 받은 호출만 계산 |

단일 가중 점수는 만들지 않는다.

## 실측 결과

조건: ChatGPT SSO의 `gpt-5.6-luna`, 과제 20개, 과제당 1회, macOS, Node 25.4. 자료는 공개 자료(openwiki-sds)와 합성 자료(order-service)다. 기록은 `verification/eval-live/`에 있고 저장소에 올리지 않는다.

| 답변 전달 | 4 | 7 | 17 | 15 | 17 |

| 그중 OpenWiki 에이전트 | 0 | 0 | 0 | 620 | 287 |

| 후보 | 변경 |
|---|---|
| B1 | 거절 사유와 유효한 값을 도구 결과에 담음. 승인만 남은 제안은 두 번째 검토에서 전달 |
| B2 | 진행 설명 안내를 도구마다 반복하지 않고 한 번만 전달. 앱 조작이 불가능한 호스트에서는 앱 도구를 제외. 검토 판정 정규화 |
| B3 | Wiki 질문을 OpenWiki 에이전트에 위임. 읽기 결과의 규칙 중복 제거. 읽기 9,000자 상한. 검토 4회 상한. 질문은 `ask_user`로 |
| B5 | 전수 검토는 Wiki 전체가 필요할 때만 요청. 한 파일 안 검색은 모두 표시. Wiki에 답이 없으면 소스 검색. 출처 경로 전달. 압축 뒤에도 사용자 메시지 원문 유지 |
| B6 | OpenWiki 답을 바꾸지 않고 전달. 읽기는 200줄 전체를 전달하고 검토에는 나눠서 전달. 보호 메시지가 들어가지 않으면 요약에 맡김 |
| B7 | 읽기를 한 응답에서 함께 실행. 앱 조작: 값 읽기, 사유별 안내, 영수증에 바뀐 컨트롤, 제안에서는 검토 없이 전달. 계획의 빠진 상태를 호스트가 채움 |

B5에서 통과하지 못한 과제:

| 과제 | 결과 | 원인 | B6 조치 |
|---|---|---|---|
| D1 | 실패 | 읽기 9,000자 상한 때문에 답이 있는 296번째 줄까지 읽지 않음 | 읽기 상한 제거 |
| D2 | 오류 | OpenWiki 에이전트가 Wiki 전체 검토를 선택해 144회 호출. 과제당 80회 한도 초과 | 위임 호출을 따로 세고 한도를 400회로 둠 |
| D3 | 실패 | 답은 맞음("안내되어 있지 않습니다"). 정답 목록에 없는 표현 | 정답 목록에 표현 추가(사용자 결정) |
| L1 | 오류 | 보호한 메시지가 22,000 토큰 창에 들어가지 않아 압축 실패 | 들어가지 않는 메시지는 큰 것부터 요약에 맡김 |

B6 측정은 끝까지 가지 못했다. 12번째 과제에서 모델 세션이 끊겨 8개가 실행되지 않았다. 실행된 12개의 결과는 아래와 같다. 같은 시각에 앱 조작 측정이 같은 세션을 함께 써서 시간 값은 실제보다 길다.

| 과제 | 결과 | 원인 | B7 조치 |
|---|---|---|---|
| C1~C5, K1, L2 | 통과 7 | | |
| D1 | 실패 | 한 응답에 읽기 4개를 요청했으나 첫 호출만 실행됐다. 답에 두 값이 빠졌다 | 부작용이 없는 읽기는 한 응답에서 함께 실행 |
| D2 | 오류 | Wiki 전체 검토가 10분을 넘었다(위임 190회) | 과제 시간 한도를 20분으로 |
| D3 | 사람 확인 필요 | 정답 조건은 통과. 답이 `HTTP_PROXY`를 언급해 확인 대상으로 표시됐다 | 없음 |
| L1 | 오류 | 계획 단계가 `status` 없는 계획을 두 번 돌려줘 실행이 시작되지 않았다 | 빠진 상태는 호스트가 채움. 다시 요청할 때 어긴 규칙을 알림 |
| L3 | 오류 | 모델 세션 끊김 | 없음 |

읽는 법:

- B3은 위임을 처음 넣은 후보다. 세 과제가 Wiki 전체 검토에 호출 한도를 다 썼고, 검색 결과 제한이 한 파일 안 검색에도 적용되는 결함이 있었다.
- 과제당 1회 측정이다. 같은 후보를 다시 재면 결과가 달라질 수 있다.
- 이 모델 세션은 사용량을 돌려주지 않는다. 입력 토큰과 캐시 비율은 측정하지 못했다.
- B6부터 평가 조건이 두 가지 바뀐다. 위임 호출을 따로 세고, D3와 W3의 정답 목록이 넓어진다. B5 이전과 통과 수를 비교할 때 이 차이를 함께 본다.

## OpenWiki 에이전트의 비용

Wiki 질문은 OpenWiki 에이전트가 자기 문맥에서 조사한다. 검색 방식과 결과 형식은 OpenWiki의 것을 그대로 쓴다(사용자 결정 2026-09-29).

| 질문 | OpenWiki 호출 | 조사 시간 |
|---|---:|---:|
| 사실 하나(K1, 기본 포트 등) | 5~9 | 12~35초 |
| 여러 문서에 걸친 질문(W2, W3, W4) | 12~18 | 50~90초 |
| Wiki 전체 검토(D2, 46만 자) | 약 150 | 약 5분 |

일반 질문에서 조사원은 2명이 병렬로 일한다. Wiki가 24,000자를 넘으면 OpenWiki가 반대 근거를 찾는 조사원을 하나 더 둔다.

## 한 응답의 여러 호출

B5 측정에서 주 에이전트가 요청한 도구 호출은 252회였다. 그중 61회는 실행되지 않았다. 단계 실행 규칙이 한 응답에서 첫 호출만 실행하기 때문이다. 61회 중 46회는 읽기 뒤에 요청한 읽기였다. B7부터 부작용이 없는 읽기 13개는 한 응답에서 모두 실행한다. 수정, 제안, 질문, 앱 조작, 위임은 이전처럼 하나씩 실행한다.

## 빌드 상태

2026-09-29 기준 `npm run compile`, `npm run build`, `npm run test:ui`가 통과한다. 앱 번들에 계측이 들어 있다.

기준 HTML은 성공 색으로 초록 `#148A5C`, `#E6F6EE`를 쓴다. 공유 `agent-deck.css`는 브라우저 누비의 결정에 따라 두 값을 파랑으로 둔다. Desktop은 공유 파일을 바꾸지 않고 `design/workspace-identity.css`에서 기준 HTML의 값을 되돌린다. `scripts/check-identity.mjs`는 Desktop 계층이 값을 정하면 그 값을, 아니면 공유 값을 기준 HTML과 대조한다.

## 한계

- 문자열 검사는 예상하지 못한 표현의 정답을 놓칠 수 있다. 실패한 과제는 `result.json`의 답변을 직접 읽어 확인한다.
- 과제가 20개다. 두 보고서의 차이는 관찰이며 우열의 입증이 아니다.
- 압축 과제는 모델의 문맥 한도를 22,000 토큰으로 낮춘 조건이다. 실제 사내 모델의 한도와 다르다. 압축 품질은 `eval/compaction.mjs`로 따로 잰다.
- 합성 자료에는 Claims가 없다. 검색 결과는 항상 미검증으로 표시된다.
- 새 Git 저장소로 시작하므로 Wiki 생성 커밋이 작업 공간에 없다. 커밋 기준 최신성은 측정하지 않는다.
