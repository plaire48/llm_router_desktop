# Code Wiki semantic review

출처 파일과 버전이 맞는 것만으로 문장이 사실이라고 판단하지 않는다. Native repository runner의 페이지 제출 전에 선택한 모델로 별도 내용 검토를 수행한다.

## 반영

- 작성 대화와 분리된 검토 문맥에 페이지 전체, 유지/추가/수정한 Claims와 실제 원문을 전달한다. 입력 조건, 호출 흐름, 계산 중간값, 예외, 시간 경계, 과거 설명과 현재 구현을 대조한다.
- 모든 Claim에 검토 결과가 있어야 한다. 근거 인용은 실제 읽은 원문의 부분 문자열이어야 한다. 근거가 부족한 `uncertain`도 승인하지 않는다. 인용하지 않은 본문도 전체 검토한다. 특히 `항상`, `때만`, `없다`, `그대로 남는다` 같은 단정과 상태 보존 문장을 별도 검토 대상으로 뽑아 각각의 판정을 요구한다. 단어 추출 자체는 사실 판정이 아니며 원문과 조건을 대조하는 검토가 뒤따른다.
- 정상 항목은 같은 논리와 원문을 공유할 때 `supported` 그룹으로 묶어 판정 출력을 줄인다. 모든 Claim과 본문 단정 항목은 정확히 한 번 포함되어야 하며 중복, 누락, 범위 밖 번호는 거절한다. 정상 그룹에도 실제로 확인한 입력, 시간과 범위 조건을 짧게 남긴다. 오류와 불확실 항목은 개별 이유를 유지한다. 문서 전체 읽기, 실제 인용 검증과 제출 직전 원본 재확인은 생략하지 않는다. 수정된 문서의 과거 정상 판정을 그대로 재사용하지 않는다.
- 생성 시점과 이후 조회 시점의 콜백 값을 구분한다. 최초 시각이 유한하다는 조건을 이후 시각에도 자동으로 적용하지 않는다. 무한 만료값과 같거나 NaN인 조회 시각의 비교도 실제 코드 조건으로 검토한다.
- 재시도를 설명할 때 롤백과 멱등성 구현 여부를 명시한다. 구현이 없으면 실패 전에 발생한 효과가 다음 시도에서 중복될 수 있다는 한 문장을 재시도 설명 옆에 둔다. 검토기는 중요한 누락도 확인하며 작성기는 지적 전체와 영향받는 기존 Claims를 한 번에 수정하고 관련 없는 설명을 추가하지 않는다.
- 검토기가 원문에 없는 인용을 내면 오류 위치를 돌려주어 같은 검토 문맥에서 한 번만 교정한다. 인용이 다시 틀리면 승인하지 않는다. Claim의 오류와 실제 본문 인용을 구분하며 이 복구도 전체 4회 검토 호출 예산 안에 둔다.
- 틀린 내용은 문장과 수정 방향을 작성기에 돌려보낸다. 단순히 Claim만 지우고 잘못된 본문을 유지하도록 하지 않는다. 기존 Claim의 오류에는 저장된 ID를 돌려주어 같은 항목을 수정하게 하며, 새 Claim만 추가하고 틀린 기존 항목을 유지하지 않도록 안내한다. 참이지만 모든 경우를 열거하지 않은 설명까지 늘리도록 요구하지 않는다.
- 문서 수정과 제출을 페이지별로 순차 처리한다. 독립적인 원문 읽기는 병렬로 유지한다. 제출 완료 뒤 같은 작업의 추가 수정은 실행하지 않는다.
- 제출 직전에 검토한 페이지와 읽은 원문의 내용을 다시 비교한다. 이후 기존 Claims 버전 검증과 페이지 저장 계약을 그대로 수행한다.
- 검토기가 추가로 찾은 파일의 경로만 같은 페이지의 다음 검토에 재사용하고 내용은 다시 읽는다. 설정 파일을 찾기 위한 반복 모델 호출을 줄이며 오래된 원문을 캐시하지 않는다.
- 오류 후 상태가 유지된다는 설명은 실패 이전의 조회, 삭제와 부수 효과도 추적한다. 마지막 쓰기를 실행하지 않았다는 사실만으로 원래 상태 보존을 승인하지 않는다.
- 일반 애플리케이션의 빠른 시작에 OpenWiki 자체 예약 갱신/설치 안내가 불필요하게 늘어나지 않도록 작성 규칙을 좁혔다. 해당 연동 운영을 요청한 경우와 실제 애플리케이션 빌드/테스트/배포 안내는 유지한다.
- 자동 AGENTS 안내문은 예약 갱신이 실제 구성되었다고 단정하지 않는다. CI나 배포의 존재/동작은 실제 구성과 실행 증거로 구분한다.
- 검토 중단/불완전 응답/해결되지 않은 지적은 미완료로 남긴다. 이미 완료된 페이지와 원래 갱신 승인 계약을 유지하며, 검토 실패를 완료 페이지로 바꾸지 않는다.
- 기존 진행 UI에 `내용 검토`를 표시하고 실패 사유와 재시도를 안내한다. 새로운 모달이나 디자인 토큰을 만들지 않는다.

## 경계

- 검토기는 읽기와 결과 제출만 가능하다. 사용자 저장소 코드를 실행하거나 수정하지 않는다. 실모델 평가에서 실행하는 반례는 별도로 고정한 합성 코드뿐이다.
- 한 검토는 모델 호출 최대 4회, 페이지 최대 60,000자, Claims 최대 100개와 추가 본문 단정 문장 최대 80개, 원문 최대 48개/합계 160,000자(개별 80,000자)다. 범위를 넘으면 자른 자료만 보고 통과시키지 않고 미검토로 남긴다. 큰 단일 파일의 범위별 검토는 후속 과제다.
- 작성기의 제출 검토는 시도당 최대 6회다. 문서와 Claims가 그대로인데 세 번 거절되면 진전 없음으로 중단한다. 검토 실패는 같은 문서를 새로 완료한 것으로 기록하지 않는다.
- 이는 모델 기반 정적 내용 검토다. 실행 증명, 모든 오류 제거 또는 수학적 검증으로 표시하지 않는다. 같은 모델의 작성/검토에는 공통 편향이 남을 수 있다.
- 초기 생성과 갱신의 native runner에 적용한다. 읽기 전용 질문, 외부 MCP의 수동 페이지 제출, Personal 수집 전체에 이 검사가 적용되었다고 확대 해석하지 않는다.

## 비교 방법

`eval/wiki-semantic-live.mjs`는 기존 `order-service`와 추가 `cache-retry` 고정 자료를 공식 Claude Code Opus/medium으로 생성한다. 이전 주문 서비스 10개 기준과 두 반례를 그대로 사용하고, 새 예제의 정답은 `eval/wiki-semantic-rubric.json`에 고정했다. `eval/wiki-semantic-probe.mts`는 단일 거짓 주장 5개, 올바른 주장 4개와 전체 페이지의 미등록 거짓 주장 2개를 별도로 측정한다. 함수 내부에 한정한 올바른 설명을 다른 함수의 예외 때문에 잘못 거절하지 않는 사례, 조회의 만료 삭제 후 하위 작업이 실패하는 사례도 포함한다. 전체 캐시 문서의 잘못된 미래 시각 조건도 별도 회귀로 유지한다. 모든 실패와 중단은 결과에 남긴다. 평가에서 발견한 문제를 개선에 사용했으므로 두 자료는 독립적인 미공개 검증 세트가 아니다.

결과와 생성된 문서는 `verification/wiki-semantic-review-2026-10-16/`에 보관한다. 모델의 자체 검토 통과와 별도의 사실 채점, 원문 해시 확인, 생성 시간은 구분한다.

## 검토 출력과 속도 비교

`--output=wiki-review-speed-2026-10-16`으로 별도 결과 폴더를 지정할 수 있다. 기존 결과는 덮어쓰지 않는다. 같은 합성 코드, 모델과 추론 수준, 페이지 수, 순차 생성 조건에서 벽시계 시간, 모델 호출, 의미 검토 횟수와 판정 출력 크기를 비교한다. 속도 개선은 실제 생성 결과를 이전과 같은 사실 기준으로 다시 채점한 경우에만 보고한다. 모델 서비스 변동과 작은 표본의 한계를 남긴다.
