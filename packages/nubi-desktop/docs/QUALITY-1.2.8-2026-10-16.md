# 누비 Workspace Beta 1.2.8 검증 기록

최종 Windows 설치 검사와 마지막 실모델 생성 결과를 확인해 1.2.8 수정 빌드의 공개를 진행합니다. 확인한 범위에서 배포를 막는 실패는 없으며 아래의 미검증 환경은 별도로 남깁니다. 이전 날짜의 개별 작업 문서는 당시 확인 범위이며 이번 최종 판정은 이 문서를 기준으로 합니다. 최종 설치 빌드 기준은 `19369bd727050c73ccf459aec85d6f6d4a7de1f8`입니다. 위키 실모델 측정 코드 `0461bc636814442b1ac493a05c0d311547c092c8` 이후 변경은 설치 안내 문구, 해당 Windows 화면 검사와 명령 복구 검사의 대기 조건뿐입니다. 검사 종료 정리와 결과 문서는 실행 번들 변경과 구분합니다.

## 반영 범위

- 코드 위키 전체 내용과 원문 조건 대조, 과장과 과거 정보 구분, 재시도 효과의 중복 가능성, 간결한 문서와 묶음 판정.
- 메일 HTML 본문과 진짜 첨부 구분, 원문과 첨부 수집 설정, 데이터 초기화, 결재 실패 단계 안내.
- 새 탭 SAML의 POST와 opener/session 보존, 사용자가 확인하는 세션 만료 팝업, GHES 이름 옆 상태 이모지.
- 최근 검증 실패를 오래된 성공이 덮지 않도록 보완하고 승인한 수정 명령의 후속 검증을 연결.
- 동시 시작 복원 공유, 공통 모달 토큰과 좁은 화면, 아이콘과 글자 정렬.

전체 게이트 첫 실행은 새 캐시 평가 자료의 목록 기대값 누락으로 실패했습니다. 목록을 고친 전체 재실행은 위 단위 검사 결과로 통과했습니다. 그 뒤 메일 화면은 판정을 마친 후 빌드 서비스가 남아 종료되지 않았습니다. 임시 검사 프로세스만 정리하고 esbuild를 명시적으로 닫도록 보완한 뒤 메일 검사를 다시 통과했습니다. 나머지 게이트는 원래 순서대로 모두 실행해 통과했습니다. 단일 `test:gates` 프로세스의 마지막 종료 코드 0으로 표현하지 않습니다.

화면은 실제 제품 컴포넌트와 스타일을 쓰는 로컬 fixture이며 회사 계정 데이터가 아닙니다. 에이전트 UI의 모델은 fixture입니다. 별도 실모델 위키 평가는 아래 범위로 구분합니다.

## 실모델 위키

공식 Claude Code Opus 5.5, medium과 같은 두 합성 코드 자료를 사용합니다. 출처 검증과 내용 채점을 구분하고 실패한 실험도 보존합니다. 마지막 오판 보완 후 기존 11개 반례와 한계 설명/정밀도 보장을 구분하는 2개를 포함해 13개를 모두 통과했습니다. 앞선 평가 자료 경로 오류와 정상 조건의 과도한 거절은 기록에 남깁니다. 최종 생성은 두 예제의 사실 기준 22개를 충족했습니다. 주문은 7분 42초에서 5분 24초, 캐시는 11분 4초에서 5분 17초로 줄었습니다. 각 1회 최종 측정이며 일반 성능으로 확대하지 않습니다. 두 빠른 시작 예제도 직접 실행해 통과했습니다. 자세한 수치와 모든 후보는 `WIKI-QUALITY-1.2.8-2026-10-16.md`를 따릅니다.

## Windows

최종 실행 `38821525639`가 모든 게이트를 통과했습니다. Windows Server 2025 Datacenter에서 설치, 이전 버전 업그레이드, 동일 버전 재설치, 앱 실행, 무인 업데이트 후 재실행, 제거, 시스템 Git 없는 실행을 확인했습니다. 업그레이드 22.0초, 재설치 21.1초, 제거 1.8초였으며 마침 버튼 이후 앱 창 표시까지 2.1초였습니다. 이 수치는 해당 runner의 1회 측정이며 사용자 PC의 예상 시간으로 보장하지 않습니다.

실제 설치 화면에서 새 첨부 지원 안내와 Office 설치 요건, 진행률/경과 시간/남은 시간, 기본 상세 표시, 새 아이콘과 완료 화면을 확인했습니다. EXE는 172,619,466바이트이며 SHA-256은 `e7a372777b73012e16879e5d5f9570becb55afc33885d62ccf5d62055e00ce57`입니다. 다운로드 파일, 체크섬 파일과 GitHub 자산의 SHA-256이 일치합니다. Authenticode는 NotSigned입니다.

 앞선 실행에서 대용량 평가 자료를 Git에 넣는 5분 제한과 포털 검사 창 초기 로드 실패를 발견했습니다. 대용량 준비 제한은 제품의 10분 기준에 맞추고, 포털 검사는 실제 앱처럼 보이는 창과 웹 영역에서 수행하며 실패 코드를 기록합니다. 회사 TLS나 브라우저 보안을 낮추지 않았습니다.

실제 Windows 11 사용자 PC, 사내망의 GHES/메일/결재, Office 2016/NASCA는 이번 Mac 및 GitHub runner 검사로 확인되지 않습니다. 이 범위가 모두 검증되었다고 표시하지 않습니다.

## 설치와 배포

새 Windows x64 EXE와 SHA-256, 설치/재설치 검사 보고서, `Publish-NubiUpdate.ps1`, `INSTALL-AND-UPDATE-1.2.8.md`, `WINDOWS-UPDATE-DEPLOYMENT.md`를 같은 릴리즈에 제공합니다. 기존 1.2.8 사용자는 같은 버전이므로 새 EXE를 직접 실행해 재설치합니다. 사내 nuri 배포는 회사 PC에서 별도로 수행합니다.

## Windows 줄바꿈 회귀 보완

실제 Windows 검사에서 부분 갱신 후 새 체크아웃의 CRLF 때문에 문서와 검증 기록의 해시가 달라지는 오류를 발견했습니다. Mac에서도 `core.autocrlf=true` 복제만 실패하고 false는 통과하는 것으로 재현했습니다. 문서 버전은 CRLF만 LF로 정규화하며 내용, 공백과 빈 줄 차이는 유지합니다. 오래된 바이트 해시나 실제 수정으로 검증 기록이 맞지 않으면 문서와 Claims를 보존하고 해당 문서를 다시 검토합니다. 원본 소스 근거 검증과 검토 중 변경 감지는 유지합니다.

추가 전체 OpenWiki 검사는 처음 제한된 실행 환경에서 localhost 서버 열기가 거절되어 중단했습니다. 같은 명령을 localhost 사용이 허용된 환경에서 다시 실행해 3,553건 통과, 3건 건너뜀을 확인했습니다. 제한된 실행의 실패 로그도 보존합니다.

최종 설치 화면 감사에서 첨부 읽기를 미지원으로 설명한 과거 안내를 발견했습니다. 본문/첨부 읽기와 Office 문서에 필요한 Office 설치 안내로 바꿨습니다. 실제 설치창의 두 문구를 확인하고 과거 미지원 문구가 있으면 실패하도록 Windows 화면 검사도 보완했습니다. 이 변경으로 다시 패키징한 최종 설치 파일의 실제 화면에서도 두 문구를 확인했습니다.

설치 안내 재패키징 중 Windows 명령 복구 검사가 한 번 실패했습니다(`state did not settle`). 이 검사는 Git Bash를 100ms 만에 종료하면서 사전 출력과 3초 내 진단 완료를 요구해 시작/종료 지연과 경쟁할 수 있었습니다. Windows 합성 명령만 3초 제한, 자연 종료는 30초 이후, 진단 대기는 15초로 분리했습니다. 실제 timed_out 상태, 출력 보존, 진단 1회, 실행 1개 조건은 유지하며 실패 시 현재 상태를 기록합니다. 제품 제한시간은 바꾸지 않았고 Mac 관련 13건과 최종 Windows 복구 게이트를 통과했습니다.
