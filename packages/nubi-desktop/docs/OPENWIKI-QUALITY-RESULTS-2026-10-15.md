# OpenWiki 품질 평가와 개선 결과

검색의 누락과 메일 원문 왜곡 위험을 줄였습니다. 다만 자동 채점 점수를 실제 정확도로 볼 수는 없습니다. 생성 문서의 과장된 설명과 답변의 반복은 추가 개선이 필요합니다.

## 실제 평가

Claude Code의 Claude Opus 5.5, medium으로 Code 20문항과 Personal 20문항을 각각 3회 실행했습니다. 실제 Desktop 에이전트의 계획, 도구, 원문 읽기, 결과 검토를 사용했습니다. 회사 데이터 대신 고정된 합성 자료를 사용했습니다.

| 분야 | 실행 | 자동 기준 통과 | 세 번 모두 통과한 문항 |
| --- | ---: | ---: | ---: |
| Code | 60 | 58 | 18/20 |
| Personal | 60 | 59 | 19/20 |
| 합계 | 120 | 117 | 37/40 |

**117/120은 정확도 97.5%를 뜻하지 않습니다.** 자동 채점은 키워드와 출처를 검사합니다. 실패한 Code 2회는 같은 의미의 다른 표현을 놓친 사례였습니다. 반대로 통과한 답변에서도 필요조건을 충분조건으로 바꾸는 오류를 발견했습니다. 원래 점수와 수동 검토를 따로 보존했습니다.

이 실행에서는 모두 답변과 핵심 출처를 반환했고 원본 변경이나 실행 오류는 없었습니다. Code에서 OpenWiki 위임 호출 5회도 관찰했습니다. 응답 시간 중앙값은 Code 42.9초, Personal 42.9초입니다. 최대 세 평가가 같은 제공자를 공유했으므로 독립 실행 속도로 해석하면 안 됩니다.

## 반영한 개선

- **메일 원문 보존:** 인용한 문장과 값이 같고 원문에 실제 존재할 때만 추출 기록으로 받습니다. 거절, 조건, 정정을 임의의 승인이나 확정 값으로 바꾸지 않도록 했습니다. 원문 해시와 문자 위치를 함께 남깁니다.
- **이력 보존:** 메일을 역순으로 가져와도 A → B → A 변경 이력이 남습니다. 같은 시각의 충돌은 숨기지 않습니다. 저장 실패 때는 이력과 새 기록을 함께 되돌립니다.
- **긴 메일:** 첫 3,000자만 읽던 경로를 겹침이 있는 여러 구간으로 넓히고 실제 읽은 범위와 실패를 기록합니다. 한도를 넘는 내용은 전체를 읽었다고 표시하지 않습니다.
- **전체 위키 검색:** 첫 400개 파일 안에서만 순위를 매기던 제한을 바꿨습니다. 프로젝트별 캐시로 수정된 본문만 다시 색인하고, 삭제되거나 제외된 파일은 검색에서 제거합니다.
- **답변 검토:** 필요조건과 충분조건, 정보 부재와 사실 부재, 관찰일과 효력 발생일을 구분하도록 보강했습니다. 추가 지침도 기존 문맥 예산 안에 포함됩니다.
- **가독성:** 짧게 답하라는 지침과 항상 표를 붙이라는 지침의 충돌을 없앴습니다. 표는 비교에 도움이 될 때만 사용합니다. 반복 설명이 완전히 해결된 것은 아닙니다.

관련 자동 검사 150개와 런타임 빌드가 통과했습니다. 별도 실모델 메일 추출 검사 5개도 통과했습니다.

## 검색 성능

1,200개 합성 위키 문서의 마지막 문서를 찾는 시험에서 기존 검색은 놓쳤고 수정본은 찾았습니다. 첫 검색 175ms, 캐시 사용 검색 5회 중앙값 56ms, p95 71ms였습니다. 기존 제한 검색은 51ms였으므로 첫 검색이 빨라졌다는 결과가 아니라, 범위 확대와 본문 재사용을 확인한 결과입니다.

## 생성 품질은 별도 과제

11개 소스의 실제 폴더 위키 생성은 10분 11초와 모델 호출 38회로 완료됐습니다. 문서 12개, claim 파일 7개 안의 claim 75개, 생성 기록과 원본 체크포인트를 보존했습니다. 원본 폴더에는 `.git`을 만들지 않았습니다.

하지만 본문 대조에서 오류를 찾았습니다.

1. 정수 곱셈에는 오차가 없다고 단정했습니다. 안전 정수 범위를 넘는 중간 계산에서는 실제로 결과가 달랐습니다.
2. 알 수 없는 상태는 항상 false라고 설명했지만 `toString` 입력에서는 TypeError가 발생했습니다.
3. 도식 하나는 렌더링 검사 후 텍스트로 대체되어 도식으로 표시되지 않았습니다.

생성 완료와 최신 원본 해시는 내용의 정확성을 보장하지 않습니다. 생성 문서 전체의 주장별 검증, 과도한 일반화 방지와 도식 복구가 다음 우선순위입니다. 이번 생성물은 고쳐서 성공처럼 보이지 않고 원본 평가 산출물로 보존했습니다.

## 검증 범위

이번 결과는 이 Mac의 합성 자료와 선택한 Claude 모델 기준입니다. 사내 메일 실계정, Windows 설치판, 다른 모델, 모든 생성 문서의 정확도를 검증한 결과가 아닙니다. 과제도 이번 작업에서 작성한 수용 검사이며 독립된 비공개 시험 세트가 아닙니다.

원시 자료는 `verification/openwiki-quality-2026-10-15/`에 있습니다. `summary.json`은 120회 기준선, `manual-review.json`은 수동 검토, `generation-folder/content-audit.json`은 생성 본문의 재현 가능한 문제를 담고 있습니다. 구현 상세와 재현 명령은 [개선 기록](OPENWIKI-QUALITY-IMPROVEMENTS-2026-10-15.md)에 있습니다.

## 수정 후 재평가

최종 검토 보강과 표 지침 수정 후 4문항을 각각 3번, 총 12회 다시 실행했습니다. 120회 기준선과는 다른 소스 해시로 보관합니다.

- 자동 기준은 전후 모두 11/12입니다. 수정 후 한 건은 같은 의미의 표현을 키워드 검사가 놓쳤습니다.
- 12개 답변을 직접 읽었을 때 앞서 발견한 필요조건/충분조건 혼동과 권한 정보 부재의 과장은 재현되지 않았습니다. 이는 해당 사례의 재현 결과이며 일반 정확도 보증은 아닙니다.
- 표가 포함된 답변은 12/12에서 0/12로 줄었고 평균 글자 수는 733자에서 677자로 줄었습니다. 반복 설명은 남아 있어 가독성이 완전히 해결됐다고 보지는 않습니다.
- 현재 상태를 과하게 단정하는 첫 문장 한 건은 남았습니다. 과거 메일에 없는 후속 상태를 현재 상태로 단정하지 않도록 하는 추가 보완이 필요합니다.
- 중앙 응답 시간은 43.4초에서 50.6초였습니다. 제공자 동시 부하가 달라 원인 비교는 어렵지만, 사용자 응답 속도가 개선됐다고 주장할 근거는 없습니다.

최종 판단: **검색 범위와 기록의 무결성은 개선됐습니다. 생성 문서의 사실성, 첫 문장의 정확한 범위, 반복 설명과 전체 응답 시간은 남은 과제입니다.** 소스 반영과 런타임 빌드까지 완료했으며 Windows 설치판 배포나 사내 실계정 검증은 이번 범위에 포함하지 않았습니다.
