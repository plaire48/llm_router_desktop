# Luna 5.6와 Sol 5.6 하네스 비교

## 사용자 지적 반영

10월 1일 사용자가 실제 AI Pro 모델의 256K/512K/1M 문맥 한도를 재확인했다. 이번 모델 품질 비교에 기존 L1 22K 진단을 선택한 것은 평가 목적에 맞지 않았다. 실행 중인 Sol의 L1을 중단했고, 이후 비교는 모델 카탈로그의 실제 한도를 사용하는 일반 Agent 5개와 가상 앱 8개만 포함한다. 정상 한도로 끝난 결과를 다시 실행하지 않고 원본 기록을 보존해 재집계한다. Luna와 Sol의 현재 카탈로그 한도는 모두 272,000 토큰이다.

기본 과제 선택에서 한도 덮어쓰기가 있는 진단을 제외하고 평가 실행기에서도 기본 차단한다. 기존 축소 시험은 과거 진단 기록이며 실제 272K 모델의 긴 문맥 품질 실패로 해석하지 않는다. 실제 긴 문맥은 X1~X3의 자료 조회와 대화 누적 조건으로 검증하며, 이번 13개 과제가 256K/512K/1M 전체 용량을 검증한 것은 아니다.

## 확정 비교: 실제 모델 한도

같은 R30 소스와 정상 문맥 한도로 수행한 13개 과제를 집계했다. Sol에서 완료한 10개는 보존하고, 중단 뒤 남은 일반 과제 3개만 `R32-sol-normal-rest`에서 실행했다. 종료 시 동일 후보 해시를 확인했다. [비교표와 원본 연결](../verification/eval-live/R32-catalog-comparison/comparison.md)은 두 완성 보고서의 후보, 자료, 과제, 도구와 한도를 검사한 결과다. 집계 폴더의 `derive.mjs`와 각 `manifest.json.sources`가 원본을 가리킨다.

| 범위 | Luna 5.6 | Sol 5.6 |
|---|---:|---:|
| 일반 Agent 자동 채점 | 4/5 | 4/5 |
| 일반 Agent 답변 전달 | 5/5 | 5/5 |
| 가상 앱 독립 상태 검사 | 7/8 | 8/8 |
| 가상 앱 질문 대기 | 1 | 0 |
| 일반 Agent 주 실행기 / OpenWiki 호출 | 60 / 31 | 65 / 27 |
| 가상 앱 주 실행기 / OpenWiki 호출 | 108 / 10 | 76 / 6 |

일반 Agent의 실패는 서로 다르다. Luna E1은 필요한 50,000원 기준을 답변에 명시하지 않았다. Sol W4는 현재 제공자 17개와 Wiki에 빠진 세 제공자를 맞게 설명했지만, `AI Pro` 표시 이름을 채점기의 `aipro` 문자열과 일치시키지 못했다. 원본 정답이나 결과를 사후 변경하지 않았다. `falseCompletion` 원시 필드는 검토 ready와 자동 채점 불일치이며, 두 건을 실제 작업 성공을 꾸민 사례로 단정하지 않는다. 의미와 표시 이름을 처리하는 독립 채점 개선이 필요하다.

과제당 한 번의 관찰이며 모델 우열의 통계적 증거가 아니다. 실제 모델 로그인과 추론을 사용했지만 앱 입력은 가상 Windows 환경이다. 실제 Windows 조작, AI Pro 실계정, 1M 전체 문맥 용량을 검증한 결과가 아니다.

## 기준

누비의 ChatGPT 로그인 경로에서 `gpt-5.6-luna`와 `gpt-5.6-sol`을 같은 하네스와 과제로 측정한다. OpenMetadata는 제외한다. 개발 중인 하네스의 재현 가능한 비교이며 제품 전체 정확도나 사내 모델 성능을 뜻하지 않는다.

- 일반 작업: W1, W4, C2, L3, E1. Wiki 조회, 뒤처진 Wiki와 소스 대조, 코드 수정, 사용자 정정, 실패한 테스트 진단.
- 제외: L1의 22,000 토큰 압축 진단. 사용자 지적 후 이번 비교에서 제거했다.
- Computer Use: A3, A12, A17, A18, A19, A21, A23, A25. 묶음 입력과 저장, Wiki 규정 연결, 검색과 Enter, 더블 클릭, 문맥 메뉴, 드래그, 이어 쓰기와 저장 키, 비밀번호 입력 거절.
- 각 모델에서 과제당 1회 실행한다. 수정 후 집중 재측정은 별도 표로 남기며 전체 결과를 대체하지 않는다.
- 실제 파일의 숨은 테스트, 변경 범위와 가상 앱 최종 상태를 채점한다. 모델의 완료 선언과 자체 검토는 독립 통과 근거가 아니다.
- 답변 전달, 독립 통과, 잘못된 완료, 질문 대기, 호출 수를 분리한다. 동시 실행과 서버 부하가 있어 시간은 참고치다.
- 정답, 입력, 한도를 통과에 맞춰 변경하지 않는다. 모의 사용자의 답변 부족은 확인 필요로 남긴다.
- 두 로그인 세션의 공개 모델 정보는 모두 문맥 272,000 토큰과 이미지 지원을 반환했다. `provider-status.json`에 인증값 없이 기록했다. 이는 카탈로그 한도이며 실제 최대 문맥 성공을 측정한 결과는 아니다.

## 방법과 선택 근거

[OpenAI 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices)의 과제에 맞춘 반복 평가와 [Anthropic 에이전트 평가 지침](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)의 최종 환경 상태, 실행 기록 확인, 능력 평가와 회귀 평가 분리를 적용한다. 작은 과제와 한 번의 실행으로 모델 우열을 확정하지 않는다.

기존 Pi 실행기와 Node 테스트, 고정된 공개 자료와 합성 자료, Desktop의 실제 도구와 승인 흐름을 재사용한다. 별도 에이전트 프레임워크를 추가하면 운영 하네스와 평가 대상이 달라지므로 추가하지 않는다. Pi의 기존 MIT 의존성을 유지하며 새 패키지나 외부 추적 서비스를 추가하지 않는다. 모델 토큰은 세션 메모리에만 있고 평가기는 전용 로컬 소켓을 사용한다.

## 재현과 수정

기존 회귀 26개 중 3개 실패를 재현했다. 최신 도구 결과 뒤에 `contextOnly` 호스트 상태가 붙으면 압축기가 그 상태만 최신 메시지로 남겼다. 모델이 아직 읽지 않은 검색 결과, 여러 파일의 읽기 결과와 OpenWiki 답변을 먼저 요약해 결과 누락과 재읽기 반복이 생겼다.

공통 `createRunContext`에서 끝의 호스트 상태와 마지막 실제 대화 그룹을 함께 보존한다. 도구 호출과 결과 쌍을 나누지 않는다. 강제 압축에도 같은 경계를 적용한다. 그 결과 하나가 창보다 크면 기존 Desktop의 축소와 원문 재조회 경로로 처리한다. 요약을 수정 관찰이나 승인으로 승격하지 않는다.

수정 후 기존 회귀 26/26, Desktop 전체 634/634가 통과했다. 공통 압축기에는 여러 도구 결과 뒤 상태가 붙는 경우와 너무 큰 결과가 호스트 복구로 넘어가는 경우를 추가했다. 실모델 결과는 별도로 아래에 기록한다.

추가로 발견한 문제:

1. A19에서 UIA가 지원하지 않는 동작에 단일 클릭을 권하는 공통 오류 문구가 선택 반복을 유도했다. `details.reason`과 실패 동작에 따라 안내를 나눴다. 화면 밖 메뉴는 먼저 열고 다시 관찰하며, 목록의 화면 밖 항목은 스크롤한다. 입력 권한과 승인 검사는 바꾸지 않았다. 관련 회귀 34개가 통과했다.
2. A19 반복 측정에서 승인 카드 없이 “승인을 기다립니다”라고 끝내고 검토가 `ready/pending`으로 받아들이는 실패를 관찰했다. 완전한 호스트 목록에서 실제 대기/실행/미확정 동작이 모두 없을 때만 `revise/unknown`으로 되돌린다. 미확정 동작, 누락된 목록과 진행 중인 작업은 재제안 근거로 삼지 않는다. 검토와 이어 실행 회귀 14개를 확인했다.
3. A12에서 이미 답한 메모 범위를 다시 묻는 문제가 있었다. 안내 문구만 추가한 검토 재생 3회 중 2회는 재질문했고, 답변을 별도 요구사항으로 넣은 실험도 일관되지 않았다. 이 두 실험은 제품에 반영하지 않았다. 정답이나 가상 사용자 답을 바꾸지도 않았다.

## 비교를 막은 조건

기존 Sol 세션은 9월 29일에 시작됐고 제공자 코드가 9월 30일에 수정됐다. 수정 전 기본 과제에서 Luna와 Sol 모두 2/2를 통과했지만 연결 코드 버전이 같다는 증거가 없으므로 모델 우열 비교로 사용하지 않는다. 첫 새 Sol 로그인은 3분 콜백 대기가 만료됐고, 이후 R30 스냅샷에서 새로 연 로그인은 성공했다. 기존 세션의 인증값을 가져오지 않았다.

R29 실행 중 공유 소스가 다른 작업에서 변경돼 후보 해시 검사가 다음 묶음 실행을 중단했다. Luna의 가상 앱 8개 결과는 5개 통과, 2개 질문 대기, 1개 답변 문자열 실패였다. 비밀번호 과제의 실제 입력은 0건이다. 실행 당시 소스 전체를 고정하지 않았으므로 이 결과를 완전한 모델 비교에 포함하지 않는다.

이후 `verification/harness-snapshots/R30`에 실행 소스, 생성 모듈과 고정 자료를 복사했다. 의존성 설치 경로만 기존 잠금 버전을 참조한다. R30-control은 같은 스냅샷에서 앱 오류 안내 변경만 제거한 대조군이다. 새 평가기는 종료 시 스냅샷 해시도 재검사한다.

## 실측 산출물

- 수정 전 작은 기준 측정: `verification/eval-live/R28-{luna,sol}-baseline/`.
- 중단된 진단 측정: `verification/eval-live/R29-luna/`, `R29-sol-old-session-unscored/`. 완성된 비교 결과가 아니다.
- 각 비교 폴더의 `manifest.json`: 하네스 해시, 과제와 가상 앱 정의 해시, 자료 해시, 한도, 모델과 실행 환경.
- `runner.mjs`: 실행한 평가 조합. `completion.json`은 종료 시 소스 해시 일치 여부를 기록한다.
- `agent/`와 `computer/`: 개별 결과, 전체 실행 기록과 보고서.
- 고정 소스의 Luna 측정: `verification/eval-live/R30-luna/`.
- 앱 오류 안내 수정 전후 각 3회 측정: `verification/eval-live/R30-computer-replay/`. 집중 측정이며 전체 품질 점수가 아니다.
- 채택하지 않은 검토 지침 실험: `R30-review-replay/`, `R30-review-replay-structured/`.

Computer Use는 Mac에서 가상 Windows 앱을 조작한다. 실제 Windows 11 입력, 실사용 앱, VSIX 설치와 사내 모델 검증은 이번 결과에 포함하지 않는다. 실제 모델 응답은 사용하지만 화면과 마우스/키보드 호스트는 시뮬레이터다.

### 문맥 메뉴 과제 3회씩

| 후보 | 독립 통과 | 나머지 결과 | 주 실행기 호출 |
|---|---:|---|---|
| 같은 스냅샷, 기존 오류 안내 | 1/3 | 질문 대기 2회 | 11, 35, 12 |
| 원인별 오류 안내 | 2/3 | 승인 카드 없이 승인 대기로 끝남 1회 | 4, 15, 20 |
| 원인별 안내 + 실제 승인 대기 검사 | 3/3 | 없음 | 14, 26, 18 |

이 표는 A19 하나의 집중 평가다. R31의 전체 앱/Agent 품질 점수로 바꾸어 말하지 않는다. R31에서 2번째 실행의 최종 모델 검토는 `revise`였지만 독립 앱 상태 검사는 복사본 생성을 확인했다. 자체 검토와 독립 결과는 서로 다른 지표다. R31 스냅샷은 종료 시 후보 해시가 일치했다.

R30의 E1은 실제 테스트를 실행해 7개 중 5개 통과와 2개 실패, 코드의 무료 배송 기준 30,000원과 테스트 입력 49,999원의 차이를 설명했다. 자동 검사는 답변에 요구한 50,000원이 없어 실패로 기록했다. 원인 설명의 유용성과 문자열 검사 한계를 함께 남기며 정답 목록을 수정하지 않았다.

R30의 L1 압축 스트레스는 443초 후 `context_input_too_large`로 중단됐다. 압축은 5회 기록됐다. 마지막 실행기 답변은 소스 수정안만 준비했고 검사와 문서 변경은 실행되지 않았다고 구분했으며, 최종 검토도 `revise`였다. 주 실행기가 한 번에 제안한 3개 도구 중 뒤의 2개는 기존 순차 실행 경계가 `deferred`로 반환했다. 원래 보존 조건은 마지막 요약에 남았지만 최종 적용과 숨은 검사는 완료하지 못했다. 오류를 조건 보존 성공으로 바꾸지 않는다. 이 진단 결과를 실제 272K 모델의 실패나 이번 모델 비교의 개선 우선순위로 사용하지 않는다.

평가 기본값 수정 후 관련 회귀 28개와 비교기 검사 3개가 통과했다. 공유 작업공간의 다른 변경으로 생성 OpenWiki 모듈과 mail 런타임 간 내보내기 불일치가 발생해, 평가 변경의 28개 검사는 고정 R31 런타임에 해당 평가 변경만 적용한 `R32-eval-guard`에서 확인했다. 실모델 실행은 처음부터 고정 R30 소스를 사용하므로 영향을 받지 않았다. 이 시점의 전체 공유 작업공간 빌드 성공으로 표시하지 않는다.
