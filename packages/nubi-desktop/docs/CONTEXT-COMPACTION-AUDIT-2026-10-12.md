# 자동 압축 점검 — 2026-10-12

현재 Desktop은 공통 누비 context-manager를 사용한다. OpenWiki가 대화 전체를 대신 압축하는 구조는 아니다. 압축 동작과 원문 보존은 회귀 검사로 확인했으며, 실제 모델의 반복 압축 후 의미 보존 정확도는 이번 검사만으로 확정하지 않는다.

## 현재 흐름

1. 제공자 카탈로그의 모델 문맥 한도를 유지한다. 출력 여유를 따로 예약하며, 큰 입력 창에서는 전체 한도의 75%에 자동 요약을 시작한다. 예: 262,144 → 196,608. 작은 입력 제한은 입력 예산의 75%를 사용한다.
2. 제공자가 보고한 입력 토큰과 새로 붙은 내용의 추정치를 사용한다. 도구 정의도 포함한다. 정확한 계수가 없는 경우 추정으로 표시한다.
3. 대화 이력은 최근 1~2개 사용자 턴을 남기고 오래된 앞부분을 요약한다. 실행 중에는 최근 도구 호출/결과 묶음, 현재 요청과 원래 요청, 호스트의 현재 요구사항/승인/실행 기록을 유지한다. 긴 중간 사용자 메시지 모두를 무제한으로 보존하는 것은 아니다.
4. 목표, 제약, 결정, 완료, 남은 작업, 참조를 JSON으로 요약한다. 긴 입력은 여러 조각으로 처리하며, 잘못되거나 잘린 요약은 같은 원문으로 한 번 더 요청한다. 구조와 크기 검사는 의미 보존 보증과 다르다.
5. 원본 대화는 SQLite에 남는다. 저장 요약은 메시지 경계와 SHA-256에 묶여 수정된 이력에 재사용되지 않는다. `read_conversation`으로 이 대화의 원문을 다시 읽을 수 있다.
6. 압축 후 오래된 파일 관찰로 편집을 승인하지 않는다. 원문이 그대로 남은 관찰만 복원하고 Wiki 근거는 현재 문서와 다시 대조한다. 요약 자체는 실행 완료나 쓰기 승인이 아니다.

## 이번 수정

- 실제 광고하는 도구만 최초 이력 및 실행 문맥 계산에 포함한다. 이전에는 lean 모드에서도 등록된 모든 도구를 계산해 이력을 먼저 압축할 수 있었다. 기존 P1 시험 입력은 수정 후 불필요한 요약 없이 처리된다. 압축 필요 시나리오는 별도 compaction-turn 검사로 유지한다.
- 요약 호출의 maxTokens를 Desktop transport에서 제공자까지 전달하고, OpenAI-compatible 제공자는 해당 호출에만 적용한다. 첫 요약 2,048/4,096 및 재시도 한도는 공통 예산을 따른다. 일반 답변의 출력 한도는 바꾸지 않는다.
- ChatGPT 브라우저 연결은 Pi의 별도 Responses 어댑터를 사용한다. 이 수정으로 ChatGPT 서버의 출력 한도나 서버 전용 compaction 지원이 추가됐다고 표시하지 않는다.

## OpenWiki를 더 활용하는 방향

메일 질문은 이미 선택한 메일 원문과 해당 Personal 정리를 같이 읽는다. 프로젝트는 ask_openwiki/wiki_query와 원문 범위를 읽는다. 이는 압축과 별개인 자료 조회다. 오래된 대화를 무조건 Personal에 쓰면 임시 판단, 잘못된 사실, 과거 승인이 장기 기억으로 섞일 수 있다.

후속 개선은 요약의 참조에 원문 위치/해시/당시 시점을 유지하고, 날짜/금액/식별자 같은 정확한 질문에는 원문을 재조회하는 방식이 적합하다. 위키를 생성하는 시점과 사용자 대화를 압축하는 시점을 한 작업으로 묶지 않는다.

## 남은 품질 검증

- 카탈로그의 실제 문맥 한도에서 충분한 대화를 만들어 연속 3회 이상 압축한다. 과거 22K 축소 시험은 진단 사례이며 일반 품질 점수가 아니다.
- 최신 정정, 금지 조건, 금액/날짜, 선택한 메일 범위, 완료/미완료 상태, 출처 연결, 원문 재조회 후 답변을 독립 채점한다.
- 압축 전후 정답률, 소요 시간, 요약 비용, 회수 토큰과 요약 실패를 따로 기록한다. 근거 없는 단일 종합 점수나 JSON 유효성만으로 완료하지 않는다.
- 회복 가능한 요약 실패의 반복을 실행 사이에서도 억제할 필요가 있는지 실제 호출 기록으로 판단한다. 현재 실행 안에서는 재시도 지점을 뒤로 미루지만 실행 사이의 실패 상태는 별도 저장하지 않는다.
