# 시작과 기록 조회 최적화

2026-10-14. 사용자의 ‘느리지만 iOS 같은 느낌과 애니메이션은 유지’ 요청에 따른 변경이다. 최신 1.2.5 소스의 인증 수정과 기존 Claude 변경을 유지했다. 이번 작업은 설치 파일 배포가 아니다.

## 확인한 원인과 변경

### 시작 시 읽는 코드

실제 배포 번들의 정적 import 의존성을 합산했다. 기존 초기 JavaScript는 4,821,955바이트였고, 같은 브랜드 PNG의 base64 문자열이 두 모듈에 각각 약 1.17MB씩 들어 있었다. 또한 기본 화면에서 사용하지 않는 앱/문의 구현과 도움말까지 초기 의존성에 포함돼 있었다.

- 같은 브랜드를 공통 원본으로 연결했다. 배포 빌드는 원본 PNG 바이트를 그대로 외부 파일 한 개로 내보낸다. 리사이즈, 재압축, 색상 변경은 없다.
- AI Workspace의 앱/Talk/문의 구현은 해당 화면을 열 때 불러온다. 문의 헤더의 React context를 작은 독립 모듈로 분리해 context 참조만으로 전체 문의 화면을 읽지 않게 했다.
- 처음 필요한 JavaScript는 1,971,239바이트로 약 59.1% 감소했다. 별도 이미지 881,288바이트는 이 JS 수치에 포함하지 않았다. 첫 화면의 해당 이미지까지 합치면 2,852,527바이트다. 전체 앱 설치 크기가 59% 줄었다는 뜻은 아니다.
- 파일 로더와 지연 로딩은 기존 esbuild/React를 사용한다. 새 라이브러리를 추가하지 않았다. 테스트 fixture에서는 기존 data URL 접근을 유지해 시각 검사 경로를 깨지 않는다.

### 기록이 쌓인 프로젝트

`overview`와 매초 조회하는 `state`는 DB의 전체 task/proposal/process 목록을 가져와 JSON을 파싱한 뒤 50/20개로 잘랐다. 기록이 쌓일수록 화면 갱신과 다른 요청을 처리하는 worker의 동기 작업이 늘어난다.

- 화면에서 사용할 개수를 SQLite LIMIT으로 먼저 적용했다. 기존 정렬과 반환 내용을 유지했다.
- LIKE prefix 조회에 맞는 NOCASE 인덱스를 추가했다. 기존 데이터는 유지하며 첫 열기에서 인덱스를 만든다.
- 50개 목록에 없는 오래된 선택 대화는 별도로 추가한다. 전체 대화 검색과 agent가 사용하는 무제한 조회는 유지한다. 승인/복구 기록이나 원문을 삭제하거나 생략하지 않는다.

## 유지한 경험

시네마틱 인트로, 새의 동작, View Transition, 모달 진입/퇴장 시간과 공통 색상/서체/CX 토큰을 변경하지 않았다. 모델 응답이나 서버 대기 시간을 가상 진행률로 숨기지 않는다. 줄인 것은 초기의 불필요한 로딩과 전체 기록 반복 파싱이다.

## 측정과 회귀 검사

[최종 결과](../verification/performance-2026-10-14/results.json)와 실행 로그를 같은 폴더에 보관한다.

| 측정 | 이전 | 변경 후 | 범위 |
| --- | ---: | ---: | --- |
| 초기 JavaScript | 4.82MB | 1.97MB | 정적 초기 의존성, 약 59% 감소 |
| 상태 조회 중앙값 | 35.68ms | 12.11ms | 합성 대화 3,000개, 20회 |
| 상태 조회 p95 | 47.56ms | 12.47ms | 같은 합성 기록 |
| 첫 화면 중앙값 | 445ms | 399ms | macOS Electron 3회, 인트로 제외 |
| 프로젝트 준비 중앙값 | 1,267ms | 1,205ms | 작은 Git 프로젝트 |
| JS heap 중앙값 | 19.43MB | 13.42MB | 같은 화면 순서, GC/OS 영향 있음 |
| 전환 프레임 간격 p95 | 21.8ms | 21.7ms | 실제 View Transition 유지 |

각 측정 묶음의 첫 launch는 5.68초와 5.49초였으며 이후 실행보다 훨씬 느렸다. OS/Electron 실행 캐시 영향을 이번 수정의 효과로 주장하지 않는다. 기존/변경 후 모두 측정한 화면 전환 구간에서 50ms 이상 long task는 없었다. 서버/모델을 연결하지 않은 작은 UI 흐름에 한정된다. 화면 클릭 시간은 Playwright가 애니메이션 안정화를 기다리는 시간도 포함하므로 순간 입력 지연으로 해석하지 않는다.

전체 검사 1,249개 중 1,053 통과, 실패 0, 건너뜀 196. 전체 검사 시작 이후 추가한 번들 회귀 1개도 별도 통과했다. Electron 빌드와 identity 검사 통과. AI Workspace UI는 1100/440px, 채팅 전송은 1280/440/360px에서 지연 응답/즉시 말풍선/초안/대기/실패 복구를 확인했다.

 `measure-desktop-performance.mjs`는 실제 Electron을 임시 저장소와 작은 Git 프로젝트로 3회 실행한다. 첫 화면/프로젝트 준비, 화면 열기, 실제 View Transition 중 프레임 간격, long task와 메모리를 기록한다. 자동화에서 인트로가 생략되므로 그 시간을 ‘사용자가 실제 앱에 진입하는 전체 시간’으로 주장하지 않는다. 실행 캐시와 OS 부하의 영향을 구분하며 최초 OS cold launch 한 번의 값을 일반 성능으로 사용하지 않는다.

`measure-state-performance.mjs`는 합성 긴 답변 3,000개를 저장하고 최근 50개+이전 선택 대화 한 개가 나오는 동일한 state API를 워밍업 3회 후 20회 측정한다. 실모델 응답 속도나 사내 서버 성능 측정이 아니다.

회귀 검사는 기록 순서, 수정/삭제, 재열기, 오래된 대화 선택/검색, 프로젝트별 실행 보존을 확인한다. 빌드 검사는 초기 의존성에서 앱/문의 구현이 빠졌는지와 이미지가 원본과 byte-for-byte 동일하며 한 번만 출력되는지 확인한다. 실제 앱과 Talk의 목록/열기/등록/오류/재로그인 및 1100/440px 화면도 검사한다.

## 근거와 다음 실환경 확인

[Electron 성능 지침](https://www.electronjs.org/docs/latest/tutorial/performance)의 필요한 시점에 모듈 읽기와 동기 작업 최소화를 적용했다. [esbuild 파일 로더](https://esbuild.github.io/content-types/#file)를 사용해 이미지를 JS 문자열에서 분리했다. 모션을 없애는 방식이나 새 UI 프레임워크 도입은 선택하지 않았다.

Windows 11에서 기록이 많은 실제 프로젝트, 사내 메일함, 서버 지연과 모델 응답까지 포함한 체감 시간은 별도 확인해야 한다. 특히 첫 설치 뒤 기존 기록에 인덱스를 만드는 시간은 기록 규모에 따라 달라진다. 로컬 결과를 전체 기능/모든 PC의 무끊김 보증으로 확대하지 않는다.
