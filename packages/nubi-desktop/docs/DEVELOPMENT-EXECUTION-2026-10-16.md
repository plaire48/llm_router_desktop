# 개발 실행 첫 적용과 확인 범위

2026-10-16. 대상은 전용 Electron 누비 Workspace다. 사용자가 승인한 [개발 사이클 분석과 벤치마크 계획](../../../docs/research/2026-10-16-workspace-dev-cycle-oss-context-benchmark.md)의 첫 적용이다.

## 개발에서 달라지는 점

| 상황 | 이번 적용 |
| --- | --- |
| npx 생성기와 설정 도구가 질문을 기다림 | 승인한 명령을 실제 PTY로 실행한다. 최신 출력을 읽은 뒤 정확한 입력을 별도 승인으로 한 번 전달하고 같은 작업을 이어간다. |
| 서버 시작 로그만 있고 페이지가 열리지 않음 | 해당 작업의 살아 있는 프로세스 로그에서 관찰한 localhost URL에만 HTTP 확인을 수행한다. 이후 실제 브라우저 동작 확인을 안내하고 완료 검토에 실행 근거를 연결한다. |
| 문법은 맞지만 타입이나 호출자를 놓침 | 기존 TypeScript 컴파일러 worker에 JS/TS 진단, 정의, 참조 조회를 추가한다. 원문 해시와 조회 범위를 반환한다. |
| 사람과 에이전트가 다른 PowerShell을 사용함 | 실행 파일 발견 로직을 공유한다. PowerShell 7 설치 경로와 PATH를 확인하고 Windows PowerShell로 이어진다. 실제 Windows 실행 성공은 별도다. |
| 입력 승인이나 서버 후속에서 전체 작업을 다시 시작함 | 기존 Pi와 명령 후속 계약을 사용한다. 동일 승인과 입력은 영수증으로 중복을 막고 기존 계획을 이어간다. |

모델은 `propose_setup_action`에서 `interactive:true`를 선택할 수 있다. 입력은 `read_process_output`의 현재 `inputRevision`을 읽고 `propose_process_input`으로 제안한다. 개행도 입력의 일부이며 화면에는 JSON 이스케이프를 표시한다. 그 사이 출력이나 입력이 변하면 승인을 거절하고 다시 관찰한다. 입력에는 항상 허용을 제공하지 않으며 관리자 실행과 제어 문자 입력은 지원하지 않는다. 비밀번호나 자격 증명을 모델 입력으로 전달하지 않는다.

`inspect_dev_server`는 최대 5초, 본문 8KiB의 HTTP 응답 검사다. 포트가 명시된 localhost, 127.0.0.1, IPv6 loopback만 허용하고 redirect와 임의 호스트는 거절한다. `functionalVerified:false`, `processOwnership:not_verified`를 유지한다. 로그에 출력한 주소가 해당 프로세스가 점유한 포트라는 OS 증명은 아니다. 실제 페이지 입력/클릭과 요구 결과는 기존 BrowserHost와 Playwright 경로로 확인해야 한다. 최신 실패나 중지 후 과거 응답 성공을 완료 근거로 사용하지 않는다.

`inspect_code`는 대상과 같은 폴더를 우선한 닫힌 정적 스냅샷이다. 최대 200파일, 전체 4MiB, 파일당 256KiB다. 표준 라이브러리, 설치 의존성, tsconfig alias, 프로젝트 plugin과 미저장 버퍼는 읽지 않는다. 누락과 미해결 import를 반환하며 전체 프로젝트 타입 검사나 수정 권한을 대신하지 않는다. 프로젝트의 실제 typecheck/test 명령은 계속 필요하다.

## 기존 구현과 오픈소스 재사용

새 실행 프레임워크를 중첩하지 않았다. 기존 Pi, 승인 카드, Processes, SQLite 영수증, 명령 후속, 분석 worker를 확장했다. 실제 PTY는 이미 설치된 node-pty, 의미 탐색은 기존 TypeScript 5.9.3, 화면 검사는 기존 Playwright와 Electron을 사용한다. Codex unified exec의 세션/입력/출력 분리 구조를 참고했으며 다른 에이전트 런타임 전체나 인증 저장소를 가져오지 않았다.

일반 조회에 도구 설명이 계속 늘지 않도록 세 개발 도구는 개발/환경 작업에서 노출한다. 기존 작은 문맥 도구 예산 검사를 유지한다. 문맥 압축 기본값은 75%이며 변경하지 않았다. 90% 고정 정책은 앞선 가상 재생에서 요약 호출은 감소했지만 추정 입력 합은 약 17.7% 증가했다. 실제 모델 품질 비교 없이 더 효율적이라고 판단하지 않는다.

## 확인과 최초 실패

검사 원본은 [증거 폴더](../verification/development-execution-2026-10-16/)에 보존한다.

- 새 기능 검사를 먼저 실행해 실패를 확인한 뒤 구현했다. 실제 POSIX PTY, 입력 1회, 다른 작업/오래된 관찰/제어 문자 거절, HTTP 주소 바인딩, 최신 실패/중지 판정, 컴파일러 타입 오류와 파일 간 참조, Pi fixture의 입력 후 작업 이어쓰기를 포함한다.
- 빌드한 macOS Electron의 실제 main → IPC → 서비스 → PTY/HTTP/컴파일러 worker 경로 5개가 통과했다. 실제 `npx --offline --no -- nubi-development-fixture`로 격리된 로컬 bin을 실행했고 TTY, HTTP 200, 타입 오류, 중복 승인 방지와 서버 중지를 확인했다. 외부 패키지 다운로드, 프레임워크별 설치와 모델은 호출하지 않았다.
- 승인 React 컴포넌트는 1280/440px와 100/125%의 4개 조합에서 승인 1회, 정확한 입력 표시, 실행 기록, 중지 콜백과 가로 넘침 0을 확인했다. 이는 컴포넌트 브라우저 fixture이며 native 앱의 모델 제안 흐름 성적은 아니다.
- 기존 native Electron shell 검사는 실제 파일 저장/재읽기, Git 비교/이력, 직접 입력 PTY, Ctrl+C, 한글/폴더 이동 유지, 인앱 웹과 좁은 화면을 확인했다. 단일 실행 시간은 일반 성능 벤치마크로 삼지 않는다.
- 첫 전체 회귀에서 실패 4건이 있었다. 개발 도구 추가로 생긴 도구 배열 참조 변경 1건은 수정했다. 나머지 3건의 모델 호출 횟수 기대값은 원본 소스를 제공하는 loader로 변경 전에도 같은 실패를 재현했다. 현재 제한된 복구 흐름에 맞게 기대값을 정정하고 실제 읽기 횟수, 원래 기준의 재전달, 제안 없음과 원본 보존 조건을 유지했다.
- 첫 빌드는 성공했지만 실제 앱 시작은 ESM `import.meta.url`을 CJS main으로 묶는 경로에서 실패했다. PTY native 로딩을 CJS helper로 분리하고 node-pty를 external로 유지한 뒤 다시 빌드해 실제 앱 검사 5개를 통과했다. 빌드 성공만으로 앱 실행 성공을 보고하지 않는다.

최종 `npm test`는 전체 1,666개 중 1,470개 통과, 실패 0개, 환경별 건너뜀 196개다. 약 348.5초가 걸렸다. 빌드와 디자인 검사도 통과했다. 관련 집중 검사는 60개 통과와 Windows 전용 1개 건너뜀이다. native shell 검사는 22개 확인 항목을 통과했다. 실행 수와 파일/빌드 해시는 [implementation-summary.json](../verification/development-execution-2026-10-16/implementation-summary.json)에 기록했다.

## 남는 검증과 다음 적용

현재 relay는 `worker_disconnected`여서 실제 모델의 자율 개발 성적은 측정하지 못했다. Windows ConPTY, PowerShell 실제 버전/실행, 설치/업데이트와 사내 서비스도 미검증이다. 로컬 소스와 macOS 개발 앱 확인을 Windows 설치판 완료로 표시하지 않는다.

다음 적용은 현재 실패 trace에 따라 관련 코드 지도 선택, 프로젝트 설정을 반영한 의미 분석, 다른 언어의 LSP 어댑터를 순서대로 검토한다. 75/85/90/적응형 정책은 동일 모델과 실제 카탈로그 문맥, 같은 출력 예약과 개발 과제로 비교한다. 실제 완료율, 요구 보존, 중복 실행, 전체 usage와 작업 시간을 함께 측정한 뒤 기본 정책을 정한다. 이 후속 기능이나 실모델 비교는 이번 첫 적용의 통과 범위가 아니다.
