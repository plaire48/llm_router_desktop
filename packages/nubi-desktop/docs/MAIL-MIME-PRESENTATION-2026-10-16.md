# MIME 내용으로 첨부 메일 읽기

사용자 설명: 첨부로 들어온 파일도 기존 `.mysingle`과 같은 MIME 파싱 방식으로 읽는다. 파일 확장자에 의존하지 않고 실제 내용을 확인한다. 본문은 본문으로 보여주며 내부에 실제 파일이 있을 때만 첨부 목록에 넣는다.

2026-10-17에 제품 실행 경로를 연결했다. 이전의 설계 전용 확인과 구분한다. 실제 Office 화면 삽입은 별도이며 아직 구현하지 않았다.

## 표시와 사용자 흐름

| 구성 | 표시 |
| --- | --- |
| 제목, 발신/수신/참조, 날짜 | 기존 메일과 같은 머리글 위계 |
| 텍스트/HTML 본문 | 메일 본문. 가짜 `본문.html`/`본문.txt` 첨부를 생성하지 않음 |
| 본문 인라인 이미지 | 기존 MIME presentation/MailBody 경로 |
| 실제 내부 파일 | 내부 첨부 목록과 다운로드 |
| 원래 받은 MIME 컨테이너 | 원본 첨부 다운로드로 바이트 그대로 보존 |

첨부 열기는 오른쪽 기존 보조 문서 영역을 사용한다. 부모 메일과 선택을 유지하고 닫은 뒤 다시 열 수 있다. 기존 메일 UI, 아이콘, 글자와 색 토큰을 재사용한다.

사용자 후속 요청으로 일반 문서용 긴 안내/중복 질문 입력창을 제거했다. 오른쪽 제목은 `첨부 메일`로 표시하고 머리글에서 메일 제목, 발신자 이름과 보조 주소를 구분한다. `AI에 질문`, 추출 텍스트 보기와 원본 다운로드를 기존 메일 도구 줄에 모은다. 질문은 기존 중앙 에이전트의 초안/명시적 전송 흐름을 사용한다. 첨부 열기나 다운로드만으로 대화로 이동하거나 질문을 자동 전송하지 않는다. 내부 파일의 미열람 범위는 목록 아래 짧게 유지한다.

## 공통 토큰 후속 보완

클래스 재사용만으로 일치했다고 판단한 첫 화면은 부족했다. 실제 적용 값을 대조해 일반 패널 header의 12px 간격과 메일의 8px 간격, 첨부 행의 보조색/일반 굵기 차이를 확인했다. `desktop-mail-source`의 글꼴/색/배경과 머리글/첨부 행을 공통 토큰으로 통일했다. 미열람 안내도 공통 보조 글자 크기와 간격을 사용한다.

격리된 HTML 본문에는 부모 CSS 변수가 상속되지 않아 기존 고정 15px 글자와 브라우저 기본 제목 크기가 적용됐다. MailBody가 고정된 허용 토큰 목록과 루트 글자 크기만 iframe에 전달하고 스타일/크기 변경을 반영한다. HTML 기본 본문/제목/링크/보조색/강조/문단 간격은 같은 토큰을 사용한다. 원본 HTML의 명시적 인라인 서식과 표/이미지, 정화/스크립트 차단/CSP는 유지한다. 모델에 보내는 추출 텍스트나 원문 바이트는 바꾸지 않는다.

`computed-styles.json`은 실제 부모 메일과 첨부 미리보기의 적용 값을 기록한다. 최종 1480/1100/440 화면에서 비교 가능한 메일 요소 10종의 적용 값 차이는 각각 0건이다. 시험은 글꼴/크기/굵기/행간/글자색/패딩/마진/둥글기/간격의 일치를 확인하며, iframe의 본문 크기/서체/색과 제목 크기도 호스트와 대조한다. hover에 따른 표면 차이와 원본이 지정한 서식을 앱 기본 토큰과 혼동하지 않는다. 기존 HTML 복구/실제 첨부 보존/스크립트 제거/좁은 화면 회귀는 `html-regression.log`에 별도 기록했다.

## 실행 연결

- `runtime/mail-mime-content.mjs`: 헤더 문법, 메일 식별 헤더, Content-Type, MIME-Version 또는 기존 내보내기 식별자를 확인한다. 일반 `.dat`/`.bin` 파일도 내용이 맞으면 해석한다. 확장자만으로 확정하지 않는다.
- `runtime/document-extract.mjs`: 기존 제한된 첨부 worker에서 공통 `normalizePortalMail`/`parsePop3Content`를 재사용한다. 모델용 결과에는 본문과 작은 머리글을 포함하고 원문 base64/내부 파일 바이트를 넣지 않는다.
- `runtime/desktop-features.mjs`: 수동 열기도 기존 portal worker로 해석한다. 취소/메일 세대, 부모 원문 해시와 컨테이너 바이트를 다시 확인하고 기존 읽기 영수증을 저장한다.
- `ui/MimeMailPreview.jsx`, `ui/DocumentPreview.jsx`: 기존 MailBody 정화/iframe 격리를 사용하고 `presentation=attachment`인 실제 파일만 나열한다. `desktop-mail-source`의 공통 여백/머리글과 메일 도구 스타일을 재사용한다.
- `runtime/mail.mjs`, Electron main/renderer: 부모 원문/첨부 ID/첨부 해시/내부 ID/내부 해시를 확인해 원래 내부 파일 바이트를 기존 저장 대화상자로 넘긴다. 저장 후 실제 파일 크기와 해시를 확인하는 기존 계약을 유지한다.

문서 읽기의 64 MiB 파일/2,000,000자 한도를 유지한다. 목록 미리보기의 32,000자 제한을 문서 전체 읽기에 재사용하지 않는다. 화면/AI 읽기는 기존 60,000자 범위로 나누고 남은 범위를 명시한다. 내부 파일은 자동 분석하지 않는다.

## 한계

- 내부 첨부는 한 단계 목록/다운로드까지 연결했다. 재귀적으로 모든 중첩 메일을 여는 탐색기는 구현하지 않았다.
- MIME-Version/내보내기 식별자나 지원 Content-Type이 없는 파일과 다른 사내 전용 포맷을 MIME으로 추측하지 않는다. 실제 회사 원문은 제공받아 검증하지 않았다.
- 과거 실패 캐시 전체를 자동 재처리하지 않는다. 원본이 보관된 첨부를 사람이 다시 열면 새 파서로 읽는다.
- 원본 미보관 설정으로 이미 버린 컨테이너/내부 파일을 복구하지 않는다. 추출 본문만 보관된 경우 기존 읽기 범위를 유지한다.
- Office 2016/NASCA 문서의 native 읽기/열기 및 실제 Office 화면 삽입은 별도다.

## 검증 근거

기록: `verification/mail-mime-container-2026-10-16/` (작업 시작일 기준 폴더명).

- `baseline.log`: 기존 회귀 31/31.
- `red.log`/`green.log`: 첫 재현 2건의 `document_format` 실패와 수정 뒤 통과.
- `long-body-red.log`: 32,000자 이후 내용 유실 재현. 수정 뒤 관련 회귀 34/34는 `focused.log`.
- `full-test.log`: 전체 Node 회귀 1,746건 중 통과 1,549/건너뜀 197/실패 0. 이후 화면 정리의 최종 검사는 별도 `final-focused.log`와 Electron 재실행으로 구분한다.
- `final-focused.log`: 화면 정리 후 관련 회귀 58/58 통과.
- `build.log`: 최종 Electron 빌드 성공. PowerShell이 없어 Windows Office reader 확인은 건너뛴다.
- `native-checks.json`, `native.log`, `native-mail*.png`: 실제 빌드한 macOS Electron의 합성 EML 수집/암호화/IPC, 본문 iframe, 실제 내부 첨부, 부모/내부 파일 바이트 일치, 닫기/재열기/Enter와 Space 텍스트 전환, 질문 동작 한 개/중복 입력창 제거, 도구 겹침 없음을 확인했다. 저장 대화상자의 선택 경로는 시험이 주입했다. 1100/440 viewport와 루트 글자 20px를 확인한다.
- 최초 UI 시험에서는 fixture의 가져오기 폴더 분류가 받은 메일함과 달랐다. `AUTO_INBOX`로 fixture를 수정했다. 다음 실행은 native 창 리사이즈 뒤 스크린샷 제한 시간에 걸렸다. viewport 크기와 실제 innerWidth를 검증하는 시험으로 수정했다. 제품 성공으로 이 실패 이력을 지우지 않는다.
- `design-check.log`: 당시 전체 디자인 정적 검사는 기존 `ui/native-document-preview.css`의 고정 글자 크기에서 실패했다. 후속 [전체 화면 토큰 점검](DESIGN-TOKEN-AUDIT-2026-10-17.md)에서 전체 UI와 함께 수정하고 정적 검사/빌드/실제 Electron MIME 흐름을 다시 통과했다. iframe의 번들 한글 글꼴 로드도 후속 검사에서 확인했다.

합성 메일과 macOS Electron 결과다. 실제 회사 `.mysingle`, 사내 실계정, Windows 11/Office 2016/NASCA, 실제 모델 답변이나 설치판 배포 성공으로 확대하지 않는다.
