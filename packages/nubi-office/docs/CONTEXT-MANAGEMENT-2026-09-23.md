# Office 컨텍스트 관리 개선

기준: Windows Office 2016, 사내 카탈로그의 Qwen 3.8 27B. 실제 API ID와 사용자가 선택한 모델을 유지한다. 2026-09-23 소스 반영이며 설치파일/번들/native 빌드는 실행하지 않았다.

## 확인한 문제와 반영

| 문제 | 실제 적용 | 보존 경계 |
|---|---|---|
| 작업창이 최근 20개만 보내고 실행기가 다시 최근 8개/20개와 각 메시지 앞부분을 잘라냄 | 작업창에 남아 있는 전체 대화를 전달. 실행별 원문 저장소와 검색 색인을 만들고 현재 문맥에 필요한 정확한 구간을 전달 | 전달되지 않았거나 창 종료로 사라진 대화를 복원하는 기능은 아님. native 전달 한도는 아래 참고 |
| 오래된 업무 사실을 다시 가져올 도구가 없음 | Excel 셀/양식, 새 통합문서, Word/PPT 실행기에 `recall_context` 연결. query 검색과 sourceId/offset 순차 조회 지원 | 역할, 시간 순서, 원문 위치, 전체 길이, 다음 위치 보존. 과거 assistant 주장은 검증 근거가 아님 |
| 문서 페이지를 읽어도 원하는 입력 항목을 찾기 어려움 | Word/PPT `search_document`로 현재 실행이 읽은 항목의 제목/태그/이름/본문/노트 검색. offset/itemId로 native 재조회 | 아직 안 읽은 페이지는 검색 대상이 아님. 검색 결과만으로 쓰기를 승인하지 않음 |
| 도구 결과와 스키마를 합친 요청 크기를 검사하지 않음 | 공통 호출 경로와 Excel 독립 분석 경로에서 무손실 그리드 압축 후 전체 messages+tools 크기 검사 | 원본 수식/값, 승인, 실행 결과를 삭제하거나 의미 요약하지 않음. 초과한 동일 요청의 네트워크 재시도 금지 |
| 도구 호출 횟수만으로 문맥 재구성 시점 판단 | 기존 8회 기준에 누적 요청 크기 기준 추가. 확인한 셀 상태/초안/완료 단계/답변으로 재구성 | 완료된 쓰기를 재실행하지 않음. 결과 유실은 기존 receipt 조회 규칙 유지 |
| Word/PPT 현재 항목 분량만 계산 | 페이지 색인과 생략 ID까지 포함해 모델 문맥을 제한. 단계별 실제 완료 상태도 함께 전달 | 원본 페이지/최종 검토 근거는 별도 유지 |

## 방법론과 라이브러리 선택

- **[Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)**: 필요한 시점에 원문을 조회하는 방식, 가벼운 참조, 구조화된 작업 상태를 적용했다. 작업 결과/업무 사실을 모델이 임의로 요약한 문장으로 교체하지 않는다. 모델 기반 요약과 실제 정확도 향상을 구현/검증했다고 주장하지 않는다.
- **[LangGraph memory](https://docs.langchain.com/oss/javascript/concepts/memory)**: 실행별 문맥과 장기 기억의 분리, 모델 메시지와 상태 저장소의 분리를 참고했다. 현재 Pi 실행기와 중복되므로 LangGraph 런타임/외부 체크포인트 DB는 추가하지 않았다.
- **[MiniSearch 7.2.0](https://github.com/lucaong/minisearch)**: **실제 production 의존성으로 도입**. MIT, 외부 의존성 0, Node 메모리 내 검색. 제목/본문의 정확한 출처를 되찾는 용도로 사용한다. 한국어 조사에 대응하는 2글자 검색 항목과 코드/숫자 분리를 추가했다. 정규화는 색인에만 사용하며 원문은 변경하지 않는다. fuzzy 검색과 외부 임베딩 호출은 사용하지 않는다. 의미 검색/한국어 형태소 분석과 같은 기능은 아니다.
- **기존 Pi / p-retry / fast-check**: 같은 모델과 실행기를 유지하고, 입력 초과는 영구 오류로 분류해 동일 요청을 반복하지 않는다. fast-check로 원문 분할/재결합과 기존 관찰 보존을 검사했다.
- **토크나이저**: 사내 Qwen 모델의 실제 tokenizer/config를 확인하지 못했다. 다른 모델용 tiktoken 수치를 Qwen의 정확한 토큰 수로 사용하는 방식은 채택하지 않았다. 실제 사용량은 기존 provider 보고값만 사용한다.

MiniSearch MIT 전문은 `licenses/minisearch-MIT.txt`에 포함되며 기존 설치 스크립트가 licenses 디렉터리를 함께 복사한다. 별도 검색 서버, Python, 사용자가 추가 설치할 서비스, 계정 연결은 없다. 새 의존성의 Windows 번들 검증은 최종 빌드 때 필요하다.

## 원문과 모델 문맥의 계약

1. 원래 요청, 같은 실행에서 받은 답변, 계획/완료 상태, native 바인딩/수식/값과 receipt는 기존의 권위 있는 상태로 유지한다. 검색 결과나 요약문이 이를 덮어쓰지 않는다.
2. 과거 대화는 실행별 저장소에 원문으로 유지한다. 최근 메시지의 앞/뒤 구간, 직전 명시적 조회, 첫 요청, 검색 관련 구간을 우선하되 결과는 원래 순서로 정렬한다. 사용자 정정은 시간 순서로 해석한다. 관련성 순위 자체가 사실의 권위나 현재값을 결정하지 않는다.
3. 대화 working window는 JSON 기준 16,000자 이내, 한 원문 구간은 1,800자다. 검색은 최대 4구간, 직접 조회는 1구간을 반환한다. `nextOffset`으로 손실 없이 이어 읽을 수 있다. 최대 500개 메시지/원문 1,000,000자이며 초과를 묵시적으로 자르지 않는다.
4. 새 조회는 문맥 재구성 뒤에도 최근 조회 구간으로 유지한다. 같은 구간을 반복 읽은 횟수는 작업 진전으로 계산하지 않는다. 현재 입력 답변은 검색 대상으로 축소하지 않고 기존 답변 계약 안에서 그대로 전달한다.
5. Word/PPT 검색은 같은 host/scope/document/fingerprint의 현재 캐시만 허용한다. native 적용 후 페이지 캐시가 교체되면 다음 검색은 새 캐시로 다시 색인을 만든다. 검색이 0건이어도 문서에 해당 사실이 없다고 단정할 수 없다.
6. 작업 내용은 worker 메모리 안에만 있다. 검색 색인을 별도 파일/서버에 저장하지 않는다. NASCA 원본의 열기/저장은 기존 Office 경로를 유지한다. 현재 모델 요청에 선택된 문맥을 보내는 기존 경계는 같다.

## 예산과 남은 한계

- 120,000자: 누적 tool 결과가 있는 Excel actor의 조기 문맥 재구성 기준. 원래 요청만 큰 경우 의미 없이 같은 checkpoint를 반복하지 않는다.
- 240,000자: JSON messages+tools의 로컬 요청 상한. `requestContext` 지표에 실제 문자/UTF-8 byte 최대값과 차단 횟수를 기록한다. **모델 토큰 한도나 Qwen 처리 용량의 보증이 아니다.** 시스템 프롬프트와 스키마도 이 수치에 포함한다.
- 220,000자: 작업창의 runStart payload 상한. native pipe의 250,000자 한도에 여유를 두고 전송 전에 알린다. 원래 대화/입력 초안은 유지한다. 매우 긴 대화를 분할 전송하는 프로토콜은 미구현이다.
- Word/PPT 전체 근거 검토의 **180,000자 상한은 그대로**다. 전체 근거가 넘으면 완료 판정을 내리지 않는다. 부분 평가만 합쳐 전체 완성을 승인하는 오류를 피하려면, 다음 단계에서 요구사항별 근거 연결과 문서 전체 관계 검증을 갖춘 계층 검토가 필요하다.
- router/planner/final reviewer는 자동으로 선택된 과거 문맥을 받으며 직접 recall 도구를 실행하지 않는다. actor는 recall을 사용할 수 있다. 어느 단계든 중요한 과거 사실을 반드시 모두 회수한다는 보장은 없으며, 누락/모호한 사실은 HITL로 확인해야 한다. retrieval 정확도와 누락률은 실제 모델로 평가해야 한다.
- durable/보호된 장기 기억, 재시작 복구, 전체 회사 양식 검색, 임베딩 검색, 실제 Qwen tokenizer/출력 여유 기반 예산과 모델별 자동 조정은 미구현이다.

## 검증

`verification/context-management-review.json`에 소스 해시, 실행 검사와 입력 크기 비교를 기록한다.

- 실제 Pi 기반 코드 흐름에서 Excel 셀 편집/새 통합문서/Word/PPT의 recall 연결, 원래 승인/검증 경계와 한 번만 쓰기 확인.
- 앞자리 0/수식/Unicode 원문 재조립 property test 100회, 고정 seed `23923`. 기존 native 항목 보존 property test 100회 유지.
- 오래된 한국어 업무 값과 이후 정정, 실행 격리, 잘못된 원문 포인터, 혼합 fingerprint, 변경 후 오래된 검색 결과 제거, 전체 요청 초과 시 provider 미호출/재시도 0회 확인.
- 고정 30개 한국어 대화 fixture에서 대화 문맥 JSON은 기존 Word/PPT·셀 경로 26,733자 / 새 통합문서 경로 66,831자에서 15,144자. 예전 8/20개 범위 밖 코드도 이번 window에 회수됨. **대화 문맥 문자 수 비교이며 전체 요청 비용, 토큰 절감률, 추론 속도 또는 모델 정확도 측정이 아니다.**
- Windows Office 2016, 회사 SSO, Qwen 실계정, NASCA 저장/재열기, native/installer는 실행하지 않았다.

## 후속 근거 완전성 점검

[근거 완전성과 검토 중 변경 방어](EVIDENCE-INTEGRITY-2026-09-23.md)를 반영했다. 잘린 원문 또는 길이를 확인할 수 없는 기존 입력칸은 전체 검토 완료/양식 등록의 근거가 될 수 없다. 검색과 하위 분석에도 부분 근거임을 유지하고 AI 검토 후 native fingerprint를 다시 확인한다. 위 180,000자 상한과 미구현 계층 검토 범위는 유지한다.

후속 [초안 원문 페이지 조회](WORKSPACE-PAGING-2026-09-23.md)는 SDK 안내를 원문/위치 계산에서 분리하고 줄 페이지의 개행과 Unicode 문자 위치를 보존한다. 메모리 초안과 번들 참조 조회의 수정이며 native 항목 추가 읽기나 대용량 계층 검토 구현은 아니다.

## 최신 정정과 요약의 우선순위 보강

[추가 재검증](CONTEXT-PRIORITY-2026-09-23.md)에서 최신 사용자 원문을 먼저 배치하고 자동 요약은 남은 공간에 넣도록 수정했다. 최신 메시지의 부분 범위를 표시하며 원래 요구사항과 원문 조회는 유지한다. 반환 객체 변경과 작은 문맥 예산 초과도 차단한다.
