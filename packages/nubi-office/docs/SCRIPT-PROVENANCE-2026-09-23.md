# 연속 계산의 원본 의존성과 결과 보존

2026-09-23. 기준 게시 소스 `d722764995f9262b2cc767e181ca772d9cb5ea94`. Windows Office 2016 및 사내 Qwen 3.8 27B 기준과 기존 모델 선택을 유지한다. 빌드는 실행하지 않았다.

## 재현과 수정

기존 run_script는 바로 앞 코드/입력/결과 해시만 비교했다. 원본 JSON → A 계산 → B 계산 뒤에 원본 JSON이나 A 코드가 바뀌어도 B의 current가 true일 수 있었다. 오래된 A 결과를 B에 다시 넣는 호출도 허용했다. 두 결과 경로에 별도 초안이 있어도 계산 결과로 덮어썼다. 수정 전 새 회귀 검사 3개 모두 실패했다.

- 명시적 inputPath로 연결한 계산은 원본 입력과 앞 단계 코드의 SHA-256 의존성을 함께 전달한다. 중간 결과 두 자리를 순환 재사용해도 원본 의존성을 지우지 않는다. 경로별 중복을 합치고 최대 16개로 제한하며 무한 실행 기록을 쌓지 않는다.
- 실행 전과 결과 반영 직전에 원본 의존성을 확인한다. 변경된 원본이나 수정된 중간 결과를 발견하면 script_dependency_changed를 반환한다. 기존 결과는 유지하며 모델이 실제 원본을 읽고 필요한 계산 체인을 새로 작성하도록 안내한다. 자동 재실행은 없다.
- context의 lastScript와 결과 read의 scriptProvenance는 현재 의존성 일치 여부를 표시한다. 반환 객체를 외부에서 수정해도 내부 증거는 바뀌지 않는다. current:true는 같은 원본에 대한 계산 결과라는 의미이며 업무 정답이나 문서 완료의 증거가 아니다.
- 결과 위치는 입력/원본 의존성과 겹치지 않는 두 자리 중 비어 있거나 누비가 만든 뒤 수정되지 않은 곳만 사용한다. 사용자 초안, 수동 수정된 결과, 바인딩된 시트 초안은 덮어쓰지 않는다. 두 자리 모두 사용할 수 없으면 script_result_conflict로 중지한다. 임의의 새 출력 경로나 기존 초안 자동 삭제는 추가하지 않았다.
- 계산 중 선택한 결과 위치가 바뀌어도 반영하지 않는다. 의존성 확인, 메모리 저장, 영수증 발행은 해당 실행의 동기 구간에서 처리한다. 실패/취소 시 기존 결과와 Office 문서의 범위는 그대로다.
- 새 오류도 기존 복구 감독기에 연결한다. 변화 없는 오류 3회 후 같은 실행의 HITL을 기다린다. 연속 실패 자체를 작업 진전으로 계산하거나 p-retry로 스크립트를 재전송하지 않는다.

세 앱의 번들 계산 참조 문서에 수정 절차와 한계를 반영했다. 사용자가 복사한 숫자, 별도 경로로 수동 복제한 JSON, 모델이 새 input 문자열로 재작성한 값에는 의존성이 자동 추적되지 않는다. 추적 범위는 이번 실행의 명시적 inputPath 체인이다. 저장된 영구 lineage, 임의 데이터 흐름 분석, Office 수식 의존성 분석을 구현한 것은 아니다.

## 방법론과 오픈소스 판단

| 근거 | 실제 적용과 비채택 |
|---|---|
| [DVC repro](https://doc.dvc.org/command-reference/repro) / [의존성과 산출물 해시](https://doc.dvc.org/user-guide/project-structure/dvc-files), Apache-2.0 | 의존성 변경 시 뒤 단계 결과를 새 상태로 취급하지 않는 패턴을 적용했다. DVC 패키지/CLI/코드 복사는 도입하지 않았다. Python과 디스크 캐시/외부 저장소를 요구하는 전체 실행기는 현 Office 메모리/NASCA 경계에 맞지 않는다. |
| [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 현재 문맥을 요약해도 원본 증거와 재조회 포인터를 유지하는 기존 설계에 의존성 상태를 연결했다. 해시만으로 사실 정확도를 승인하지 않는다. |
| 기존 Pi 0.86.1 / QuickJS 0.32.0 / Node crypto | 기존 작성/실행 도구와 실제 WASM 계산, SHA-256을 재사용했다. 범용 DAG 엔진이나 새 런타임 의존성은 추가하지 않았다. |
| 기존 p-retry 8.0.1 / Office 복구 감독기 | 추론/허용된 읽기의 복구는 유지하되 계산 도구는 모델이 결과를 읽고 다시 결정한다. 새로운 중첩 재시도 루프는 없다. |

원문이나 계산 결과를 DVC 캐시 또는 평문 sidecar에 저장하지 않는다. 실행 메모리 안에 해시와 경로만 추가한다. 기존 결과 JSON/코드와 모델 전달 범위는 기존 작업공간 정책을 따른다.

## 검증과 한계

- 수정 전 3개 회귀 검사 실패. 수정 후 개발 작업폴더 관련 검사 50/50 통과.
- 게시 작업폴더 전체 소스 검사 410/410 통과. 디자인 정적 검사 0건, 기존 공유 UI 24개 파일 일치.
- 실제 QuickJS로 원본 40 → A의 +1 → B의 ×2 = 82 계산, 원본 변경 후 10 → 11 → 22 재계산을 확인했다. 추가 8회 결과 슬롯 순환에서도 의존성은 3개로 유지됐다.
- 원본/코드 변경, 실행 중 원본/결과 위치 변경, 사용자 결과 슬롯/바인딩 보호, 반환 객체 변조, 오래된 결과 읽기의 상태 표시, 무진전 3회 복구를 검사했다.
- 기존 합성 모델/Office 승인 흐름 검사는 유지했다. 실제 Qwen의 재계산 계획 정확도, Office 2016 COM/설치, 기업 SSO/NASCA, 토큰/지연/비용 개선은 미측정이다. 합성 검사 수를 실제 모델 정확도 점수로 변환하지 않는다.
- 대용량 문서 계층 검토, 긴 native 항목 원문 조회, 보호된 재시작 복구, Python/외부 스킬 설치는 남아 있다. 별도 개발 공유 UI 7파일의 기준 차이는 이번 게시에 포함하지 않았다.
