# 로컬 도구 오류 복구 재검증

2026-09-23. 게시 기준 `9ea643b4a27021bb506782677cd6f58a0ca61da9`. 목표 환경은 Windows Office 2016과 사내 Qwen 3.8 27B다. 이번 결과는 실제 Pi 실행기에 오류를 주입한 소스 검사다. 모델 판단과 Office 응답은 fixture이며 실모델 정확도나 Windows 동작 검증이 아니다. 빌드와 설치 파일 생성은 하지 않았다.

## 재현한 문제와 수정

| 항목 | 수정 전 | 이번 반영 |
|---|---|---|
| Excel 셀 작업의 실패한 자료 읽기 | 존재하지 않는 작업 파일을 9회 요청한 뒤 복구 확인. 요구한 3회 정책과 불일치 | 각 로컬 도구의 반환 오류를 공통 복구 감독기에 즉시 전달. 작업 진전 없는 세 번째 실패에서 같은 실행의 HITL 대기 |
| Excel 새 문서의 잘못된 셀 초안 | 거절된 chunk를 9회 반복한 뒤 확인 | 초안 읽기/쓰기/완료 검사의 반환 오류도 같은 정책 적용. 거절된 내용은 초안에 반영하지 않음 |
| 문맥 재구성 후 오류 소실 | 원래 실패가 일반 `agent_stalled`로 바뀌어 복구 모델에 원인을 충분히 전달하지 못함 | 오류 도구, 코드, 원인과 수정 안내를 길이 제한된 `localToolFailure`로 다음 문맥에 유지 |
| 복구 이중 집계 | 개별 오류를 처리한 뒤 Pi의 반복 오류 종료까지 추가 오류로 셀 위험 | 바로 직전 결과가 이미 처리된 오류인 경우에만 Pi 종료를 중복 집계하지 않음. 새 모델 판단이 시작되면 해당 표시는 초기화 |
| Word/PPT 로컬 오류 | 자료/스크립트 오류가 일반 무진전 오류로 바뀜 | 원래 오류를 유지하고 `recoveryHandled` 결과는 외부 실행기에서 다시 집계하지 않음 |
| 변경된 코드/초안의 진전 | Excel 공통 오류 감독기는 작업 메모리의 실제 변화를 진전에 포함하지 않음 | 기존 `workspace.progress()`의 자료 읽기 위치와 코드/초안 내용을 사용. 실패 횟수나 새 요청 ID는 진전이 아님 |

로컬 도구 호출은 한 번만 실행한다. 재시도 라이브러리로 도구 함수를 반복하지 않는다. 오류 결과를 읽은 모델이 다음 호출을 결정한다. native Office 쓰기, 응답 유실, 영수증 확인, 변경 승인과 저장 승인은 기존 경로를 유지한다. 복구 확인은 편집 승인을 대신하지 않는다. 사용자가 중지하면 다시 호출하지 않는다.

오류 원문은 실행 메모리의 기존 도구 결과로 유지하고, 문맥 전환용 진단은 허용한 문자열 필드만 복사한다. 원인 필드는 240자, 안내는 600자로 제한한다. 다른 도구의 성공만으로 미해결 오류를 지우지 않으며, 같은 도구가 성공하면 이전 진단을 해제한다. 디스크 복구나 NASCA 보호 저장을 구현한 것이 아니다.

## 방법론과 오픈소스 판단

- [Anthropic의 도구 설계/평가](https://www.anthropic.com/engineering/writing-tools-for-agents): 도구 결과에 의미 있는 정보를 반환하고 실제 호출 기록에서 반복/실패를 평가하는 방법을 적용했다. 모델의 완료 문구 대신 호출 수, 원인 보존, 변경된 최종 셀, 취소 후 추가 호출 여부를 확인한다.
- [p-retry](https://github.com/sindresorhus/p-retry) 8.0.1, MIT: 이미 도입한 inference/허용된 읽기 복구를 유지한다. AbortSignal과 중단 계약은 재사용하지만 스크립트나 native 변경 함수를 retry에 넣지 않는다. 로컬 오류 정책은 기존 감독기에 연결해 복구 소유자를 하나로 유지한다.
- Pi 0.86.1, MIT: 기존 도구 실행/대화 관리와 실패 결과 계약을 그대로 사용한다. 반복 실패 후 Pi가 중단한 문맥에는 보존된 원인을 다시 넣는다. 공통 브라우저 실행기를 복사하거나 이번 변경에서 수정하지 않았다.
- [fast-check](https://github.com/dubzzz/fast-check) 4.10.2, MIT: 기존 개발 의존성을 사용해 100개 진전/실패 시퀀스를 독립 카운터와 비교했다. seed `2392303`. 실제로 변경된 작업만 실패 누적을 초기화하며 도구 호출 횟수가 몰래 늘어나지 않는지 검사한다.
- 추가 프레임워크/패키지는 도입하지 않았다. 이번 문제는 기존 복구 정책과 실행기의 연결 누락이며, 별도 retry 계층은 중복 집계와 변경 재실행 위험을 늘린다. 의존성과 번들 크기 변화가 없다.

## 검증과 한계

- 수정 전 새 회귀 검사 두 개가 모두 실패했다. Excel 셀 읽기와 문서 chunk 모두 기대 3회 대신 실제 9회였다.
- Excel 셀/초안, Word, PowerPoint의 3회 실패 확인과 사용자 대기 중 무호출을 검사한다. Excel은 같은 run으로 재개하고 별도 편집 승인을 받은 뒤 값 42를 한 번만 반영한다. Word/PPT는 재개한 다음 호출의 원래 오류, 다시 3회 실패한 뒤 중지, native 쓰기 0회를 확인한다.
- 원인별 카운터, 진전 시 초기화, 결과 보존/진단 길이, 취소 대기, native 도구가 자동 retry 대상이 아님을 검사한다. 기존 실제 QuickJS 계산/오류 수정 검사도 함께 유지한다.
- 검사 수와 게시 파일 해시는 `verification/local-tool-recovery-review.json`에 기록한다. 이전 품질 검증 파일은 당시 결과로 보존한다.
- 별도 개발 중인 공유 UI 기준 불일치 7개 파일은 이번 변경에 포함하지 않는다. 게시본의 고정된 공유 UI 검사를 기준으로 전체 회귀 검사를 수행한다.

## 남은 우선순위

1. P0: 실제 Qwen와 Windows Office 2016에서 작성 품질, 저장 후 재열기, 원본 보존, 오류 복구, 회사 인증과 NASCA 평가. 미측정이다.
2. P1: 180,000자를 넘는 최종 문서 근거의 계층 검토와 실제 Qwen 토큰/지연/비용 측정.
3. P1: 보호된 실행 상태 저장과 재시작 후 native 영수증 재조정. 현재 실행 메모리 보존과 별도다.
4. P1: Python과 외부 스킬 의존성의 기업 정책 기반 설치. 현재 QuickJS 실행은 이를 제공하지 않는다.
5. P2: 복잡한 Word 입력 필드와 PPT 혼합 서식/표/차트 쓰기의 native 보존 검사 확대.

이번 수정을 모든 오류 경로의 완전한 복구나 실제 모델의 자기 수정 능력 증명으로 해석하지 않는다. 도구 스키마 오류, 연결 오류, 미확정 native 변경은 각 기존 계약과 회귀 검사 범위를 따른다.
