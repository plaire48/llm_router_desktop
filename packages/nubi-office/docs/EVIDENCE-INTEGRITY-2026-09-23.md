# 문서 근거 완전성과 검토 중 변경 방어

2026-09-23. 기준 게시 소스 `37fc82131cacb378688e2b9eca8a34576ef2ded9`. Windows Office 2016과 사내 Qwen 3.8 27B 기준을 유지한다. 이번 결과는 소스와 합성 응답을 이용한 제어 흐름 검사이며 실제 모델 정확도나 COM 검증이 아니다.

## 재현한 결함과 수정

수정 전 네 회귀 검사가 모두 실패했다. 잘린 Word 본문으로 최종 검토가 완료됐고, 최종 AI 검토 중 Word/PPT 원본을 바꿔도 완료됐다. 원문 근거 구성 함수도 잘린 항목을 전체 근거로 허용했다.

- Word의 4,000 UTF-16 단위 초과 본문/입력칸에 잘림과 원래 길이를 전달한다. 짧은 입력칸의 기존 스냅샷은 유지한다. 문자 수는 Qwen 토큰 수가 아니다.
- 전체 검토는 잘린 항목을 `evidence_incomplete`로 거절한다. 양식 등록도 복사/카탈로그 저장 전에 같은 조건을 확인하며 native 등록 경로에도 잘림 방어를 추가했다. 부분 단계 검토는 관찰한 범위만 사용할 수 있다.
- 검색의 페이지 수집 완료와 본문 전체 수집을 분리한다. 원래 길이를 모르면 null로 남긴다. 하위 분석 모델이 누락 없음으로 응답해도 원본이 잘렸으면 보고서를 partial로 유지한다.
- Word/PPT의 단계/최종 AI 검토 결과를 받아들일 때 native 문서를 다시 읽고 기존 fingerprint와 대조한다. 검토 중 원본 변경은 `source_changed`로 종료하며 사용자의 편집을 덮어쓰지 않는다. 저장/쓰기의 기존 HITL과 별도 충돌 검사는 유지한다.
- 화면에는 연결 오류 대신 원문 잘림과 기존 변경 유지 안내를 표시한다.

이 수정은 숨겨진 원문을 새로 읽어오는 기능이 아니다. 전체 근거가 없을 때 완료를 주장하지 않도록 한다. 기존 native가 길이 표시 없이 4,000자를 반환한 입력칸은 정확히 4,000자인지 잘린 것인지 알 수 없어 미확인으로 취급한다. 새 native의 `truncated:false`와 원래 길이가 있는 4,000자 입력칸은 완전한 근거로 사용할 수 있다. 잘림 표시와 길이가 모순되면 관찰 자체를 거절한다.

기존 카탈로그에 긴 문단 또는 경계 길이 입력칸이 들어 있다면 새 메타데이터 때문에 재사용 시 스냅샷 차이가 발생할 수 있다. 이 경우 실제 원본을 재분석하고 다시 등록해야 한다. 자동으로 다른 스냅샷을 승인하지 않는다. 짧은 항목의 메타데이터는 바꾸지 않았다.

## 방법론과 오픈소스 선택

| 근거 | 실제 반영 | 채택하지 않은 범위 |
|---|---|---|
| [Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) | 원본 근거와 압축/부분 관찰을 구분하고 누락 상태를 검색과 분석에 전달 | 부분 요약으로 전체 근거 대체 |
| [Microsoft optimistic concurrency](https://learn.microsoft.com/en-us/ef/core/saving/concurrency) | 기존 Office fingerprint를 검토 전후 비교하는 설계 원칙 적용 | EF/DB 런타임 도입, 원자적 문서 잠금 보장 |
| [MiniSearch](https://github.com/lucaong/minisearch), MIT | 이미 도입한 7.2.0 검색에 원문 범위 메타데이터 연결 | 새로운 검색 엔진/임베딩 의존성 |
| [LangGraph workflows](https://docs.langchain.com/oss/javascript/langgraph/workflows-agents) | 계층 검토의 후속 설계 후보로 검토 | 이번 런타임 도입이나 계층 검토 구현으로 표시하지 않음 |

기존 Pi 실행기와 복구 경로를 유지했다. 새 패키지나 라이선스 변경은 없다. COM UI/STA, NASCA의 Office 열기/저장 경로를 유지하고 ZIP 재저장이나 평문 sidecar를 추가하지 않았다.

## 검증과 남은 범위

- 수정 전 회귀 검사 4개 모두 실패. 수정 후 개발 작업폴더의 관련 검사 83/83 통과.
- 게시 작업폴더 전체 소스 검사 384/384 통과. 디자인 정적 검사 0건, 검토된 공유 UI 24개 파일 일치.
- 실제 Pi 실행 코드에 고정 모델 응답과 native fixture를 연결한 검사다. 잘린 근거에서는 최종 모델 호출이 시작되지 않고, 검토 중 원본 변경에서는 완료되지 않는 것을 확인했다.
- native C# 세 파일은 소스 변경만 했다. 컴파일, 설치 파일 생성, Windows Office COM, Qwen 실호출, 회사 SSO, NASCA 저장/재열기는 실행하지 않았다.
- 검토마다 native 읽기 한 번이 추가된다. 실제 Office 지연 시간은 미측정이다. 확인 직후 미래 변경까지 막는 원자적 잠금은 아니다.
- 180,000자 초과 전체 문서의 요구사항별 계층 검토, 긴 단일 항목의 숨겨진 부분 읽기, 보호된 영구 실행 복구와 Python/외부 스킬 의존성 설치는 남아 있다.
- 별도 개발 중인 공유 UI 7개 파일의 기준 차이는 이번 게시 변경에 포함하지 않았다. 개발 작업폴더 전체 검사가 모두 정상이라는 의미가 아니다.
