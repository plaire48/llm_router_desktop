[측정 결과와 수정 기록](LIVE-SIM-RESULTS-2026-09-29.md): `gpt-5.6-luna`와 모의 호스트로 20건을 측정했다. 수정 전에는 **20건 중 2건 통과, 15건 중단**이었다. 중단의 원인은 대부분 모델의 판단이 아니라 하네스였다. 계획이 거절될 때 이유를 전달하지 않았고, 시트 이름이 붙은 주소와 `{"set_values":{...}}` 모양의 편집을 거절했으며, 등록에 충족할 수 없는 완료 조건을 허용했다. 기록에서 확인한 결함 18건을 재현 검사와 함께 고쳤다.

모든 수정을 반영한 반복 측정: 양식 등록 9/12, 재사용 10/12, 결정적으로 채점하는 편집 12/12, 양식 채우기 3/8. 등록에 성공한 실행에서 제안한 입력 항목은 모두 정답 항목표와 같았다.

**Office 회귀 877개 중 875 통과.** 남은 2건은 아래의 제품 결정 대기 항목이다. 양식을 한 번에 요약하는 `worker/form-map.mjs`를 추가했으나 아직 실행기에 연결하지 않았다.

이 수치는 실제 Excel 2016, 사내 Qwen, NASCA의 결과가 아니다. 실행마다 편차가 있다. 불필요한 질문과 값 축약은 남아 있다.

## 2026-09-29 모의 호스트와 실모델 실측 기반

[실행 방법](../eval/README.md): Windows와 Excel이 없는 개발 PC에서 실제 모델로 worker를 실행하는 평가 전용 도구 `eval/sim`을 추가했다. 쓰기 검증은 native `WorkbookEngine`의 규칙을 JS로 옮겼고 native 계약 시나리오를 검사로 이식했다. 수식은 `@ironcalc/nodejs` 0.8.3(MIT, 개발 의존성)이 계산한다. 로그인은 세션 프로세스가 한 번만 수행하고 인증값은 그 프로세스 메모리에만 둔다.

합성 양식 4종(지출 결의서, 출장 신청서, 교육 신청서, 견적서)과 정답 항목표를 만들었다. 양식 등록은 제안한 항목의 정밀도와 재현율로, 재사용은 작성한 사본의 값과 계산 결과, 비대상 셀 보존으로 채점한다. 기존 평가에는 양식 등록과 등록본 재사용 사례가 없었다.

**Office 회귀 844개 중 842 통과**(새 검사 130개 포함), 배포 고정 Pi 0.86.1에서도 같다. 남은 2건은 아래 절의 제품 결정 대기 항목이다. 제품 worker와 UI, native 소스는 이 항목에서 바꾸지 않았다.

**실모델 측정은 아직 실행하지 않았다.** 모의 호스트의 결과는 실제 Excel 2016, 사내 Qwen, NASCA, 회사 양식의 정확도가 아니다. 보고서 종류를 `simulated-host-live-model-evaluation`으로 분리했다. 미리 작성한 모델 응답으로 실행기와 채점기를 검사한 것은 모델 성능의 근거가 아니다.

## 2026-09-29 병합 라벨 힌트와 공유 소스 변경 대응

[인계 기록](HANDOFF-2026-09-29.md): 09-26~28 공유 소스 변경 뒤 Office 회귀 검사가 708개 중 6개 실패하는 것을 확인하고 원인을 조사했다. 4건을 고쳤고 **Office 회귀 714개 중 712 통과**다. 배포 고정 Pi 0.86.1에서도 같은 결과다. CX 디자인 검사는 위반 0개다.

- 양식 분석의 라벨 힌트가 병합 라벨을 놓치던 결함을 고쳤다. native는 병합 종속 셀의 값을 비워 읽으므로, 여러 칸을 병합한 라벨 옆의 입력 칸은 힌트를 받지 못했다. 이제 병합 기준 셀의 문구를 쓴다.
- 공유 검증기가 거절 사유에 추가한 스키마 힌트를 Office 안내 문구가 설명한다. 힌트는 호스트가 선언한 속성 이름만 담으며 검사가 이를 확인한다.
- 설정 단추의 접근성 이름 "더 보기"를 되살렸다.

**남은 실패 2건은 제품 결정이 필요하다.** 질문 안내 문구의 위치, 공유 CSS의 초록색이 파란색으로 바뀐 점이다. 색상 변경 때문에 `npm run design:check`의 UI 동일성 검사도 실패한다. 공유 UI 기준 해시는 갱신하지 않았다.

병합 라벨 힌트가 실제 모델의 항목 제안을 개선하는지는 측정하지 않았다. 실제 Office 2016, Qwen, NASCA는 미검증이며 native와 설치 빌드는 실행하지 않았다. [외부 방법 조사](TEMPLATE-SNAPSHOT-RESEARCH-2026-09-29.md)의 권고는 채택 결정이 아니라 후보다.

## 세 앱의 공통 양식 목표와 현재 차이

사용자가 확정한 목표는 **기존 양식 분석 → 구조 스냅샷 → 사용자 정보 수집 → 원본의 사본에 입력 → 보존/내용 검증**이다. 스냅샷은 스크린샷을 뜻하는 것이 아니라 버전/fingerprint, 확인한 항목과 입력 위치, 수식/서식/문단/표/도형 등 앱별 구조와 미확인 속성을 담는 읽기 전용 분석 명세다. 실행 계획과 사용자 답변은 이 명세와 별도로 관리한다. 필요한 사실만 객관식/주관식 HITL로 묻고, 추가로 받은 사실을 같은 실행에서 반영한다.

실제 양식의 기준은 Office가 연 원본과 그 사본이다. 분석 명세나 화면 이미지에서 문서 전체를 다시 생성해 원래 양식을 대체하지 않는다. 값과 구조가 바뀌었으면 이전 스냅샷을 그대로 쓰지 않고 재분석/재확인한다. 저장하는 문서와 분석 명세는 회사 보호 경로를 따라야 하며 평문 sidecar를 만들지 않는다.

| 앱 | 현재 연결된 경로 | 아직 연결되지 않은 전체 흐름 |
|---|---|---|
| Excel | 입력창 +에서 분석/등록/검색/이름 변경/목록 제거, 지원 입력 영역과 내부 XML 명세를 이용한 사본 작성 | 회사 공용 카탈로그, 모든 양식/속성의 완전한 지원과 실환경 보존 검증 |
| Word | 양식 요청 시 승인 → Office SaveAs2로 사본 먼저 생성 → 제한된 범위 재바인딩/관찰 비교 → 입력/최종 저장. 일반 원본 편집은 별도 유지 | native 컴파일/Word 2016/NASCA 실행, 복잡한 입력 유형, 회사 공용 배포 |
| PowerPoint | 양식 요청 시 승인 → Office SaveCopyAs/Open으로 사본 먼저 생성 → 제한된 범위 재바인딩/관찰 비교 → 선택 슬라이드/단순 텍스트 수정/최종 저장 | native 컴파일/PowerPoint 2016/NASCA 실행, 폭넓은 입력 항목 매핑, 회사 공용 배포 |

따라서 **Word/PPT가 이미 Excel과 동일한 재사용 양식 흐름을 완성했다는 의미가 아니다.** 사본 선행/스냅샷 바인딩 흐름의 소스를 추가했으며, 다음 기능 과제는 지원 입력 유형 확대와 실제 Office에서의 전체 흐름 검증이다. 후속 변경에서 앱별 + 목록과 DPAPI 보호 스냅샷 저장/재사용 소스를 연결했다. 사본 흐름도 실제 Office 검증이 필요하다. 현재 열린 문서를 승인 후 직접 수정하는 일반 편집과 양식 사본 작성은 구분한다.

## 적용한 방법론과 오픈소스

후속 [앱별 양식 목록](TEMPLATE-CATALOG-2026-09-23.md): JSON Forms의 명세/화면/값 분리 패턴을 참고하고 기존 누비/CX 폼을 재사용했다. 저장 보호는 Windows DPAPI를 직접 사용하며 새 런타임 라이브러리는 추가하지 않았다. 기존 fast-check/Testing Library/axe로 경계·상호작용을 검사한다.

후속 [양식 사본 선행](TEMPLATE-COPY-2026-09-23.md): Microsoft native 저장/열기 API와 Anthropic의 명시적 워크플로 방법론을 적용했다. 기존 Pi/검토/영수증 경로를 재사용하며, Open XML SDK 검증은 유지하고 pptx-automizer/PowerTools의 ZIP 편집 경로는 NASCA 때문에 채택하지 않았다.

후속 [브라우저 하네스 이식](BROWSER-HARNESS-ADOPTION-2026-09-23.md): Anthropic/DeepAgents의 격리된 역할/근거 반환 패턴을 기존 Pi 실행기에 적용하고, Office 직렬 편집과 HITL은 유지했다. 신규 런타임 설치 없이 기존 분석 큐를 공통화했다.

후속 [컨텍스트 관리 개선](CONTEXT-MANAGEMENT-2026-09-23.md): MiniSearch 7.2.0 실제 도입과 LangGraph memory 방법론 참고, 원문 보존/조회·전체 요청 예산의 검증을 추가했다.

Word의 `Temporary`는 편집 후 컨트롤을 제거할 수 있고, XML 매핑은 다른 연결 값에도 영향을 줄 수 있다. 해당 입력칸은 쓰기 대상에서 제외한다. 콘텐츠 컨트롤 ID는 COM의 unsigned 표기와 XML의 signed 표기를 대응시킨다. [Temporary](https://learn.microsoft.com/en-us/office/vba/api/word.contentcontrol.temporary), [XMLMapping](https://learn.microsoft.com/en-us/office/vba/api/word.contentcontrol.xmlmapping), [ID 계약](https://learn.microsoft.com/en-us/office/vba/api/word.contentcontrol.id).

주변 Word XML 비교는 선택 입력칸의 내용/placeholder와 세션 ID·맞춤법/페이지 계산 캐시를 제외한 **본문 XML** 비교다. 입력칸 안의 시각적 동일성, 머리말/꼬리말과 외부 style part 전체, 인쇄 결과 또는 NASCA 암호화의 증거가 아니다. 기존 XML 매핑, 잠금, 임시, 중첩, 다중 행 입력칸을 해제하거나 일반 텍스트로 강제 변환하지 않는다.

## 로컬 Python 스킬 추가

[Python 스킬 하네스](PYTHON-SKILLS.md)를 Excel/Word/PowerPoint 공통 실행기에 연결했다. 설치와 실행은 각각 승인하며, Python 결과는 기존 native 반영/검토/저장 절차로 전달한다. 로컬 실제 설치/실행 검사를 통과했다. Windows 환경 제한, 설치 배포 및 실제 Office/Qwen 검증은 서로 다른 검사로 유지한다. 외부 스킬 저장소 자동 설치와 Python 생성 파일 가져오기는 이번 범위에 없다.

## 작업 위치와 화면 확인 (후속 구현)

실제 Office 선택/스크롤, 별도 UIA 관찰 프로세스, 메모리 캡처, 독립 읽기 전용 화면 검토와 채팅 미리보기를 연결했다. 실패한 캡처는 완료한 변경을 다시 실행하지 않는다. [선택 근거와 검증 구분](OFFICE-VIEW-HARNESS.md)을 따른다. Windows 실제 Office 2016과 Qwen 품질은 미검증이다.

## AI 가상 커서와 지원되는 UIA 동작

사용자 커서와 독립된 표시를 만들고 내장 Windows UIA 패턴을 사용한다. 물리 마우스 입력과 Vanara 의존성은 제거했다. 요소 identity/bounds/hit-test 확인, 클릭/휠 HITL, 실행 영수증, 입력 후 native 재확인과 미확정 작업 중지를 연결했다. Windows WinForms에서 사용자 커서 불변, semantic 클릭/스크롤 효과, 표시의 포커스/클릭 통과, 이동/만료 대상 거부, 동일 요청과 소비한 관찰의 중복 입력 차단을 검사했다. 로컬 소스 검사와 브라우저 검사는 Office/Qwen 정확도 검증이 아니다. 새 설치 파일 검증은 릴리스 첨부 증거를 따른다. 상세 선택 근거와 한계는 [Office 화면 하네스](OFFICE-VIEW-HARNESS.md)를 참고한다.
