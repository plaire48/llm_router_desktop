# 스킬 활용과 최소 입력

## 문제와 변경

기존 규칙형 스킬은 실행 전에 등록된 질문을 전부 순서대로 물었다. 사용자가 요청에 이미 쓴 정보나 열린 문서의 내용도 확인하기 전이었다. 질문/선택지/입력 방식 설정은 이 초기 고정 설문 방식의 잔여 UI였다. ZIP/폴더 패키지는 이미 별도 폼 없이 등록하고 Pi 도구로 활용하고 있었다.

이제 스킬은 작성 규칙과 필요한 정보의 기준이다. 사전 설문이나 별도 분류 모델을 추가하지 않고 기존 Office 실행기가 요청 확인, 원문 읽기, 계획, 필요한 질문, 실행, 검토를 담당한다.

| 구분 | 적용 |
| --- | --- |
| 새 스킬 등록 | ZIP 또는 폴더 하나 선택. SKILL.md와 하위 자료를 기존 방식으로 등록 |
| 기존 규칙 편집 | 이름과 작성 규칙. 입력 방식/선택지/질문 추가 설정 제거 |
| 기존 질문 | 삭제하지 않고 접힌 확인 항목으로 보존. 실행기의 정보 요구사항으로 전달 |
| 정보가 이미 있음 | 관련 사용자 발언과 현재 문서 근거를 확인해 활용 |
| 필수 정보 부족/충돌/모호함 | 의존하는 쓰기 전에 기존 ask_user/계획 질문으로 확인 |
| 빈 양식 요청 | 실제 업무 인스턴스 값이 없어도 빈 입력칸 작성 가능 |
| 레이아웃/도구/질문 형식 | 기존 에이전트가 결정. 사용자에게 내부 설정을 요구하지 않음 |
| 승인 | 문서 반영/저장/Python 설치와 실행의 기존 HITL 유지 |

`startSkillIntake`는 같은 실행 ID와 취소/응답 영수증을 유지하는 연결 계층이다. 직접 질문하거나 추가 모델을 호출하지 않는다. 셀 직접 모드도 `continuousInput:true`로 질문 후 같은 실행을 이어간다. Word/PPT와 기존 Excel 셀 실행은 원본을 읽은 뒤 계획한다. 새 Excel 문서는 기존 계획/작성/검토 질문을 사용한다.

## 문맥과 출처

- 선택한 기존 규칙형 스킬의 원문, 정보 요구사항, 과거 명시적 답변을 `workspace.skillContext()`의 활성 스킬에 유지한다. 기존에는 SKILL.md 파일만 메모리에 있고 활성 패키지 문맥에서는 빠져 있었다.
- 계획/작성/오류 복구/최종 검토에서 활성 스킬을 요약과 별도로 전달한다. 스킬 원문을 합성한 사용자 메시지로 추가하지 않는다.
- 이전 스킬 답변 캐시는 정확한 규칙 fingerprint가 맞을 때만 전달하며, 이번 업무에 유효한지는 에이전트가 다시 판단한다. 현재 사용자의 수정이 우선한다. 모델 추정을 명시적 답변 캐시에 쓰지 않는다.
- 채팅 폼의 승인된 전달 결과 `inputAnswers`를 후속 요청의 질문/답변 이력으로 복원한다. 실패한 작업에서 받은 실제 답변도 보존하지만 실패한 모델의 완료 주장은 제외한다. 선행 0이나 수식 문자열을 바꾸지 않는다.
- 예시, 기본 선택지, 다른 업무의 과거 답변, 모델 주장만으로 업무 사실을 채우지 않도록 공통 스킬 정책에 명시한다. 모호한 사용자 결정은 질문한다. 이 정책의 실모델 준수율은 별도 측정 대상이다.

## BP와 오픈소스 선택

- [Agent Skills 클라이언트 가이드](https://agentskills.io/client-implementation/adding-skills-support): 목록 → 활성 원문 → 필요한 리소스의 단계적 로딩, 압축 시 활성 지침 유지. 기존 Pi/MiniSearch와 활성 스킬 문맥을 보강했다.
- [Codex Skills](https://developers.openai.com/codex/skills): 재사용하는 지침/자료와 필요에 따른 스킬 활성화 참고. Codex 런타임이나 특정 OpenAI 모델을 새로 연결한 것은 아니다.
- [OpenCode Skills](https://opencode.ai/docs/skills/): 설명 기반 발견과 도구를 통한 필요 시 로딩 참고. 사용자에게 작업별 입력 폼을 먼저 설계시키지 않는 기존 패키지 경로를 규칙형 스킬에도 적용했다.
- [Anthropic Building effective agents](https://www.anthropic.com/engineering/building-effective-agents): 단순한 구성부터 시작하고 실제 필요가 있을 때 역할을 분리하는 원칙 참고. 별도 입력 분류 에이전트는 문서를 읽기 전에 중복 질문/호출을 유발하므로 추가하지 않았다.
- 실제 재사용: [Pi의 스킬 구현](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/src/core/skills.ts), 고정 Pi 0.86.1 도구 실행과 스킬 파싱, MiniSearch 7.2.0 문맥 조회, 기존 질문/영수증/복구 실행기. 기존 라이선스와 THIRD-PARTY-NOTICES를 유지하며 신규 패키지는 추가하지 않았다.

독립 원문 조사는 기존 읽기 전용 하위 에이전트를 계속 사용한다. 부모가 스킬의 관련 조건을 계획 요구사항과 위임 작업에 포함하고 질문을 통합한다. 하위 에이전트가 각자 사용자에게 설문하거나 별도 쓰기/승인을 실행하지 않는다. 모든 스킬 원문을 각 워커에 무조건 복제하는 기능이나 새 멀티에이전트 프레임워크를 도입한 것은 아니다.

## 검증과 남은 범위

합성 모델과 실제 실행기로 다음을 검사한다: 세 Office 호스트의 원본 조회 후 질문, 같은 ID 재개, 응답 중복/충돌, 추론 중 취소, 셀 직접 모드와 자동 라우팅, 저장 승인 유지, 알려진 입력의 선행 설문 제거, Excel 계획/작성/최종 검토의 스킬 보존, 질문 답변의 후속 요청 전달, 스킬 편집 저장/재진입의 기존 항목 보존.

이는 Qwen이 모든 상황에서 누락과 모호함을 정확히 판단한다는 증거가 아니다. 실모델에서는 이미 알려진 값, 일부 누락, 원문과 사용자 요청 충돌, 빈 양식, 변경된 과거 답변, 스킬 예시와 실제 값 구분을 독립 정답으로 평가해야 한다. Windows Office 2016/실제 Qwen/NASCA는 미검증이며 native/설치 파일 빌드와 배포를 수행하지 않는다.

최종 검사: 배포 고정 의존성 `npm run test:pinned` **687/687 통과**, 실패/취소/건너뛰기 0개. 공유 디자인 24개 일치, 위반 0개. 정적 Chromium 화면 114개에서 가로 넘침과 axe 자동 위반 0개이며 색 대비 일부는 미확인이다. 스킬 편집 캡처를 직접 확인했다. 결과는 `verification/skill-autonomy-quality.json`에 기록했다.
