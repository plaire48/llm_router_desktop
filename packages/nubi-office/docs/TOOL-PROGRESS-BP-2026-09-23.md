# 반복 호출과 실제 진전 감지

2026-09-23. Qwen 3.8 27B 기준의 Windows Office 2016 실행기를 점검했다. 모델 이름이나 제공자, 기존 Pi 실행기를 바꾸지 않았다. 빌드와 설치 파일 생성은 실행하지 않았다.

## 발견한 빈틈과 반영

기존 오류 감독기는 실패 응답과 문맥 전환의 진전 여부를 검사한다. 하지만 읽기가 계속 성공하거나 동일한 초안을 덮어써도 요구한 문서는 완성되지 않을 수 있다. 성공 응답 수와 도구 호출 횟수는 완료 근거가 아니다.

`worker/tool-progress.mjs`를 Excel 범위 편집/양식, Excel 새 문서, Word/PPT 실행기에 연결했다.

1. 선택된 읽기/분석 도구와 메모리 초안 패치의 입력을 정규화한다. 객체 키 순서는 무시하고 배열 순서는 보존한다. 초안 도구의 JSON 문자열도 내부 객체로 비교한다.
2. 문서 지문, 단계 완료, 확인한 범위/페이지, 실제 초안, 수락한 답변처럼 실행기가 보유한 상태가 바뀌었는지 비교한다. 모델의 진행 선언이나 호출 횟수는 진전으로 세지 않는다.
3. 진전 없이 같은 호출을 세 번째 시도하면 실행 전에 차단한다. 2개 또는 3개 호출을 번갈아 반복하는 패턴도 세 주기에서 감지한다. 최대 9개의 SHA-256 입력 지문만 메모리에 유지하며 입력 원문을 별도로 저장하지 않는다.
4. 모델에 `tool_loop_detected`, `actionIssued:false`와 다음 동작을 바꾸라는 피드백을 준다. 계속 반복되면 기존 복구 승인 화면에서 같은 실행을 보존하고 기다린다. 새로운 재시도 루프나 대기 타이머를 추가하지 않는다.
5. 사용자가 계속하기를 선택해도 차단했던 도구를 자동 재실행하지 않는다. 새 모델 결정부터 이어가며 기존 편집/저장 승인은 따로 유지한다. 취소 뒤에는 추가 호출을 허용하지 않는다.

네이티브 쓰기, 사본 생성, 저장은 이 감지 대상이 아니다. 기존 승인/receipt/readback 검증을 유지하며 범용 재시도에 넣지 않는다. 도구 오류도 기존 오류 감독기가 처리한다. Word/PPT에서 감지된 반복을 다시 일반 `agent_stalled` 복구로 넘기지 않아 중복 대기/중복 승인을 막았다. 문맥을 재구성해도 같은 guard와 복구 피드백을 유지한다.

## 검사 결과

기준 소스 `98e73d53f86ab433d51d818518ebce94e56e2ba7`와 새 실행기에 동일한 반복 응답을 주입했다. 실제 Pi와 Office worker 경로를 사용했지만, 모델 및 Office 응답은 스크립트로 제공했다. 복구 HITL을 자동 승인하지 않았으며 첫 확인 대기에서 실행을 취소했다.

| 시나리오 | 이전 | 반영 후 |
|---|---:|---:|
| Excel 같은 선택 읽기: 첫 복구 HITL까지 actor 호출 | 9 | 4 |
| 위 시나리오의 native 읽기 요청 | 13 | 4 |
| Excel 같은 초안 조각: 첫 복구 HITL까지 actor 호출 | 9 | 5 |

원시 집계는 `verification/tool-progress-comparison.json`에 있다. 기준 커밋의 별도 체크아웃을 준비한 뒤 `node scripts/check-tool-progress.mjs /path/to/baseline/packages/nubi-office`로 재현할 수 있다. 이 숫자는 해당 반복 시나리오의 제어 비용이며 일반 작업 속도, 토큰 절감률, 문서 정확도 측정이 아니다.

검사는 입력 키 순서, 짧은 순환, 다른 범위 읽기, 실제 진전 초기화, 초안 유지, 같은 run에서 복구 후 한 번만 쓰기, 별도 저장 승인, Word/PPT 반복/취소, 오류 감독기 분리, 취소 후 호출 차단을 포함한다. 전체 소스 검사 결과와 소스 해시는 `verification/tool-progress-review.json`에 기록한다.

| 높음 | worker 재시작 뒤 실행 복원 없음 | 현재 메모리 체크포인트와 DPAPI 양식 저장을 구분한다. 보호된 실행 저널, 원래 문서 바인딩, receipt 조회 후 재개를 설계해야 한다. 문서가 바뀌거나 쓰기 결과가 불명확하면 자동 재실행하지 않는다. |
| 높음 | 큰 Word/PPT 최종 검토는 180,000자 근거 한도 | 범위별 원문 근거를 가진 계층 검토와 요구사항 커버리지 집계가 필요하다. 요약만으로 전체 합격시키지 않아야 한다. |
| 높음 | 사내 Qwen 및 Office 2016/NASCA 실증 없음 | 기존 평가 실행기로 실제 요청, 도구 입출력, 네이티브 readback, 사용자 문서 품질 평가를 수집해야 한다. 미연결 환경을 합격으로 표시하지 않는다. |
| 중간 | 외부 스킬 설치/Python 실행/자동 의존성 설치는 미구현. 동봉 스킬 로더/메모리 편집은 [후속 SDK 도입](CODING-SDK-ADOPTION-2026-09-23.md), 제한된 JS 계산은 [QuickJS 도입](DOCUMENT-SCRIPT-RUNTIME-2026-09-23.md)으로 연결 | 격리된 실행 환경, 의존성 고정/라이선스, 회사 설치 정책, 산출물 검사와 네이티브 가져오기 계약부터 연결한다. OpenCode의 일반 셸 도구를 Office 프로세스에 직접 노출하지 않는다. |
| 중간 | Word 복잡한 필드, PPT 혼합 서식/표/차트 수정 제한 | 읽을 수 있는 요소와 안전하게 수정할 수 있는 요소를 구분하고 네이티브 계약을 개별 확대한다. 원본 보존/시각 검증을 통과하기 전 지원 도구로 광고하지 않는다. |

이번 감지는 의미상 잘못된 계획 전체를 판정하지 않는다. 서로 다른 입력을 무한히 생성하거나 값을 계속 바꾸는 실패는 별도의 요구사항 검토와 기존 진전 감독기가 필요하다. 실제 모델 평가를 통해 관측 상태와 임계값의 오탐/미탐을 추가 확인해야 한다.
