# 하네스 개선 — 질문 후 이어가기와 업무 평가

최초 평가의 P0 문제부터 소스를 개선했다. Qwen 3.8 27B 기준, 현재 Pi 실행기와 누비 UI/모델 선택을 유지했다. 구현 성숙도는 동일 가중치 기준 **55→62/100**으로 재평가했다. 작업 보존은 1→3/5, 평가 체계는 1→2/5다. 이것은 코드/제어 검증에 대한 판단이며 실제 모델 정확도 향상 수치가 아니다. Windows Excel 2016·회사 Qwen·NASCA 실환경 정확도는 계속 `null`이다.

## 적용한 변경

### 1. 질문이 나와도 같은 작업에서 계속한다

- 문서 계획 중 누락 정보, 시트 작성 중 질문, 최종 검토 중 확인 모두 `request_input`으로 대기한다. 실행은 종료되지 않는다.
- 질문/답변과 수락된 시트, 현재 부분 초안, 선택 모델을 보존한다. 같은 질문 응답을 다시 전달해도 중복 반영하지 않으며, 같은 영수증 ID에 다른 내용은 거부한다.
- 최종 검토 중 답변을 받으면 Excel을 다시 읽는다. 기다리는 동안 fingerprint가 바뀌면 사용자 수정을 덮어쓰거나 저장하지 않는다. Excel busy 읽기는 읽기 전용 재시도 경로를 사용한다.
- 기존 누비 QuestionForm을 그대로 사용한다. 계획 단계·진행 기록·사용자 답변이 같은 대화 메시지에 남는다.

재현 결과: 이전에는 첫 시트 초안 1개→질문→새 실행/초안 0개였다. 현재는 질문 전후 **동일 실행, 초안 1개 유지, planner 호출 1회**다. 별도의 완료 경로 검사에서는 답변 뒤 둘째 시트만 계속하고 첫 시트 내용이 그대로인 상태로 검토·저장 승인에 도달했다.

### 2. 최초 실행 응답이 사라져도 실행을 다시 만들지 않는다

UI가 `requestId`를 생성하고 실행 요청에 포함한다. 응답이 timeout으로 유실되면 `runLookup`을 읽기 전용으로 호출해 현재 실행을 찾는다. 찾지 못하면 실패를 알리며 새 실행을 자동 시작하지 않는다. 현재 실행의 동일 ID·동일 payload 중복 요청은 기존 상태를 반환하고, 다른 payload는 충돌 오류다. 실행 ID를 아직 받지 못한 취소도 requestId에 바인딩된다.

범위는 **현재 worker 프로세스의 현재 실행**이다. 재시작 이후 영속 멱등성이나 여러 과거 실행의 재개를 보장하지 않는다. 자동 `runStart` 재전송은 여전히 금지한다.

### 3. fast-check를 실제 도입했다

`fast-check 4.10.2`와 전이 의존성 `pure-rand 8.4.2`를 개발 의존성으로 고정했다. 라이선스는 MIT이며 고지·원문을 보관했다. 제품 worker에는 import하지 않는다.

`tests/document-continuity.test.mjs`는 실제 문서 실행기를 대상으로 모델 기반 검사 200회(고정 seed 23092026, 시나리오당 최대 30명령)를 수행한다. 상태 모델은 질문 대기/저장 승인 대기/취소와 답변 여부만 관리한다. 제품 내부 구현을 복제하지 않는다. 답변 영수증의 응답 유실, 재전달, 중복/충돌 응답, 잘못된 ID, 빈 입력, 상태 조회, 취소를 생성한다. 실패하면 fast-check가 줄인 명령 순서와 seed로 재현할 수 있다.

불변조건은 실행 ID 유지, 첫 시트 보존, planner 재시작 없음, 승인 없는 저장 없음, 취소 이후 재개 없음이다. 이는 LLM 성능 평가가 아니라 상태 제어 검사다. [fast-check 공식 방법](https://fast-check.dev/docs/advanced/model-based-testing/)

### 4. 문서·양식 평가 경로와 외부 정답을 추가했다

corpus v4는 **총 16개**다. 기존 편집 8개와 새 문서 4개(성적표, 시트 간 예산, 빈 성적 양식, 인원 질문 후 예산), 기존 양식 4개(앞자리 0, 병합 입력/질문, 계산식 보존, 날짜 형식)가 있다. 직접 작성한 합성 업무 사례이며 회사 대표 문서 16개를 평가했다는 뜻은 아니다.

- 문서 mode는 실제 `startDocumentAgent`를 사용한다. native 평가 호스트가 별도 Excel 인스턴스에서 생성 문서를 열고 저장·재열기해 관찰한다. 파일 저장은 fixture별 승인 목록과 명시적 평가 실행 동의가 있어야 한다.
- 원래 운영 경로와 같은 `DocumentPort`를 사용한다. 평가 프로세스가 생성한 전용 디렉터리만 생성/저장 대상으로 주입하며, 제품의 기본 경로는 유지한다. 모델 payload는 저장 위치를 지정할 수 없다.
- 평가 호스트 protocol 4를 요구한다. 이전 EXE는 버전 불일치로 차단한다. 새 native 소스는 아직 빌드/COM 실행하지 않았다.
- 외부 `documentChecks`는 모델이 만든 계획에서 가져오지 않는다. 요구 값·수식의 정확한 참조·시트 수·셀 속성·재계산·저장 후 상태를 검사한다. 상수 답, 문자열 속 함수 이름, 비슷하지만 다른 범위 참조는 통과하지 못한다.
- 양식 항목 승인은 사례에 지정한 입력 anchor·형식·필수 여부와 일치해야 한다. 질문 응답도 사전 정의한 사례만 한 번 제공한다. 예상하지 못한 질문·넓어진 입력 영역·복구 승인은 자동 처리하지 않는다.

정확한 셀 위치를 지정한 사례가 상당수여서 자유 배치 문서 작성 능력 전체를 대표하지 않는다. 기업 양식의 다양성, 그림/인쇄의 실제 가독성, 보호 정책은 별도 보류 평가 집합과 실제 Excel 검증이 필요하다.

### 5. 사람 판정과 반복 비교를 연결했다

의미 판정은 여전히 `needs_review`로 남긴다. 실평가가 끝나면 `review-template.json`에 기준별 빈 판정표를 만든다. 평가자가 기준마다 통과 여부·이유·관찰 근거를 작성하면 `eval/review-cli.mjs`가 별도 결과 파일로 합산한다. 소스·모델·시작 시간·호스트·사례 결과를 함께 해시해 다른 실행의 판정이 섞이는 것을 막는다. 결정적 셀 검사 실패는 사람 판정으로 덮어쓸 수 없다. 원본 보고서는 유지한다.

이 로컬 파일 경로는 판정자 이름을 기록하지만 신원을 인증하지 않는다. 모델 채점자를 사람 기준에 보정한 실측 결과도 아직 없다. 운영 모델의 자기평가가 정답으로 자동 들어가지는 않는다.

`eval/compare.mjs`는 실측 보고서만 받으며 모델·소스·평가 집합·분석 동시성이 다른 결과를 분리한다. 반복 성공 여부, 검토 대기 수, 성공 작업의 p50/p95 시간, 모델 호출 분포를 집계한다. 빨리 실패한 작업을 성공 성능 향상으로 계산하지 않으며 가격이 없으므로 금액 비용은 미측정으로 남긴다.

이는 실제 결과·실행 기록·독립 채점을 나누고 코드/모델/사람 평가를 조합하는 [Anthropic 평가 방법](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)을 적용한 것이다. 기존 [Promptfoo assertions/custom provider](https://www.promptfoo.dev/docs/configuration/expected-outputs/) 설정은 16개 사례로 확장했다. Promptfoo 본체나 실서비스 모델을 실행한 결과는 아니다.

## 실패·복구 계약

| 실패 지점 | 처리 | 유지해야 할 것 / 금지 |
|---|---|---|
| 문서 작성 중 누락 정보 | 같은 실행의 입력 폼에서 대기 | 수락 시트와 부분 초안 유지, 새 planner/실행 생성 금지 |
| 입력 응답 ACK 유실 | 동일 toolResult만 재전달 | 중복 반영 금지, 다른 결과는 충돌 |
| 최종 검토 중 원본 변경 | 새 readback의 fingerprint로 중단 | 사용자 변경 덮어쓰기/저장 금지 |
| 최초 runStart 응답 유실 | requestId로 현재 실행 조회 | runStart 자동 재전송 금지 |
| 실행/입력 중 사용자 취소 | 대기 해제·모델 중단 | 늦은 응답으로 재개 금지 |
| 예상 밖 평가 질문·복구 승인 | 사례 및 suite 중단 | 평가기가 자동 승인해 무한 반복 금지 |
| worker/Excel 재시작 | 현재는 재개 불가를 명시 | 과거 영수증 없이 쓰기 재실행 금지 |

[LangGraph interrupt/resume](https://docs.langchain.com/oss/javascript/langgraph/interrupts)과 [checkpoint 개념](https://docs.langchain.com/oss/javascript/langgraph/persistence)은 설계에 참고했다. 두 번째 실행 프레임워크는 추가하지 않았다. 일반 SQLite/JSON에 회사 문서를 저장하는 방식도 추가하지 않았다. 현재 상태는 worker의 중앙 메모리에 있으며 완료·취소·worker 종료 시 수명이 끝난다. 인증값 저장과 분리된다.

## 검증 범위와 남은 일

제어 검사는 새 문서 질문의 세 위치, 읽기 오류 복구, 원본 변경, 중복 영수증, 최초 실행 응답 유실, 평가 오답·의미 판정·성능 집계의 부정 사례를 포함한다. `verification/harness-assessment-checks.json`에 실제 검사 수와 source hash를 기록한다. `eval/audit.mjs`는 파일을 작성하거나 Excel을 실행하지 않는 제어 재현이다. 테스트 픽스처의 응답은 실제 Qwen 출력이 아니다.

**남은 우선순위:** 보호된 영속 checkpoint와 재시작 복구, 대표 기업 양식/자유 배치 문서의 보류 평가 집합, 판정자 보정, 실제 Qwen 순차/병렬 비교, Excel 2016 설치·계산·인쇄·NASCA 저장/재열기. 비용/지연의 실제 기준 측정과 영속 비식별 진단도 남아 있다. OpenTelemetry 규약은 후보로 유지하며 아직 SDK나 외부 전송 서비스를 추가하지 않았다.

빌드·설치 파일 생성·Windows 실행은 사용자의 최종 빌드 요청 전까지 하지 않는다. 새 소스 경로가 이전 설치본에 이미 반영됐다고 안내하지 않는다.
