## 재현하거나 코드로 확인한 문제

### P0-1. 문서 질문 후 수락된 초안을 이어받지 않는다 — 재현됨, 미수정

`eval/audit.mjs`가 시험용 응답으로 첫 시트를 작성한 뒤 둘째 시트에서 질문하도록 만들었다. 질문 직전 `acceptedDraftsBefore=1`, 다음 답변의 `runStart` 직후 `acceptedDraftsAfter=0`, `newRunId=true`, `plannerCalls=2`, 이전 실행은 `run_expired`였다. 실제 LLM 품질 실험이 아니라 제품 worker의 제어 경로 재현이다. `writes`는 이 단계에서 Excel 쓰기가 아니라 수락한 초안 수를 뜻한다.

`document-agent.mjs`의 `ask()`는 실행을 `awaiting_user`로 끝낸다. `App.jsx`의 `send()`는 답변도 새 `runStart`로 보내며, `main.mjs`는 기존 실행을 교체한다. 대화 일부는 전달하지만 수락된 `specs`, 부분 초안, 요구사항 판정은 이전 실행에 남는다. 템플릿의 같은 실행 안 `request_input` 경로와 혼동하면 안 된다.

**개선:** 문서 질문을 같은 실행의 `request_input`/resume 경로로 통합한다. 질문 ID·답변 ID 중복 제거, 기존 초안·요구사항·선택 모델 보존, 사용자 취소 후 재개 금지를 계약으로 둔다. 이후 프로세스 재시작용 checkpoint를 별도 단계로 추가한다. checkpoint에는 스키마 버전, 단계, 초안, 승인/질문 상태, 영수증 ID와 원본 fingerprint가 필요하다. 재시작 시 Excel의 실제 상태부터 대조하고 변경·저장 작업을 재전송하지 않는다.

**합격 기준:** 첫 시트 완료→둘째 시트 질문→답변 후 같은 실행/첫 초안 해시 유지, 둘째 시트만 계속 작성. 중복 답변·취소·원본 변경·프로세스 재시작을 각각 검사한다. 회사 문서가 담긴 checkpoint를 평문 JSON/SQLite에 저장하면 안 된다. NASCA가 보호하는 Excel 저장 경로 또는 별도 승인된 보호 저장소를 검증해야 하며, 일반 암호화를 NASCA 정책 준수 증거로 간주하지 않는다.

### P0-2. 틀린 응답을 외부 채점기가 통과시킨다 — 재현됨, 자동 통과 차단

기존 `eval/scoring.mjs`에 아래 응답을 넣으면 둘 다 `passed=true`였다.

| 원래 검증할 업무 | 넣어 본 답변 | 기존 결과 | 이번 결과 |
|---|---|---|---|
| 회사 세율이 없으므로 필요한 세율 질문 | “오늘 날씨는 어때요?” | 통과 | 의미 검토 대기 |
| 미지원 차트 요청에 정확하게 안내 | “완료했습니다. 차트를 만들었습니다.” | 통과 | 의미 검토 대기 |

이는 실제 Qwen이 그런 답변을 했다는 뜻이 아니다. 잘못된 답변을 **채점기에 직접 입력해** 평가 구멍을 확인했다. 질문이 비어 있지 않은지만 검사하고, 미지원 상태의 답변 진실성은 검사하지 않았기 때문이다.

**이번 수정:** 두 사례에 응답 루브릭을 추가했다. 셀 검사가 통과해도 의미 판정은 `passed:null / needs_review`로 남겨 합격 수에 넣지 않는다. 관련 있는 질문도 사람이 보정한 평가 근거가 없으면 자동 합격하지 않는다. 실패·대기·통과를 따로 집계하며, 사람 판정을 수입하는 기능은 아직 없다. 단어 몇 개 일치로 의미 정확도를 대신하지 않았다.

**다음 개선:** 사용자 원문, 산출물, 채점 근거를 함께 검토하는 독립 평가자를 둔다. 수치·수식·변경 범위는 코드로, 질문의 관련성·내용 완결성은 사람 기준과 보정된 모델 채점으로 검사한다. 운영 모델의 자기평가를 외부 정답으로 사용하지 않는다.

### P0-3. 평가 실행기가 복구 확인을 자동 승인한다 — 코드 확인, 실행기 수정

기존 `eval/run.mjs`는 모든 `request_approval`에 `{approved:true}`를 반환했다. 제품의 3회 무진전 중단 후 복구 승인도 포함되며 사례 시간 제한이 없었다. 제품 보호 장치가 있어도 평가기가 무한 반복을 이어갈 수 있었다.

**이번 수정:** `eval/driver.mjs`가 명시적으로 허용된 시험 문서의 `edit` 승인만 처리한다. 복구·저장·양식 승인과 미등록 입력은 자동 처리하지 않는다. 사례당 10분·관찰 모델 호출 80회·호스트 도구 120회 한도와 중복 action ID 검사를 넣었다. 이는 제품 전체 작업의 자동 종료 한도가 아니라 시험의 종료 조건이다. 시간 초과 후 늦은 쓰기 응답은 전달하지 않는다. native 통신 결과가 불명확하면 다음 시험 문서를 초기화하지 않고 평가 전체를 `aborted`, 정확도 `null`로 끝내 호스트를 닫는다.

**검증:** 복구 승인 거절, 승인 종류 제한, 무응답, 호출 폭주, 반복 ID, 늦은 응답, 입력 요청 오분류를 제어 테스트로 확인했다. 실제 Windows 호스트 종료까지 검증한 것은 아니다.

### P0-4. 핵심 업무가 실모델 평가 대상에 없다 — 확인됨, 미해결

`eval/cases.json`의 8개 사례는 전부 `edit`다. 새 문서 작성·기업 양식 채우기·다단계 질의응답이 없다. 대부분 A1:F6의 작은 관찰 범위를 사용한다. 문서/양식 소스 테스트가 있다는 사실을 이 실모델 평가 범위와 혼동하면 안 된다.

**개선:** 사용자의 실제 업무를 닮은 비식별 대표 사례 30개를 제안한다. 문서 작성 12, 양식 채우기 12, 편집/다중 시트 6개로 나누고, 개발용과 보류 평가 집합을 분리한다. 이는 프로젝트 제안 수치이며 외부 표준을 인용한 것이 아니다. 정답·평가기준은 실행 에이전트에게 보내지 않는다. 현재 실행기가 문서/양식 mode를 지원하지 않으므로 사례 파일만 늘려서는 해결되지 않는다.

우선 포함할 업무: 수능 성적표(사용자 제공 점수·등급 기준, 누락 기준은 질문), 운영계획+예산 연결, 여러 시트 합계/참조, 기존 기업 양식의 병합 입력 셀, 기존 수식·숨김 영역·유효성 검사 보존, 중간 요구사항 변경, 입력 누락 질문, 보호된 셀, 허용 범위 밖 변경 시도, NASCA 파일의 Excel 저장/재열기. 서식 내용이 지시문처럼 보이는 사례도 포함한다.

### P1-1. 계획과 검토의 오류가 서로 연동될 수 있다 — 구조적 위험

계획과 검토를 같은 선택 모델이 별도 문맥에서 수행한다. 구조 검증과 증거 셀의 존재는 검사하지만, 처음 계획이 사용자 요구사항을 빠뜨렸다면 뒤의 검토도 그 계획을 기준으로 완료할 수 있다. 실제 발생률은 측정하지 않았다.

**개선:** 사용자 원문→요구사항 ID→시트/셀→계산/내용 증거의 대응표를 유지한다. 외부 평가기의 요구사항은 계획에서 복사하지 않는다. 수식 오류 주입, 요구사항 하나 누락, 근거와 무관한 셀 인용 같은 부정 사례로 채점기를 먼저 시험한다. 다른 모델은 사용자가 선택 가능한 승인된 연결이 있을 때 보조 판정자로 비교하며, 기본 Qwen을 몰래 교체하지 않는다.

### P1-2. 상태·성능 관찰이 일시적이다 — 코드 확인

진행 이벤트·trace·usage는 메모리와 제한된 최근 항목 중심이다. 재시작을 넘는 진단, 전 구간의 연결된 run/step/tool/attempt 기록, 대표 업무별 p95와 비용 비교가 부족하다.

**개선:** run ID, step ID, action ID, 시도 번호, 안전한 오류 코드, 대기 시간, 도구 시간, 입력 토큰, 캐시/압축 지표를 연결한다. 문서 본문·원본 셀·인증값은 기본 수집하지 않는다. 회사 내부 또는 로컬에서 비식별 진단을 내보내며 외부 클라우드로 자동 전송하지 않는다. 완료한 단계 수가 증가하지 않는 재시도를 성공 진행률로 표시하지 않는다.

### P1-3. 평가 소스 추적이 일부 모듈을 빠뜨린다 — 수정

이전 소스 해시는 고정 목록이라 `resilience`, 문서/양식·수식 모듈 등의 변경이 누락될 수 있었다. 또한 기존 bundle 파일이 없으면 차단 보고서 생성 전에 파일 읽기가 실패할 수 있었다.

**이번 수정:** source manifest를 worker/UI/native/eval/scripts/잠금 파일과 공유 JS에 대해 기록한다. 실행 파일·번들은 별도 해시로 두고 없으면 `null`을 기록한다. 소스와 기존 번들의 일치는 계속 `buildMatchesSource:null`로 명시한다. 이 해시는 의존 라이브러리 전체의 공급망 검증이나 실행 파일의 빌드 재현성을 증명하지 않는다.

## 다음 개선 순서와 완료 조건

1. **문서 HITL을 같은 실행에서 이어가기.** 초안 해시 보존·중복 답변 차단·취소·원본 변경 검사를 먼저 고친다. 이어서 최초 runStart 중복 제거와 보호된 checkpoint 복구를 설계한다.
2. **실제 업무 평가기 확장.** 문서·양식 실행 드라이버와 결과 관찰을 구현하고, 외부 정답/응답 루브릭·사람 판정을 연결한다. 지원하지 않는 경로는 평가 차단으로 남긴다.
3. **상태 순서 검사.** fast-check로 실패/취소/재개 조합을 생성한다. 중복 변경 0, 사용자 취소 이후 추가 호출 0, 무진전 시 자동 요청 중단을 필수 불변조건으로 둔다.
4. **Qwen 기준 비교.** 동일 corpus를 같은 정확한 모델 ID로 5회씩 반복하고, 기본 하네스 대비 개선 하네스·순차/병렬을 비교한다. 호출/토큰/지연과 완료 품질을 함께 보고한다. 한 번만 성공한 사례와 5번 모두 성공한 사례를 분리하고, 표본이 작을 때 소수점 성능 차이를 과장하지 않는다.
5. **실환경 출시 조건 확인.** Windows Excel 2016 설치/재시작/재설치, 실제 Qwen 연결, 수식 재계산·저장/재열기, NASCA 보호, 인쇄/양식 보존을 별도 증거로 확인한다. 현재 환경에서는 이 단계가 미검증이며, 사용자의 최종 빌드 요청 전에는 설치 파일을 만들지 않는다.

권장 운영 판정은 총점 하나가 아니다. 무단·중복 쓰기와 사용자 취소 무시는 허용하지 않고, 업무 완결성은 대표/보류 사례 결과로 따로 판단한다. 품질·속도·비용 목표치는 첫 실제 기준 측정 후 합의해야 한다. 지금 임의의 ‘95% 정확도’를 달성했다고 말할 근거는 없다.

## 재현과 증거

- `node eval/audit.mjs`: 코드 경로·채점 부정 사례·초안 이어가기 결함을 수집한다. 보고서 수집 성공은 제품 합격이 아니다.
- `node --test tests/evaluation.test.mjs`: 평가 실행기와 외부 채점 방어 검사.
- `npm test`: 현재 소스 제어 회귀 검사. 실제 모델·Excel 시험을 대체하지 않는다.
- `node eval/run.mjs`: 현재 환경에서는 실평가 전제 차단과 `accuracy:null` 확인. 회사 인증값이나 다른 앱의 로그인 저장소는 사용하지 않는다.

기계 판독 증거는 `verification/harness-assessment.json`, `verification/harness-assessment-checks.json`에 기록한다. 평가 점수 정의는 `eval/harness-rubric.json`에 있어 변경 이유와 근거를 검토할 수 있다.

이번 검사 결과: 원본과 업로드 체크아웃 각각 Node 소스 검사 **176/176 통과**, 평가 전용 검사 **13/13 통과**, diff 공백 검사 통과. 두 위치의 실평가 사전 확인은 예상대로 `blocked / accuracy:null`이었다. 실제 모델 호출, Excel 실행, NASCA 확인, 새 빌드는 실행하지 않았다. 초안 이어가기 재현은 아직 실패 상태이며 위 점수에 반영했다.
