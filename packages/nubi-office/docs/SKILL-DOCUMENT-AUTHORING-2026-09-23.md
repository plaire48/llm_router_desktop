# 스킬 기반 새 문서 작성과 Python 실행 설계

상태: 2026-09-23 설계와 부분 구현. 후속으로 [Pi Coding SDK 기반 기본 스킬 발견/읽기와 메모리 초안 편집](CODING-SDK-ADOPTION-2026-09-23.md)을 구현했다. Python 실행기, 외부 스킬 설치, 의존성 자동 설치와 설치 번들은 미구현/미검증이다. 빌드는 실행하지 않는다.

후속으로 [QuickJS 기반 JavaScript 계산](DOCUMENT-SCRIPT-RUNTIME-2026-09-23.md)을 세 앱에 연결했다. 이 문서의 Python/의존성 설치 제안과 구분한다.

## 현재 소스에서 확인한 경로

- Excel은 `worker/main.mjs` → intent agent → document agent로 새 통합문서를 작성한다. 셀 선택이나 등록 양식이 필수는 아니다. 계획, 단계별 초안, 수식 사전 검사, native Excel 계산/readback, 최종 저장 승인을 사용한다.
- Word/PPT는 content agent의 create 계획과 native `office_create`로 새 문서를 만든다. 현재 구현된 문단/표/슬라이드/노트 도구와 저장 경로를 사용한다. 모든 Office 기능을 생성할 수 있다는 뜻은 아니다.
- worker는 Pi Coding SDK로 앱별 동봉 SKILL.md를 발견하고 필요한 본문/참조 자료를 읽는다. 메모리 초안의 정확한 코드 치환을 지원하며 Excel의 현재 시트 JSON 초안을 기존 commit 경로에 연결한다. 스킬 선택/설치 UI와 Python 실행 기능은 없다. `runtime-lock.json`과 설치 구성은 Node를 번들링하며 Python은 포함하지 않는다.
- 기준은 Windows Office 2016과 기업 카탈로그의 Qwen 3.8 27B다. 모델별 계정이나 Python용 별도 LLM을 요구하지 않는다. 실제 Office/회사 모델의 성공 검증은 별도다.

## 사용자 흐름 제안

원하는 문서를 채팅에 입력하면 업무에 맞는 스킬을 발견하고 필요한 내용만 불러온다. 직접 고르고 싶을 때는 기존 + 안에서 양식과 스킬을 볼 수 있게 한다. 작성 모드 선택을 필수로 만들지 않는다.

예: “분기 업무 보고서를 만들어줘” → 보고서 스킬 → 필요한 사실 질문 → 목차/내용 계획 → Word 문단과 표 작성 → 결과 검토 → 승인 후 저장.

예: “이 숫자로 예산 집행표를 만들어줘” → 집계 스킬 → 필요한 경우 Python으로 합계/정규화 계산 → 구조화된 결과 확인 → Excel 2016 수식/표 작성 → 실제 계산값 검토 → 저장.

사용 중인 스킬과 현재 단계, 실행한 도구, 결과/오류와 다음 작업은 기존 진행 UI에 표시한다. Python 사용 여부를 사용자가 매번 선택할 필요는 없다. 등록 양식을 선택한 경우에는 그 원본/입력 범위/수식 보존 계약을 함께 적용한다.

## 스킬 구성과 활성화

[Agent Skills 규격](https://agentskills.io/specification)의 `SKILL.md`, 선택적인 `scripts/`, `references/`, `assets/` 구조를 따른다. 처음에는 이름/설명만 문맥에 넣고, 해당 스킬이 선택되면 본문을, 필요할 때만 참조 자료를 읽는다. 기존 상태 재구성에도 활성 스킬 ID/버전/해시와 필요한 지침을 유지한다.

스킬은 문서 작성 방법과 품질 기준을 제공한다. Office 도구가 지원하지 않는 기능이나 회사 파일 접근 권한을 추가할 수 없다. 호스트와 의존성을 확인하고 맞지 않는 스킬은 이유를 설명한다. 모델 카탈로그를 선별하거나 Qwen의 실제 API ID를 만들어 내지 않는다.

외부 스킬의 라이선스/Windows 호환성/도구 요구사항을 확인한 후 해당 작업 계약에 맞게 연결한다. [Anthropic skills 저장소](https://github.com/anthropics/skills)의 문서 스킬은 별도 라이선스이므로 저장소가 공개됐다는 이유로 그대로 복사하거나 오픈소스로 표기하지 않는다. 포맷 지원과 특정 스킬의 재사용 허용은 별도 확인 사항이다.

## Python 실행 계약 제안

Python이 필요한 스킬에는 앱 전용 CPython과 검토한 의존성을 같이 배포한다. 사용자가 Python/터미널/pip를 별도로 설치하거나 실행하지 않는 흐름이다. 공식 [Windows embeddable distribution](https://docs.python.org/3.12/using/windows.html#the-embeddable-package)은 앱에 포함하는 용도로 제공되며, 의존성도 앱 배포자가 함께 관리하는 방식을 설명한다. 정확한 버전/배포 아키텍처/해시와 라이브러리는 채택할 실제 스킬에 맞춰 고정해야 한다.

1. 스킬 ID/버전, 고정된 스크립트 ID, 입력 스키마로 호출한다. 문자열 shell 명령을 모델이 생성해서 실행하는 인터페이스를 사용하지 않는다.
2. 허용된 데이터를 JSON으로 전달하고 검증된 JSON 결과를 받는다. 도구 결과의 업무 오류, 프로세스 오류, 시간 초과, 사용자 중지를 구분한다. 출력 크기를 제한하고 로그에 인증값/회사 원문을 남기지 않는다.
3. Python은 집계, 정규화, 통계 계산과 문서 구성 데이터 등에 사용한다. pandas 같은 외부 라이브러리는 필요할 때만 호환성/라이선스/패키징을 확인해 추가한다. 단순 계산은 표준 라이브러리로 시작할 수 있다.
4. 반환 데이터는 기존 문서 스키마/도구 허용 범위로 검증한다. 실제 Office 편집, 계산 readback, 저장, NASCA 경로는 기존 native 도구가 담당한다. 기존 암호화 양식을 Python 라이브러리로 직접 열거나 ZIP 재저장하지 않는다.
5. 실패 시 구조화된 입력/오류/이전 결과를 보고 수정한다. 결과가 불명확한 문서 생성/저장은 반복하지 않는다. 순수 계산과 Office mutation의 재시도 정책을 분리하고 기존 중지/진전 없음 규칙을 유지한다.

검토된 동봉 스크립트부터 지원하는 것과 임의 외부 Python을 지원하는 것은 다른 범위다. 별도 프로세스 실행만으로 파일/네트워크 격리가 보장되지는 않는다. 임의 스크립트 지원에는 Windows의 실제 프로세스 제한/자원 제한/파일·네트워크 경계와 프로세스 트리 종료 검증이 선행되어야 한다. SKILL.md의 `allowed-tools`를 권한 상승으로 해석하지 않는다.

새 파일을 직접 생성하는 Python 스킬은 별도 어댑터가 필요하다. 결과 파일 검사, native Office 열기/반영, 보호된 최종 저장과 실패 복구 계약을 갖추기 전에는 범용 지원으로 광고하지 않는다. Linux 전용 도구나 LibreOffice를 전제하는 스킬도 원본 그대로 호환된다고 가정하지 않는다.

## 작업 중 의존성 자동 설치 요구사항

사용자는 별도 선택한 스킬이 아직 없으며, 작업 도중 필요한 도구/라이브러리가 없을 때 직접 설치하지 않고 이어가기를 원한다. 다음 기능을 후속 구현 범위로 추가한다. 현재 자동 설치 기능이 구현된 것은 아니다.

`필요 패키지 확인 → 기존 환경/캐시 검사 → 고정 버전 설치 → import/계약 검사 → 같은 실행의 미완료 단계 재개`를 하나의 하네스 단계로 표시한다. 승인된 출처/패키지 정책 안에서는 건별 사용자 설치 요청을 요구하지 않는다.

- 앱 전용 Python 환경과 스킬 ID/버전별 의존성 공간을 사용한다. 시스템 Python/PATH나 다른 업무 프로그램의 환경은 변경하지 않는다. 인증값은 전달하지 않는다.
- 스킬의 선언된 dependency/import 매핑과 잠금 정보를 사용한다. `ModuleNotFoundError`의 문자열을 그대로 패키지명으로 삼아 임의 설치하지 않는다. 재발하는 같은 import 실패는 설치 루프로 반복하지 않는다.
- 패키지명, 버전, 플랫폼, 다운로드 출처와 해시를 검증한다. 설치 중인 환경을 실행에 사용하지 않고 준비된 환경으로 전환한다. 설치 동시 호출은 한 번으로 합치며, 버전 충돌은 별도 스킬 환경에서 해결한다.
- 기존 캐시 → 사내 패키지 저장소 → 설정상 허용된 공개 저장소 순으로 정책에 맞춰 해결한다. 외부망이 막히면 사내 미러나 미리 제공한 의존성 묶음을 사용한다. 어느 경로도 없으면 필요한 항목과 원인을 보여주고 진행 상태를 보존한다. 인증서 검증을 끄지 않는다.
- 모델에는 패키지 준비 상태와 간결한 오류만 돌려준다. 회사 문서 내용은 패키지 저장소로 전송하지 않는다. 사용자 취소, 저장 응답 유실과 문서 mutation에는 자동 설치/재실행 규칙을 적용하지 않는다.
- OS 관리자 권한이나 드라이버/시스템 프로그램 설치가 필요한 도구는 일반 Python 패키지와 구분한다. 기업 정책 밖 설치를 우회하지 않는다. 라이선스/운영체제 때문에 준비할 수 없는 스킬을 모든 스킬 지원으로 표시하지 않는다.

오픈소스 후보는 [uv의 버전 잠금/환경 동기화](https://docs.astral.sh/uv/pip/compile/)와 [사내 인덱스 설정](https://docs.astral.sh/uv/concepts/indexes/)이다. 현재 제품에 추가하지 않았으며, Windows 대상 아키텍처, 앱 전용 CPython 배치, 해시 검사와 오프라인 설치를 실검증한 뒤 채택한다. 동봉 Python에 pip가 있다고 가정하지 않는다. 검사된 wheel/의존성 팩을 배포하는 방법도 비교한다.

## 구현 순서와 검증 기준

1. 앱별 기본 스킬과 Excel 현재 초안 편집을 기존 Pi/진행/승인 실행기에 연결했다. 실제 Office/회사 모델 평가는 별도이며 사용자 지정 외부 스킬은 후속이다.
2. 동봉 스킬 목록/해시/단계적 로드/활성 문맥은 연결했다. 자연어 선택과 +에서 명시 선택/설치 UX는 후속으로 검증하고 양식 바인딩과 충돌하지 않게 한다.
3. Python이 필요하면 고정 스크립트의 JSON 입력/결과 계약부터 연결한다. 정확한 집계 정답, 잘못된 입력, 시간 초과, 중지, 과도한 출력, 프로세스 종료, 변경된 스크립트와 의존성 누락을 검사한다.
4. 스킬에 따라 작성한 산출물을 Office에서 다시 읽어 실제 값/수식/문단/표/슬라이드와 요구사항을 확인한다. 스크립트 exit code 0이나 모델의 완료 선언만으로 문서 성공을 인정하지 않는다.
5. 최종 빌드 요청 후 한 설치 파일에 필요한 공통 런타임/의존성을 넣고 Windows x86/x64, 오프라인 설치, Office 2016, Qwen, NASCA 환경을 검증한다. 현재 설치본에 Python이 포함되었다고 설명하지 않는다.

현재 채택: Agent Skills의 단계적 문맥 로드와 스킬/실행 도구 분리, Pi Coding Agent SDK 0.86.1의 스킬/검색/읽기/편집 도구, p-map 7.0.4의 분석 동시성 실행. 기존 Pi/Office 하네스를 유지하며 CPython/의존성 관리와 스크립트 실행은 후속 구현 대상이다. [도입 근거와 검증 범위](CODING-SDK-ADOPTION-2026-09-23.md)를 따른다.
