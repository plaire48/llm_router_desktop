## 회귀 검사 기준선

수정 전 2026-09-29 macOS, Node 25.4.0, `npm test` 결과: **708개 중 702 통과, 6 실패.** `docs/IMPROVEMENT-STATUS.md`의 704/704 기록과 다르다. 1, 3, 5, 6번은 고쳤고 2, 4번이 남았다.

실패한 검사:

1. real App keeps Nubi identity while showing host-specific welcome, input and tools
2. answer guidance stays inside the field and no send-key helper appears below it
3. native and JSON tool protocols reject invalid fields without echoing values or unknown property names
4. Office consumes the reviewed Nubi UI snapshot without silent component or CSS drift
5. shared browser approval keeps preview separate from a locked explicit decision
6. App preserves the answer until acknowledged and exposes the pending question from the composer

### 공유 실행기에 대한 주의

- `agent-runtime.js`가 09-25 기준 53KB에서 109KB로 커졌고, 가져오는 모듈 60개 중 40개가 마지막 Office 검토 이후 바뀌었다.
- 해시로 감시하는 것은 UI 파일뿐이다. worker가 쓰는 공유 실행기에는 변경 감시가 없다.
- 분석 시점(2026-09-29 00:17~00:24)에도 공유 폴더가 수정되고 있었다. 다른 작업과 겹치므로 이 저장소의 `extensions/aipro-chat`는 그 시점의 상태다.
- Office 실행 경로에서 도구 호출, 스키마 검증, 스트리밍을 깨는 차이는 찾지 못했다. 전체 모듈을 검토한 결과는 아니다.

### 확인하지 못한 것

- 변경된 UI 파일 10개의 검토 당시 원본. 비교는 기준 해시와 09-23 번들, 날짜가 있는 사본으로 했다.
- Windows와 제품 번들 Node 22.23.2에서의 결과. 모든 실행은 macOS, Node 25.4.0이다.
- 새 스키마 힌트가 실제 Qwen에 도움이 되는지 여부.

## 코드에서 확인한 양식 흐름의 한계

| 위치 | 현재 동작 | 영향 |
|---|---|---|
| `worker/template.mjs` `inspect` | 20셀씩 페이지 조회 | 300셀 양식이면 읽기만 15회 모델 왕복 |
| `worker/template.mjs` `analyzeTemplate` | 셀별 판정, 힌트는 왼쪽과 위쪽 이웃뿐. 병합 라벨은 이번에 고쳤다 | 제목, 입력부, 표, 합계 같은 영역 개념 없음. 라벨과 입력 칸 사이에 빈 칸이 있으면 여전히 힌트가 없다 |
| `define_template_fields` | 단일 셀 항목 최대 30개 | 반복 행 표를 항목으로 표현 못 함 |
| 저장 명세 `profile` | 주소, 이름, 값 종류, 필수 여부만 저장 | 업무 의미와 작성 규칙이 남지 않음 |
| 양식 분석 실행 | 단일 실행기가 순차 수행 | `worker/analysis-jobs.mjs` 하위 분석기가 양식 등록에 연결되지 않음 |
| `eval/cases.json` | 양식 채우기 4개만 있음 | 양식 등록, 등록본 재사용 사례가 없음 |

실제 영향의 크기는 측정하지 않았다.

native 쪽 제약: `ExcelTemplateStore.cs`의 레코드 검사는 `schemaVersion`, `id`, 전체 30,000자, `profile.address` 1,000셀, `profile.fields` 1~30개만 확인한다. 레코드에 영역, 표, 작성 규칙을 추가하는 것은 native 변경 없이 가능하다. JS 쪽 `validateTemplateRecord`는 허용 키를 제한하므로 함께 고쳐야 한다.

## Windows에서 이어갈 때

### 준비

```powershell
cd packages\openwiki
npx pnpm@11.25.0 install --frozen-lockfile
cd ..\..\extensions\aipro-chat
npm ci
cd ..\..\packages\nubi-office
npm ci
npm test
```

세 곳 모두 설치해야 한다. `packages/nubi-office`는 `extensions/aipro-chat`의 소스를 상대 경로로 가져오고, 그 공유 소스가 다시 `packages/openwiki/src/agent/wiki-question.ts`를 가져온다. openwiki 설치를 빼면 `minisearch`를 찾지 못해 검사 파일 45개가 시작 단계에서 실패한다. 세 폴더의 상대 위치를 유지해야 한다.

Node는 22.22 이상이 필요하다. openwiki의 TypeScript 소스를 Node가 직접 읽는다.

**확인한 것:** 업로드한 저장소를 macOS에서 새로 복제해 위 순서로 설치하니 작업 폴더와 같은 결과(708개 중 702 통과, 같은 6건 실패)가 나왔다. Windows에서는 확인하지 않았다.

`packages/openwiki/dist/`는 저장소에 없다. 브라우저 확장의 openwiki 시각화 기능과 관련 검사에 필요하며 `pnpm build`로 만든다. Office 검사에는 필요하지 않다.

저장소의 `.gitattributes`는 줄바꿈 변환을 끈다. `design/shared-ui.json`이 공유 UI 파일의 해시를 기록하므로 줄바꿈이 바뀌면 검사가 실패한다.

### Windows에서 가능해지는 것

- `eval/run.mjs`의 실제 Excel 평가. `native/Nubi.Office.EvalHost` 빌드가 필요하다.
- 모의 호스트(`eval/sim`)는 Windows에서도 그대로 실행된다. 계산기에 Windows x64와 arm64 바이너리가 있다. 소켓은 Windows에서 이름 있는 파이프를 쓴다. Windows에서 실행해 보지는 않았다.
- 실제 Excel이 있으면 기존 평가 실행기가 더 정확하다. 다만 기존 실행기에는 양식 등록 메서드(`template_register`, `template_catalog_index`)가 없어 평가 호스트 확장이 필요하다.
- 설치 파일 빌드는 사용자가 최종 빌드를 요청한 뒤에만 한다 (`AGENTS.md`).
