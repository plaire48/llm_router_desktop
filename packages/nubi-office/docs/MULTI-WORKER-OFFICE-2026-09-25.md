# 문서 분할 워커와 Windows 화면 검토

2026-09-25. 긴 Word/PPT 검토를 **범위 분할 → 병렬 읽기 → 요구사항별 통합 → 부모의 원본 확인**으로 연결했다. 채팅은 전체 워커 계획과 각 워커의 담당 범위, 대기/검토/오류/수신 상태를 보여준다. 기존 Windows UIA와 캡처 경로도 개선했다.

## 방법론과 채택 범위

| 공식 근거 / 오픈소스 | 판단과 실제 반영 |
|---|---|
| [Anthropic multi-agent research](https://www.anthropic.com/engineering/multi-agent-research-system) | 조정자와 독립 워커의 역할/범위/출력 계약을 적용했다. 동일 문서를 여러 워커에게 전부 복사하지 않고 담당 구간과 원래 조건만 전달한다. 해당 연구의 성능 수치를 Office/Qwen 성능으로 인용하지 않는다. |
| [OpenAI Agents SDK orchestration](https://openai.github.io/openai-agents-js/guides/multi-agent/) | 주 실행기가 작업과 결과를 관리하는 구조를 참고했다. Office 승인/저장 권한을 하위 에이전트로 넘기는 handoff는 도입하지 않았다. SDK 런타임은 추가하지 않았다. |
| [p-map](https://github.com/sindresorhus/p-map), 기존 Office `createAnalysisJobs` | 기존 MIT 라이브러리와 스케줄러를 실제 재사용했다. 배치당 최대 4개 작업, 모델 동시 호출 최대 2개. ChatGPT 제공자는 기존 정책대로 1개. 취소, 시간 제한, provider/model 바인딩, 성공 캐시, 429 후 직렬 전환을 유지한다. |
| 기존 Pi / p-retry 하네스 | 문서 주 실행기와 단일 복구 감독기를 유지했다. 하위 호출에 별도 무한 재시도 루프나 native 쓰기 권한을 추가하지 않는다. |
| Codex/OpenCode 소스 비교 | [기존 고정 소스 비교](COMPETITIVE-BENCHMARK-2026-09-25.md)의 도구 권한 분리와 실제 결과 기반 상태 판단을 유지했다. 범용 코드 실행기/셸을 Windows Office 제어기로 교체하지 않았다. |

병렬 수를 무조건 늘리는 대신 사내 Qwen 부하와 취소/복구를 먼저 통제했다. 선택한 모델을 그대로 사용하며 Qwen의 이미지 입력 지원을 추측하지 않는다. 이미지 확인과 native 문서 확인은 다른 근거다.

## 역할과 실행 순서

1. **주 실행기:** 원래 요청과 답변, 스킬/양식 문맥을 보존하고 native 페이지의 연속성, 중복, 잘림, 버전을 확인한다.
2. **구간 워커:** 독립된 문맥에서 할당한 원문을 읽고 요구사항별 지지 근거, 충돌, 미확인, 무관을 반환한다. 인용은 해당 구간 원문과 정확히 일치해야 한다. 워커가 Office를 읽거나 쓰지는 않는다.
3. **부모 확인:** 배치의 모든 모델 호출이 끝난 뒤 Office를 순차 조회한다. 동일 문서와 provider/model을 읽기 전후에 확인해야 구간 결과를 채택한다.
4. **통합 워커:** 서로 독립된 요구사항을 병렬로 검토한다. 각 워커는 해당 요구사항에 대한 모든 구간 결과를 받고, 구간 사이의 관계/순서/합계를 입증하지 못하면 미확인으로 둔다.
5. **최종 판정:** 코드가 충돌과 미확인을 보존한다. 통합 모델의 완료 선언이 하위 문제를 지울 수 없다. 문서 반영과 저장은 기존 주 실행기의 HITL과 영수증 검증을 따른다.

구간당 근거 48,000자, 최대 64구간의 기존 한계를 유지한다. 항목 자체가 너무 크거나 원문이 잘린 경우 해결된 것으로 간주하지 않는다. 임의 크기 문서의 무제한 재귀 분할, 하위 워커의 자율 PC 조작, Excel 통합문서 전체의 자동 분할 검토까지 구현한 것은 아니다. Excel의 기존 `analyze_ranges`, 화면의 `review_office_view` 읽기 전용 병렬 분석은 그대로 유지한다.

## 실패와 진행 표시

- 한 배치가 일부 실패하면 성공한 형제 결과를 캐시에서 재사용하고 실패한 모델 호출만 복구한다. 끝난 이전 배치를 다시 시작하지 않는다. 실패 원인과 수정 지시를 다음 호출에 전달한다.
- 모든 하위 호출이 정착한 뒤 부모만 복구 HITL을 연다. 무진전 세 번이면 기존 확인 절차로 멈춘다. 서버의 Retry-After를 유지한다.
- 진전은 문서/단계/요구사항/답변에 고정한 구간 식별자로 한 번만 집계한다. 같은 내용을 반복 검토하거나 캐시를 읽은 것을 새 진전으로 계산하지 않는다.
- 채팅에 `구간 검토 2/7 / 통합 검토 0/3`처럼 전체 현황을 표시한다. 진행 중인 워커와 범위를 노출하고, 전체 대기 목록과 결과는 `워커별 역할과 결과`에서 확인한다. 완료 카운트는 문서 작성 완료가 아니라 부모가 채택한 검토 작업 수다.
- 사용자 취소와 실패는 남은 워커 상태를 정착시키며 스피너가 계속 돌지 않는다. UI도 종료 상태를 다시 확인해 오래된 running 상태를 미완료로 표시한다. 비공개 추론은 표시하지 않는다.

## Windows 조작과 이미지 확인

기존 `inspect_office_view`, `show_document_target`, `act_office_view`, `review_office_view`를 유지한다. COM 선택/스크롤, UIA Invoke/SelectionItem/Scroll, 독립적인 가상 커서 표시를 사용하며 사용자의 OS 커서는 움직이지 않는다. 화면 검토는 최대 세 개 기준을 기존 읽기 전용 워커에 맡길 수 있다.

이번에는 **PrintWindow/GDI 캡처 실패가 성공한 UIA 관찰까지 폐기하던 문제**를 수정했다. 캡처만 실패하면 이미지와 해시를 비우고 텍스트 관찰을 반환한다. 전면 창/프로세스/문서 재검증은 그대로다. 다른 캡처 API나 물리 입력으로 우회하지 않는다. [캡처 개선 근거와 검사](WINDOWS-CAPTURE-FALLBACK-2026-09-25.md).

전체 창 축소로 작은 글자가 보이지 않을 수 있으며 영역별 고해상도 crop은 후속 범위다. 텍스트 검토를 실제 픽셀 검증이나 전체 문서 레이아웃 검증으로 표시하지 않는다.

## 검증과 남은 조건

- 관련 소스 검사 46개 통과: 최대 2개 동시 호출, native 확인의 직렬화, 부분 실패 재사용, 세 번 실패 후 HITL, 인용/충돌 보존, 원본 변경, native 읽기 중 모델 변경, 취소와 화면 상태를 검사했다.
- 고정 배포 소스 기준 전체 543개와 디자인 검사 통과. 현재 개발 폴더는 544개 중 541개 통과, 기존 실행기/UI/A2A 기준 불일치 3개 실패를 유지한다.
- Chromium 소스 화면 미리보기 102개 통과. 워커 화면은 320/380/1100px에서 가로 넘침과 자동 접근성 검사 위반이 없었다. 320px 스크린샷을 직접 검토했다. 자동 검사의 미확인 항목과 실제 WebView2 검증은 구분한다.
- 공통 UI 해시가 개발 폴더에서 다른 문제는 그대로 남는다. 미리보기 성공만으로 검토 기준 해시를 갱신하지 않았다. 전체 검사 결과는 [상태 반영표](IMPROVEMENT-STATUS.md)에 기록한다.

**모의 모델/native 응답과 소스 검사는 실제 Windows 11, Office 2016, NASCA, Qwen 정확도/비용/속도 검증이 아니다.** native와 설치 파일은 빌드하지 않았으며 기존 0.8.4 설치 파일에는 이 변경이 아직 없다. Office A2A는 계속 보류한다.
