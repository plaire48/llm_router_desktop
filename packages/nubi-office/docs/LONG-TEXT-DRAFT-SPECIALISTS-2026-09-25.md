# 긴 원문과 새 Excel 전문 작업 품질 점검

2026-09-25. 기준은 Windows Office 2016과 실제 카탈로그의 Qwen 3.8 27B다. 아래는 소스 반영과 합성 계약 검사이며 실제 Office 또는 모델 품질 측정이 아니다. 설치 파일과 native 빌드는 실행하지 않았다.

## 반영한 변경

- Word 문단/입력칸과 PPT 도형/노트에 `office_read_text`를 연결했다. 원문 항목과 문서 fingerprint를 고정하고 읽기 전후 native 상태를 확인한다. 1회 최대 8000 UTF-16 단위, 전체 필드 SHA-256과 조각 해시, 다음 오프셋을 반환한다. 별도 평문 파일은 만들지 않는다.
- 작업 모델이 `read_document_text`로 필요한 부분을 조회한다. 원본 페이지는 편집 범위의 기준으로 유지하고, 완전히 수집한 필드만 별도 검토용 사본에 넣는다. PPT 제목과 노트의 잘림을 구분한다. 잘린 내용을 전체로 보거나 항목 수를 원문 완독으로 해석하지 않는다.
- 결과 검토 전에 잘린 원문을 순서대로 읽는다. 8000자를 넘는 필드는 고유한 검토 조각으로 나누고 기존 병렬 구간 검토기에 전달한다. 인용은 원본 항목/필드, UTF-16 위치, 해시로 다시 연결한다. 원본 항목 수와 조각 수는 별도 집계한다.
- 같은 문장을 더 짧게 재조회해도 확보한 원문과 진전을 잃지 않는다. 진전은 새로 읽은 범위의 합집합으로 계산한다. 문서/모델 변경, 위조 해시, 누락 구간, 취소 후 응답은 검토 성공이 아니다.
- 새 XLSX 작성에 `delegate_draft_tasks`를 연결했다. 모델이 필요한 역할, 시트, 목표와 선행 작업을 정한다. 하위 모델은 최대 24셀의 JSON 후보만 제안한다. 주 실행기가 내용을 확인하고 기존 chunk/commit, Excel 계산/readback, 최종 검토와 저장 승인으로 통합한다.
- 전문 작업은 최대 8개, 모델 호출은 최대 2개 동시 실행한다. 성공한 형제를 보존하고 부분 결과의 후속 작업은 차단한다. 초안/답변/모델이 바뀌면 이전 제안은 무효다. 401은 중단하고 429는 기존 단일 복구 감독기가 Retry-After를 따른다.
- 새 Excel의 유효한 500자 요구사항이 하위 문맥의 400자 제한에 걸리던 계약을 수정했다. 원래 조건을 자르지 않는다.
- PPT 2000항목 한도가 빈 슬라이드에서 빠지는 경우와 읽기 전용 초안 슬라이드의 전체 교체를 막았다. worker도 승인 전에 동일한 읽기 전용 조건을 검사한다.

## BP와 오픈소스 선택

[Anthropic의 context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)의 필요한 원문만 조회하는 방식과 격리된 하위 문맥을 참고했다. Office에서는 모델 요약만 보존하지 않고 원문 해시, 위치와 미확인 범위를 유지하도록 적용했다. 이는 해당 방법론을 Office에 맞게 적용한 것이며 Claude와 같은 성능을 입증한 것은 아니다.

기존 Pi 0.86.1, p-map 7.0.4와 [dependency-graph 1.0.0](https://github.com/jriecken/dependency-graph)을 실제 재사용한다. 모두 MIT 라이선스의 기존 의존성이며 추가 에이전트 프레임워크나 실행기 설치는 없다. 호출/캐시/취소/복구를 중복 구현하지 않고 Office 원문 및 초안 계약만 확장했다. Qwen의 토큰 한도와 모델 정확도는 실측하지 않았으므로 문자 예산과 혼동하지 않는다.

[Word Range.Text](https://learn.microsoft.com/en-us/office/vba/api/word.range.text)와 [PowerPoint TextRange.Text](https://learn.microsoft.com/en-us/office/vba/api/powerpoint.textrange.text)의 native 텍스트 접근을 사용한다. 같은 속성에 값을 쓰면 문서를 바꾸므로 신규 조회 경로에는 setter를 두지 않는다. NASCA가 처리하는 Office 문서를 일반 ZIP 편집기나 Python으로 다시 저장하는 라이브러리는 이 경로에 도입하지 않았다.

## 검증과 남은 범위

**고정 Pi 0.86.1 전체 638/638 검사 통과**, 디자인 공통 24개 파일 일치/위반 0개다. 이번에는 화면 레이아웃을 변경하지 않았으며 Chromium 화면 검사는 다시 실행하지 않았다. 최종 검사 수와 소스 해시는 `../verification/long-text-draft-specialists.json`에 기록한다. 검사에는 실제 Pi 실행기 위의 합성 provider/native, Word/PPT 꼬리 원문 인용, UTF-16 경계, 해시 위조, 범위 누락, 원문 불변, 취소, 모델 변경, 전문 작업 의존 관계 및 부모 통합이 포함된다. C#은 소스 계약만 검사했다.

| 구분 | 현재 상태 / 후속 과제 |
|---|---|
| 긴 필드 조회 | 구현. 실행 내 최대 200만 UTF-16 문자 예산, 검토 최대 64배치. 임의 크기 문서 지원은 아님 |
| Native 항목 조회 | 기존 2000항목/200슬라이드/200 Word 입력칸/8M Word XML/128 PPT run 상한 유지. 조각마다 전후 항목 조회하므로 lazy paging과 변경 세대 추적의 실제 COM 성능 검증 필요 |
| 역할별 긴 항목 분석 | 32K 이하 source 예산의 `analyze_document`/동적 DAG에 완전히 읽은 원문 연결. 그보다 큰 단일 항목은 최종 분할 검토 지원, 역할별 임의 오프셋 할당은 후속 |
| 새 Excel 공동 작성 | 제한된 후보를 주 실행기가 통합. 다수 에이전트의 동시 COM 쓰기나 임의 시트 직접 수정은 미지원 |
| Office 기능 확대 | 혼합 서식 직접 편집, 표/차트 생성 및 기업 공용 양식 배포는 별도 계약과 검증 필요 |
| 실행 재시작 | 현재 실행 메모리만 유지. 보호된 지속 체크포인트/재시작 복원 미구현 |
| 실환경 품질 | Windows 11 설치, Office 2016 COM, Qwen 실호출, NASCA 저장 후 재열기 미검증 |
| 배포 | 반복 수정 단계. 이번 변경이 기존 0.8.4 EXE에 들어 있다고 표시하지 않음 |

남은 항목은 미완료다. 소스 검사 통과를 전체 기능 완료나 문서 정확도 점수로 대체하지 않는다. Office A2A는 사용자 결정대로 구현하지 않는다.
